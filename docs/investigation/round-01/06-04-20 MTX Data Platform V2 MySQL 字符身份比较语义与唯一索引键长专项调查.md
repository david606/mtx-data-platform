| `utf8mb4_bin` 是 `PAD SPACE`，`utf8mb4_0900_bin` 是 `NO PAD`。前者下 `'a '` 与 `'a'` 比较相等，后者不相等 | 同上，以及 [12.8.5](https://dev.mysql.com/doc/refman/8.0/en/charset-binary-collations.html) |
| `PAD SPACE` 比较时尾随空格无意义。`NO PAD` 把尾随空格当普通字符。`VARBINARY` 每个字节都参与比较，包括尾随空格 | [12.8.5](https://dev.mysql.com/doc/refman/8.0/en/charset-binary-collations.html) |
| `utf8mb4_unicode_ci` 下 `Bar` 与 `Bär` 比较同时命中。`Ä=A`、`Ö=O`、`Ü=U` 在 `utf8mb4_general_ci` 与 `utf8mb4_unicode_ci` 都成立。`utf8mb4_unicode_ci` 还有 `ß=ss` | [12.8.6](https://dev.mysql.com/doc/refman/8.0/en/charset-collation-effect.html)，[12.10.1](https://dev.mysql.com/doc/refman/8.0/en/charset-unicode-sets.html) |
| 非二进制列即使使用 `_bin`，在客户端字符集不同时仍会做字符集转换。`VARBINARY` 按字节复制，不做这种转换 | [12.8.5](https://dev.mysql.com/doc/refman/8.0/en/charset-binary-collations.html) |
| `UNIQUE` 只保证索引值互异。前缀唯一只覆盖前缀。前缀长度对非二进制列按字符计，对二进制列按字节计 | [15.1.15](https://dev.mysql.com/doc/refman/8.0/en/create-index.html) |

## 3. 字符比较语义

三种相等现在没有被证明为同一件事。

| 层次 | 当前事实 |
| --- | --- |
| 应用层字符串相等 | 这些身份还没有持久化实现。Java `String` 相等比较的是码元序列：大小写、尾随空格和不同 Unicode 规范化形式都不折叠。这是语言行为，不是已经接受的身份规则 |
| 业务身份相等 | Pipeline 把各段字段值当作身份组成部分。正文没有规定大小写折叠、去掉尾随空格，或做 NFC/NFD。阻断内容另有已写明的记号：显式 `EMPTY` 不等于空字符串 |
| MySQL 索引相等 | 由列的字符集和排序规则决定。唯一索引冲突使用的就是这套相等，不是应用层码元相等 |

因此三者可以不一致。默认服务器排序规则 `utf8mb4_0900_ai_ci` 不区分大小写、不区分重音，而且是 `NO PAD`。若身份列继承它，`A` 与 `a` 会落进同一个唯一键，而尾随空格仍然区分。这和码元相等不同，也和 `utf8mb4_bin` 不同。项目尚未选择排序规则，所以不能把「默认就是 `0900_ai_ci`」写成已经采用。未指定时手册会落到这个默认，这是风险，不是选型。

分项：

| 差异 | 手册事实 | 对身份的影响 |
| --- | --- | --- |
| 大小写 | `_ci` 不区分，`_cs` 与 `_bin` 按权重区分 | `_ci` 会把仅大小写不同的字段路径或标识并成一个键 |
| 重音与展开 | `utf8mb4_unicode_ci` 下 `Bar`=`Bär`，且 `ß`=`ss`。`utf8mb4_general_ci` 是 `ß`=`s`，不是 `ss` | 非二进制、非 `_bin` 的规则可以把不同码位序列判成同一个键。手册没有写插入前统一做 NFC 或 NFD |
| 尾随空格 | `PAD SPACE` 下尾随空格不影响比较。`NO PAD` 和 `VARBINARY` 下影响。`LIKE` 不论排序规则都把尾随空格当有效字符 | `utf8mb4_bin` 仍会把 `'a'` 与 `'a '` 当成同一个唯一键。`utf8mb4_0900_bin` 不会。名称里的 `bin` 不表示尾随空格语义相同 |
| `VARCHAR` 与 `VARBINARY` | 前者是字符序列，比较走排序规则，客户端字符集不同时会转换。后者是字节序列，不转换，尾随空格有效 | 同一段文本用不同编码写入 `VARBINARY`，会变成多行。写入 `VARCHAR` 时，转换可能先改变字节，再按排序规则比较 |
| 唯一索引 | 冲突判断的是索引值，不是原始码元 | 排序规则一旦把两个业务值判成相等，第二行不能插入。读胜出行时读到的是先写入的那一个原值，不是后写入的那个 |

`CHAR` 在检索时去掉尾随空格，`BINARY` 用 `0x00` 填充且检索不去掉。二者都会改变取回的值。本轮比较的存储方案不使用它们。

## 4. 候选存储方案

只比较，不选定。

| 方案 | 是否改原始值 | 不同字符串被看成相同 | 同一逻辑身份变成多行 | 查询、索引与后续变更 | 是否还要另存原值 |
| --- | --- | --- | --- | --- | --- |
| `VARCHAR` 加明确排序规则 | 值按所选字符集保存。客户端字符集不同时，插入前会转换 | 会。`_ci`、`_ai`、展开规则和 `PAD SPACE` 都会合并不同码元 | 会。若业务以后规定的相等比该排序规则更宽，未折叠的两种写法都能插入 | 查询必须使用同一套相等，否则索引相等和查询相等分叉。事后改排序规则可能让已有行突然冲突或突然不再冲突 | 若转换或排序规则会合并值，不另存原值就无法再区分它们 |
| `VARCHAR` 加二进制排序规则 | 仍可能因客户端字符集转换而改变字节。比较本身按码位或 `utf8mb4` 字节 | `utf8mb4_bin` 仍合并仅尾随空格不同的值。`utf8mb4_0900_bin` 不合并尾随空格，也不做大小写或重音折叠 | 会。NFC 与 NFD、以及仅尾随空格不同的值，在 `0900_bin` 下是不同键 | 与码元相等更接近，但仍不是 Unicode 规范化相等。两套 `bin` 不能互相替代 | 转换仍可能发生，所以仅靠取出的列不能证明输入字节未变 |
| `VARBINARY` | 不按字符集转换。存进去的字节就是以后比较的字节 | 字节不同即不同。尾随空格 `0x20` 有效 | 会。同文不同编码、或同字符不同规范化字节，都会变成多行 | 键长按声明字节数计算，不乘 4。非法 UTF-8 也能存。人工查询依赖客户端把字节解释成文字 | 字节列本身可以是原值。若业务身份是文本，编码和规范化版本必须另有决定，否则「原字节」没有唯一解释 |
| 应用层规范化后只存规范值 | 会。除非规范规则是恒等 | 会。不单射的规则把多个输入收成一个存储值 | 会。调用方漏做规范化时，同一业务值会有两行 | 算法、编码、字段边界和版本都还没有。换版本会使旧行和新行不再可比 | 不另存输入，就不能发现规范规则把两个身份合并了 |
| 原值与规范值分开保存 | 原值列可以不改。规范值列是另一份 | 取决于唯一约束放在哪一列。放在规范值上，仍会合并不单射的输入 | 若唯一约束只放在原值上，两种规范前写法可以并存 | 两列都进索引时，键长按两套最大字节相加，现在更不能证明放得下 | 这是本表里唯一明确保留原值的方案。哪一列才是业务身份，仍未决定 |

阻断内容已经规定显式 `EMPTY` 不等于空字符串。若那四列使用不区分大小写的排序规则，`EMPTY` 与 `empty` 会被当成同一个内容。若使用 `PAD SPACE`，`EMPTY` 与带尾随空格的写法也会被当成同一个内容。这不改变 `EMPTY` 的逻辑定义，只说明排序规则可以破坏已经写下的区分。

## 5. 唯一索引键长

三个长度不要混用。

| 名称 | 含义 | 来源 |
| --- | --- | --- |
| 字符数 | `VARCHAR(M)` 的 `M`，或逻辑字符串的字符个数 | 列宽尚未指定。逻辑值的字符数只对已经写死的记号有意义，例如阶段标记「标准化」是三个字符，这不构成列宽 |
| 最大字节数 | 建整列索引时用来对照上限的值。`utf8mb4` 下按 `M × 4`。`VARBINARY(M)` 的 `M` 本身就是字节 | 12.9.1 与 17.22 的例子。推导，不是实测 |
| 实际存储字节数 | 某一行的 `L`，再加 1 或 2 字节长度前缀 | 13.7。短值的 `L` 可以远小于 `M × 4`，不能用来证明整列唯一索引建得成 |

组合键的上限检查值是各列最大字节数之和。现有身份都少于 16 列，16 列上限不构成缺口。前缀索引不采用：它的唯一性不到整列。

上限本身还有未选参数：

| 条件 | 手册给出的上限 |
| --- | --- |
| `DYNAMIC` 或 `COMPRESSED`，且页大小按手册与 3072 对应的 16KB | 3072 字节 |
| 同上，页大小 8KB | 1536 字节 |
| 同上，页大小 4KB | 768 字节 |
| `REDUNDANT` 或 `COMPACT` | 767 字节 |

行格式和 `innodb_page_size` 都没有项目决策。不能把 3072 当成已经适用的那个上限。

尚缺的列参数是每一段身份的声明最大长度，以及该列是字符型还是字节型。没有这些数，下面每一条组合键都无法证明能够建立，也无法证明一定超限：

| 候选组合 | 段数 | 现在能写的式子 | 缺口 |
| --- | --- | --- | --- |
| 观测四段 | 4 | `utf8mb4` 时为四段 `M × 4` 之和 | 四段的 `M` 都没有 |
| 字段结果三段 | 3 | 三段 `M × 4` 之和 | 三段的 `M` 都没有 |
| `normalizationIdentity` | 观测四段再加两个版本 | 六段之和。空转换版本还不能用 NULL 充当唯一列 | 各段 `M`，以及空版本的非空物理表示 |
| `versionFixKey` | 观测四段、`taskId`、阶段标记 | 若拆成列，就是这些列的最大字节之和 | 各段 `M`。阶段标记的三个字符不是列宽 |
| 阻断三段 | `taskId`、阻断码、主体 | 三段之和 | 各段 `M` |
| 完整性审计 | 四段逻辑组成，其中一段是键列表 | 列表还没有物理列，不能代入 | 列表如何按字段存放，而不是默认序列化 |
| 单列标识 | 重放、尝试、快照、契约版本 | 单列 `M × 4`。`M × 4` 大于当时适用的上限，则整列索引不能建立 | 生成算法和 `M` 都没有 |

算术边界，仍不是实测，也不作为列宽建议：在 `utf8mb4`、16KB、`DYNAMIC` 或 `COMPRESSED` 这组手册数字下，各列声明字符数之和若大于 768，则 `Σ(M × 4)` 大于 3072。四段身份即使平均分配，也要每段的 `M` 已知后才能判断。某一段单独超过当时的上限，整组唯一索引同样不能建立。`VARCHAR` 允许声明到 16383 字符，所以「类型用了 `VARCHAR`」本身不证明键放得下。

## 6. 哈希辅助

领域身份仍不用哈希代替。只写 SHA-256 不构成证明。算法、字段编码、字段顺序、字段边界、哈希前是否做 Unicode 规范化，以及这套规则的版本，都还没有决定。不得用哈希把尚未确定的来源事件身份掩盖成一个定长键。

| 方案 | 碰撞时发生什么 | 能否证明业务身份相同 |
| --- | --- | --- |
| 只有哈希的唯一索引 | 两个不同原身份算出同一摘要时，第二行不能插入。读到的行是先写入的原身份 | 不能。摘要相同不是身份相同 |
| 哈希唯一索引，冲突后再读原字段 | 唯一索引已经拒绝第二行。回读可以发现摘要相同而原字段不同，但不能把第二份身份存下来 | 不能把这次冲突当成 `ALREADY_EXISTS`。06-04-19 已写明这一点 |
| 哈希普通索引，再用原字段精确比较 | 碰撞不阻止第二行。普通索引不提供唯一性 | 不能。比较原字段才是相等判断。它也不替代 06-04-19 已经排除的先查后插 |
| 原字段组合唯一索引 | 没有哈希碰撞。冲突由排序规则下的索引值决定 | 只有在该排序规则与业务身份相等被证明一致时，才是业务身份唯一。这一致性尚未证明。键长也尚未证明 |

若将来因为键长才增加摘要列，原身份列仍要保留，冲突和读取仍比较全部逻辑字段。摘要列是否建立，仍是待正式决策。

| `versionFixKey` | 观测身份、`taskId`、阶段标记「标准化」 | 观测各段的风险仍在。阶段标记是固定文字，不另造写法 | 组成列的 `M` 未知。是否独立成表未决 | 表是否独立，以及各段长度和排序规则 | 否 |

| ReplayRequest | `replayRequestId` | 若标识是字符串，单列排序规则仍会合并不同写法 | 算法和列宽未定。单列也可能超过上限 | IR-03 的生成算法与列类型 | 否 |

`rawPayloadRef` 只作为观测身份的一段和任务行上的权威引用。本调查不给原文字节建 MySQL 唯一约束。

## 8. 未决问题

- 字符集、排序规则、行格式、页大小。
- 各身份段的声明最大长度，以及用字符列还是字节列。
- 空 `conversionRuleVersion` 的非空物理表示。
- 规范化算法是否存在。若存在，它的编码、边界和版本。
- 哈希是否需要。需要时的算法、规范化和版本。
- 稳定事件身份的字段，以及重放、尝试、快照、契约版本标识的生成算法。
- 完整性审计键列表的按字段存放方式。
- 长度前缀的 1 或 2 字节是否计入 3072。手册举例没有加上，也没有排除。
- 以上全部没有 8.0.46 实测。

## 9. 对 N-10 的补充

N-10 已经写明：组合唯一键在字符集和排序规则未定时不能执行，键长是否超过 3072 字节未实测，哈希不能代替领域身份。本轮补上的是比较语义和计算缺口，不改变那些结论。

可以加进后续比较的事实：

- 未指定字符集时，手册默认是 `utf8mb4` / `utf8mb4_0900_ai_ci`。该默认会合并大小写和重音，但不合并尾随空格。项目没有采用它。
- `utf8mb4_bin` 与 `utf8mb4_0900_bin` 的尾随空格语义相反。不能只写「二进制排序规则」。
- `VARBINARY` 避免字符集转换，也避免不了「同文不同字节」造成的多行。
- 键长按各列最大字节数之和对照上限，不按某一行的实际字节数。列宽未知时，观测四段、字段结果、版本固定、阻断和单列标识都不能证明可建。
- 哈希唯一索引在碰撞时会拒绝第二个不同身份。回读只能发现，不能把碰撞收成 `ALREADY_EXISTS`。

N-10 的「不选定最终索引」仍然有效。本文件没有把它改成已接受规则。

## 10. 后续工作与准入

可以继续的只有比较：在不指定列宽的前提下维持上述公式；为每一段身份列出「谁有权规定最大长度」，而不是先填一个数；把 `utf8mb4_bin` 与 `utf8mb4_0900_bin` 的尾随空格差异留在候选表里。

定稿之前仍要有正式决策：字符集、排序规则、列宽、行格式、页大小、空转换版本的非空表示、IR-03 的身份字段。实现之前仍要单独授权，并在 MySQL 8.0.46 上验证选定组合的比较结果和整列唯一索引能否建立。本文件不安排这次实验，也不连接数据库。

仍然禁止：DDL，MySQL 驱动和客户端，持久化 Java，Create-or-Get 的生产实现，用默认 `0900_ai_ci` 或某一种 `bin` 当作已经选定，用哨兵填空转换版本，把 `taskId` 加入观测身份，发明稳定事件身份，用哈希代替尚未确定的来源身份，把本轮推导写成 8.0.46 实测。Stage C 没有因此获得准入。
