## 4. 统一身份语义模型

下面只是语义分类，不是 Java 类，也不是表字段。

| 语义 | 含义 | 与其他身份的关系 | 当前证据 |
| --- | --- | --- | --- |
| SourceOrderIdentity | 来源平台里的一张业务订单 | 一张订单可以有多次创建、支付、退款、取消。订单身份不等于其中一次事件 | 四类来源都没有一份已证明的订单号字段可以写入 V2。旧代码里的订单号不能回填 |
| SourceEventIdentity | 来源契约证明稳定、唯一、范围明确，并且能区分同一订单上不同业务事件的身份 | 只有它才能作为非重放 Task 的 Create-or-Get 依据。同一事件再次到达应回到原任务 | 四类来源都没有 |
| DeliveryIdentity | 一次 HTTP 回调或一次 Kafka 投递 | 可以重复、丢失响应或换 offset。不能未经证明就当成业务事件 | Kafka 的 topic、partition、offset 只定位投递。京东 `timestamp` 也未证明是投递号 |
| TaskIdentity | V2 的 `taskId` | 内部逻辑任务。先有来源事件身份，才知道该不该复用已有任务。新生成一个 `taskId` 不能完成去重 | 算法未设计。依赖 IR-03，也还不能单独关闭 |
| ReplayIdentity | 调用方给出的 `replayRequestId` | 显式重放是另一个任务。普通重复投递不写这个标识 | 算法未设计。06-04-23 的 A-11 仍待补 |

基数：一个 SourceOrderIdentity 对零个或多个 SourceEventIdentity。一个 SourceEventIdentity 对一个非重放 TaskIdentity。一个 ReplayIdentity 对一个新的 TaskIdentity，不复用原任务的幂等键。一个 SourceEventIdentity 可以对应多次 DeliveryIdentity。

生命周期：来源事件身份在契约声明的范围内应跨重试不变。订单状态更新若是新业务事件，应使用新的事件身份，而不是改写原任务。内部 `taskId` 一旦与某个已声明事件绑定，重复投递不替换权威 `rawPayloadRef` 和权威 `receivedAt`。这个规则来自 Pipeline 和 06-04-10，在身份尚未声明时没有可绑定的任务。

平台字段名不要求相同。适配器以后可以映射各自的原始列，但映射表现在是空的。不能把四家收成同一个 `eventId` 列再假装已经统一。

## 6. Task 创建幂等设计约束

非重放任务的幂等身份等于来源契约已经声明的稳定接入事件身份。这是 Pipeline 第 4.2 节和 06-04-10 的现行规则。内部 `taskId` 是这条身份所指向的逻辑任务，不是这条身份本身。

可自动 Create-or-Get 的前提，缺一不可：

1. 该来源契约声明了稳定事件身份。
2. 作用域写明平台、商户、门店、应用或消息种类里哪些必须参加。
3. 重试复用该身份，并且同一订单上的不同业务事件使用不同身份。
4. 空值、格式错误、同一身份对应不同正文，都有契约语义。
5. 字段可以按非空值比较。比较用的字符集和排序规则仍是 06-04-24 的待确认项，不在这里选定。

现在四类来源都不满足。因此不建立来源级去重，也不采用「每次接收分配一个内部号并自动建任务」。后一种做法会产生两个任务，业务还没有书面接受。

06-04-19 把「来源已声明稳定身份时的任务创建」列为 A 类 Create-or-Get：普通 `INSERT` 加完整列唯一，不先锁一条 `RUNNING` 任务。身份字段未定，所以这条唯一索引现在不能建，也不能做虚构字段的实验。任务行上的锁、`CURRENT` 计数和先查后插都不能代替它。那是 IR-02，不因本调查关闭。

同一已声明身份再次到达：返回先插入成功的任务，不替换第一次保存的权威 `rawPayloadRef` 和权威 `receivedAt`。本次新引用不进入原任务的观测。正文差异是完整性异常，不是更新。身份尚未声明时，没有这行任务，也就没有可覆盖的权威输入。

显式重放使用 `replayRequestId`，指向新的 `taskId`。普通重复投递不写该标识。生成算法未设计，A-11 仍待补。

## 7. Kafka offset 与故障恢复边界

MySQL 与 Kafka 不是一个本地事务。至少一次投递不能推出不会重复建任务。重复任务要靠来源身份上的唯一约束，而该约束现在不存在。不得先提交 offset，再补任务。

有稳定身份并且原文介质已经选定时，候选顺序仍是 06-04-10 的第 7 节：校验身份，保存原文，Task Create-or-Get，确认 MySQL 事务已提交，然后才提交 offset。offset 提交失败则下次投递回到原任务。介质未选定是 IR-15。在此之前，即使身份以后出现，也不能把「先建任务、后补原文」写成已经安全。

没有稳定身份时，当前安全状态是：不建任务，不提交这条消息的 offset。分区会停住。这是运行风险，不是丢弃消息的理由。隔离保存可以让分区继续，但介质、保留和恢复负责人都未选，所以现在不能实施。隔离记录不是任务，也不生成 `replayRequestId`。不引入 Inbox、Outbox 或 DLQ。

| 情况 | 能否提交 offset | 任务与原文 | 依据 |
| --- | --- | --- | --- |
| 任务创建成功，原文保存也成功 | 只有两步的提交都已确认，才可以提交 offset | 可以进入后续 Worker。权威引用使用这一次保存的引用 | 06-04-10。介质仍是 IR-15，当前做不到同证 |
| 原文保存成功，任务创建失败 | 不提交 | 不留下半成品任务。已保存原文是否可再读，等介质决定 | 不能用原文成功代替任务成功 |
| 任务语句已返回成功，客户端没收到提交结果 | 不提交，直到按 06-04-19 确认事务结果 | 未确认前不再插入。确认是原任务后才复用 | `COMMIT` 未发送与 `COMMIT` 已发送仍是两种状态。本轮未执行 |
| Create-or-Get 的 `COMMIT` 结果不确定 | 不提交 | 新连接加锁读。缺行或读失败都不当成「可以再插一条并提交 offset」 | 06-04-19 第 6.3 节。实验未跑 |
| offset 已提交，但任务没有持久化 | 这是要避免的顺序。若已经发生，消息不能靠同一 offset 再读到 | 当前规则禁止这条顺序。没有故障注入记录 | 不承诺能够自动补建 |
| 任务已持久化，offset 尚未提交 | 下次投递再提交 offset | 有身份则必须回到原任务，不新建 | 06-04-10 场景 14。未执行 |
| 重复消息到达，原任务已在 | 确认原事务已提交后再提交本次 offset | 复用任务，不替换权威引用 | 前提是身份已声明。当前来源不适用 |
| 来源身份缺失或无法验证 | 不提交 | 不建任务。不用 `receivedAt`、offset、分区号、消费者实例、`taskAttemptId` 或报文字节哈希拼键 | Pipeline 与 06-04-10 |
| 原文保存介质不可用 | 不提交 | 不把任务写成已经可重放。任务行是否允许先出现，仍等 IR-15 | 06-04-10 第 7 节 |

Worker 领取、代次和 `taskAttemptId` 发生在任务已经存在之后，由 IR-07 约束。它们不参加来源事件身份。

## 8. 身份命名空间与候选唯一键

不把下面每一项都拼进唯一键。只有契约证明「离开该范围后同一取值会指向上不同的事件」时，该项才成为身份的一部分。其余只可留作查询或审计属性。

| 候选 | 是否身份组成部分 | 当前证据 |
| --- | --- | --- |
| `sourcePlatform` | 适配器用来隔开不同来源。它不是报文里的事件号 | 四家字段名不同，必须分开适配。这是设计约束，不是某一列已经存在 |
| `platformAccountId` | 未知。条件必需仅当契约证明账号之间会重复 | 无 |
| `merchantId` | 未知 | 京东 `venderId` 被写成「分发标识」，作用域未确认，不能直接当成商户命名空间 |
| `storeId` | 未知 | 美团本页没有门店号 |
| `sourceEventType` | 未知。消息种类不同可能是不同事件 | 淘宝闪购目录只有种类名。团购没有这份目录 |
| `sourceEventId` | 只有来源真的提供并定义时才可以有 | 四类来源都没有这份字段。不新增一个空列 |
| `sourceEventVersion` 或序号 | 仅当来源写明语义 | 京东 `timestamp`、`statusId` 都不是 |

订单号、金额、时间、报文字节哈希、`rawPayloadRef`、`receivedAt`、Kafka offset 不进入身份。订单号至多在契约证明之后描述 SourceOrderIdentity。

## 11. 调查结论

1. POS 堂食没有可用身份字段。仓库没有这份契约。
2. 京东外卖的 `orderCreated` 页有 `venderId`、`billId`、`statusId`、`timestamp`。四列都不可当作稳定事件身份。`billId` 只是页面上的消息单据 ID。
3. 美团外卖的已确认订单推送页没有读到订单号或事件号。金额字段不可用作身份。
4. 淘宝团购没有官方字段页。闪购消息码和富智云旧团购键都不可用。
5. 四类来源都不具备已证明的 SourceEventIdentity，也都不能把订单身份、投递身份或内部 `taskId` 当成它。
6. 不同平台的字段语义已经不同，以后必须按各自契约做适配。现在没有可适配的事件字段。
7. Task 创建幂等的边界是：没有契约声明的稳定事件身份，就不自动建任务。新生成 `taskId` 不能解决重复。显式重放仍走 `replayRequestId`，算法未定。
8. Kafka offset 只在对应 MySQL 结果已经确认提交，并且原文可再读之后提交。无身份时不提交。MySQL 与 Kafka 没有跨系统本地事务。
9. 可以由现有证据确定的，是上述否定结论。必须向平台或业务确认的，是第 10 节的问题。确认之前不补字段。
