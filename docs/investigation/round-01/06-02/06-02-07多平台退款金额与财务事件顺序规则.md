# 06-02-07 多平台退款金额与财务事件顺序规则

证据等级：代码已确认、生产结构已确认、自动化测试已验证、真实报文已验证、生产样本已验证、代码推断、待业务确认、未发现。本轮没有导出生产订单样本，因此没有“生产样本已验证”的金额口径。

## 富智云退款事实

`FuiouRefundFactMapper` 27–61 行：只有 `payState` 为已退款才产出事实。`refundId` 是 `paySsn`，关联原支付 `sourcePaySsn` 和订单 `orderNo`。金额是 `refundAmt`，空则抛错。成功时间是 `refundTm`。`refundType` 固定 `UNKNOWN`，注释说明单笔退款额等于原支付额也不能当成整单全退。商家、平台、其他承担都写 `null`。

商品明细在 `FuiouRefundItemFactMapper`，金额和数量来自退款商品行。累计不在 Mapper 完成。

## 富智云累计

`FuiouRefundContributions`：

- 格式 2 按退款号 `refundSsn` 保存根金额和明细。同一号重复时，更高 `version` 覆盖；同版本不同值记冲突，不采用先到值（272–281 行）。
- 全部退款根金额已知且无缺口时，订单累计退款是各笔根金额之和（131–135 行）。
- 商品累计是各笔该商品行金额之和，且各行合计必须等于该笔根金额，否则不发布商品金额（233–240、183–222 行）。
- 负数金额或数量直接抛错（274–275 行）。
- 新缺口不清掉上一次已经接受的商品值。
- 旧格式按商品最后值合并，不能反推每笔贡献；新格式遇到旧状态会要求从历史原文重建（25–28 行）。

这支持多次退款按退款号累加，也支持一行上的部分数量。是否允许退款超过已付：累计方法没有和支付额比较。商家承担退款额没有计算公式，事实列保持 `null`。

退款后营业额：计算器不读退款。商家收入公式是 `userPay - 已完成退款额 - 储值赠送`（627–638 行），输入不齐则返回 `null`，不是写成 0。

## 财务顺序

`FuiouFinancialSequence` 只用于不可变 `paySsn`：

- 普通号 = 业务时间毫秒 × 1_000_000 + `eventId` 对 1_000_000 取模（22–27 行）。
- 同一业务时间的不同事件靠事件号尾数区分，尾数碰撞时顺序不保证业务先后。代码没有另做同一毫秒仲裁。
- 修复号 = 该业务时间全部普通尾数上界再加 1（38–39 行）。注释写明可能等于下一业务版本的普通号，不能用于可更新来源。
- 它不比较退款和支付谁先发生，也不重放金额。迟到事件若版本号更小，退款合并里的 `accept` 会保留较新版本。

## 美团

`MeituanRefundFactMapper` 29–48、77–100 行：金额来自 `money`，元转分。小于 0 拒绝。部分退款类型下金额缺失会走单独分支。未发现商家承担列赋值。多次退款是否累加取决于退款 ID 和 Reducer 的退款水位，不在这个 Mapper 里求和。

## 淘宝闪购

`TaobaoRefundFactMapper`：退款头金额来自 `totalPrice`，元转分；商品行来自 `money`。数量另映射。未发现承担方拆分。

## 京东售后

`JdAfsRefundMapper` 98–145 行：退款号来自售后服务单。只有状态成功才写 `refundUserMmoney`（源字段名就是这个拼写）到 `refundAmount`，否则金额为 `null`。成功明细用 `cashMoney` 的 `longValue()` 和 `skuCount`。这里没有元转分。`longValue()` 在小数 JSON 上会截断，不是 `longValueExact`。类型风险见精度报告。

退款类型先写 `UNKNOWN`，Reducer 再用 `originalPaidAmount` 和成功金额判断整单或部分（`CanonicalOrderReducer` 1072 行附近）。申请、处理中、成功、失败来自 `afsServiceState`。未发现退款金额超过已付时的拒绝。迟到与重复由版本和唯一键处理，不由财务顺序类处理。
