## 3. 决策一：权威发生时点

决策编号：D-IR10-01。确认选项：定义 B。业务确认状态：已业务确认。业务确认日期：2026-11-26。确认依据：业务决策负责人明确确认接受定义 B。架构批准：待架构批准。

已确认语义：

- 拒绝责任事实成功 `COMMIT` 时，拒绝事件正式发生。
- 责任事实 `COMMIT` 前发生进程故障，不认定为已经形成权威拒绝事件。
- 责任事实 `COMMIT` 后，即使最终审计记录尚未补写，也允许根据已提交责任事实恢复补写。
- 恢复只消费已提交的责任事实，不按补写当时的任务状态重新判定历史分类。

责任事实不是现行实体。Pipeline 第 11.1 节把同类待处理记录列为未选。业务确认不把它变成已经批准的表。若架构以后批准，这一行至少要能表达任务身份、被拒绝的 `blockIdentity` 与四个内容字段、当时有效阻断的身份与内容，以及持锁重读时任务尚未终态。物理形状、索引和字符集仍待架构批准。本文不规定它们。

选择定义 B 的理由：其他进程只能看见已经成功提交的行。任务行和有效阻断只能说明第一条阻断已经登记，恢复不出尚未写入的被拒绝身份。把发生时点放在一次成功的责任事实 `COMMIT` 上，崩溃后才有可消费的分类依据，并且补写不再用当前任务状态改写历史。

放弃定义 A 的代价：内存仲裁可以已经作出，进程崩溃后却没有权威持久化事实。业务会认为事件已经发生，系统无法恢复。这与 Pipeline「待处理责任不能只留在崩溃进程的内存里」冲突。日志、trace、`receivedAt` 和 Worker 本地时钟不能代替这一行。

放弃定义 C 的理由：若最终审计 `COMMIT` 才算发生，审计提交前崩溃同样不能从任务和有效阻断恢复被拒绝身份。定义 C 还把「行已提交」和「分类正确」绑在同一次提交上，而现行审计事务不锁任务行，序列 A 的种类在未改锁之前仍然未决。

`COMMIT` 结果不明时，不得把责任事实记成已发生，也不得记成确定未发生。读不完整不等于没有这行。这一读法尚未验证，也不能直接套用 06-04-19 第 6.3 节。如何判定，留在第 6 节的后续设计，本次不选定。

## 4. 决策二：序列 A 分类规则

决策编号：D-IR10-02。确认选项：规则 C。业务确认状态：已业务确认。业务确认日期：2026-11-26。确认依据：业务决策负责人明确确认接受规则 C。架构批准：待架构批准。

序列 A 的前提保持 06-04-39 第 4 节，不改写：

1. Worker A 读取任务，状态为 `RUNNING`。
2. Worker A 读到有效阻断 A。
3. Worker A 在内存中仲裁出身份 B 被拒绝。
4. Worker A 尚未提交审计记录。
5. Worker B 把任务推进到 `FAILED` 并成功 `COMMIT`。
6. Worker A 随后尝试写入审计记录。

已确认语义：

- 责任事实事务锁定任务行。
- 持锁重新读取任务状态和有效阻断。
- 根据锁定后的权威状态确定分类。
- 插入责任事实，并在同一事务中提交。
- 任务终态事务必须遵守相同的任务行锁协调边界。终态事务也锁这一行，从而排队。
- 后续审计补写只依据已经提交的责任事实，不根据恢复时的任务当前状态重新分类。

选择规则 C 的理由：分类依据和发生时点落在同一条已提交的责任事实上。终态先取得锁并提交之后，责任事务重读到终态，就不再创建「终态前」的责任事实。责任事务先取得锁并提交之后，终态等待，补写不再打开序列 A 那种「先读到 `RUNNING`、终态已提交、随后才写」的空隙。

放弃规则 A 的代价：现行非锁定审计写入不能证明序列 A 的分类。先读到 `RUNNING` 不能证明随后应是拒绝审计。先提交 `FAILED` 也不能单独证明应是迟到审计。不得仅凭两次 `COMMIT` 的先后推断种类。

放弃规则 B 的代价：审计事务自己承担任务行锁和分类职责。那样没有一条更早的责任事实可供崩溃后恢复。责任事实与最终审计的职责边界也不清楚。规则 B 还不创建定义 B 所依赖的那一行。

规则 C 的物理协议仍未批准。该事务不能放进现行 B 类，因为 B 类要求阻断为空。也不能放进现行 A 类，因为 A 类不锁 `RUNNING` 任务。锁顺序应是先任务行，再责任事实索引，不先锁尝试行。这是待批准的协调要求，不是已经实现的锁。06-04-11 只证明已经取锁的事务会排队，没有证明责任事务会取锁。MySQL 8.0.46 上的排队、死锁和隔离级别都未验证。`FAILED` 与 `SUCCESS` 的条件不因这把锁而改写。责任事实 `COMMIT` 确认前崩溃，按定义 B 事件尚未发生，内存仲裁不可恢复。

## 5. 已确认组合与仍待完成的代价

业务已确认的组合是定义 B + 规则 C。架构批准仍是待架构批准。

按已确认的业务语义：

1. 责任事实 `COMMIT` 前，不认定为正式发生。
2. 责任事实 `COMMIT` 后，具备恢复补写的依据。最终审计未写时，其他进程仍按该行补写。
3. 分类与任务终态的竞争，通过同一任务行锁协调。依据是锁内重读，不是两次 `COMMIT` 的时间比较。
4. 需要新增责任事实的持久化设计。这是新实体和新事务，不是把事实塞进已经结束的阻断登记事务，也不是 Inbox、Outbox 或 DLQ。实体是否成立，仍待架构批准。
5. 需要明确身份、唯一约束、不可变内容和保留策略。逻辑身份和物理唯一约束挂在 IR-02。保留、归档和删除挂在 IR-15。两项都未决定。
6. 需要设计跨进程恢复补写。补写者不是原 `CURRENT`，消费组分区归属也不能代替执行权。补写是另一次提交，有自己的 `COMMIT` 不明窗口。机制尚未设计。
7. 需要真实 MySQL 8.0.46 并发实验和故障注入，以及随后的 E2E 用例更新。这些都未执行。

主要未解决风险与 06-04-39 相同：新实体、两次 `COMMIT` 不明、唯一约束和保留策略都未决。成功类终态要求有效阻断为空。已提交的成功终态不能再配上一条「终态前阻断曾存在」的责任事实。那种并存是完整性异常，不新增错误码，也不把结果修成「带阻断的成功」。

架构批准通过之后，才依次做下面的设计。本次更新只列出事项，不选定物理实现：

1. 责任事实实体及其逻辑身份。至少要能表达第 3 节已确认的那些事实，不在这里定表名、列类型或存储产品。

4. 任务终态推进的锁协调。终态事务与责任事实事务使用同一任务行锁。不改 `FAILED` 与 `SUCCESS` 的现有条件。
5. 责任事实 `COMMIT` 结果不确定时的恢复判定。不明不等于成功，也不等于确定失败。不套用 06-04-19 第 6.3 节。
