## 3. 权威发生时点

下面四种定义都不是本轮选出的业务语义。先把五个时点分开。它们不是同一个瞬间。

| 时点 | 现行方案 A 里有没有 |
| --- | --- |
| 读取任务状态 | 有。拒绝审计不锁任务行。06-04-11 第 7 节。这次读取可以是普通读。06-04-11 写明普通一致性读不是随后写入的围栏 |
| 判定拒绝身份和分类 | 有规则，没有和终态事务绑在同一把锁上。Pipeline 第 11.1 节用「终态未提交」或「终态已提交」描述判定。它没有写这个判断发生在审计 `COMMIT` 的同一时刻 |
| 拒绝审计 `INSERT` | 语句成功还不是事务已提交。06-04-19 第 6.1 节对可执行插入是这么写的。审计还没有可执行协议 |
| 拒绝审计 `COMMIT` | 行这时才对其他进程可见。它不取得任务行锁，所以提交瞬间的任务状态不必等于前面那次读取 |
| 终态事务取得任务行锁并 `COMMIT` | 有。`FAILED` 和成功类终态都先锁任务行。06-04-11 第 7、8 节。这笔事务可以插在上面的读取和审计 `COMMIT` 之间 |

因此，审计 `COMMIT` 先于或后于终态 `COMMIT`，都不是分类结果本身。分类要看判定当时使用的那次任务状态。那次读取若在锁外，终态可以在读取之后、审计提交之前完成。现行文档没有把这个空隙的结果写成拒绝审计，也没有写成迟到审计。见第 4.9 节序列 A。

### 3.1 定义 A：内存仲裁完成即发生

Worker 已经判定「终态前、已有阻断 A、身份 B 被拒绝」，但数据库还没有对应行。另一个进程读不到 B。进程崩溃后，内存、本地队列和调用栈都消失。Pipeline 第 11.1 节把这种情况排除在即时重试之外。

它不能跨进程恢复，也不能覆盖任意步骤的崩溃。终态后的新身份和「曾经在某进程内存里被拒绝」无法区分，因为后者没有留下行。它不需要本地时钟，但它依赖进程内存，也就是事务外状态。没有 `COMMIT`，所以也没有可核对的提交结果。06-04-35 已写明不能把内存事件记成已持久化。

### 3.2 定义 B：拒绝责任事实成功 `COMMIT` 才发生

只有责任行已经成功提交，这次拒绝才算发生。尚未提交的内存仲裁不算。因此它恢复的是已提交的责任行，不是所有曾经在内存里仲裁过的拒绝。06-04-36 写过同一边界。

跨进程恢复依赖于这行确实提交，并且行里固定了身份、四个内容字段、当时的阻断，以及「持锁重读时尚未终态」。最后一项是 06-04-35 第 4.5 节的待决策条件。没有这把锁，一行里自填的「尚未终态」仍可能来自事务外缓存。崩溃发生在 `COMMIT` 确认之前，按这个定义事件尚未发生，不能事后补成已经发生。`COMMIT` 尚未发送、已发送但响应丢失、以及读不完整，都不能记成已发生或确定未发生。06-04-09 第 2、5 节。不依赖 Worker 本地时钟。责任行本身尚未批准。

### 3.3 定义 C：最终拒绝审计成功 `COMMIT` 才发生

这是现行文档里唯一已经写出的、能够跨进程看见的审计行。审计行一旦提交成功，任务再进入终态，已有种类保持拒绝。E2E-116，未执行。审计行提交之前崩溃，其他进程看不到 B。

「终态已提交，且该身份还没有任何记录，则首次写入是迟到审计」说的是分类判定使用的任务状态已经是终态。Pipeline 第 11.1 节的 `LATE_BLOCK_RECORDED`，06-04-19 第 3 节。它不是「终态 `COMMIT` 的时间戳早于审计 `COMMIT`」。拒绝审计不锁任务行。分类若来自更早的一次普通读取，这次读取和后面的审计 `COMMIT` 之间，终态事务可以先提交。提交完成时的任务状态，不能倒推成分类读取时的任务状态。也不能因为终态 `COMMIT` 更早，就断定这次审计一定是迟到审计。这个空隙是第 4.9 节序列 A，结果未决。

它能跨进程读到的只有已提交的审计行。`COMMIT` 不明时必须完整读取，不能另写一条来收场。不依赖本地时钟。定义 C 只回答「哪一次提交让行变得可见」。它不证明分类读取和终态提交已经串行。定义 C 不等于复审方案 C。方案 C 要另外写明锁、重读、分类、插入和提交的顺序，现在没有这段协议。

### 3.4 定义 D：其他

Pipeline 还列出「持久化待审计任务并扫描」和「其他可验证机制」，都未选定。它们若要在崩溃后仍能读到身份，仍然必须先有一次成功 `COMMIT`。否则和定义 A 一样不可恢复。把终态推迟到拒绝审计提交之后，会改掉「审计完成与终态是两个状态」，也会改掉 `FAILED` 不把拒绝审计并入自己的事务。本文不采用。没有已批准的第四种组件。不引入 Inbox、Outbox、DLQ 或 Redis 锁。

## 4. 八种竞态

「现行」指今天的文档，没有责任事实这行。「假设」只描述 06-04-35 第 4.5 节若以后被接受时的差别，不是已有能力。有效阻断 A 已经提交，除非某一场景写明不是。

### 4.1 场景一：拒绝侧事务先取得任务行锁

现行拒绝审计不取这把锁，所以本场景在现行事务里不发生。

假设未批准协议成立，并且该事务尚未 `COMMIT`：持久化的只有阻断 A 和 `RUNNING` 的任务。责任行对其他事务不可见。拒绝审计未写。终态事务若也要这把锁，只能等待。不允许把未见行恢复成拒绝审计，也不允许写成迟到审计。崩溃则事件按定义 B 或 C 尚未发生。重复插入要等唯一约束，现未验证。

该事务 `COMMIT` 已确认之后：责任行可见，任务仍可是 `RUNNING`，阻断仍是 A，最终审计可以还没有。允许别的 Worker 按该行补写拒绝审计。不允许改成迟到审计。不允许改 Task 或 Attempt。补写不是第二次发生。

### 4.2 场景二：`FAILED` 终态事务先取得任务行锁

现行：终态事务持锁，阻断仍是 A，`status` 仍是 `RUNNING`，于是提交 `FAILED` 和尝试 `RELEASED`。拒绝审计不在这笔事务里。提交前，已确认的持久化事实是阻断 A 和 `RUNNING`。提交后，任务是 `FAILED`，阻断仍是 A。若此时还没有 B 的审计行，B 没有持久化。不允许把只存在于内存的 B 恢复成拒绝审计。`FAILED` 的条件没有改。

这不等于「此后任何一次审计 `COMMIT` 都是迟到审计」。Worker 若在 `FAILED` 之前已经读过 `RUNNING`，再在 `FAILED` 之后提交审计，分类结果未决，见第 4.9 节序列 A。Worker 若第一次读取就看见 `FAILED`，并且该身份还没有行，现行首次写入规则才是迟到审计，见序列 B。

假设责任行已经在更早的事务里确认提交：它仍然是拒绝分类。随后的 `FAILED` 不把它改成迟到审计。最终审计仍可另一次补写。

### 4.3 场景三：`SUCCESS` 终态事务先取得任务行锁

成功类终态要求有效阻断为空。06-04-11 第 8 节。阻断 A 已经提交时，这笔 `SUCCESS` 匹配不到行，不能提交带阻断的 `SUCCESS`。任务保持 `RUNNING`，阻断保持 A。拒绝审计仍看它自己有没有提交。不允许为了让 `SUCCESS` 成功而清掉 A，也不允许凭这次失败的终态事务制造一条拒绝或迟到审计。

若任务已经是无阻断的 `SUCCESS`，则拒绝前提「当时已有有效阻断」与这行矛盾。后来的新身份按现行规则是迟到审计。不得用锁外曾经见过的 `RUNNING` 补一条终态前拒绝。这种组合若同时出现，是完整性异常。06-04-35 第 5.6 节。不新增错误码。

### 4.4 场景四：拒绝侧 `INSERT` 之后、`COMMIT` 之前崩溃

`COMMIT` 尚未发送。插入对其他会话不可见，或者会随未提交事务消失。不能从断连推断已提交或已回滚。06-04-11 第 7 节。持久化且已确认的仍是阻断 A 和当时的任务状态。B 的审计或责任行都算尚未确认。不允许恢复成拒绝审计，也不允许用迟到审计把这次不明收场。可能尚未发生，以后重试也可能再插入。唯一约束未验证，所以不能保证只有一行。

### 4.5 场景五：`COMMIT` 已发送，响应丢失

客户端不知道服务器提交了没有。已确认可见的只有阻断 A 和任务行，直到另一条连接把 B 的身份完整读完。读不完整不等于没有这行。不允许写成拒绝审计，也不允许写成迟到审计来代替这次不明提交。误记失败会丢，误记成功会在缺少唯一约束时重复。责任行和审计行若是两次提交，必须分开读。一边的结果不证明另一边。

### 4.6 场景六：`COMMIT` 已确认，Worker 随即崩溃

已确认的那一行还在。06-04-09 第 5 节从已提交记录继续。若确认的是拒绝审计，任务可以仍是 `RUNNING` 或已经终态，阻断仍是 A，审计已在。允许同一内容幂等，不允许改成迟到审计，不允许再插一行。若确认的是未批准协议下的责任行而审计还没有，允许按该行补写拒绝审计。若两种行都没有确认提交，崩溃后没有可恢复的 B。

### 4.7 场景七：两个 Worker 同时拒绝不同的 `blockIdentity`

两条身份都不是有效阻断。已确认的共同事实是阻断 A。每条身份在自己的审计 `COMMIT` 确认前都尚未持久化。任务在终态事务提交前可以仍是 `RUNNING`。两条不同身份各留一行不是重复。同一身份的重复属于场景八。没有持久化的那条，在进程崩溃后丢失。

每条身份的种类看它自己的分类读取，不看它的 `COMMIT` 和终态 `COMMIT` 谁更早。读取时已经看见终态、且该身份还没有行，现行规则是迟到审计。读取时看见 `RUNNING` 和阻断 A，而终态在这次读取之后、审计 `COMMIT` 之前完成，现行文档没有定义这一条是拒绝还是迟到。先提交成功的审计行，若已经是拒绝审计，随后的 `FAILED` 不改它的种类。不能把「终态夹在两次 `COMMIT` 中间」写成已经证明后一条变成迟到审计。

### 4.8 场景八：两个恢复者同时补写同一拒绝审计

没有已提交的分类事实时，两个恢复者都没有可写的拒绝来源，不允许补写。已有同一身份、同一内容的拒绝审计时，逻辑上只留一条，后写者得到 `REJECT_AUDIT_ALREADY_RECORDED`。E2E-117，未执行。不允许一条写成拒绝、另一条写成迟到。不改 Task、Attempt 或阻断。IR-02 未验证，不能宣称数据库已经拒绝第二行。

### 4.9 读取、终态和审计提交的三种顺序

方案 A 不锁任务行。下面只按这个现行形状写。不把未写明的结果补成拒绝或迟到。

序列 A：Worker 读到 `RUNNING` 和有效阻断 A，随后终态事务提交 `FAILED`，然后该 Worker 才 `INSERT` 并 `COMMIT` 拒绝审计。

已确认的持久化事实在终态提交后是 `FAILED` 和阻断 A。审计行在它自己的 `COMMIT` 确认前还不存在。分类读取时点早于终态 `COMMIT`，审计 `COMMIT` 时点晚于终态 `COMMIT`。Pipeline 第 11.1 节和 06-04-19 第 3 节都用「终态是否已经提交」描述首次写入，但没有写这次判断必须在审计事务里、持任务行锁重读之后再做。06-04-11 第 7 节又写拒绝审计不锁任务行。因此本序列的种类没有定义。未决。不能记成拒绝审计，也不能记成迟到审计。允许或不允许恢复，同样未决：没有已提交的分类事实可供另一个进程读取。事件可能留下一行，种类却没有规则。重复风险仍看 IR-02，未验证。

序列 B：`FAILED` 已经提交。Worker 这时才第一次读取该任务和这个尚无记录的身份，然后创建审计。

持久化事实是 `FAILED`、阻断 A，以及读取时还不存在的 B。分类读取已经看见终态。现行首次写入是迟到审计。Pipeline 的 `LATE_BLOCK_RECORDED`，06-04-19 第 3 节。这和序列 A 的差别是：序列 B 的判定输入就是已提交的终态，不是更早的 `RUNNING`。允许写成迟到审计。不允许写成拒绝审计，除非该身份已经有拒绝行。另一个进程不能把这次迟到写成更早的拒绝。丢失的是「内存里曾经拒绝」这一说法，不是已提交的迟到行。

序列 C：拒绝审计已经成功提交，然后任务进入 `FAILED`。

审计行已在，种类是拒绝。随后的终态不改这一行。06-04-11 第 7 节，06-04-19 第 3 节，E2E-116，未执行。任务变为 `FAILED`，阻断仍是 A。允许同一内容幂等。不允许改成迟到审计，不允许再插一行。这是已有记录的规则，不是序列 A 的首次写入。

方案 A 因此还没有证明三件事：分类判定和终态提交之间有串行关系；种类严格由两个 `COMMIT` 的先后决定；不存在「先读到旧的 `RUNNING`，终态提交之后才写入审计」的竞态。序列 A 就是这个竞态，结果未决。这些都不是已经实现或已经验证的行为。

## 5. 业务事件和数据库提交不是同一件事

若业务要求「只要内存里已经仲裁为拒绝，即使数据库还没提交，崩溃后也必须恢复出拒绝审计」，崩溃点上的依据是空的。其他进程看不到那次仲裁。日志、trace、`receivedAt`、Worker 本地时钟和当前任务状态都重建不出身份 B 和四个内容字段。重试只对还活着、并且还握着这次调用的 Worker 有效。这是持久化边界，不是再加一次重试就能补上的。

若把成功 `COMMIT` 定义为「行已经可见」，这只说明其他进程从这一刻起能读到该行。它不说明分类读取和这次 `COMMIT` 是同一时刻，也不说明终态 `COMMIT` 与审计 `COMMIT` 的先后就是种类。方案 A 不锁任务行。Worker 可以先读到 `RUNNING`，终态再提交 `FAILED`，审计最后才提交。现行文档没有定义这次写入是拒绝还是迟到。见第 4.9 节序列 A。

只有在一份尚未批准的协议里，把锁、重读、分类、插入和 `COMMIT` 写成同一事务的固定顺序，才能讨论「先提交的事务决定分类」。那是方案 C 或带任务行锁的方案 B，都未批准，也未验证。在那种协议被写明之前，不能把「抢到提交的算拒绝，没抢到的变成迟到审计」写成现行代价。

已经提交的拒绝审计，后来的终态不改种类。这是序列 C，依据是已有记录，不是两次 `COMMIT` 的时间比较。定义 A 想让未提交的内存仲裁在进程死亡后仍然算拒绝，现有材料做不到。

不能同时保证这两句：

- 每一次已经做出的内存仲裁，崩溃后仍是拒绝审计。
- 崩溃时数据库里可以还没有这行，并且不使用日志或时钟来找回它。

## 6. 终态要不要等待

现行 `FAILED` 不等待拒绝审计或责任事实。它的条件只是代次、`CURRENT`、`RUNNING`，以及阻断等于已登记的那一条。06-04-11 第 8 节。本文不改这句。

现行 `SUCCESS` 也不等待拒绝仲裁。它要求有效阻断为空。阻断 A 已经提交时，它提交不了。它同样看不见其他进程内存里尚未插入的身份。

终态事务只和同样锁任务行的事务排队。现行拒绝审计不锁任务行，所以终态事务不会因为「有人正在内存里拒绝」而等待，也不会挡住一次已经读完、尚未提交的审计。终态可以落在分类读取之后、审计 `COMMIT` 之前。终态事务也不读取「是否还有未提交的拒绝仲裁」。那个事实不在数据库里。

因此可以存在数据库发现不了的进程内待处理拒绝。`FAILED` 可以先提交。这是现行「两个状态」的结果，不是本轮新加的等待。它也不证明随后那次审计会变成迟到审计。序列 A 仍未决。

## 7. 三种方案各自保证什么

| 保证 | 方案 A：维持现有审计事务 | 方案 B：另加责任事实 | 方案 C：审计事务自己锁任务行 |
| --- | --- | --- | --- |
| 已提交的拒绝审计在终态后不改类 | 规则有。E2E-116 未执行 | 同左 | 同左 |
| 内存仲裁在提交前崩溃后仍能恢复 | 不能 | 不能。只恢复已经成功 `COMMIT` 的责任行 | 不能。提交点仍是审计行 |
| 终态先提交后，未落库的身份仍算拒绝 | 分类读取已经看见终态时，现行首次写入是迟到审计。读取早于终态、审计 `COMMIT` 晚于终态时，种类未决。不宣称 `COMMIT` 顺序决定分类 | 不能，除非责任行在终态前已经确认提交。该行未批准。是否用任务行锁固定读取，仍要单独决定 | 不能。而且只有锁、重读、分类、插入、提交的顺序写明之后，才谈得上串行。该协议未批准，未验证 |
| 用锁把「尚未终态」固定进同一次提交 | 没有这把锁 | 仅当第 4.5 节被接受。未批准，未验证 | 同左，而且要改「不锁任务行」 |
| `FAILED` / `SUCCESS` 条件 | 不变 | 谓词可以不变。对方持锁时只会排队 | 同 B |
| 两次 `COMMIT` 都可能不明 | 只有审计一次 | 责任一次，审计再一次 | 只有审计一次 |

方案 A 保持现有独立审计事务，不加任务行锁。分类读取和审计提交之间的竞态没有解决。它不宣称两个 `COMMIT` 的先后决定种类。

方案 B 仍是候选。只有责任事实成功 `COMMIT` 之后，别的进程才有恢复依据。它恢复不了这次提交之前的内存仲裁。这份事实要不要锁任务行、怎样和终态事务排队，是另一项决定，本文不作出。

方案 C 是让审计事务取得任务行锁。只有协议写明锁定、持锁重读、分类、插入和提交的顺序，才能讨论分类是否与终态串行。现在没有这段文字。方案 C 不是已批准设计，也没有 MySQL 实验。

方案 B 不能被说成「凡是内存里发生过的拒绝都能恢复」。没有成功 `COMMIT` 的仲裁，方案 B 和方案 A 一样没有行。

## 8. 不可实现的保证

在不把未提交状态写成持久化事实、并且不使用日志、trace、时钟或当前任务状态回推的前提下，下面几句不能同时成立：

1. 进程死亡后仍能恢复每一次只存在于内存的拒绝仲裁。
2. 方案 B 或方案 C 覆盖了 `COMMIT` 确认之前的崩溃。
3. 终态事务能够知道其他进程里尚未插入的拒绝，并因此等待，同时又不改变现有 `FAILED` 和 `SUCCESS` 条件，也不增加持久化事实。
4. 任务行锁代替物理唯一约束，保证两个恢复者只有一行。
5. 用终态之后的任务状态，判断终态之前曾经拒绝过哪个身份。

第 3 句若改成「终态必须等待」，就要改 Pipeline 的两个状态和 06-04-11 第 8 节。本文不改。即便改成等待，数据库仍然等不到它看不见的内存仲裁。要等待，那个仲裁必须已经变成行，或者持有任务行锁直到自己的 `COMMIT`。持锁的进程若在 `COMMIT` 前死亡，锁会随事务结束释放，身份仍然可以没有提交。

## 9. 决策输入

已经明确、但还没有 8.0.46 实验的事实：一个任务最多一条有效阻断。拒绝审计不是第二条有效阻断，不参与终态，失败不撤销阻断。它独立提交，不锁任务行，不要求 `CURRENT`。已有拒绝审计不因后来的终态改类。分类读取已经看见终态、且该身份还没有行时，首次写入是迟到审计。`FAILED` 不把拒绝审计并入自己的事务。成功类终态要求阻断为空。`COMMIT` 不明不得推断成败。日志不是审计。读取时点和审计 `COMMIT` 时点不是同一件事。

尚未批准的设计：责任事实这行、第 4.5 节的第三类锁、方案 C 的锁和重读顺序、终态后把尚无记录的身份补写成拒绝审计、审计专用的 `COMMIT` 不明读法、物理唯一约束、保留期限。序列 A 的种类也还没有规则，不能靠改写本文把它补上。

需要另行选定的业务语义，本报告不代选。这里是两个问题，不是一个问题的两种说法：

1. 拒绝事件的权威发生时点用定义 A、B 还是 C。定义 A 在进程死亡后不可恢复。定义 C 只让已提交的审计行可见，不自动回答分类读取和终态提交谁先谁后。
2. 不增加新的持久化事实时，方案 A 与终态并发，分类依据到底是哪一次任务状态。序列 B 和序列 C 有现行规则。序列 A 没有。未决，不能从「终态 `COMMIT` 更早」推断为迟到审计，也不能从「曾经读到 `RUNNING`」推断为拒绝审计。

06-04-34 的 R-02 写的是：终态提交之后，缺失的拒绝审计若按「没有同身份记录」第一次写入，现行分类是迟到审计。这对应序列 B 那种判定输入已经是终态的首次写入。它没有覆盖序列 A。

语义选定之前不能继续的设计：不新增责任事实，不改拒绝审计的锁，不改 `FAILED` 和 `SUCCESS` 的条件，不把方案 B 或方案 C 写成已批准，不把恢复补写写成已经可以按拒绝分类插入，不关闭 IR-10。

建议的决定顺序，仍不是决定本身：

1. 先回答上面两问。第一问决定未提交的内存仲裁算不算必须留下的事件。第二问决定方案 A 的读取空隙要不要有种类。两问可以分别回答。
2. 若第一问的答案是不算，跨进程只恢复已经提交的审计行。这不自动关闭序列 A。
3. 若第二问要求种类与终态串行，才需要一份写明锁、重读、分类、插入和提交顺序的协议。方案 C 是改现有审计事务。方案 B 是另加一行，而且只在该行 `COMMIT` 之后可恢复。两者都未批准。方案 C 仍然没有比审计行更早的事实。
4. 然后才写 `COMMIT` 不明的读法、IR-02 的唯一约束和 IR-15 的保留。不把这些提前做成实现。

06-04-36 建议暂不实施 B 和 C。本文同意。发生时点和序列 A 的分类依据都还要人来选。
