MySQL 8.0 手册提供的是一般机制，不是本项目实验。本轮核对过的页面如下。

- [17.7.2.2 autocommit, Commit, and Rollback](https://dev.mysql.com/doc/refman/8.0/en/innodb-autocommit-commit-rollback.html)：默认新连接开启 `autocommit`，一条语句自成事务。显式 `START TRANSACTION` 后要有 `COMMIT` 或 `ROLLBACK`。`autocommit` 关闭时，会话结束前没有明确提交的最后一笔事务会被回滚。`COMMIT` 使当前事务的修改永久化，并对其他会话可见。`COMMIT` 和 `ROLLBACK` 都释放本事务的 InnoDB 锁。手册没有把「客户端没有收到成功包」定义成回滚。
- [17.7.2.3 Consistent Nonlocking Reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html)：普通一致性读看到的是时间点之前已经提交的修改，看不到未提交或该时间点之后才提交的修改。可重复读下，同一事务里的一致性读沿用第一次建立的快照。手册中的双会话例子是：B 已经 `COMMIT`，A 在自己提交并重新读取之前仍然看不到这一行。要看更新的状态，手册提到 `READ COMMITTED`，或 `SELECT ... FOR SHARE` 等到持有最新行的事务结束。本项目没有选定其中任何一种，也没有在 8.0.46 上执行。
- [19.2 Replication Implementation](https://dev.mysql.com/doc/refman/8.0/en/replication-implementation.html)：副本自己向源请求二进制日志并执行。每个副本按自己的进度重放，可以落后于源。仓库没有复制拓扑。这条只说明：副本上看不到行，不能证明源没有提交。

[15.7.8.4 KILL Statement](https://dev.mysql.com/doc/refman/8.0/en/kill.html) 写的是终止连接或语句，并说明 `KILL` 返回时清理可能还没结束。它没有给出「另一条连接据此区分已提交和已回滚」的方法。本轮不把 `KILL`、`information_schema` 或性能库选成恢复手段。

## 4. COMMIT 前故障与 COMMIT 不确定性分类

三类不能并成「事务失败」。

| 类别 | 客户端能够确定的事 | 不能写成 |
| --- | --- | --- |
| 尚未进入 `COMMIT`，并且回滚或未提交已经被确认 | 请求没有发出，数据库也明确结束了这笔未提交事务 | 权威事实已发生 |
| 语句执行结果不确定 | 调用的是 `INSERT` 或更早的语句，但没有完整结果，而且可以确定当时还没发 `COMMIT` | 已形成，或者已经回滚 |
| `COMMIT` 结果不确定 | `COMMIT` 可能已经发出，成功包没有回到客户端 | 失败，或者已经成功 |

本地异常、日志时间和 Worker 重启都不提供数据库结果。收到成功响应的调用方可以认定已经提交。没有这份响应的另一个进程不能借用「对方大概失败了」。

### 4.1 尚未进入 COMMIT，且结果已经明确

| 场景 | 分类 |
| --- | --- |
| 开启事务前失败 | 事务没有开始。没有责任事实。调用方可以另开新事务，按规则 C 重新锁、重读。不复用失败前的内存状态 |
| 取得任务行锁前失败，错误完整返回，连接仍可用，且尚未发送 `COMMIT` | 同上。锁没有拿到，不表示分类已经完成 |
| 拿到锁之后、锁内读取前失败，且回滚已经确认 | 没有插入。新事务必须重新锁、重新读 |
| 锁内读完、`INSERT` 前失败，且回滚已经确认 | 内存中的分类不是权威内容。新事务重新读 |
| `INSERT` 明确失败，事务明确没有进入 `COMMIT`，回滚已经确认 | 未形成。允许新事务按规则 C 重做 |
| 死锁错误完整返回，并且整笔回滚已经确认 | 未形成。允许新事务重做。未完整返回的死锁错误不属于本行 |
| 可以确定 `COMMIT` 尚未发送，并且原连接仍可用 | 未形成。应在这条连接上结束事务，再另开事务。不在第二条连接上并行插入 |

这些许可只覆盖「回滚或未提交已经被确认」。确认来自数据库的完整结果，不来自进程已经退出。

### 4.2 语句执行不确定

| 场景 | 分类 |
| --- | --- |
| `INSERT` 执行期间断连，尚未发送 `COMMIT` | 语句是否执行完不知道。06-04-19 第 6.5 节。不是 `COMMIT` 不确定，也不是已确认回滚 |
| 可以确定 `COMMIT` 尚未发送，但原连接已经断开 | 未形成这一判断只在「确实没发送」的范围内成立。未发送不等于服务器已经回滚。06-04-42 第 4.4 节已分开这两句 |
| 锁等待超时的错误包不完整，或完整返回后连接断开，整笔回滚还没被确认 | `innodb_rollback_on_timeout` 未选。默认不能把整笔回滚当成已经发生。不属于 `COMMIT` 不确定 |

这三行都不允许重新 `INSERT`。也不把它们写成权威事实。

### 4.3 COMMIT 结果不确定

| 场景 | 分类 |
| --- | --- |
| 客户端发出 `COMMIT` 后连接中断 | 结果不确定。没有成功响应不等于没有提交 |
| 数据库可能已经提交，成功响应丢失 | 同上 |
| 提交过程中连接中断 | 同上。客户端无法把「还在提交」和「已经提交」分开 |
| Worker 在发送 `COMMIT` 之后崩溃 | 同上。崩溃时刻不是数据库结果 |
| 原连接失效，不能再读取原事务状态 | 原连接上的回滚返回值不能证明服务器已经提交或已经回滚。06-04-19 第 6.3 节 |

这几行都不允许重新 `INSERT`。在独立读取完成并分类之前，不写成已提交，也不写成未提交。

### 4.4 COMMIT 已确认成功

客户端收到 `COMMIT` 成功响应时，责任事实已经发生。Worker 随后崩溃，不撤销这次提交。拒绝审计可以还没写。那是 D5 的补写缺口，不是责任事实未发生。

另一个没有看见该成功响应的 Worker，不能从自己的空内存推断这笔已经失败。它只能做第 5 节的独立读取。

## 5. 独立恢复读取方案比较

候选边界，未批准，未实现：

1. 不复用已经失效或状态不明的原连接，也不在原事务上继续等它的锁。
2. 使用另一条连接上的新事务读取。缓存、进程内状态和日志不是权威记录。
3. 查找键是 D1 的 `blockIdentity`。读到行之后按第 6 节比较，不先看摘要。
4. 读取不完整、连接再次中断或结果不能分类时，保持不确定，停止写入。
5. 不使用 `READ UNCOMMITTED` 把尚未提交的插入看成已经发生。隔离级别本身仍未选定。
6. 不规定等待秒数。一次看不见，也不自动变成下一次的缺行结论。

| 读法 | 手册或设计能支持的方向 | 本轮不能拿它做的结论 |
| --- | --- | --- |
| 源库上的新事务 | `COMMIT` 之后的修改对其他会话可见。新的读取有机会看见已经提交的行 | 一次看不见不等于未提交。可重复读事务不推进时间点时，对方提交后仍可能看不见 |
| 可能落后的副本 | 副本重放源库日志，进度独立 | 副本缺行不能证明源库没有提交。仓库也没有拓扑。不把副本选成缺行判定点 |
| 普通一致性读 | 只看见该快照之前已提交的行 | 暂时没有行，可能是未插入、未提交、快照太早，或读的是副本。四种不能靠这一次分开 |
| 加锁读 | 手册写 `FOR SHARE` 会等到持有最新行的事务结束。06-04-19 把「还在等」排除在缺行之外 | 本轮不选定这条 SQL。等待超时不是缺行，也不是提交结果。`innodb_rollback_on_timeout` 未选 |
| 读取连接自己失败 | 没有完整结果 | 保持不确定。不用失败前的空结果 |
| 读到行但内容不一致 | 已有提交记录，载荷不同 | `BLOCK_CONTENT_CONFLICT`，停止。不覆盖 |
| 暂时没有行 | 这次查询没有看见 | 不是「确认不存在」，不是回滚，不允许重新 `INSERT` |

看见一行，说明这个身份上已经有提交记录。它不需要把「原连接那一个数据包一定成功了」补写进原事务的历史。定义 B 看的是有没有成功 `COMMIT` 的责任事实，不看哪一个客户端收到了包。

缺行要同时排除四件事，本轮一项都没有可执行的判定：原事务仍在提交或尚未结束；断连后服务器端还没把该事务收束；快照或副本使已提交行暂时不可见；读取本身不完整。`information_schema` 里当前没有该事务，也只能说明列表里现在没有它，不能区分已经提交和已经回滚。本轮不选这个查询。因此「独立读取确认不存在」没有打开。缺行继续保持不确定。以后若要讨论再插入，必须另有能够同时证明这四项的读取，并且新事务重新执行规则 C，而不是复用旧内存。那个读法现在不存在，也不用等待秒数代替。

## 6. D1、D2 内容核验规则

读到记录之后：

1. 用 `taskId`、稳定阻断码、阻断主体核对是不是这一条身份。不新增 `rejectionIdentity`。身份字段读不齐：停止，不进入补写，也不插入。
2. 逐项比较 06-04-45 的完整候选内容：被拒绝阻断的四个字段、分类结论、锁内非终态 `status` 副本、当时有效阻断的身份、当时有效阻断的四个字段副本。不用摘要代替逐项相等。
3. 不把拒绝审计的四字段规则扩大成这次比较。审计行是否存在，不改变责任事实这一次的核验。

| 核验结果 | 处理 |
| --- | --- |
| 同身份、完整内容一致 | 确认是同一条已提交责任事实。不重新 `INSERT`，不覆盖 |
| 同身份、内容不同 | `BLOCK_CONTENT_CONFLICT`。停止。不插入，不覆盖，不改成迟到 |
| 读取不完整，或某一项不能分类 | 保持不确定。不插入 |
| 身份无法核验 | 停止。不得进入 D5 |

责任事实行还不存在时，只有第 7 节把缺行收成「确认不存在」之后，才讨论下一步。本轮没有这种读法，所以不讨论再插入。

## 7. 独立读取结果分类与停止边界

| 分类 | 含义 | 是否允许重新 `INSERT` |
| --- | --- | --- |
| `COMMIT` 前明确故障 | 事务未进入 `COMMIT`，并且回滚或未提交已经被数据库完整结果确认 | 允许按新事务重新执行规则 C。不复用旧事务的内存状态 |
| 语句执行不确定 | 语句没有完整结果，或 `COMMIT` 未发送但服务器端回滚未被确认 | 不允许。也不能写成已形成 |
| `COMMIT` 已确认成功 | 客户端已经收到成功响应。责任事实已发生。审计可以尚未写入 | 不允许 |
| `COMMIT` 结果不确定 | 不能确认提交或未提交 | 不允许 |
| 独立读取确认存在且内容一致 | 找到这条身份上的已提交责任事实，完整内容一致 | 不允许 |
| 独立读取确认存在但内容冲突 | 完整性冲突 | 停止，不允许 |
| 独立读取不完整 | 无法得出结论 | 保持不确定，不允许 |
| 独立读取确认不存在 | 只有同时证明第 5 节那四项之后，才允许讨论下一步 | 本轮没有这种读法。不得仅凭普通查询缺行就允许 |

原 Worker 崩溃、新 Worker 接手时，新 Worker 没有原调用栈。它从「结果不确定或语句不确定」进入独立读取，不从「明确故障」进入。两个 Worker 同时恢复，单次读取不保证只有一行。那是 D7。读到冲突内容则停止，不各自插入。

## 8. D3、D5、D7、IR-02 依赖关系

| 机制 | 边界 |
| --- | --- |
| D3 | 任务行锁只排列分类和终态。锁成功、锁内读成功都不是已提交的证明。明确故障后的新事务必须重新锁、重新读 |
| D5 | 只消费 D4 已经确认存在、并且内容核验通过的责任事实。本轮不决定补写执行者、扫描器、调度或待办表。审计自己的 `COMMIT` 不明以后沿用同一分类原则，对象换成审计身份，步骤不在这里设计 |
| D7 | 唯一约束保证并发下的权威行。一次读取不能代替它。唯一冲突之后的胜出读取是另一条路径：插入已经被数据库明确拒绝，本事务没有留下新行。那不是 `COMMIT` 已发送。胜出行仍按 D2 比较。读不完则停止，不改叫 `COMMIT` 不确定 |
| IR-02 | 物理唯一索引未建。因此现在也不能用「唯一冲突」来探测责任事实是否提交。先查后插在没有索引时可以留下两行。D4 不关闭 IR-02 |

不能共用的两套恢复：

- 唯一冲突读取：数据库已经明确返回冲突，再读胜出行。确认缺行在 06-04-19 第 6.4 节仍是待决策，不插入。
- `COMMIT` 不确定读取：连原事务有没有提交都不知道。更不能因为普通查询暂时没有行而插入。

06-04-11 第 5.2 节的领取重读不用于这条身份。06-04-19 第 6.3 节在确认缺行后的再插入不用于责任事实。第 6.5 节里「确认缺行也不插入」与本候选一致，但它仍是设计文本，不是 8.0.46 实验。

## 9. MySQL 8.0.46 实验矩阵

下列实验都未执行。本轮不连接数据库，不执行写语句。预期结果是候选原则下应当观察到的现象，不是已经测得的结果。

| 编号 | 前置条件 | 操作 | 观察 | 预期 | 失败判定 | 是否写库 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| E1 | 显式事务，`COMMIT` 成功包已返回 | 另一条连接按身份读取 | 行是否可见，内容是否逐项一致 | 可见且一致。审计可以还没有 | 把成功提交读成不存在，或内容被覆盖 | 是 | 未执行 |
| E2 | `COMMIT` 已在服务器完成，客户端丢弃成功包 | 废弃原连接后独立读取 | 行与内容 | 按已提交处理，不第二次插入 | 把丢包当成回滚并再插入 | 是 | 未执行 |
| E3 | `INSERT` 尚未发出 `COMMIT`，然后断开原连接 | 新连接读取；原事务结束前再读一次 | 等待中的锁、缺行或随后出现的行 | 结束被确认前不插入。普通缺行不写成回滚 | 断连后立即再插入 | 是 | 未执行 |
| E4 | `COMMIT` 包已经发出，响应未返回 | 不根据客户端异常分类，只做独立读取 | 读到、读不到或读失败 | 读到且一致才确认。否则保持不确定 | 把未知结果写成失败或成功 | 是 | 未执行 |
| E5 | E1 的行已经提交 | 只在源库新事务中读取 | 身份和完整内容 | 确认存在且一致 | 只用四个审计字段或摘要比较 | 是，读取前需要已提交行 | 未执行 |

| E7 | 源库已提交，副本故意落后 | 在副本上查同一身份 | 副本缺行时源库是否仍有行 | 副本缺行不能判未提交 | 按副本空结果再插入 | 是 | 未执行 |

| E9 | 已有一条内容不同的已提交责任事实 | 按同一身份读取并逐项比较 | 比较结果 | `BLOCK_CONTENT_CONFLICT`，停止 | 覆盖或再插入 | 是 | 未执行 |
| E10 | 两个 Worker 同时对同一身份做恢复读取 | 并发读，并在没有索引时观察插入 | 行数和内容 | 单次读取不代替唯一约束。内容冲突则停止 | 两个都插入成功仍被当成正确 | 是 | 未执行 |
| E11 | 原进程在发送 `COMMIT` 后退出，新进程没有该响应 | 新进程只做独立读取 | 它是否凭空内存判断失败 | 没有成功响应的新进程不得推断失败 | 新进程直接再插入 | 是 | 未执行 |

## 11. 候选设计与未决事项

候选原则，待架构负责人评审，未批准：

1. 只有数据库完整结果已经确认「未进入 `COMMIT` 且已回滚或未提交」时，才允许新事务按规则 C 重做。
2. 语句执行不确定和 `COMMIT` 结果不确定都停止插入。没有成功响应不是失败。
3. 独立读取使用新连接和新事务，按 D1 查找，按 D2 全量逐项比较。
4. 读到一致的已提交行，就确认这条责任事实已发生，不再插入。
5. 读不完整、身份不能核验或内容冲突，都停止。内容冲突沿用 `BLOCK_CONTENT_CONFLICT`。
6. 一次普通查询没有行，不是确认不存在。本轮也不接受加锁读缺行作为确认不存在。
7. 副本缺行不能证明源库没有提交。
8. 不规定等待秒数。不引入恢复任务表、Inbox、Outbox、DLQ 或 Redis 锁。

仍未决：隔离级别、驱动、连接池、复制拓扑、加锁读的具体语句、如何证明原事务已经以回滚结束、D5 的执行者、D7 的索引、IR-02 和 IR-15。架构是否接受本候选，以及是否接受 D1、D2、D3，都还没发生。

## 12. 本轮结论及禁止事项

本轮只完成 D4 的调查。D4 仍待架构批准。

已有设计事实是 06-04-19 对「`COMMIT` 已发送」和「`COMMIT` 未发送」的分界，以及普通查询缺行不能当作可插入。已确认业务语义仍是定义 B。手册说明了提交的可见性、快照看不到后来的提交，以及副本可以按自己的进度落后。这些都不是 MySQL 8.0.46 上的本项目实验。E1 至 E12 和相关 E2E 均未执行。

D5、D7、IR-02、IR-15 不因本调查关闭。

本轮禁止：修改既有报告、ADR 和代码，执行 SQL 写操作，新建模块，把候选写成架构批准，把手册写成实验通过，把丢包写成提交失败，把缺行写成回滚，以及用任务行锁代替已提交事实。
