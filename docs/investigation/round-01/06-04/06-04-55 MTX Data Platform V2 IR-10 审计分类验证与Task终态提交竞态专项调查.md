## 3. 拒绝审计与任务终态竞态时序

本节只保留过渡路径：06-04-11 的拒绝审计不锁任务行，直接按读取到的任务状态写入。它还没有一条已经提交的责任事实。规则 C 的分类不在这张表里，分类时点也不在这里重开。

起点与 06-04-40 的序列 A 相同：任务上已有已提交的有效阻断 X，终态尚未提交，审计事务读到这个状态，认为拒绝审计 Y 的前提成立。Y 与 X 不同。此时审计尚未 `INSERT`，或已经执行 `INSERT` 但尚未 `COMMIT`。终态事务取得任务行锁并成功 `COMMIT`。审计事务继续 `INSERT` 并 `COMMIT`。

终态事务不需要这条过渡审计持有的锁。审计不改任务行。两边锁的不是同一行。因此终态不必等这条审计。这是 06-04-11 的锁分配加上「不同行互不相等」的设计推论，不是 8.0.46 的执行记录。责任事实事务与终态事务的屏障见第 4 节，不套用本段。

| 时点 | 分类路径上能说的话 | 还不能说的话 |
| --- | --- | --- |
| 验证读取时 | 这次读所看见的已提交版本上，终态尚未提交，有效阻断是另一条 X | 不证明 `INSERT` 时仍然如此，也不证明审计 `COMMIT` 时仍然如此 |
| `INSERT` 时 | 语句能否看见终态，取决于这条语句的读视图，见第 7 节。`INSERT` 写的是审计行，语句本身不重算任务前提 | 插入成功不是前提仍成立 |
| 审计 `COMMIT` 时 | 提交的是审计事务里的修改。不锁任务行时，这次提交不读取、不锁定任务行 | 提交成功不是「终态仍未提交」 |
| 这条过渡写入的业务句子 | 06-04-11 把拒绝审计放在终态提交前追加。责任事实分类的时点已由规则 C 定为锁内重读，并与责任事实同一笔 `COMMIT`，不在本表重开 | 过渡写入的读取、`INSERT`、审计 `COMMIT` 三句没有被写成等价。本轮不为这条过渡写入新选时点 |

### 3.1 读取与 `INSERT` 在同一事务

事务仍不锁任务行。终态可以在第一次读取之后、`INSERT` 之前提交，也可以在 `INSERT` 之后、本事务 `COMMIT` 之前提交。同一事务只让审计行的写入和本事务一起提交或一起回滚。它不把任务行的终态和这次读取绑在同一个提交里。

可重复读下，第一次普通一致性读会固定快照。终态若在这次快照之后才 `COMMIT`，同一事务里稍后的普通读仍用这份快照，看不见新终态。于是「同一事务里再读一次」仍然认为前提成立。手册依据是 [17.7.2.3](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html)。项目未选这个级别，也未实验。

读已提交下，每一次普通一致性读使用自己的快照。紧挨着 `INSERT` 之前的那一次读，有机会看见已经提交的终态。手册依据是 [17.7.2.1](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html)。看见之后就不应再把这次当成分类路径上的拒绝审计。没有看见的那一段仍然存在：最后一次普通读返回之后，终态事务仍可取得任务行锁并 `COMMIT`，然后审计事务再 `COMMIT`。读已提交未选定，未实验。

### 3.2 读取与 `INSERT` 分属不同事务

前一笔事务结束时，它的快照和它没有拿过的任务行锁都不留给后一笔。后一笔 `INSERT` 使用自己的读视图。终态可以严格地落在两笔事务之间。前一笔读到的「尚未终态」不进入后一笔的提交条件。06-04-11 没有为拒绝审计写一条带终态条件的 `INSERT`。

### 3.3 两种提交顺序

| 顺序 | 过渡的直接审计写入 | 审计补写 |
| --- | --- | --- |
| 终态先 `COMMIT`，审计后 `COMMIT` | 写入当时「终态尚未提交」已经不成立。06-04-40：先读到 `RUNNING` 不能证明随后应是拒绝审计。06-04-54 把继续插入记为过期分类。终态先提交也不能单独证明应改写成迟到审计 | 若责任事实已经在终态之前按规则 C 提交，补写依据是那一行，不是当前终态。这次顺序是定义 B 允许的后一笔 `COMMIT`。用「现在已终态」取消或改判补写，会违反「不按当前状态重新分类」 |
| 审计先 `COMMIT`，终态后 `COMMIT` | 审计提交时终态尚未提交，与「终态提交前追加」同向。终态随后按已登记阻断走自己的条件。审计行不改终态 | 同样是两笔独立 `COMMIT`。审计先提交不使责任事实提前发生。没有已提交责任事实时，这行不是补写依据 |

过渡写入在终态先提交之后仍然插入，本轮维持 06-04-54 的类别：过期分类，不是合法拒绝。补写不能套用这一句。两条若共用一次「读到终态就改判」的检查，补写会被当前状态改写。那会碰到定义 B。责任事实分类不参加这张表：它的时点是锁内重读，发生点是它自己的 `COMMIT`。

规则 C 若真的先执行，序列 A 在责任事实事务上会被锁挡住：终态不能在责任事实持锁期间先提交。审计补写发生在责任事实 `COMMIT` 之后，种类已经在那一行上。这个协议未实现。在它未实现时，用审计事务里的不锁重读代替规则 C，既到不了审计 `COMMIT`，也代替不了责任事实的发生点。

## 4. 终态提交屏障与责任事实不存在的协议内证明

本节只讨论遵守规则 C 的责任事实事务，以及与它使用同一条任务行锁的终态事务。迟到审计仍不锁任务行。下列顺序是设计推论，不是 8.0.46 的执行记录。锁在事务提交或回滚时释放，依据是 [17.7.3](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)。新的普通一致性读看见快照建立前已经提交的修改，依据是 [17.7.2.3](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html)。项目没有选定隔离级别，也没有把这两句做成实验。

协议屏障要同时用到四件尚未强制执行的事：全部责任事实写入都先锁这条任务行并持锁重读；终态事务使用同一把锁；终态一旦提交就不再改回非终态；读者使用的是源库上、建立在这次终态 `COMMIT` 之后的读视图。缺任何一件，本节的缺行就退回 06-04-50 已经否定的那些读法。

四个结论保持分开：协议内不存在；数据库全局不存在；业务上可以执行首次迟到分类；D6 已经关闭。本节至多触及第一句的候选，不触及后三句。

### 4.1 场景 A：责任事实事务先取得任务行锁

1. 责任事实事务取得任务行锁。
2. 持锁读取任务状态和有效阻断。
3. 插入责任事实。
4. 该事务成功 `COMMIT`。定义 B：拒绝事件此时发生。锁随之释放。
5. 终态事务随后取得同一把锁。
6. 终态事务成功 `COMMIT`。
7. 迟到审计在这次终态 `COMMIT` 之后建立新读视图，再查询责任事实。

责任事实事务在终态取得锁之前已经结束。终态事务拿不到锁，就不能进入自己的 `COMMIT`。因此这次已成功的责任事实 `COMMIT`，发生在终态 `COMMIT` 之前。这是锁顺序推论，不是实验。

新读视图若第一次普通读发生在终态 `COMMIT` 之后，快照晚于步骤 4。手册语义下，源库上这次读取应当看得见步骤 4 已经提交的责任事实。看不见只在读视图更早、读的不是源库、身份不对或结果不完整时才另说。那些情况不进入本节的否定证据。

若上述新读视图确认任务已是终态，并且责任事实缺行：步骤 4 的那笔提交没有留下这一行。它不能把场景 A 里已经成功的另一身份提交解释掉。缺行只针对这次查询的身份。

### 4.2 场景 B：终态事务先取得任务行锁

1. 终态事务取得任务行锁。
2. 持锁读取状态和有效阻断。
3. 更新终态并成功 `COMMIT`。
4. 后续责任事实事务取得同一把锁。
5. 它重读到终态。
6. 按规则 C 不创建终态前的责任事实。06-04-40、06-04-44 序列 B。
7. 迟到审计在终态 `COMMIT` 之后建立新读视图，查询责任事实。

尚未结束、并且遵守规则 C 的责任事实事务，在终态持锁期间只能等待。终态 `COMMIT` 并释放锁之后，它才能取得锁。取得之后必须重读，不能再用等待前的非终态插入终态前责任事实。所以终态成功 `COMMIT` 排除的是：还有一笔遵守规则 C 的事务，能在此后合法提交一条新的终态前责任事实。

已经在终态取得锁之前提交的责任事实，仍应按场景 A 被新读视图看见。场景 B 的缺行不表示「曾经提交过、又被终态擦掉」。终态事务不删除责任事实。

新读视图中的缺行，在场景 B 的前提下表示：这次查询的身份上，没有一笔早于该读视图的已提交责任事实；此后遵守规则 C 的事务也不会再补一条终态前责任事实。现行确认里没有另一种「终态之后才允许新建」的责任事实。这句只覆盖协议内。

### 4.3 场景 C：终态提交前已经存在的旧读视图

新事务、新读视图、读视图建立在终态 `COMMIT` 之后，是三个条件。`REQUIRES_NEW` 只表示挂起调用方并新开事务。它不表示读视图取在终态之后，更不自动等于最新读。仓库没有传播配置。

| 读法 | 与终态 `COMMIT` 的先后 | 缺行能进入协议内否定证据吗 |
| --- | --- | --- |
| 可重复读事务在终态 `COMMIT` 前已经建立普通一致性读 | 快照更早。终态和终态前刚提交的责任事实都可以看不见 | 不能。06-04-49 |
| 可重复读的新事务在终态 `COMMIT` 之后才第一次做普通读 | 新事务，而且读视图晚于终态 `COMMIT` | 在第 4.4 节的其余前提也成立时，可以作为候选。未实验 |
| 读已提交事务在终态 `COMMIT` 之后执行的那一次普通读 | 该语句自己的快照晚于终态 `COMMIT`。级别未选 | 同上一行，仅对该语句。未实验，不构成选定级别 |
| `REQUIRES_NEW` 已新开事务，但第一次普通读在终态 `COMMIT` 之前 | 有新事务，没有「读视图在终态之后」 | 不能 |
| `REQUIRES_NEW` 已新开事务，第一次普通读在终态 `COMMIT` 之后 | 新事务与新读视图都落在终态之后 | 与第二行相同，仍是候选。未实验 |

### 4.4 场景 D：违反规则 C 的旁路

下列入口都使屏障停在协议内，不能把缺行说成数据库里再也不会有责任事实：

| 旁路 | 屏障覆盖不到的原因 |
| --- | --- |
| 不锁任务行，直接写责任事实 | 终态事务不等它。它可以在终态 `COMMIT` 之后插入 |
| 锁了任务行，但不检查终态 | 拿到锁以后仍可能插入终态前责任事实。规则 C 的重读被跳过 |
| 用旧快照判断之后再写 | 等待期间终态已经提交，普通读仍可能看见非终态。06-04-51 第 4.1 节 |
| 责任事实与终态不用同一条任务行 | 两笔不再互相等待。终态 `COMMIT` 不能排除另一把锁上的写入 |

06-04-51 第 4.1 节的锁定读缺行，还要求后一个事务自己取得任务行锁。本节的候选不把这个要求加到迟到审计上。迟到审计按 06-04-11 不锁任务行。屏障来自终态事务已经拿过这把锁并成功 `COMMIT`，不是来自迟到事务再去锁一次。这不放宽 06-04-51 的证明范围，也不把两种缺行收成同一种。

### 4.5 证据边界

| 读取和协调条件 | 能证明什么 | 不能证明什么 | 证据等级 |
| --- | --- | --- | --- |
| 普通事务缺行 | 这次读没有返回行 | 不证明未提交、未终态、旧快照或身份错误之外的任何一层 | 已有调查。06-04-46、06-04-50。不能支持 D6 |
| 可重复读的旧快照缺行 | 该快照里没有这一行 | 不证明终态 `COMMIT` 前没有提交，也不证明此后不能再提交 | 手册推论加已有调查。未实验 |
| 新事务在终态 `COMMIT` 后建立新读视图并缺行 | 还要同时确认是源库、查询完整、读视图确实晚于该次 `COMMIT`，才表示快照前没有这一行 | 不证明写入都遵守规则 C，也不证明此后没有旁路。单独的新事务缺行仍按 06-04-50，不能支持 D6 | 手册推论。未实验。单独一行还不是协议内否定证据 |
| 读已提交在终态 `COMMIT` 后读取并缺行 | 与上一行相同，且只对这一次语句 | 级别未选。不能写成项目行为 | 手册语义。未实验 |
| 新读视图在终态 `COMMIT` 后，同时看见任务已终态且责任事实缺行 | 同上，并确认终态已经进入这只读视图 | 还没要求全部写入遵守规则 C | 设计推论。未实验 |
| 责任事实与终态都遵守规则 C 的同一任务行锁，终态 `COMMIT` 已确认，且上一行的读视图缺行 | 协议范围内：没有早于该读视图的已提交责任事实；此后也不会再有合法的终态前责任事实 `COMMIT` | 不是数据库全局不存在。不是首次迟到的执行许可。不是 D6 关闭 | 协议内设计推论。规则 C 的物理协议未批准、未实现。未实验 |
| 存在不遵守规则 C 的写入旁路 | 只能说明协议内那一句的前提已经不成立 | 不能再用缺行宣称全局不存在，也不能排除终态之后的新插入 | 已有调查。06-04-51 |
| 终态 `COMMIT` 结果不确定 | 屏障的前提「终态已经成功提交」不成立 | 不能从缺行反推那次终态失败或成功。D4 不改写 | 已确认边界。06-04-40、06-04-46 |
| 只读副本，且不能证明副本已追上这次终态 `COMMIT` | 副本上的缺行只说明这只副本的读视图 | 不证明源库没有责任事实。06-04-49 | 已有调查。未实验 |

在「全部责任事实写入都强制执行规则 C、终态不可重新打开、两笔事务使用同一条任务行锁」这些前提同时成立时，终态成功 `COMMIT` 之后建立的新读视图若确认终态并查不到该身份的责任事实，协议内设计推论是：该协议范围内不存在已提交责任事实，也不存在此后合法提交的终态前责任事实。

这仍不是数据库全局不存在。前提本身未被架构批准，也没有实现。它也不是「可以执行首次迟到分类」：首次迟到还要处理已有阻断或审计记录、D7 的同类型重复，以及 06-04-50 尚未选定的策略。它更不是 D6 已经关闭。它只作为以后 D6 决策可以引用的候选前提。

## 5. 迟到审计与 D6 证据边界

时序：任务终态已经提交。审计事务读取后认为迟到前提成立。另一个事务或恢复流程接着处理相关业务事实。审计事务再 `INSERT` 并 `COMMIT`。

终态提交之后，现行设计允许变化的和不再允许变化的，要分开。

| 对象 | 终态提交之后 | 证据 |
| --- | --- | --- |
| `status` | 五个终态值的条件更新匹配不到另一终态，不能覆盖 | 06-04-11。已有设计。未在 8.0.46 执行 |
| 有效阻断 | 不再登记第二条。同一身份再次到达不是迟到 | Pipeline 第 815、818 行 |
| 已有拒绝审计 | 不改成迟到审计 | 06-04-11 |
| 责任事实的补写 | 可以在终态之后另一次 `COMMIT` 写下拒绝审计 | 定义 B。种类不按当前状态重判 |
| 遵守规则 C 的新责任事实 | 锁内读到终态，就不再插入「终态前」的责任事实 | 规则 C 的推论。事务未实现 |
| 不遵守规则 C 的写入、`COMMIT` 仍不确定的责任事实 | 可能在迟到读取之后才变得可见，或根本不能判定 | D3 未实现。D4 仍开放 |
| 同身份的另一笔迟到审计 | 两个前提都成立的写入仍可能各提交一行 | D7。未实现 |

所以「再读一次任务行，确认仍是终态」只重复终态已经提交。它不证明该 `blockIdentity` 没有责任事实、没有拒绝审计、没有另一条迟到审计。

06-04-50 写明：普通缺行、读已提交下的缺行、`FOR SHARE` 缺行、新事务缺行，都不能支持「责任事实不存在」。那些读法没有同时要求读视图晚于已确认的终态 `COMMIT`，也没有要求全部写入遵守规则 C。缺了这些条件时，本轮维持 06-04-50，不把缺行升级。第 4.5 节的协议内候选是另加的一层，不改写 06-04-50，也不关闭 D6。

06-04-51 第 4.1 节的锁定读缺行仍要求后一个事务自己取得任务行锁。迟到审计不锁任务行，不满足那一组前提。把迟到事务里的任意缺行说成全局不存在，超出那一节，也超出第 4 节。

因此本节时序里，迟到分类在读取当时即使看见「已终态、任务行上没有这条有效阻断」，仍然没有可执行的 D6 证明。第 4.5 节的候选前提今天没有被强制执行。恢复流程若在这之后按已提交责任事实补上拒绝审计，随后的迟到 `INSERT` 会留下拒绝与迟到并存。06-04-50 把这种并存标成尚未解决的跨类型冲突。再读任务行看不见这次补写，除非这次读取同时包含那张尚未存在的审计表，并且读视图晚于补写的 `COMMIT`。即便看见了，窗口仍停在最后一次读取和迟到 `COMMIT` 之间。

Pipeline 第 818 行的「还没有任何记录」与 D6 的证明不是同一句话。本轮不把字面条件写成已经可以执行 `LATE_BLOCK_RECORDED`。

## 6. 同类型审计并发时序

分类前提的竞态，和两笔前提都成立时的双插，不是同一类问题。

| 时序 | 类别 | 再读任务行能做什么 | 物理唯一约束才能做什么 |
| --- | --- | --- | --- |
| 两个 Worker 都读到：有效阻断是 X，终态未提交，Y 与 X 不同，拒绝行尚未看见 | 同类型。两边的分类前提可以同时成立 | 不能把两笔排开。两笔都不锁任务行 | 尚未实现。Pipeline 第 839 行要求同一身份、同一内容只留一条。没有约束时两行都可以 `COMMIT` |
| 两个 Worker 都读到终态已提交，并都认为迟到前提成立 | 同类型，而且 D6 的证明两边都没有 | 再读终态只重复已终态 | 同类型至多一行仍是 D7。它不产生 D6 的缺席证明 |
| 一个 Worker 验证拒绝前提之后，另一个 Worker 提交终态 | 分类路径的前提随后变化。第 3 节 | 不锁任务行时挡不住终态先提交 | 只有一行插入时，唯一约束不会触发。它挡不住单独的一笔过期插入 |
| 两个 Worker 的快照不同：一个看见未终态，一个看见已终态 | 一个走拒绝字面，一个走迟到字面 | 各自再读一次，仍可能一个快照旧、一个快照新 | 分表的唯一索引各管各的表。06-04-51 第 5 节。两行仍可都提交 |

不同快照得到不同种类，是可见性加上分类路径，不是同类型幂等。06-04-40 禁止仅凭两次 `COMMIT` 的先后推断种类。先提交的那一行不自动成为正确种类。

## 7. 读取与写入事务边界比较矩阵

「能证明」只覆盖这次读取自己的读视图。「不能证明」都包含：不证明审计 `COMMIT` 时前提仍成立，也不证明责任事实全局不存在。隔离级别未选。`REQUIRES_NEW` 在仓库里没有配置。

| 读取方式 | 事务边界 | 快照行为 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- | --- |
| 同一可重复读事务中的普通读 | 与后面的 `INSERT` 可以是同一笔 | 第一次普通一致性读固定快照。手册 17.7.2.3 | 快照时点之前已提交的任务状态 | 快照之后终态是否已经 `COMMIT`。同一事务再读一次普通读，推论上仍看不见。未实验 |
| 同一读已提交事务中的普通读 | 与 `INSERT` 可以是同一笔 | 每次普通一致性读换快照。手册 17.7.2.1 | 该语句开始时已经提交的状态 | 该语句返回之后到审计 `COMMIT` 之间终态能否提交。级别未选 |
| 独立短事务读取 | 读完就结束，`INSERT` 在另一笔 | 新事务的第一次一致性读建立自己的快照 | 这只快照之前的已提交状态 | 短事务的结果不会锁住终态，也不会成为后一笔 `INSERT` 的条件 |
| `REQUIRES_NEW` | 只有真正挂起调用方并新开事务时，才离开调用方的旧快照 | 新事务的快照取在它自己第一次一致性读之时。06-04-49 | 调用方旧快照不再约束这一次新读 | 不自动等于最新状态。新事务若在终态 `COMMIT` 之前就已经做了普通读，仍看不见后来的终态。仓库没有传播配置 |
| 锁定读任务行 | `SELECT ... FOR UPDATE` 或 `FOR SHARE` 会锁任务行，并看到最新已提交版本。手册 [17.7.2.4](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html) | 加锁读不是一致性读。普通一致性读忽略行锁 | 若持有到审计 `COMMIT`，终态事务要等这把锁 | 这就是审计锁任务行。违反 06-04-11。只锁一下再放，窗口从放锁重新打开。锁定读缺行仍不是 D6 的全局不存在 |
| 读取与 `INSERT` 分属不同事务 | 两笔各自提交 | 后一笔不继承前一笔的快照 | 前一笔只证明它自己的时点 | 两笔之间终态可以 `COMMIT`。前一笔的「前提成立」不进入后一笔 |

手册保证的是快照和锁的可见性。它不保证 Pipeline 的返回码。普通 `SELECT` 在 `SERIALIZABLE` 以外不加锁，见 [17.7.3](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)。项目没有选定 `SERIALIZABLE`。把隔离级别升到它上面，会让普通读加锁，从而碰到「审计不锁任务行」。本轮不选。

读视图的建立时点早于「准备 `INSERT`」这句话。调用方事务里更早的一次普通读，在可重复读下就已经固定快照。把验证查询写在方法末尾，推论上躲不开这次更早的快照。06-04-49 已写下这句，本轮不把它升级成实验结果。

## 8. 候选方式及其约束

四个都不批准。

| 方式 | 对第 3 节窗口 | 违反或不依赖的约束 |
| --- | --- | --- |
| 1. 写入前重新读取，不锁任务行 | 窗口缩到最后一次读取返回之后、审计 `COMMIT` 之前。终态仍可在这段里成功提交 | 不违反「不锁任务行」。依赖尚未选定的隔离级别才知道这次重读看见哪一版。不能代替同类型唯一约束。不能代替 D6 |
| 2. 读取与 `INSERT` 放在同一事务，仍不锁任务行 | 不消除窗口。可重复读下还可能让同一事务看不见中途提交的终态 | 不违反「不锁任务行」。不改变定义 B 和规则 C，也没有实现它们。同一事务不使审计行成为责任事实 |
| 3. 另用协调载体或改任务行来拖住终态 | 终态的 `WHERE` 不读载体。06-04-54。载体先提交不阻止终态 `COMMIT`。要让终态等待，就得让审计占用终态也要锁或要改的任务行 | 审计改任务行，违反 06-04-11「不改任务状态」。载体若先于任务行被责任事实或终态事务锁定，与 D3 的调查边界不一致。载体不是责任事实权威。未批准 |
| 4. 审计也锁任务行并持有到自己的 `COMMIT` | 反事实。终态会等待，从而在这把锁释放前不能提交 | 违反「审计不锁任务行」。不是既定决策。锁不是唯一索引，两个审计仍可在先后重读之后各写一行。若先锁别的协调资源再锁任务行，与 D3 方向不一致 |

方式 1 和方式 2 都不把过渡写入的读取、`INSERT` 和审计 `COMMIT` 收成一个时点。规则 C 的分类时点仍是锁内重读，不由这两种方式重新打开。方式 4 能让终态等审计，代价是改变现有锁分配；它仍然不提供同类型物理唯一，也不代替第 4 节的协议内候选。

在审计不锁任务行、不改任务行的前提下，本轮没有找到一种协调方式，能让终态事务在最后一次分类读取和审计 `COMMIT` 之间无法提交，同时保持定义 B、规则 C 和 D3 的既有边界。这句话只覆盖上表四种方式，不是宣布以后任何数据库形状都做不到。

## 9. `COMMIT` 不确定性与恢复边界

| 观察 | 归类 | 恢复 |
| --- | --- | --- |
| 审计 `COMMIT` 已发送，没有响应 | 这一笔的 `COMMIT` 不确定。不是终态已经提交的证明，也不是前提仍成立的证明 | 另一次读取看审计行是否在。不从任务终态反推这行的种类 |
| 终态 `COMMIT` 已发送，没有响应，审计还在进行 | 终态自己的不确定。D4 的对象仍是责任事实，不把终态不确定改记成责任事实不确定 | 终态是否提交，重读任务行。不能用审计事务的旧快照宣布终态失败 |
| 过渡审计行已经提交，随后发现终态更早提交 | 过期分类已经落成行。与 `COMMIT` 不确定不是同一类 | 不覆盖，不把拒绝行改成迟到。不新增返回码。如何处置留下未决，本轮不设计删除 |
| 补写行已经提交，当时任务已是终态 | 定义 B 允许的后一笔。不是过期分类 | 不按当前状态改种类 |
| 唯一冲突 | 某一条约束拒绝了语句 | 先确认约束和胜出类型。类型与调用路径不同就停止。06-04-51。冲突不是 `COMMIT` 不确定 |
| 缺行 | 可能是旧快照、未提交、身份不对，或确实没有 | 不解释为全局不存在，不据此插入迟到，也不据此宣布某次 `COMMIT` 失败 |

## 12. 调查结论与下一步决策输入

1. 已确认业务语义。定义 B、规则 C、两笔 `COMMIT` 不变。责任事实的分类时点是锁内重读，并与责任事实同一笔 `COMMIT`。本轮不把这个时点重新列为待决策。分类与终态的竞争靠同一把任务行锁。补写只消费已提交责任事实，不按当前任务状态重判。拒绝审计和迟到审计不锁任务行。同身份再次到达且内容相同，是 `ALREADY_BLOCKED`。
2. 官方手册保证。可重复读下普通一致性读复用第一次快照，新事务的快照看见建立前已经提交的修改。读已提交下每次普通读换快照。锁在提交或回滚时释放。普通一致性读忽略行锁。这些都还不是本仓库的配置，也没有在 8.0.46 上为本时序执行过。
3. 协议内设计推论。在全部责任事实写入都遵守规则 C、终态事务使用同一把锁、终态提交后不再打开、终态 `COMMIT` 已确认时，终态成功 `COMMIT` 构成终态前责任事实的协议屏障：先持锁的责任事实事务必在此前结束；后取得锁的责任事实事务重读到终态后不再插入。终态之后、源库上新建的读视图应当看得见此前已经 `COMMIT` 的责任事实。同一读视图确认终态并且缺行，只是协议范围内的否定证据候选。它依赖主库、读视图建立时点、终态不可逆和这套锁协议。
4. 这条候选证明不了的事。它不是数据库全局不存在。不锁任务行、不检查终态、沿用旧快照或不共用同一任务行的旁路都把它打穿。它不是首次迟到的执行许可，也不是 D6 关闭。D7 的同类型物理唯一性仍然独立开放。
5. 过渡写入仍在。06-04-11 的直接拒绝审计不锁任务行。写入前重读保证不到它的 `COMMIT`，同一事务也不消除这段窗口。`REQUIRES_NEW` 只有在新事务的第一次普通读发生在终态 `COMMIT` 之后时，才看得见这次终态。这条过渡写入不是规则 C。
6. 待架构批准事项。规则 C 的物理协议、D3、第 4.5 节要不要成为以后 D6 决策的候选前提，都未批准。协调载体不批准。审计改锁任务行不是决策。隔离级别未选。
7. 未执行实验。第 11 节全部实验，以及 E2E-075、E2E-088。首次迟到今天仍不能执行。

下一步不是实现，也不是 ADR。D6 若要引用第 4.5 节，先要单独决定是否把「全部写入遵守规则 C」和「终态不可重新打开」写成可强制的协议，并完成第 11 节实验 8 至 10。在那之前，缺行保持 06-04-50 的边界。过渡审计不锁任务行的残余窗口也不用改锁来消除。D6 与 D7 继续开放。
