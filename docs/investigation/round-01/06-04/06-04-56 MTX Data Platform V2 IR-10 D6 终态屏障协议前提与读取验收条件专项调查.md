## 4. A 至 F 并发时序

全部是设计时序，不是 8.0.46 的记录。取得锁只说明对方若持有同一把锁，则对方的事务已经结束。结束可以是提交，也可以是回滚。不能从「锁等到了」推出「前一笔成功提交了责任事实」。

### 4.1 时序 A：责任事实先取得锁

责任事实事务持锁、重读、插入并成功 `COMMIT`，然后释放锁。终态事务在等待期间不能提交。它随后取得锁，读到的是已提交状态。

责任事实可以已经成功提交。终态此时还没确认，要等它自己的 `COMMIT` 成功。恢复时可以依赖的是：另一次源库读取看见这条已提交责任事实。看见一行不是 D6。恰好一行且内容读全，走 D2，并留在 D5 的发现，不写迟到。没看见，要先排除旧快照、副本和查询不完整，不能直接当协议内缺行。

### 4.2 时序 B：终态先取得锁并成功提交

终态事务持锁提交并释放锁。之后责任事实事务才取得锁，必须重读。锁内已是终态时，规则 C 不创建终态前责任事实。

终态已经确认。遵守协议的后一笔不能成功提交新的终态前责任事实。此前若已有成功 `COMMIT`，应被终态之后的新读视图看见，见时序 A。恢复依赖：终态 `COMMIT` 已确认，加上第 5 节里晚于这次提交的源库读视图。缺行在第 3 节前提都成立时，才是协议内候选。前提未核验时，停止分类。

### 4.3 时序 C：责任事实持锁期间回滚

责任事实事务在提交前失败并整笔回滚。没有定义 B 的发生。锁释放后，终态事务可以取得锁并提交。

不存在这一种「已经成功提交」的责任事实。终态可以随后确认。恢复不能把这次回滚记成责任事实曾经发生，也不能把等待结束记成它曾经提交。若回滚本身没有被完整错误确认，不进入本时序，转入时序 D 或 F。

### 4.4 时序 D：责任事实 `COMMIT` 不明，随后有终态请求

`COMMIT` 可能已经发送，客户端不能确认。终态事务若还在等这把锁，说明对方事务还没结束，终态不能提交。锁一旦释放，对方已经结束，但结束仍可能是提交或回滚。客户端的不明不会因为锁释放而自动查清。

终态尚未把「责任事实是否发生」变成已知。06-04-51：缺行不能反推那次 `COMMIT` 的结果。恢复要另一次独立读取，并且那次读取本身还要满足第 5 节。在读到恰好一条完整行、或确认这只读视图有资格谈论缺行之前，分类停止。不插入第二笔来覆盖不明。

### 4.5 时序 E：终态 `COMMIT` 不明，随后有责任事实请求

屏障前提「终态已经成功提交」不成立。责任事实事务若遵守规则 C，仍要先锁任务行并重读，不能用等待前的非终态继续插入。重读结果不完整，或不能确认终态是否提交，就整笔回滚，不插入。

这时也不能开始 D6。D6 要求终态提交结果明确。用缺行宣布终态失败，或宣布责任事实不存在，都超出证据。

### 4.6 时序 F：死锁、断连、进程退出

| 故障 | 可以依赖什么 | 必须停止的地方 |
| --- | --- | --- |
| 死锁错误完整返回，并且整笔回滚已确认 | 06-04-19、06-04-46：可以新开事务，重新锁、重新读 | 不把这次回滚写成责任事实已发生。新事务仍要规则 C |
| 错误不完整，不能确认整笔回滚 | 没有 | 不重试插入，不开始迟到分类 |
| 断连发生在 `COMMIT` 可能已发送之后 | 没有客户端侧的成功或失败 | 留在 D4。不从终态请求的等待结果推断 |
| 进程在持锁期间退出 | 服务器最终会结束该事务并释放锁。客户端不知道是提交还是回滚 | 与时序 D 相同。锁释放只说明事务结束 |

| 任务状态与责任事实分两条 SQL | 读已提交下是两次快照。可重复读下若同属已有快照，则两次都旧 | 否 | 各条语句自己的视图 | 两次结果属于同一逻辑时点。中间可以插入一次 `COMMIT` |
| 同一条 SQL 同时读任务行和责任事实 | 一条普通一致性读语句使用它实际采用的那一个读视图 | 否。可重复读下，当前事务若已经有旧视图，后执行的这一条仍可能沿用它。读已提交下，该语句自己的快照仍必须晚于终态 `COMMIT` | 可以避免两条独立 SQL 各自观察不同的语句快照 | 不能把 SQL 执行时间晚于终态 `COMMIT` 当成读视图也晚于该 `COMMIT`。不是已批准的最终读法。语句未设计，未实验。锁定读若锁住任务行，迟到路径不能采用 |

`REQUIRED` 加入的是调用方已有事务。它是否看见旧读视图，取决于隔离级别，以及该事务此前有没有建立过一致性读视图。可重复读下，已经建立的事务级读视图可能被后面的普通一致性读继续使用。读已提交下，每条普通一致性读语句建立自己的读视图。因此 `REQUIRED` 本身既不保证旧快照，也不保证新快照，不能充当 D6 的独立读取时点。仓库没有传播配置，这句不是已实现行为。

同一条普通一致性读语句可以让任务行和责任事实避开两条独立 SQL 各看各的语句快照。可重复读下，若当前事务在这条 SQL 之前已经建立旧的一致性读视图，后执行的单条 SQL 仍可能沿用那只旧视图。所以要证明的是这条 SQL 实际使用的读视图建立在目标终态成功 `COMMIT` 之后，不是这条 SQL 的执行时间晚于该 `COMMIT`。读已提交下，这条语句自己的语句级快照同样必须晚于该 `COMMIT`。本轮不把单条 SQL 选成最终读取方案，也不选定隔离级别或传播方式。

读取位置：仓库没有数据源，不能证明语句打在主库。只读副本上的缺行只说明那只副本。06-04-49。不能证明副本已经追上这次终态 `COMMIT` 时，缺行无效。

锁定读缺行：06-04-51 第 4.1 节只在责任事实事务持锁到结束、后一个事务取得同一把锁、相关写入都走这把锁时，才是协议内否定证据，并且那个读者是下一笔责任事实事务，不是 D6。06-04-55 的候选改由终态事务已经拿过锁并成功 `COMMIT` 来形成屏障，迟到事务自己不锁任务行。两种缺行都不是全局不存在。本轮不选其中一种当作最终读法。

恰好一条：必须做 D2。内容读全且与本次到达不是「没有事实」，这条身份已经有责任事实，进入 D5 的边界，不进入首次迟到。内容读不全则停止。多条停止，不挑选。读到的行是拒绝审计或迟到审计而不是责任事实：种类不同，停止，不把一种当成另一种不存在。06-04-50、06-04-51。查询失败停止。

## 6. D6 首次迟到分类验收条件

下面每一条都是讨论首次迟到之前的必要条件。全部并列仍然不是充分条件，因为 06-04-50 的策略还没选定，D7 还没实现，架构也还没批准把规则 C 强制到全部入口。今天没有一条可以勾上并据此执行 `LATE_BLOCK_RECORDED`。

| 编号 | 条件 | 缺了会怎样 | 现在的状态 |
| --- | --- | --- | --- |
| 1 | 任务已确认处于五个终态值之一 | 迟到前提不成立 | 设计有终态值。本次读取是否看见，依赖第 5 节 |
| 2 | 该终态提交后不可重新打开 | 屏障可以在读完之后失效 | 已有架构设计。待数据库实验 |
| 3 | 这次终态 `COMMIT` 的结果明确成功 | 时序 E，停止 | 不明时按 D4，不改写成缺行 |
| 4 | 读取打在权威主库，而不是未证明已追上的副本 | 副本缺行无效 | 待代码核验。没有数据源配置 |
| 5 | 查询实际使用的一致性读视图建立在目标终态成功 `COMMIT` 之后。验收的是这只读视图，不是查询语句的开始时间 | 可重复读事务提前建立的旧快照、`REQUIRED` 加入旧事务、`REQUIRES_NEW` 在终态 `COMMIT` 前已经建立的旧快照、尚未追上的只读副本，以及多条 SQL 读取期间的状态变化，都可以使证据失效 | 待数据库实验。隔离级别、传播方式和 SQL 都未选 |
| 6 | 任务终态与该身份的责任事实来自能够对照的同一次证据，并且该证据使用的读视图满足条件 5 | 分两条 SQL 不能证明同一逻辑状态。单条 SQL 若沿用更早的可重复读视图，同样不满足 | 单条 SQL 只是未批准的候选。未设计，未实验 |
| 7 | 全部责任事实写入入口遵守规则 C，并持有同一条任务行锁直到事务结束 | 否则只是当前视图没看见 | 待架构批准、待代码核验 |
| 8 | 不存在绕过该协议的入口 | 协议内句子不能外推 | 待代码核验。今天没有清单 |

| 10 | 零行只在 1 至 9 都成立时，才当作协议范围内没有已提交责任事实 | 零行本身只是当前视图没读到 | 本轮调查推导。不是全局不存在 |

| 12 | 多条、跨类型、读取失败、任一 `COMMIT` 不明：停止 | 不挑选，不把拒绝行或迟到行当成责任事实缺行 | 已有调查。06-04-50、06-04-51 |
| 13 | 该身份不是已提交的有效阻断；也没有已提交的拒绝审计或迟到审计 | 有效阻断走 `ALREADY_BLOCKED`。已有审计按原种类，不改成首次迟到 | 已有架构设计。Pipeline 第 11.1 节 |
| 14 | 同类型迟到的第二笔有物理唯一约束，跨类型不靠这次缺行代替 | 分类通过仍可能双插，或与拒绝审计并存 | D7、IR-02 仍开放 |

条件 10 成立，也只走到「协议范围内不存在」。它不自动满足 13 和 14，更不关闭 D6。06-04-50 仍要求：在权威不存在被另一次已接受的读取定义打开之前，不能执行首次迟到。本轮给出的是那次定义若要被接受，至少要同时满足的门槛，不是接受本身。

## 8. 与 D5、D7、IR-02 的边界

D5 从一条已经成功提交的责任事实出发，补写拒绝审计。发现条件是读到事实，不是读到缺行。06-04-47：审计缺行今天也不能当成确认不存在，所以补写插入仍不能执行。D6 从「没有已提交责任事实」出发。把 D5 的「四字段相等就算补写完成」挪到 D6，会把已有拒绝审计当成首次迟到的结束条件，方向反了。字段相等在 D5 里还依赖尚未批准的 D3，本轮不借用。

D7 管的是同一身份上责任事实、拒绝审计、迟到审计和有效阻断会不会各留下不该同时存在的行，以及同类型会不会双插。协议内缺行不产生唯一索引。任务行锁也不产生。IR-02 仍是物理唯一约束的归属，06-04-19 与 06-04-51 都没有把它关闭。本轮不用 D6 的读取证据代替 D7。

方向也要分开。06-04-48：责任事实已提交时，迟到路径不能把这次到达当成首次。那是状态 B，归 D5 的发现，不是 D6。06-04-47 讨论的「迟到先写入、终态前责任事实后写入」只有在 D3 被依赖时才从协议上排除。D3 未批准、未实验。本轮的屏障推论不把这一交叉标成已经不可能。

## 9. 尚未解决的问题

P0：首次迟到今天仍然不能执行。协议内缺行的前提没有一条被实现或实验。当前视图缺行、协议内不存在、全局不存在和执行许可仍然是四层。D7 与 IR-02 不因本轮关闭。

P1：第 5 节的读取方式没有选定。同一条 SQL 是否作为候选语句，未设计。06-04-50 的策略 A 至 D 仍未选，停止时调用方看见哪个现有返回码也未选，本轮不新增返回码。全部入口是否遵守规则 C，没有清单。

P2：窗口时长和副本延迟的运维观察。不选监控产品。

## 10. 调查结论及后续建议

已有业务确认不变：定义 B、规则 C、补写不重分类、`COMMIT` 不明两边都不认定。已有架构设计不变：终态条件更新、审计不锁任务行、Pipeline 对已有记录种类的返回码。

本轮调查推导：终态成功 `COMMIT` 可以成为协议屏障，但只在第 3 节那些必要前提同时成立时。等待锁结束只说明前一笔事务结束，不说明它提交了责任事实。晚于该次终态 `COMMIT` 的源库读视图，应当看得见此前已经提交的责任事实；缺行在其余前提也成立时，只是协议范围内的否定证据。这一层不是数据库全局不存在。它也不是 D6 的充分条件。第 6 节的十四条都是门槛，没有任何一条或全部加在一起等于批准首次迟到。

待架构批准：把规则 C 强制到全部写入入口，以及要不要把 06-04-55 的协议内候选接进以后的 D6 决策。待代码核验：入口清单、主库路由、事务传播。待数据库实验：第 5 节每种读法，以及终态不可重新打开。待端到端验证：E2E-075、E2E-088，以及 06-04-50 已列出的缺行用例。这些都未执行。

下一步不是实现，也不是 ADR。若还要调查，只核验第 3 节里哪些前提能在不增加模块、不改审计锁的设计文本中被点名；读法仍不选定。D6 与 D7 保持开放。
