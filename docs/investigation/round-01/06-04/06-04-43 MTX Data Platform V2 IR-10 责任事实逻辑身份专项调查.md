## 3. 现有身份模型与约束

这些是仓库里已经写明的事实。责任事实本身还不是现行实体。

### 3.1 Task 身份

`taskId` 表示一条逻辑任务。一个任务最多一条有效阻断，名额按 `taskId` 计算，不是另一套阻断身份。非重放任务要回到来源契约已经声明的稳定接入事件。IR-03 核对后，现有来源资料没有给出可进入任务唯一约束的稳定事件身份。`taskId` 和 `replayRequestId` 的生成算法都未设计。显式重放是另一个任务，使用新的 `taskId`，不改写原任务。

因此 `taskId` 今天还不能独立标识一条拒绝责任事实。同一任务上可以有多条不同的 `blockIdentity`：一条成为有效阻断，其余在终态前被拒绝。只拿 `taskId` 会把这些拒绝并成一行。它可以作为组合身份的一部分，而且现行 `blockIdentity` 已经包含它。本轮不发明 Task ID 算法。

### 3.2 blockIdentity

现行定义来自 Pipeline 第 11.1 节和 06-04-19 第 3 节，两处一致：

- `taskId`
- 稳定阻断码
- 阻断主体。主体是具体字段路径，或任务级阻断的固定标记

它表示「同一逻辑阻断事件」。不含 `taskAttemptId`。06-04-19 写明物理列未冻结，并且不把 `taskAttemptId` 放进键。Pipeline 写明不含 Worker 标识：Worker 标识、发现时间和异常文本只是审计元数据，不参与身份比较，也不参与内容比较。

同一逻辑阻断跨 Worker、跨 `taskAttemptId` 重试时，内容必须来自已经持久化的执行上下文和稳定条件，不能来自本次尝试的本地值。技术重试沿用原来的 `blockIdentity` 和四个内容字段。E2E-090 预期新 `taskAttemptId` 重试同一身份和同一内容时不新增记录。该行未执行。

现行设计把同一个 `blockIdentity` 当成同一逻辑阻断，不把它当成「每一次尝试各算一条历史拒绝」。同身份、同内容是重复。同身份、不同内容是 `BLOCK_CONTENT_CONFLICT`，不覆盖，也不改种类。不同的 `blockIdentity` 是不同的逻辑阻断。其中第一条在终态前可以成为有效阻断，另一条才是拒绝。不能因为这是现有阻断身份，就自动把它批准成责任事实身份。下面第 5 节仍然要比较。

稳定阻断码本身的生成算法，这两份文档没有给出。本轮不补算法。

### 3.3 拒绝审计身份

拒绝审计沿用被拒绝的 `blockIdentity`。四个内容字段是 `snapshotId`、`contractVersionId`、`contractBodySha256`、`conditionCode`。没有子条件时 `conditionCode` 为 `NONE`。缺值使用显式 `EMPTY`，不是空字符串。`taskId`、阻断码和阻断主体只属于身份，不重复进入内容。

因此：身份是 `blockIdentity` 的三个部分。四个字段是不可变内容，不是身份。内容相同才是同一次幂等。内容不同是冲突，不是另一条身份。

`BLOCK_IDENTITY_REJECTED` 不表示审计行已经写入。`REJECT_AUDIT_NOT_RECORDED` 表示没有审计行。`REJECT_AUDIT_ALREADY_RECORDED` 只表示相同拒绝审计已经存在，不表示责任事实已经持久化。并发下同一被拒绝身份和同一内容只持久化一条拒绝审计。这是现行审计写入的逻辑规则，物理唯一约束仍属 IR-02，未建。

审计查找键与责任事实查找键是否相同，是本专项的候选，不是已经批准的等式，也不是两行可以互相代替。Pipeline 第 11.1 节写的是既有审计写入。06-04-40 确认的是责任事实的权威发生时点。没有迁移或兼容规则时，不能从审计行推出责任事实已经 `COMMIT`。Pipeline 没有这套映射，本轮也不新增实体来承接孤立审计。

### 3.4 TaskAttempt 身份

`taskAttemptId` 表示一次执行尝试。技术重试可以更换它，但必须沿用 `taskId`、已固定的执行上下文。生成算法未定。06-04-11 的重试领取创建新的 `OPEN` / `CURRENT` 尝试，不改已登记阻断，也不换已固定快照和契约。

Attempt 变化不表示逻辑阻断变了。Pipeline 把 `taskAttemptId` 写成发现这次阻断的记录属性，技术重试更换它，不因此变成另一条阻断。若把 Attempt 放进责任事实身份，同一次逻辑拒绝会在每次重试或接管后变成新身份。补写若发生在原尝试已经 `RELEASED` 或 `SUPERSEDED` 之后，就会找不到原身份，或留下多条「同阻断、不同尝试」的责任事实。这和「跨尝试仍是同一 `blockIdentity`」相反。

不纳入 Attempt 时，现行语义是合并为同一逻辑阻断，而不是把不同阶段误并。前提是内容来自已持久化的执行上下文。若重试读到的四个字段与已提交事实不同，结果是内容冲突，不是悄悄合并。这个前提是 Pipeline 已写的规则，E2E-090 未执行，所以还不是实验结论。

本轮不改 `blockIdentity`，也不改 Task、TaskAttempt 的身份规则。

### 3.5 Worker 实例身份

Worker 标识不参与身份比较。实例会重启、迁移，并发时也会有多个进程看见同一次拒绝。把实例放进身份后，另一个 Worker 的补写会得到另一套身份，已提交事实就无法按稳定键找到。本地时钟、`receivedAt` 和日志时间同样不是权威业务身份。它们可以留在日志里。

## 4. 责任事实身份语义分析

定义 B 下，权威事实是责任事实那次成功 `COMMIT`。`COMMIT` 之前的故障不认定权威拒绝事件已经发生。身份要在这次提交之后仍能被其他进程找到，并且和拒绝审计使用同一套查找键。查找键相同，不表示审计行就是责任事实，也不表示已有审计可以代替那次 `COMMIT`。规则 C 的任务行锁决定这次分类是否成立，锁本身不是身份。两个 Worker 排队之后，仍然要用同一个逻辑键判断是重复、冲突，还是另一条事实。这个判断先要读到责任事实行是否已经提交。只读到拒绝审计不够。

从现行模型能分出的业务事实只有：

- 哪一条任务。
- 哪一个逻辑阻断。
- 这条阻断在锁内被分类为拒绝，而不是有效阻断。
- 四个内容字段是否与已提交的那次相同。

「被分类为拒绝」是这行的种类和内容，不是第二套身份。有效阻断、拒绝审计和迟到审计已经共用 `blockIdentity`，种类靠既有记录和终态规则区分。责任事实若再造一个不包含这三部分的键，补写和审计就对不上。若再造一个包含 Attempt 或 Worker 的键，就把现行「同一逻辑阻断」拆开。

同一 Task 在不同 Attempt 中再次出现相同阻断码和主体时，现行文本的业务语义是同一 `blockIdentity`，不是一次新的历史拒绝。没有文档把「第二次尝试」定义成另一条必须分开保存的拒绝事实。内容若因未持久化的本地值而不同，Pipeline 禁止用那次本地值参与比较。

## 5. 候选方案比较

三案都未批准。比较的是身份，不是已经可以建表的设计。

| 项 | 方案 A：被拒绝的 `blockIdentity` | 方案 B：独立 `rejectionIdentity` | 方案 C |
| --- | --- | --- | --- |
| 身份 | `taskId`、稳定阻断码、阻断主体 | 另一套逻辑键。`blockIdentity` 只作关联 | 本轮没有有证据的第三套 |
| 与拒绝审计 | 同一查找键。补写按这个键读审计 | 必须另有映射。Pipeline 没有这套映射 | 若再加入 Attempt 或 Worker，就改了现行阻断身份 |
| 跨尝试 | 与 Pipeline「技术重试不变成另一条阻断」一致 | 新键若随尝试变化，同一次拒绝会裂成多行 | 没有独立于 A 的碰撞需要这种组合 |
| 跨 Worker 恢复 | 不依赖实例 | 键若含实例或时间，另一个进程无法复原 | 同上 |
| 同内容重复 | 同一事实，幂等复用 | 只有生成规则稳定时才复用。算法本轮不能定 | 无额外收益 |
| 同身份不同内容 | 已有 `BLOCK_CONTENT_CONFLICT`，不覆盖 | 仍要决定内容冲突算不算新键。不新造错误码的话，结果和 A 相同 | 无 |
| 不同阻断 | 不同 `blockIdentity` 就是不同事实 | 还要证明新键不会把不同阻断合成一个，或把同一阻断拆开 | 无 |
| 代价 | 依赖 `taskId` 和稳定阻断码本身稳定。两者的算法仍未定 | 两套身份、映射和一致性。没有第二套业务事实支撑 | 没有证据就不单列方案 |

方案 A 的优点是复用已经写明的逻辑阻断身份，拒绝审计不用第二把钥匙，跨 Attempt、跨 Worker 的稳定性也有现成句子。同一把钥匙只表示查找键可以相同。已有拒绝审计仍然不是已提交的责任事实。`REJECT_AUDIT_ALREADY_RECORDED` 也不是责任事实的 Create-or-Get 成功。风险是：若同一 `taskId` 上，同一阻断码和主体在业务上其实是两次不同的拒绝，A 会把它们收成一行，内容不同则冲突而不是新事实。现行文本没有这种「两次不同拒绝共用一个 `blockIdentity`」的例子。重试被定义成同一次逻辑阻断。显式重放使用新 `taskId`，因此是新的 `blockIdentity`。

方案 A 还依赖两个尚未决定的算法：`taskId`（IR-03）和稳定阻断码。这不要求本轮发明算法。它要求以后的算法保持「同一逻辑任务、同一逻辑阻断」不变。算法未定，不构成另造 `rejectionIdentity` 的理由。

方案 B 只有在存在 `blockIdentity` 表达不了的第二种业务事实时才需要。本轮没有找到这种事实。独立键的生成若依赖 Worker、时间或 Attempt，就不能跨进程恢复。若生成规则其实就是 `blockIdentity` 的三部分，它就不是独立身份，只是方案 A 的别名，并多一层映射。同一事实两套身份的一致性成本没有对应收益。本轮不指定 `rejectionIdentity` 的算法，也不采用方案 B。

方案 C 不单列。把 `taskId` 再加一次是重复，因为 `blockIdentity` 已经含有它。把 Attempt 或 Worker 加进去，会改变现行 `blockIdentity` 和审计身份，并与第 3.4、3.5 节冲突。没有证据表明还存在第三种碰撞。

候选原则，待架构评审，不是批准：责任事实的逻辑身份等于被拒绝的 `blockIdentity`。不新增 `rejectionIdentity`。

| 7. Worker 崩溃后，另一 Worker 补写 | 查找键相同。不依赖崩溃的实例 | 只有该责任事实已经成功 `COMMIT`，才仍是这一条已发生事实。`COMMIT` 不明时既不是已发生，也不是确定未发生 | 已确认提交后才按该身份补写。不明则停止 | 补写机制本身是 D5，未实现 |
| 8. 两个 Worker 并发处理同一责任事实 | 查找键相同 | 只有已经成功 `COMMIT` 的那一条才是已发生事实。两边都还没提交时，不是已经发生的同一次，也还没有冲突对象 | 已提交且内容相同则幂等；已提交且内容不同才是 `BLOCK_CONTENT_CONFLICT`。`COMMIT` 不明则停止，不二选一 | 数据库唯一约束未建。并发只会留一行尚未证明，属 IR-02 与 D7 |
| 9. 已有拒绝审计，内容与责任事实不一致 | 查找键相同 | 比较对象必须是已提交的责任事实。责任事实不存在时不是内容冲突，而是第 6.1 节的孤立审计 | 已提交且内容不一致才是 `BLOCK_CONTENT_CONFLICT`。停止。不插入，不覆盖，不改迟到，不标成功，不反向补造 | 06-04-42 已写内容冲突的候选。两行如何同时出现内容差，尚无实现 |
| 10. 责任事实已 `COMMIT`，审计尚未生成 | 身份已经确定 | 是这一条已发生的事实 | 按同一身份补写。不得改用当前任务状态重分类 | 发现未完成补写的执行者未指定。本行与第 6.1 节「审计在、责任事实不在」相反，不能对调 |

### 6.1 场景 1 的五种持久化状态

再次到达时，查找键可以相同。责任事实是否已经发生，只看它自己的事务是否成功 `COMMIT`。不能从拒绝审计推导。

| 状态 | 语义 |
| --- | --- |
| 责任事实不存在，拒绝审计也不存在 | 尚无已提交责任事实。按定义 B 和规则 C 判断本次是否可以形成责任事实 |
| 责任事实已提交，拒绝审计不存在 | 已发生的拒绝事实。进入 D5 审计补写 |
| 责任事实已提交，拒绝审计存在且内容一致 | 补写已经完成 |
| 责任事实已提交，拒绝审计存在但内容不一致 | `BLOCK_CONTENT_CONFLICT`，停止补写 |
| 责任事实不存在，但拒绝审计已经存在 | 既有审计与新的权威责任事实之间的兼容或完整性边界。不能推导责任事实已发生 |

最后一种状态留下这些限制。本轮不决定怎么迁移或补建：

- 不得把拒绝审计当作责任事实。
- 不得把 `REJECT_AUDIT_ALREADY_RECORDED` 当作责任事实 Create-or-Get 成功。
- 不得把该状态直接当成责任事实重复。
- 不得仅凭身份和内容相同，反向补造一条已经发生的责任事实。
- 不得擅自删除或覆盖已有拒绝审计。
- 不得擅自把它归为迟到审计。

这是尚未决策的兼容性边界，留待后续专项。Pipeline 描述的是既有审计写入。06-04-40 确认的是未来责任事实的权威语义。没有迁移或兼容规则时，两者不能直接等同。D1 只确定查找键候选，不决定孤立审计的处理，也不为此新增实体或模块。

## 7. 对 D2、D3、D4、D5、D7 的约束

这些约束来自身份候选。它们不关闭后续决策。

- D2：不可变快照挂在这个身份上。四个内容字段、当时的有效阻断和锁内 `status` 是内容，不是身份的一部分。身份相同而内容不同，不能靠加字段变成新身份。内容冲突只与已经成功 `COMMIT` 的责任事实比较。责任事实尚不存在时，没有冲突对象。
- D3：锁内分类决定这次拒绝是否成立，以及终态与责任事务谁先写入。任务行锁不能代替身份。锁只保证读取和插入的顺序，不回答两行是不是同一次拒绝。
- D4：`COMMIT` 不确定之后的独立读取，要能按这个 `blockIdentity` 查找候选责任事实。读不完整则保持不确定。不能改用 Attempt 或 Worker 去找。
- D5：审计补写用同一查找键定位已经提交的责任事实和拒绝审计。责任事实已提交且没有审计时才补写；内容一致算完成；内容不一致按场景 9 停止。责任事实不存在而审计已存在时，不进入补写完成，也不反向补造责任事实。该边界不是 D1 的身份结论。
- D7：并发幂等需要数据库唯一约束，约束的逻辑键是这个身份。本轮不指定索引字段、名称或 DDL。IR-02 仍开放。

## 8. 候选原则与未决问题

候选原则，待架构负责人评审，未批准：

1. 一条拒绝责任事实的逻辑身份等于被拒绝的 `blockIdentity`，即 `taskId`、稳定阻断码、阻断主体。
2. 不新增 `rejectionIdentity`。
3. `taskId` 只作为这个组合的一部分，不能单独标识一条拒绝事实。
4. 四个内容字段不是身份。同身份、同内容只有在责任事实已经成功 `COMMIT` 时，才是同一事实的重复。同身份、不同内容只有在已有成功 `COMMIT` 的责任事实时，才是 `BLOCK_CONTENT_CONFLICT`。尚不存在时没有冲突对象。身份相同不表示责任事实行和审计行可以互相代替。
5. 不同 `blockIdentity` 是不同事实。
6. `taskAttemptId`、Worker 实例、本地时间、`receivedAt` 和日志时间都不进入身份。

仍缺证据或仍待别处决定：

- `taskId` 算法和来源事件身份：IR-03。未关闭前，不能证明不同任务不会共用一个 `taskId`。
- 稳定阻断码的生成算法：文档只要求它稳定，没有给出算法。
- 物理唯一索引：IR-02。逻辑身份不是索引定义。
- 场景 2、3、8 的并发和跨尝试行为：相关 E2E 未执行。
- 方案 A 是否被架构接受：本报告不代替批准。若评审认定同一次任务上确实存在「同一阻断码和主体、但是两次拒绝」，要先改业务语义，再谈方案 B。本轮没有这种已写明的业务事实。
- 责任事实不存在、拒绝审计已经存在：后续设计中的兼容与完整性问题。不在本轮补造责任事实、删除审计、改成迟到审计，或为此新增实体。见第 6.1 节。

## 10. 本轮结论与禁止事项

仓库现有事实是：`blockIdentity` 由 `taskId`、稳定阻断码和阻断主体组成；四个字段是内容；拒绝审计使用这同一查找键；Attempt 和 Worker 不是身份。`REJECT_AUDIT_ALREADY_RECORDED` 只说明审计行已在。已确认的业务语义仍是定义 B 与规则 C：权威发生时点是责任事实成功 `COMMIT`。候选原则仍是方案 A，不用方案 B，不单列方案 C。`blockIdentity` 仍只是候选责任事实身份。身份相同不表示两行可以互相代替。责任事实不存在而审计已存在，留待后续兼容设计，本轮不补造、不删除、不改类。架构负责人尚未批准。MySQL 实验和 E2E 都未执行。

本轮禁止：修改既有设计和台账，新建实体或表，编写 DDL 或 SQL，确定物理索引和 `rejectionIdentity` 算法，改变 `blockIdentity` 或 Task、TaskAttempt 的身份规则，引入 Inbox、Outbox、DLQ、Redis 锁或新模块，宣布 D1 已获架构批准。
