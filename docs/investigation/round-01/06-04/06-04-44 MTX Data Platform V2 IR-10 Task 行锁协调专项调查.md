## 3. 定义 B 与规则 C 的锁协调要求

已经确认的业务语义要求：

- 责任事实事务和每一个把 `status` 写成终态的事务，用同一条任务行做串行点。
- 分类使用持锁之后读到的状态和有效阻断，不用锁之前的快照。
- 权威发生时点只是责任事实那次数据库事务实际成功 `COMMIT`。
- 补写不按恢复当时的任务状态重分类。那是 D5，本轮不设计补写。

这些时点必须分开，不能合成一个「已经锁住所以已经发生」：

| 时点 | 含义 |
| --- | --- |
| 取得任务行锁 | 其他要改同一行的事务在后面等。事实尚未发生 |
| 锁内读取 | 看到的是这把锁允许看见的已提交状态。读失败则不能分类 |
| 业务分类 | 按锁内状态决定这次能不能插入拒绝责任事实 |
| `INSERT` | 语句成功仍不是事务已提交 |
| 发送 `COMMIT` | 请求发出不等于库已经提交 |
| 数据库实际 `COMMIT` | 定义 B 的权威发生时点。客户端还可能没看见 |
| 客户端收到成功响应 | 调用方知道了。不知道不等于事务失败 |

事务开始时间、请求到达时间、Worker 本地时钟和日志顺序都不是这把锁上的先后。普通一致性读也不是围栏。

取得锁不等于责任事实已经发生。`INSERT` 成功也不等于已经发生。

## 4. 责任事实事务边界

候选流程，未批准、未实现：

1. 开启显式数据库事务。
2. 对目标任务行取得排他锁，并保持到本次 `COMMIT` 或回滚。
3. 持锁读取任务 `status`。
4. 持锁读取或核实当前有效阻断。权威来源是这把锁下的已提交行，不是调用方进事务前记住的 `RUNNING` 或阻断 A。
5. 按定义 B 与规则 C 判断能否形成拒绝责任事实。锁内仍非终态，且有效阻断仍是这次分类所依据的那一条，才允许继续。已经是五个终态值之一，就不插入「终态前」的责任事实。
6. 用 D1 的身份候选和当次不可变内容插入。内容清单是 D2，本轮不补列。
7. 提交事务。锁在提交或回滚时释放。
8. 只有数据库实际成功 `COMMIT`，责任事实才正式发生。

本事务不修改任务终态、有效阻断和尝试执行权。因此它不套用「先改任务、再改尝试」那一组业务条件，但锁的第一把仍是任务行，避免和终态事务反向。

它不能放进 06-04-19 的 A 类：A 类不锁一条 `RUNNING` 任务。也不能放进 B 类：B 类新插入要求有效阻断为空，而拒绝发生时有效阻断已经存在。所以它是第三类协调。这一分类仍待架构批准。

锁内读取失败、读不完整或不能分类：整笔回滚，不插入。不把残缺读数当成 `RUNNING`，也不当成已经终态。

## 5. 任务终态事务边界

五个终态值是 `SUCCESS`、`PARTIAL_SUCCESS`、`ALL_FIELDS_FAILED`、`FAILED`、`CANCELLED`。06-04-11 的设计文本为它们写了任务行锁：

| 终态 | 设计文本中的锁 | 持锁后的条件 |
| --- | --- | --- |
| 成功类三个值 | 先锁任务行，再改当时的尝试 | 有效阻断为空 |
| `FAILED` | 先锁任务行，再改当时的尝试 | 有效阻断等于已登记的那一条 |
| `CANCELLED` | 锁任务行。`PENDING`、`RETRY_WAITING` 只改任务；`RUNNING` 再改当时的 `CURRENT` | 终态为空且有效阻断为空 |

进入 `RETRY_WAITING` 也先锁任务行，但它不是终态。它要求有效阻断为空。责任事务若在等待后重读到它，必须用锁内结果。不能用等待前的 `RUNNING` 继续插入「当时还有阻断 A」的责任事实，除非锁内仍然读到那条有效阻断。现行条件写明进入等待时阻断为空，所以锁内若读到空阻断，这次拒绝分类不成立。

终态更新和锁释放在同一次提交或回滚里。设计文本没有「先提交终态、稍后再放锁」的第二步。另一个事务要等这把锁，才能看见对方已经提交的终态，或者看见对方回滚后的原状态。这是设计要求加上手册对加锁读的一般描述。仓库没有代码执行这些语句，因此还不是「所有运行路径已经串行」的代码事实。

拒绝审计和迟到审计在 06-04-11 中不锁任务行，也不写 `status`。它们不是终态入口。现行文本没有第二条把 `status` 写成终态却不锁任务行的路径。没有实现，就不能用代码搜索证明将来不会出现旁路。D3 的候选原则是：任何把 `status` 写成终态的新路径都必须先拿这同一把任务行锁。这是待批准的要求，不是已经核对过的代码清单。

本轮不把终态事务和责任事实事务收成一次提交。06-04-40 要求的是同一把锁上的排队，不是同一个事务。Pipeline 仍把审计完成和任务终态分成两个状态。

## 6. 并发时序推演

下列顺序由谁先提交这把锁决定。不是由时钟决定。全部未在 MySQL 8.0.46 上执行。

### 6.1 序列 A：责任事实事务先取得锁

责任事务先锁定任务行，持锁读到仍非终态且有效阻断仍是分类依据，插入责任事实并成功 `COMMIT`。终态事务在后面等。锁释放后，终态事务再锁、再读。

此时不变量候选：

- 权威拒绝已经发生，因为那次 `COMMIT` 成功。
- 终态事务看到的是已提交状态。`FAILED` 仍用现行条件：阻断等于已登记的那一条。成功类仍要求阻断为空。本调查不改这些条件。
- 已提交的责任事实不因任务随后终态而改类。补写按 D5，不在终态事务里重做分类。

若责任事务在锁内发现条件已经不成立，它回滚，不插入。终态事务随后看到的是没有这条新责任事实。那不是「先锁住就算发生」。

### 6.2 序列 B：终态事务先取得锁

终态事务先锁定，持锁校验并成功 `COMMIT`。责任事务随后取得锁，必须重读已提交的 `status` 和有效阻断，丢掉等待前的 `RUNNING`。

锁内已经是终态时，不插入一条「终态前已被拒绝」的责任事实。这是规则 C 的推论，不是把这次到达改判成终态前拒绝。

这次到达在没有已提交责任事实时如何记成迟到审计，是 Pipeline 对「终态已提交且该身份还没有记录」的既有首次写入，也是 06-04-43 第 6.1 节里「两边都不存在」与 D6 的边界。D3 不新确认一套迟到业务语义，也不把已有拒绝审计改成迟到。责任事实不存在而审计已经存在时，仍是 06-04-43 的兼容边界，不在本锁协议里反向补造。

### 6.3 序列 C：责任事实事务取得锁后异常

| 位置 | 能否确认没有责任事实 | 处理候选 |
| --- | --- | --- |
| 锁内读取前就失败 | 还没有插入，也没有进入 `COMMIT`。不能写成已发生 | 回滚。调用方还在时，新事务重新锁、重新读 |
| 读完之后、`INSERT` 之前失败 | 同上。分类结果留在内存里，不是权威事实 | 回滚，不插入 |
| `INSERT` 执行期间断连，尚未进入 `COMMIT` | 语句是否执行完不确定。权威事实不能写成已形成 | 不把语句不明当成 `COMMIT` 不明。后续怎么读属于 D4，本轮不关闭 |
| 可以确定 `COMMIT` 尚未发送 | 尚未形成。未发送不等于已经回滚 | 不写成已发生 |
| `COMMIT` 可能已发送，客户端无法确认 | 不能确认没有，也不能确认已有 | 保持不确定。不盲目再插入。独立读取属于 D4 |
| `COMMIT` 已确认成功，进程随后崩溃 | 事实已经发生。审计可以还没有 | 补写属于 D5。崩溃本身不撤销这次 `COMMIT` |

### 6.4 序列 D：终态事务取得锁后异常

终态事务未提交就失败或回滚：任务行仍是提交前的状态。后面的责任事务拿到锁后，读到的不是这次终态。它可以按锁内仍非终态的结果继续判断，不能假设终态已经写上。

终态 `COMMIT` 已确认成功：后面的责任事务必须看见这个终态，并按序列 B 处理。

终态 `COMMIT` 不明：责任事务不能把「终态也许提交了」当成锁内事实，也不能把「也许没提交」当成仍是 `RUNNING`。它要在自己的锁内把行读完并分类。读不完则停止，不插入。终态那一侧的不明读取属于 D4，不在这里定成成功或失败。

### 6.5 序列 E：多个 Worker

两个 Worker 为同一 D1 身份插入：任务行锁把它们对这一任务的分类排成先后。先提交并成功的那一条才是已发生事实。后一个必须重读。内容相同才谈幂等，内容不同才谈 `BLOCK_CONTENT_CONFLICT`，而且比较对象必须是已经成功 `COMMIT` 的责任事实。任务行锁不保证全库只有一行。那是 D7 的唯一约束，IR-02 仍未关闭。

两个 Worker 为不同 `blockIdentity` 插入：锁仍按任务排队，避免两个人同时用过期的 `RUNNING` 做分类。身份不同则不是同一事实。谁能成为有效阻断、谁是拒绝，仍看锁内的有效阻断，不看谁的请求先到达。

## 7. 锁顺序、死锁与异常

候选原则：任务行锁是责任事实事务和终态事务共同的第一把业务锁。先拿别的行再拿任务行，会和 06-04-11 已经写明的「先任务、后尝试」交叉。

终态路径在设计文本里是任务行然后尝试行。责任事务不改尝试执行权，因此不把尝试行锁放在任务行前面。它若还要碰责任事实自己的唯一索引，应在已经持有任务行锁之后。先碰索引再锁任务行，可能和「先任务行、再索引」交叉。这种死锁没有实验。

死锁被数据库确认并整笔回滚之后，这次事务没有成功 `COMMIT`，不能写成责任事实已发生。重试是一笔新事务：重新锁任务行，重新读，再决定插不插。若前一次其实已经提交，只是客户端当时不确定，重试不得再插第二条。区分「已回滚」和「`COMMIT` 不明」是 D4。锁等待超时在 06-04-11 中默认只回滚当前语句，`innodb_rollback_on_timeout` 未选。不能把超时写成已经提交或已经覆盖。

正确性不依赖 Redis 锁、进程内锁或单 Worker。那些锁别的进程看不见，也不能代替这把任务行锁。

## 8. MySQL 8.0.46 的证据和未验证项

| 类别 | 内容 |
| --- | --- |
| 手册可以支持、且已被 06-04-11 引用 | 普通一致性读不是随后写入的围栏。加锁读随事务提交或回滚释放。两笔都对同一行加锁的事务会排队。死锁回滚整个事务 |
| 仓库设计已经写明 | 五个终态值的设计路径先锁任务行。拒绝审计和迟到审计不锁、不写 `status`。A 类、B 类的围栏放不下责任事实事务 |
| 代码事实 | 没有 `FOR UPDATE` 的 Java 实现。不能声称运行中的终态写入已经走这把锁 |
| 必须在 MySQL 8.0.46 上实验、目前未做 | 责任事务与终态事务的实际排队。终态先提交后，后到的责任事务是否一定看见终态。先索引后任务行是否死锁。隔离级别未选时的间隙锁。锁等待超时回滚的是语句还是事务。`COMMIT` 已发送但响应丢失 |
| 目前不能证明 | 尚未存在的责任事务会取这把锁。所有未来终态入口都不会绕过它。并发下同一身份只会留下一行 |

本轮没有连接数据库，没有执行写语句。手册结论不是本项目实验通过。

## 10. 候选方案比较

| 方案 | 内容 | 与已确认语义 | 状态 |
| --- | --- | --- | --- |
| 候选 1 | 责任事务与终态事务都先锁同一任务行，持锁重读后再写，锁保持到提交或回滚。责任事务是第三类 | 符合规则 C。发生时点仍是责任事实的 `COMMIT` | 本调查的推荐原则。未批准，未验证 |
| 候选 2 | 只让责任事务锁任务行，终态维持「文本里写了锁、但不作为共同协议验收」 | 终态若有旁路，规则 C 的同一协调边界不成立 | 不作为推荐 |
| 候选 3 | 把责任事实插进终态事务 | 一次提交使「责任事实已提交、终态尚未提交」或相反的窗口消失，并改变「两个状态」 | 不采用 |
| 候选 4 | 用请求时间或 Worker 时钟排序，不锁行 | 不能形成数据库可观察的先后 | 不采用 |
| 候选 5 | Redis、进程内锁或单 Worker | 别的进程看不见 | 不采用 |

推荐原则只是候选 1。它不改成功类和 `FAILED` 的 `WHERE`，不把 A 类或 B 类改写掉。

## 11. P0、P1、P2

| 项 | 级别 | 说明 |
| --- | --- | --- |
| 同一任务行锁、持锁重读、第三类、不并事务 | P0 | 架构批准前要确认的 D3 原则。本报告只形成候选 |
| 取得锁或 `INSERT` 成功都不等于已发生 | P0 | 否则定义 B 被提前 |
| 终态先提交后不得插入终态前责任事实 | P0 | 规则 C 的分类边界。迟到如何落审计仍是既有路径和 D6，不在这里新确认 |
| `COMMIT` 不明保持不确定 | P0 边界 | 具体读法是 D4，不关闭 |
| MySQL 8.0.46 排队、死锁、超时、响应丢失 | P1 | 实施前实验。当前全部未执行 |
| 代码路径核对：每一处终态写入都先锁任务行 | P1 | 现在没有实现可核对 |
| D7 唯一约束 | P1 | 锁不能代替。IR-02 不关闭 |
| 隔离级别、`innodb_rollback_on_timeout`、索引名 | P2 | 不改变「第一把锁是任务行」时再定。间隙锁行为仍要实验 |

## 12. 调查结论与禁止事项

已有设计事实：06-04-11 把五个终态值的写入写成先锁任务行；拒绝审计和迟到审计不锁、不写 `status`；A 类与 B 类放不下这笔责任事务；Java 里没有 `FOR UPDATE`。已确认业务语义仍是定义 B 与规则 C。推荐的 D3 原则是候选 1。它尚未获架构批准。排队、死锁和故障行为尚未经 MySQL 8.0.46 实验。相关 E2E 未执行。

本轮禁止：修改既有调查和设计，执行 SQL 写操作，新建模块，引入 Inbox、Outbox、DLQ 或 Redis 锁，把两个事务并成一个，用任务行锁代替唯一约束，宣布 IR-10 或 D3 已获架构批准，把手册或设计文本写成已经完成的实验。
