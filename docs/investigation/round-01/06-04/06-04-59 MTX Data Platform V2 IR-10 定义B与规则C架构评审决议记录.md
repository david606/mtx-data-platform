## 4. 三种结果的后续处理

下列动作都要等对应那一项已经由评审人填入真实结果之后才能做。本轮一项都还没填，所以一项都不执行。

### 4.1 APPROVE

只对填了 `APPROVE` 的那一项：

1. 在本文件该行记下评审人、日期、理由和附加条件，把该行标为架构已批准。未填写的另一项保持待填写。
2. 按 `docs/decisions/` 已有写法另立一份新 ADR，不改 ADR-0002 至 ADR-0005 的状态和正文。新 ADR 的范围只包含获批的那一项语义，并抄入 06-04-58 第 4 节的排除范围。状态沿用已出现过的「已接受」或「Accepted（已接受）」。不在决议仍为空白时占用 0006。
3. 新 ADR 落盘时，才在 [docs/decisions/README.md](../../../decisions/README.md) 增加对应一行。
4. 台账同步另见第 5 节。只同步获批范围，不把 IR-10 整行写成已经关闭。
5. 调查报告保持原样。06-04-40 的业务确认列保持已确认。若另行授权回写 06-04-40 的架构批准栏，只回写获批的那一项。

物理设计、实验和实现仍按附加条件留下，不随「已接受」变成已完成。

### 4.2 REJECT

只对填了 `REJECT` 的那一项：

1. 写下拒绝理由，以及要重新讨论的是业务语义还是架构约束。
2. 保留 06-04-40 的业务确认记录，不把它改成未确认，也不删除 06-04-43 至 06-04-58。
3. 不创建已接受 ADR，不向决策索引加行。
4. 不把拒绝写成另一项也被拒绝。

### 4.3 DEFER

只对填了 `DEFER` 的那一项：

1. 写下暂缓理由、尚缺的证据，以及可以再次评审的条件。条件必须指向具体证据，不由本模板代填日期或组织手续。
2. 06-04-40 的业务确认保持已确认。架构批准保持未发生。
3. 不创建 ADR。暂缓不是拒绝，也不把该项从待表决改成已否决。

## 6. 任何结果都不自动关闭的事项

定义 B 获批、规则 C 获批，或两项都获批，都不关闭：

1. D6 首次迟到分类。
2. D7 跨类型唯一性。
3. IR-02 物理唯一约束，包括 `blockIdentity` 的列、单一键空间和 A-09。
4. MySQL 并发实验。未执行的实验不能写成已通过。
5. 责任事实的物理 DDL。
6. 责任事实的代码实现。
7. 故障恢复和 E2E 验证。

规则 C 获批尤其不表示已经选定 MySQL 隔离级别、事务传播、具体 `FOR UPDATE` SQL 或索引方案。Task 行锁不是物理唯一约束。

[ADR-0002](../../../decisions/0002-v2-module-architecture.md) 的十模块边界、[ADR-0003](../../../decisions/0003-unmapped-conflict-observation.md) 的观测范围、[ADR-0004](../../../decisions/0004-external-contract-version-resolution.md) 的契约版本解析、[ADR-0005](../../../decisions/0005-mysql-doris-storage-baseline.md) 的服务器版本，都不因本决议模板改变。
