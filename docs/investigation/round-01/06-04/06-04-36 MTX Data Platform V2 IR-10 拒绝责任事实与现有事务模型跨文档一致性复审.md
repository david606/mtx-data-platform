## 4. 现有事务模型

「Task-first」只指 06-04-11 第 7 节：同一事务既改任务又改尝试时，先 `SELECT ... FOR UPDATE` 任务行，再动尝试行，提交前不释放任务行锁。它不是 B 类围栏的别名。

「B 类」只指 06-04-19 第 6.2 节：先锁任务行，再校验代次、`CURRENT`、`RUNNING` 和有效阻断为空，然后才插入受执行权约束的领域结果。

「A 类」只指 06-04-19 第 6.1 节：不锁 `RUNNING` 任务，按完整身份插入不可变行。拒绝审计和迟到审计被写进这一侧，但审计列还不能执行 DDL，所以它们还不是可执行的 A 类。

物理唯一约束是 IR-02，尚未验证。任务行锁不代替它。`CURRENT` 计数是领取路径上的完整性检查，不承担领取串行，也不关闭 IR-02。06-04-09 第 4 节。

| 事务 | 是否锁任务行 | 是否要求 `CURRENT` | 是否改 Task | 是否改 Attempt | 依据 |
| --- | --- | --- | --- | --- | --- |
| Task Claim | 是。先锁任务行，再插入或取代尝试 | 领取前调用方没有这次的 `CURRENT`。成功提交后新尝试成为 `CURRENT` | 是。代次加一，`status` 进入 `RUNNING` | 是。插入新尝试，并取代旧的 `OPEN` / `CURRENT` | 06-04-11 第 5.1、第 7 节 |

| `SUCCESS` 以及另外两个成功类终态 | 是。然后才改尝试 | 是 | 是。`status` 改为对应终态。条件包含有效阻断为空 | 是。`SUCCEEDED` / `RELEASED` | 06-04-11 第 7、8 节 |

有效阻断写在任务行上，登记事务持有任务行锁直到自己的 `COMMIT`。后到的终态事务也要这把锁，并在持锁后按第 8 节的 `WHERE` 读取。这保护的是任务行上的阻断列，不是一条尚未设计的责任事实。

## 5. 06-04-35 第 4.5 节的锁序列

第 4.5 节自己写明六条是待决策，不是已实现协议。在这个前提下核对它的六步：

1. 责任事务先锁任务行。与 Task-first 同向。它不先锁尝试行，也不改尝试，所以没有把「先尝试、后任务」写进来。
2. 持锁重读 `status` 和有效阻断。与 06-04-11 第 7 节「事务外先读不是围栏」同向。
3. 锁内插入责任行。现行文档没有这行。插入会碰到该行自己的索引锁。索引锁不是任务行锁。
4. `COMMIT` 后释放任务行锁。06-04-11 引用的加锁读规则是锁在提交或回滚时释放。这句话覆盖已经取了这把锁的事务。它没有证明责任事务会取锁。
5. 终态事务再取同一把锁。终态路径会取锁，这是现有设计，仍未在 8.0.46 上验证。
6. 终态事务持锁重读，再按原有 `WHERE` 决定终态。`FAILED` 的条件仍然只是阻断等于已登记的那一条。责任行不改变这个条件。

因此，这六步若被另文接受，不会把 Task-first 倒过来，也不会把 `FAILED` 改成「必须等拒绝审计写入完成」。终态事务只会在对方还持有任务行锁时等待。等待是锁队列，不是新的终态谓词。06-04-35 没有把这六步写成已经成立。

不能由文档证明、必须标成待验证的行为：

- 责任事务与终态事务在 MySQL 8.0.46 上是否一定按这把锁排队。
- 隔离级别未选定。间隙锁、插入意向锁和唯一索引记录锁是否与任务行锁形成死锁，没有实验。
- 责任行 `COMMIT` 已发送但响应丢失时，另一 Worker 的终态事务是仍在等锁，还是已经提交。客户端不能从响应丢失推断哪一种。06-04-11 第 5.2 节那种「另一连接锁定读」只写了领取，没有写责任事实。06-04-09 只要求领取结果不明时按该节重读。
- 终态事务是否会用加锁之前的快照提交。设计要求终态使用加锁读，并写明普通一致性读不是围栏。这不是 8.0.46 执行记录。

责任事实与 `SUCCESS` 的关系，现有文档只证明了终态条件：成功类终态要求有效阻断为空，已提交的 `SUCCESS` 不能带着有效阻断。06-04-11 第 8 节。它阻止不了一笔不持锁、又使用旧 `RUNNING` 的插入。第 4.5 节把共同锁标为待决策，本复审同意，不把它升级成已证明的互斥。

责任行不修改任务行。所以它提交之后，终态事务重读到的仍是「`RUNNING` 且阻断为 A」，然后按现行条件提交 `FAILED`。这不是「基于旧状态」。旧状态问题只出现在不持锁、又沿用事务外 `RUNNING` 的写入。那种写入不是第 4.5 节的六步，而是现行拒绝审计已经允许的路径。

## 6. 与 A 类、B 类的分类冲突

最终拒绝审计和拒绝责任事实必须分开看。不能因为都涉及同一次拒绝，就使用同一套锁。

| 问题 | 最终拒绝审计 | 拒绝责任事实 |
| --- | --- | --- |
| 现行文档有没有这行 | 逻辑身份有。物理列和 DDL 没有 | 没有。Pipeline 只把「持久化待处理记录」列为未选 |
| 谁固定「终态前被拒绝」 | 现行规则下就是这行自己的首次提交。它不锁任务行，所以这个「终态前」还没有并发证明 | 只有第 4.5 节被接受后，才由这行的 `COMMIT` 固定。现未接受 |
| `COMMIT` 边界 | 独立于阻断登记和终态。06-04-09 第 4 节 | 若存在，是另一笔独立提交，不是审计行那一笔 |
| 是否锁任务行 | 现行：否 | 候选：是。待决策 |
| 恢复者是否锁任务行 | 幂等确认不需要为了改类再锁任务。现行恢复步骤本身未选 | 06-04-35 没有要求恢复补写再锁任务行 |
| 是否要求 `CURRENT` | 否 | 候选条件也不要求。恢复者不得变成原尝试的 `CURRENT` |
| 幂等 | `blockIdentity` 加四个内容字段。物理唯一约束未验证 | 需要自己的逻辑身份。不能用任务行锁代替。IR-02 |

把责任事务放进 B 类，和 B 类谓词冲突，不是用词问题。B 类第 5 步要求有效阻断为空。拒绝发生的前提是已经有一条有效阻断。同一事务不能既要求阻断为空，又要求阻断仍为 A。所以复审方案 B 和复审方案 C 都不能写成 B 类围栏，也不能要求 `CURRENT`。

把责任事务放进 A 类，也和 A 类冲突。A 类第 1 步是不锁定一条 `RUNNING` 任务。06-04-19 第 6 节又写任务行锁只属于 B 类。一个既要任务行锁、又不能满足 B 类谓词的事务，是第三类。现行文档没有这一类。

这个冲突是分类缺口，不是 InnoDB 上已经出现的矛盾。06-04-35 没有把六步写成现行拒绝审计。现行拒绝审计仍然是不锁任务行的追加。

## 7. 复审方案比较

### 7.1 复审方案 A：维持现有拒绝审计，不新增责任事实

终态前分类只在拒绝审计行已经提交、并且调用当时读到的任务尚未终态时，由现行首次写入规则成立。由于这笔事务不锁任务行，并发下的「当时尚未终态」没有第 4.5 节那种证明。`FAILED` 的谓词不变，也不等待审计。`SUCCESS` 仍要求阻断为空。Worker 在审计 `COMMIT` 前崩溃，其他进程读不到被拒绝身份。终态后的第一次写入按现行规则是迟到审计。这就是 06-04-34 的 R-02。`COMMIT` 不明沿用 06-04-09，但没有审计专用的已执行读法。两个 Worker 并发只留一条仍是逻辑要求，E2E-117 未执行，IR-02 未验证。不改 06-04-11 和 06-04-19 的锁分类。跨进程恢复目标达不到。

### 7.2 复审方案 B：新增责任事实，该事务取任务行锁，最终审计另一次提交

这是 06-04-34 候选 B 再加上 06-04-35 第 4.5 节。分类事实和最终审计是两行、两次 `COMMIT`。`FAILED` 的 `WHERE` 可以保持不变。进行中的责任事务若正持有任务行锁，终态事务会等待这把锁。这不等于把「拒绝审计已写入」写进 `FAILED` 条件。`SUCCESS` 与「阻断仍为 A」的先后，只有在两边都持有这把锁时才能由锁排队决定。文档没有证明责任事务会取锁，8.0.46 也没有实验。

崩溃后的可恢复性取决于责任行是否已经确认提交。确认提交且满足第 4.5 节时，另一个 Worker 可以按该行补写审计，不取得 `CURRENT`。尚未提交则不能伪造。责任行和审计行各有一次结果不明。两个恢复者并发写同一审计身份，仍要 IR-02，不能靠任务行锁保证只有一行。保留是否与审计行相同，属于 IR-15，未定。

改动范围是新的持久化事实、新的第三类锁，以及 06-04-11、06-04-19 里「拒绝审计不锁任务行」「任务行锁只属于 B 类」这两句的适用范围。最终审计自己可以仍不锁任务行。不得新增模块，不得写成 Outbox 或 Inbox。本复审不批准这个事实。

### 7.3 复审方案 C：不新增事实，只让拒绝审计事务取任务行锁

这笔事务仍然只插入现有的拒绝审计行，不并入阻断登记，也不并入终态事务。锁顺序是先任务行，再审计行的索引，不锁尝试行。`FAILED` 和 `SUCCESS` 的 `WHERE` 都不改。

它在引擎语义上不是不可执行的。具体限制是：

- 它不能放进 B 类，因为 B 类要求阻断为空，而这次插入的前提是阻断已经存在。
- 它不能放进现行 A 类，因为 A 类不锁 `RUNNING` 任务。
- 它会改掉 06-04-11 第 7 节「拒绝审计不锁任务行」。这是事务语义变更，不是实现细节。
- 发生时点仍然是这一行自己的 `COMMIT`。进程在该 `COMMIT` 之前崩溃，库里还是没有被拒绝身份。06-04-34 候选 A 仍然发现不了它。终态若已经先提交，下一次首次写入仍然是迟到审计。
- 因此它能收紧「用旧 `RUNNING` 在终态之后插入一条自称终态前的审计」，但不能满足 Pipeline 第 11.1 节「待处理责任不能只留在崩溃进程的内存里」。它不是 R-02 的跨进程恢复方案。

只比复审方案 B 少一个实体和一次 `COMMIT`。少掉的那一次，也就是崩溃后还能读到分类的那一行。

| 多 Worker | 逻辑上一条。IR-02 未验证 | 责任行和审计行都要各自的唯一约束。都未验证 | 同 A |
| 依赖 | IR-02、IR-10 | 再加新事实的 IR-15，以及第三类锁 | 改现有审计的锁分类。IR-02、IR-10 仍在 |
| 文档改动 | 无 | 新事实，并修订「锁只属于 B 类」 | 修订「拒绝审计不锁任务行」，并增加第三类 |

## 8. 锁顺序与死锁

既定方向仍是任务行先于尝试行。复审方案 B、C 若被以后接受，插入侧必须是：先锁任务行，再插入责任行或审计行，唯一冲突后的胜出读取留在这同一笔已经持有任务行锁的事务里。06-04-19 第 6.2 节对 B 类就是这个次序。不得先做无锁插入，再回头锁任务行。那会和「先任务、后索引」交叉。

| 次序 | 判断 |
| --- | --- |
| Task → Attempt | 领取、终态、`RETRY_WAITING`、`RUNNING` 取消已经如此。责任事务和拒绝审计不碰尝试行，就不构成逆序 |
| Task → 拒绝责任事实 | 只存在于未批准的复审方案 B。与 Task-first 同向。不是现行事务 |
| Task → 拒绝审计 | 现行拒绝审计不取任务锁。复审方案 C 才会变成这个次序。未批准 |
| 恢复事务先读责任行，再锁 Task | 06-04-35 没有要求恢复补写锁任务。若先锁责任行或唯一索引，再锁任务，就会和「先任务、后索引」交叉。复审意见是：分类已经提交之后，补写审计不再取任务行锁，也不要求 `CURRENT` |
| 唯一键冲突后的 winner read | 06-04-19 第 6.1 节把这次加锁读留在原事务内，并且 A 类重做不锁任务行。审计还没有可执行的专用协议。不能把第 6.3 节直接套到审计或责任行。06-04-34 的 R-04 |
| 两个恢复者 | 只应在审计身份的唯一索引上相遇。任务行锁保证不了只有一行。不用 Redis 锁或进程内锁 |

与 Attempt 行锁的死锁：责任事务不锁尝试行，终态事务是 Task → Attempt。这两笔只共享任务行锁时，是排队，不是这两把锁的逆序。唯一索引、间隙锁在未选定隔离级别下是否另有死锁，待验证。06-04-11 写明死锁整笔回滚后重试，锁等待超时默认只回滚当前语句，`innodb_rollback_on_timeout` 未选。这些都不是 8.0.46 实验。

## 9. `COMMIT` 不确定性

06-04-09 把下列情况分开。责任事实没有专用读法。领取路径的第 5.2 节不能直接改名套用。

| 情况 | 现有约束 | 复审用法 |
| --- | --- | --- |
| `COMMIT` 尚未发送 | 06-04-11 第 7 节不猜测提交结果。06-04-19 第 6.5 节处理尚未发送时的断连，不进入第 6.3 节 | 不得记成已发生或确定未发生 |
| `COMMIT` 已发送，响应丢失 | 06-04-09 第 2 节重试读取、不覆盖。第 8 节对终态是重读终态和尝试 | 另一连接完整读到对应身份之前，不分类，不另写迟到审计 |
| `COMMIT` 已确认后崩溃 | 06-04-09 第 5 节从已提交行继续 | 只对已经存在的行有效。没有行就没有事实 |
| 结果不明期间另一 Worker 提交终态 | 终态事务会锁任务行。对方若仍持有该锁，后一方等待。现行拒绝审计不持有该锁，所以等不到它 | 不明期间不得把没读到的行当成不存在 |

责任行和审计行的两次提交不能互相证明。一边已确认，不说明另一边已确认。

## 11. 复审结论

1. 已经明确的事实：领取、阻断登记、成功类终态、`FAILED`、`RETRY_WAITING` 和 `RUNNING` 取消都先锁任务行。拒绝审计和迟到审计不锁任务行，不要求 `CURRENT`，不改 Task 和 Attempt。`FAILED` 不把拒绝审计并入自己的事务。任务行锁不是物理唯一约束。这些设计都还没有 8.0.46 实验。
2. 06-04-35 新加的只是候选条件：责任行要在持有任务行锁并重读之后插入，`COMMIT` 本身不证明终态前发生。该文已标待决策。
3. 这组锁顺序没有违反 Task-first，也没有改写 `FAILED` 或 `SUCCESS` 的谓词。它还不是可以执行的证明。与 `SUCCESS` 的互斥、以及 `COMMIT` 不明期间终态能否先完成，都待验证。
4. 它与现行 A 类、B 类冲突：B 类要求阻断为空，A 类不锁任务行，而「任务行锁只属于 B 类」。冲突的是分类，不是已经落地的两笔事务。最终审计和责任事实不能共用一套锁语义。
5. 本复审不建议新增独立责任事实。只有在以后正式决定「终态可以先提交，未写入的拒绝仍必须按拒绝审计恢复」时，才需要这种事实。那是 R-02 和 R-03，现在都待决策。
6. 本复审不建议修改现行拒绝审计事务。复审方案 C 能收紧旧状态插入，但提交点仍是审计行，崩溃前仍然没有可恢复身份，而且必须改「不锁任务行」。
7. 推荐维持复审方案 A 作为现行事务语义。不实施复审方案 B，也不实施复审方案 C。理由是：B 要新实体和第三类锁，C 解决不了跨进程丢失，两者都还没有实验，也都不是 ADR。06-04-34 的进程内重试仍然不够，不能拿来代替方案 A 的缺口。
8. 仍不能确定的是：R-02 是否要求终态后的补写保持拒绝分类；若要求，第三类锁和责任行的逻辑身份由谁写；恢复者在不持有 `CURRENT` 时的授权；责任行与审计行的保留是否相同。
9. 必须在 MySQL 8.0.46 上验证、且现在都未执行的事项见第 13 节。隔离级别、`innodb_rollback_on_timeout`、唯一索引和间隙锁都未选或未证。
10. IR-10 仍然是待决策、P1。IR-02、IR-07、IR-09、IR-15 也不关闭。本推荐不是 ADR。
