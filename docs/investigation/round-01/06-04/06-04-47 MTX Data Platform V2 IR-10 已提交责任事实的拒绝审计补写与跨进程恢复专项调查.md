# 06-04-47 MTX Data Platform V2 IR-10 已提交责任事实的拒绝审计补写与跨进程恢复专项调查

本文只调查 D5：已经成功 `COMMIT` 的拒绝责任事实，怎样被别的进程发现，以及拒绝审计怎样补写。它不是架构批准，也不是实现。不关闭 IR-10、IR-02、IR-15，也不关闭 D4、D7。不修改 Java、Maven、DDL、已接受 ADR、台账和 06-04-40 至 06-04-46。没有执行数据库写入、MySQL 实验或 E2E。不新增模块，不引入 Inbox、Outbox、DLQ 或 Redis 锁，不设计唯一索引 DDL，也不把新的待办事实写成已经批准的模型。

四个词在本文里分开：

| 词 | 含义 |
| --- | --- |
| 责任事实发生 | 责任事实事务实际成功 `COMMIT` |
| 审计发生 | 拒绝审计那次事务实际成功 `COMMIT`，并且四个内容字段与责任事实一致 |
| 补写发现 | 另一个进程能够读到一条已提交、且审计义务尚未确认完成的责任事实 |
| 补写执行 | 按该事实的快照写入拒绝审计。发现本身不是执行 |

## 4. 责任事实与审计生命周期状态矩阵

进入补写执行，必须同时满足：责任事实那次 `COMMIT` 已经确认；该 D1 身份恰好一行；这一行的完整 D2 内容可以逐项核验。多行、内容冲突、读取不完整或 `COMMIT` 不确定，都不得把某一行送去写审计。

| 状态 | 能否进入补写执行 |
| --- | --- |
| 责任事实尚未发生 | 不能。内存中的拒绝不是事实。不得补造 |
| 责任事实 `COMMIT` 不确定 | 不能。先按 D4 做独立读取。读不完整或不能定位时继续停止 |
| 同一 D1 身份有多条责任事实 | 不能。不挑选。不因为内容相同就当作唯一性已经成立 |
| 恰好一行已提交责任事实，审计读取不完整 | 不能写入，也不能标成完成。这条事实仍是未完成义务 |
| 恰好一行已提交责任事实，审计读取确认不存在 | 06-04-42 把「完整读取后没有审计」列为可以进入补写的前提。06-04-46 说明普通缺行和加锁读缺行都还不是确认不存在，而且审计身份自己的权威缺行条件并未打开。因此本轮不把「扫描没看见审计」写成可以 `INSERT` |
| 恰好一行已提交责任事实，恰好一条审计，四个字段一致 | 补写已经完成。不再插入。分类证据不必出现在审计行上 |
| 恰好一行已提交责任事实，恰好一条审计，四个字段不一致 | `BLOCK_CONTENT_CONFLICT`。停止。不覆盖，不改成迟到，不把恢复标成成功，也不因此删除责任事实 |
| 审计多行，无论内容是否相同 | 停止。不挑选，不合并，不再插入，不新造错误码 |
| 审计已存在，没有对应的已提交责任事实 | 不能反向补造责任事实，也不能把审计存在写成补写完成 |
| 任务当前已是终态，但责任事实是终态前提交的拒绝 | 仍只补拒绝审计。不按当前 `status` 改成迟到 |

审计存在不能推断责任事实已经发生。`REJECT_AUDIT_ALREADY_RECORDED` 只说明审计行在。

## 5. 待补写发现机制调查

只扫描已有审计，看不见还没有创建的审计行。只扫描任务行和有效阻断，也读不出被拒绝的身份和四个字段：有效阻断是另一条身份，任务当前状态会在终态之后改变。发现必须从已经提交的责任事实读起。

| 方式 | 能否看见已提交但未写审计的事实 | 崩溃窗口 | 多实例 | 本轮判断 |
| --- | --- | --- | --- | --- |
| 启动时扫描已提交责任事实 | 能，只要事实已经 `COMMIT`，且扫描读的是这份事实 | 崩溃前已经提交的行，下次启动仍在。只存在于崩溃进程内存里的仲裁看不见，这符合定义 B | 会重复发现。重复发现不等于可以重复插入 | 发现候选。写入仍受第 4 节限制 |
| 周期性扫描同一类事实 | 与上一行相同。周期没有选定，也不用秒数代替正确性 | 两次扫描之间的已提交行留到下一次。未提交的行本来就不是事实 | 同样会重复发现 | 发现候选。频率未决 |
| 只靠原调用的内存事件或进程内回调 | 原进程还活着时能看见失败 | 崩溃、重启或换进程就丢。Pipeline 已禁止把待处理责任只放在内存 | 别的实例看不见 | 不能作为跨进程发现 |
| 事件触发，但事件本身没有和责任事实同一次提交 | 触发丢失时，事实还在，发现没有了 | 会漏 | 取决于事件能否被多个进程看到 | 不能单独作为权威发现 |
| Worker 按任务领取或 `CURRENT` 来认领补写 | 领取恢复的是执行权，不补审计。06-04-31 已写明 | 终态已提交、执行权已释放之后，领取模型不再持有这条审计义务 | 执行权排他不能变成审计幂等 | 不复用为补写执行权 |
| 独立恢复进程 | 若它只读已提交责任事实，发现能力与 Worker 扫描相同 | 同扫描 | 同扫描 | 不因此新增模块。谁来跑仍未决 |
| Kafka 消费组分区或进程存活 | 分区所有权和进程在不在，都不是这条事实的执行权 | 再均衡或重启会改归属，不改变事实是否提交 | 会把审计义务绑到无关键上 | 不采用 |

发现机制自己失败时，已提交责任事实还在。下一次完整读取可以再发现。不得把扫描失败写成审计已完成，也不得因此删除事实。

「没有审计」不是发现条件。发现条件是：读到恰好一条已确认提交的责任事实，并且它的完整内容可核验。审计缺行只影响能不能写入，而且这个缺行目前还不能当成确认不存在。

## 6. 跨进程恢复责任与执行权分析

| 职责 | 候选落点 | 不是 |
| --- | --- | --- |
| 发现 | 能读取已提交责任事实的 `app-worker` 装配。任一实例都可以读到，不依赖原 Worker 仍在运行 | `app-admin` 的管理进程。`platform-core` 里的 JDBC。Pipeline 对 Quartz 或恢复实现的依赖 |
| 领取 | 本候选不设单独租约。多个实例可以同时看见同一事实 | 任务代次、`CURRENT`、消费组所有权、进程心跳 |
| 写入 | 执行读取和 `INSERT` 的那个 Worker。内容只从责任事实快照取被拒绝身份和四个字段 | 原调用栈里的内存分类 |
| 接管 | 原进程消失后，下一次对已提交事实的完整读取。没有「原主人」需要转移 | 把原 Worker 的本地状态复制出去 |

可持久化的恢复状态，在本候选里只有两类已有目标：责任事实行，以及尚未确认完成的审计义务。审计义务的完成证据是拒绝审计那次已确认的 `COMMIT` 加上四个字段一致。Pipeline 要求成功保存后把责任标成已完成，但标记放在哪尚未设计。本轮不新增第三张待办事实来充当这个标记。

现有 Task 与 TaskAttempt 表示的是数据处理任务和一次执行尝试。拒绝事实的身份不是 `taskAttemptId`。为了复用领取模型而把 Attempt 或 Worker 写进身份，会改变 D1。领取扫描也不写入拒绝审计。因此不能把补写工作伪装成一次新的任务尝试。

缺少、且本轮不发明的语义是：审计身份上的权威「确认不存在」，以及 D7 尚未实现的物理唯一约束。没有这两样，跨进程可以发现事实，但不能安全地执行插入。

## 7. 审计补写幂等与竞态分析

四种机制各管一段，不能互相替代：

| 机制 | 管什么 | 不管什么 |
| --- | --- | --- |
| 进程内判断 | 同一次调用不要在内存里插两次 | 别的进程 |
| 任务行锁 | 分类和终态的先后 | 审计行是否只有一条 |
| 数据库唯一约束 | 并发插入后的权威行。D7、IR-02，未实现 | 内容是否一致。约束返回也不说明它就是审计身份那一个约束 |
| 胜出读取加内容比较 | 冲突之后，或独立读取之后，四个字段是否与责任事实一致 | 在约束还没定位时宣布冲突已解决 |

审计记录的查找键与被拒绝的 `blockIdentity` 相同，这是 Pipeline 已有语义。它不是把责任事实的整份 D2 内容搬进审计身份。审计上参与比较的是四个字段。分类证据仍只在责任事实上核验。责任事实的唯一性前提和审计记录的唯一性前提是两件事：一边多行或一边不能定位约束，都不能用另一边的单行来宣布已经唯一。

| 时序 | 处理 |
| --- | --- |
| 两个 Worker 同时准备补写同一审计 | 都可以先发现同一条责任事实。没有 D7 时，不能靠「我先在内存里登记」保证只有一行 |
| 两边都执行 `INSERT`，都还没提交 | 等待和锁冲突不是缺行。未确认前不把其中一边写成成功 |
| 一边 `COMMIT` 成功但响应丢失 | 审计发生与否不确定。不标完成。按 D4 的原则另开读取，对象是审计记录：先确认读到的是这一审计身份，再比较四个字段。不能把责任事实那次读取的结果抄过来当作审计已提交 |
| 一边已经确认写上审计，随后崩溃 | 事实和审计都已发生。另一个进程读到恰好一行且四字段一致，就不再插入 |
| 身份相同、四个字段一致 | 幂等完成 |
| 身份相同、四个字段不同 | `BLOCK_CONTENT_CONFLICT`，停止 |
| 同一责任事实身份对应多条审计 | 停止。不挑选，不再插入 |
| 审计在、责任事实不在 | 不补造责任事实。这不是补写成功 |
| 唯一键冲突但说不清是哪个约束 | 停止。不用一次按 D1 的查询宣布已经解决。该查询没有行时，不重试插入，也不改称 `COMMIT` 不确定 |

审计 `INSERT` 期间断连、且可以确定还没发 `COMMIT`，是语句不确定，不是审计已发生，也不是可以再插一次。普通故障且整笔回滚已确认时，才允许就这一审计身份重新准备写入；重新准备仍要先读责任事实和审计，不复用旧事务内存。

## 8. 终态后首次到达的迟到审计边界

判别依据是有没有一条已确认提交的拒绝责任事实，不是恢复时任务是不是终态，也不是两条记录谁的日志更早。

| 已提交的拒绝责任事实 | 该身份的审计 | 到达时所见任务状态 | 边界 |
| --- | --- | --- | --- |
| 恰好一行，内容可核验 | 尚未确认写上 | 已经终态 | 历史分类保持拒绝。只讨论拒绝审计补写，不改成迟到 |
| 没有，且 D4 也不能确认它存在 | 没有 | 终态后第一次到达 | 不补造终态前责任事实。现行首次写入仍是迟到审计。这是 D6，本轮不设计迟到写入 |
| `COMMIT` 不确定，或多行，或读取不完整 | 不论 | 不论 | 不写拒绝补写，也不改写成迟到 |

已经发生的拒绝不能改成迟到。没有发生的拒绝也不能用迟到审计反写成「当时已经拒绝」。任务行锁在终态事务里的作用已经结束于那次终态提交；补写不再为了改分类去抢这把锁。

## 9. IR-02、D7、IR-15 依赖

| 依赖 | 本轮用到的边界 | 不在本轮决定 |
| --- | --- | --- |
| IR-02 | 物理唯一索引未建。没有它，并发补写可能留下多条审计。先查后插改变不了这一点 | 索引字段、名称和 DDL。不关闭 IR-02 |
| D7 | 唯一约束是并发下的权威行，不是扫描、租约或任务行锁。冲突必须先定位具体约束。多行停止 | 不批准 D7，不把它写成已经实现 |
| IR-15 | 未完成补写的责任事实不得因异常标记删除。归档不是删除。没有批准的保留天数。补写要能读到身份和不可变内容；这些内容若先被删掉，恢复就没有权威来源 | 不编造天数，不设计删除或归档语句。不关闭 IR-15 |
| D8 的删除禁止 | 06-04-42 已把它列为未完成补写不得删除。停止自动恢复不等于义务完成 | 不在本文关闭 D8 |

责任事实的生命周期到审计补写确认为止仍须保留可读。审计行自己的生命周期是追加记录，不随任务终态结束，也不随责任事实被标成「已查看」而消失。两边不能互相代替，也不能互相级联删掉。

## 10. 候选方案比较

下列字母只用于本文。它们不是 06-04-34 的候选 A 至 D，也不是 06-04-36 或 06-04-41 的方案字母。

| 项 | 方案 A：从已提交责任事实发现，再决定是否写审计 | 方案 B：责任事实之外再放一条待办事实 | 方案 C：在责任事实行上放待补写标记，用标记发现 | 方案 D：只保留即时重试，或只扫描已有审计 |
| --- | --- | --- | --- | --- |
| 持久化事实 | 责任事实本身。完成证据是已提交且四字段一致的审计 | 多一条待办。Pipeline 把它列为未选，不是 Outbox 的别名 | 责任事实加上一个会变化的完成标记。标记位置未设计 | 没有新的已提交事实。审计不存在时无物可扫 |
| 崩溃后 | 已提交的责任事实仍可被其他进程读到 | 只有待办和责任事实同一次提交，崩溃后才不会漏。晚于事实提交的待办会形成新的丢失窗口 | 标记若与事实同一次提交，发现不依赖内存。标记若写错成已完成，真实缺口会被藏起来 | 原进程消失后，即时重试不存在。只扫审计则永远看不到缺口 |
| 漏发现 | 不漏已经提交的事实。漏的是尚未发生的内存仲裁，这是定义 B 要求的 | 待办写入失败或未与事实同事务时会漏 | 标记丢失或被提前写成完成时会漏 | 会漏 |
| 重复执行 | 会重复发现。不能因此重复插入 | 多个进程仍会看见同一待办 | 多个进程仍会看见同一未完成标记 | 即时重试只在原调用方还活着时发生一次 |
| 跨进程接管 | 能。不依赖原进程 | 能，前提是待办已经提交 | 能，前提是标记已经随事实提交 | 不能 |
| 唯一约束 | 写入仍依赖 D7。发现不依赖它 | 待办和审计各自都要考虑唯一性，范围更大 | 标记不是唯一约束 | 没有跨进程写入可约束 |
| 新的持久化模型 | 不需要 | 需要，且本轮不能批准 | 需要一个会更新的标记，位置未定 | 不需要，但也不构成恢复 |
| 十模块 | 装配仍可放在 `app-worker`。不新增模块，不把 JDBC 放进 Core，不把 Quartz 放进 Pipeline | 新事实放在哪个现有模块仍要单独决定。不能靠新模块解决 | 同方案 A 的模块边界，但多一个更新语义 | 不改变模块，也不补上缺口 |
| IR-02、D7、IR-15 | 写入依赖前两项。事实在补写确认前不可删 | 待办的保留又多一层，仍受 IR-15 | 标记不能被异常删除用来假装完成 | 没有可保留的新义务记录 |
| 运维 | 要有重复执行的扫描或启动读取。频率未定 | 还要监视待办积压，以及待办和事实不一致 | 要区分「标记未完成」和「审计真的没写上」 | 表面没有新组件，崩溃后义务静默丢失 |

## 11. 推荐方案及代价

推荐候选是方案 A 的发现形状，未批准，未实现。

已经成功提交、且同一身份恰好一行、完整 D2 内容可核验的责任事实，就是待补写义务的权威来源。任何 `app-worker` 实例都可以在原进程消失后读到它。不新增待办事实，不把完成标记当作发现的唯一依据，也不只扫描审计表。

写入不跟着发现自动发生。审计读取不完整、审计多行、四个字段冲突、约束不能定位，以及普通缺行尚未被证明为确认不存在时，都停止，不插入，不把义务标成完成，不删除责任事实。D7 实现之前，并发插入没有权威的失败方。因此本候选允许跨进程发现，不允许把「扫描没看见审计」实施成 `INSERT`。

代价是：在权威缺行条件或 D7 打开之前，补写执行仍然做不到。扫描会反复读到已经完成的事实，这是正确性代价，不是再插一行的理由。Pipeline 要求的「标成已完成」仍没有落点；在落点确定前，不得用一个提前写下的标记代替审计 `COMMIT`。方案 B 和方案 C 都不作为本轮推荐。方案 D 只保留为即时重试，不能覆盖跨进程。

模块边界沿用 06-04-42 的未批准候选：装配在 `app-worker`，Core 不依赖 JDBC，Pipeline 不依赖恢复实现或 Quartz，`app-admin` 不执行补写。频率、包名和谁触发扫描都不在这里确定。

## 13. 本轮结论及禁止事项

本轮只完成 D5 调查。推荐的发现候选是方案 A。它尚未获架构批准，也没有实现。补写执行被 06-04-46 的缺行边界和未实现的 D7 挡住。MySQL 实验和相关 E2E 均未执行。

已确认的业务语义仍是定义 B 与规则 C。D1、D2、D3、D4 的调查结论只作为输入，不在这里改成已批准。IR-10、IR-02、IR-15 不因此关闭。

本轮禁止：修改既有报告、ADR 和代码，执行 SQL 写操作，新建模块，引入 Inbox、Outbox、DLQ 或 Redis 锁，批准待办表或唯一索引 DDL，把审计行当成责任事实，按当前任务状态重判历史分类，把不确定或多行事实送入补写，以及把本文的推导写成已经验证的运行能力。
