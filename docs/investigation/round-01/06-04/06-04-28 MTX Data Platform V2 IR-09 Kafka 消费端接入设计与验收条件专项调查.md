## 4. Kafka Consumer 与平台职责边界

下表是本轮设计推导，用来落实 ADR-0002，不是新的模块决策。

| 组件 | 职责 | 不负责 |
| --- | --- | --- |
| Kafka Consumer | 从 Broker 取消息，维护本消费者在分区上的已提交位置，按第 6 节决定能否提交 offset | 不调用 Pipeline，不创建或修改 TaskAttempt，不写业务表，不把读到消息当成业务完成 |
| 平台接入适配层 | 识别来源和契约，提取并校验稳定事件身份，把原文交给保存能力，调用 Task 创建端口 | Kafka 类型停在这一层。不把 `ConsumerRecord` 或 Spring Kafka 类型放进 Core 或 Pipeline |
| 原始报文存储 | 可靠保存原文并保证以后还能读到。介质由 IR-15 决定 | 保存成功不是 Task 已创建，也不是 offset 可以提交 |
| Task 创建 | 仅当来源契约已经声明稳定事件身份时，按 06-04-19 第 6.1 节做 A 类 Create-or-Get | 不领取任务，不把代次从 0 改掉，不写尝试 |
| Worker | 按 06-04-11 第 5 节领取，取得大于 0 的代次和 `CURRENT` 尝试，再运行 Pipeline | 消费组分配到的分区不是执行权 |
| Pipeline | 在围栏成立时做业务处理和受保护写入。围栏见 06-04-11 第 7 节 | 不拉 Kafka，不提交 offset |

六个问题的推导结论：

1. Consumer 不能直接调用 Pipeline。Pipeline 只依赖 common 与 core，并且要等执行权成立。
2. Consumer 不能创建或修改 TaskAttempt。尝试只在领取事务里出现。创建任务时代次是 0，0 不是执行权。见 06-04-11 第 3 节。
3. Consumer 不能绕过 Task 创建去写业务表。观测、字段结果和标准化都是 B 类写入，先锁当前代次的任务行。
4. 读到消息不是业务处理完成。offset 提交成功也不是业务写入成功。
5. 接入与执行解耦：接入最多把非重放任务创建为 `PENDING`、代次 0。之后由 Worker 的领取协议决定谁执行。重复投递回到原任务，不重新领取，也不覆盖权威 `rawPayloadRef` 和权威 `receivedAt`。
6. Core 保留身份语义、Create-or-Get 和执行权端口，不出现 Kafka 类型。Kafka 客户端、分区暂停和 offset 提交放在 `platform-messaging` 的适配实现里。把适配接到存储和 Pipeline 的装配放在 `app-worker`。`app-admin` 不运行这条消费链路。

暂停的是该分区的后续业务处理，不是停掉整个 Consumer。其他分区仍按各自的连续位置处理。

## 5. 稳定来源事件身份与 Task 创建流程

身份分类沿用 06-04-26 第 4 节，本轮不新造算法。

| 语义 | 消费时怎么用 |
| --- | --- |
| SourceOrderIdentity | 描述一张来源订单。订单相同不是事件相同 |
| SourceEventIdentity | 只有契约证明稳定、唯一、范围明确，才能作为非重放 Task 的 Create-or-Get 依据 |
| DeliveryIdentity | topic、partition、offset 或一次回调。可以重复，不能当成事件身份 |
| TaskIdentity | 内部 `taskId`。新生成一个不能完成去重。算法未设计 |
| ReplayIdentity | 调用方给出的 `replayRequestId`，指向新的 `taskId`。普通重复投递不写它。算法未设计，A-11 仍待补 |

有稳定身份时的候选顺序，是 06-04-26 第 7.4 节条件 A，比 06-04-09 第 3.4 节多了原文可再读和分区连续位置：

1. 读取消息。读取成功只说明投递到达。
2. 识别来源与契约。识别失败按身份无法验证处理。
3. 提取契约声明的稳定事件身份。没有声明就不提取一个替代键。
4. 校验完整性。空值、格式错误、作用域不足、同一身份对应契约不允许的不同正文，都不进入自动建任务。
5. 保存原文，并确认以后还能读到。介质未选时，这一步现在做不到。
6. Task Create-or-Get。A 类普通 `INSERT` 加完整列唯一，不先锁一条 `RUNNING` 任务。见 06-04-19 第 6.1 节。该唯一索引现在不能建。
7. 确认 MySQL 事务结果。不确定时停在第 7 节，不提交 offset。
8. 只有条件 A 五项都成立，并且同一分区没有更早的未完成消息，才允许提交对应 offset。

| 情况 | 是否同一 SourceEventIdentity | 任务 | offset |
| --- | --- | --- | --- |
| 缺少稳定身份 | 不能判断 | 不建自动处理任务 | 不提交。停止该分区后续业务处理 |
| 字段在但无法验证 | 不能判断 | 同上。不放宽格式 | 同上 |
| 重复投递 | 只有契约已声明且取值相同才是 | 回到原任务，不替换权威引用 | 条件 A 成立后可以提交这一次投递的位置，仍不得越过更早未完成消息 |
| 同一事件出现在不同 offset | offset 不同仍是同一次事件 | 有身份则回到原任务 | 每个投递位置单独满足条件后才提交。位置本身不是身份 |
| 同一事件跨分区 | 分区不同不构成两个事件 | 有身份则仍是一个任务 | 每个分区各自遵守连续提交 |
| 同一订单上的不同事件 | 订单相同、事件身份不同 | 各自一个任务。现在四类来源没有事件号，所以不自动拆成多个任务 | 每条消息单独判断 |
| 显式 Replay | 与来源事件不是同一身份 | 只有调用方给出 `replayRequestId` 才是另一条逻辑。算法未定，不能落成唯一约束 | 重放消息也要先确认自己的 MySQL 结果，再考虑它自己的 offset |

不得使用报文哈希、`receivedAt`、回调请求 ID、`rawPayloadRef` 或 offset 拼稳定事件身份。

ADR-0004 的契约版本解析发生在任务已经进入金额路径之后。消费端创建 `PENDING` 任务，并不等于 `contractVersionId` 已经确定。

## 6. 分区与 offset 连续提交安全规则

权威表述是 06-04-26 第 7.1 至 7.3 节。本轮把它落到消费形态上，仍是设计推导，没有客户端实验。

已确认并继续沿用的规则：

1. Kafka 不会因为某条 offset 未提交，就自动停止读取或处理该分区后续消息。
2. 身份缺失或无法验证时，不能只跳过当前消息再提交更大的 offset。
3. 必须停止该分区后续业务处理，或使用能够保证连续提交位置的等效机制。具体客户端做法留给后续实现，本轮不选 API。
4. 同一分区的已提交位置不得越过尚未完成可靠处理的消息。N 未完成时，即使 N+1、N+2 已处理完，也不得提交会使 N 被跳过的位置。
5. 批量提交、异步提交和自动提交都不能绕过这条边界。06-04-26 第 7.2 节写明不依赖自动提交。
6. rebalance 或进程重启后，未完成消息不能视为成功。恢复后按已提交位置重新处理，不靠进程内存。
7. 提交资格按分区看连续位置，不按单条消息孤立判断。

| 形态 | 设计要求 |
| --- | --- |
| 单分区顺序处理 | 只有当前消息达到条件 A，或将来可执行的条件 B，才提交它的位置。下一条在此之前不做会前进提交位置的业务处理 |
| 单分区批量处理 | 批内可以读取多条。可提交的位置只能停在从已提交位置起连续完成的前缀。前缀之后有一条未完成，整批不得提交到那条之后 |
| 多分区并行 | 分区之间互不代替。分区 P1 完成，不能作为分区 P2 越过未完成消息的理由。暂停 P2 时，P1 可以继续 |
| 单分区异步处理 | 后完成的消息不得先提交。完成顺序和日志顺序不一致时，仍以分区内位置的连续前缀为准 |
| 分区暂停与恢复 | 暂停原因是身份、原文、事务结果或隔离条件未满足。恢复前必须解除该原因并重新校验。暂停不是停掉整个 Consumer |
| rebalance | 交出分区前，未确认的消息不算成功，也不补交一个越过它们的 offset。新持有者从已提交位置再读 |
| Consumer 重启 | 未提交消息必须能再次投递。内存里的“已处理”作废 |
| offset 提交失败 | 已确认的 MySQL 任务保持。下次投递按来源身份回到原任务，不替换权威引用。见 06-04-09 第 5 节对应行，该行未执行 |
| offset 提交结果不确定 | 不把该位置当成已成功，也不据此再插入任务。恢复时按来源身份读已有任务。不能用 offset 不确定去推断 MySQL 已回滚或已提交 |

06-04-10 第 7 节写「只写不提交 offset 会让该分区停住」。06-04-26 第 7.1 节已经分开这两件事。本调查以 06-04-26 为准，不改 06-04-10。台账 IR-03 的风险列仍写「若一直不提交，分区会停住」，与第 7.1 节不一致。本轮不改台账。

## 7. MySQL 与 Kafka 跨系统事务边界

MySQL 与 Kafka 不是一个本地事务。06-04-09 第 3.4 节已经写明 `COMMIT` 不包含 offset。不得声称两者可以原子完成。至少一次投递不能推出不会重复建任务。

任务创建的 MySQL 状态沿用 06-04-19，不合并：

| MySQL 状态 | 依据 | offset | 能否再 INSERT |
| --- | --- | --- | --- |
| `INSERT` 前失败，事务未开始或已确认回滚 | 没有本次权威行 | 不提交 | 可以按 A 类整次重做。当前来源因没有身份，这一步仍不执行 |
| `INSERT` 已执行，事务尚未提交 | 未提交写入不是恢复依据。06-04-11 第 5.2 节对领取有同一句，创建侧同样不能把未提交行当成功 | 不提交 | 原事务还在时不另起插入 |
| `COMMIT` 尚未发送时连接断开 | 06-04-19 第 6.5 节五种子场景。不是第 6.3 节 | 不提交。后续 offset 不得越过本条 | 新连接只加锁读。确认缺行也不重新插入。普通查询看到缺行不能推断原事务已回滚 |
| `COMMIT` 已发送，客户端没收到结果 | 06-04-19 第 6.3 节 | 不提交。恢复期间不得越过本条 | 不再插入。另一条连接加锁读。读失败、不完整或不能归类时保持不确定 |
| 唯一冲突已返回，胜出行没读完 | 第 6.4 节。不是提交不确定 | 不提交 | 不插入，不更新。确认缺行仍待决策 |
| `COMMIT` 已确认成功 | 条件 A 的 MySQL 部分成立 | 还要原文可再读，并且分区连续位置允许，才可以提交 | 重复投递读回原任务，不新建 |
| offset 提交失败 | 06-04-09 第 5 节 | 位置不前进 | 有身份则回到原任务 |
| offset 提交结果不确定 | 本轮推导。没有 Kafka 实验 | 不把更大的位置提交出去 | 不按「offset 未提交」推断 MySQL 已回滚，也不再插入一条权威任务 |

读取不完整或无法分类时保持不确定：不写入、不抢占执行权、不提交 offset。Kafka 的未提交位置不能当作 MySQL 恢复依据。

06-04-09 第 3.4 节的四步顺序仍然有效，但不够：06-04-26 还要求原文可再读，以及不得越过同一分区更早的未完成消息。以后若统一文档，以 06-04-26 第 7.4 节补上这两点。本轮不改 06-04-09。

## 8. Worker 执行权与 Pipeline 写入围栏

06-04-11 第 6 节已写：Kafka 分区再分配不是执行权接管。Kafka 消费不扫描租约，不改变代次。第 7 节把 offset 放在事务外，并且写明它不能代表执行权。

因此：

- 接入完成只表示，在身份已声明且事务已确认时，存在一条 `PENDING`、代次 0 的任务，或者重复投递回到了原任务。
- 任务创建不表示 Worker 已领取。0 不是执行权。
- `CURRENT` 只由领取事务维护。Consumer 不写这一列。
- `executionGeneration` 只按 06-04-11 第 5 节递增。Consumer 不增代次。
- Pipeline 写入必须同时满足：锁任务行、代次匹配、该尝试为 `CURRENT`、`status` 为 `RUNNING`、有效阻断为空，并且锁保持到事务结束。
- 重复投递走 Create-or-Get，不绕过它去跑 Pipeline。
- 消息重放不能恢复或覆盖旧 Worker 的执行权。旧代次再写时，锁上的代次已经变化就整笔回滚。见 06-04-09 第 5 节「新代次提交后旧代次写领域结果」，该行未执行。

| 竞态 | 设计要求 | 验证 |
| --- | --- | --- |
| 两个 Consumer 并发处理同一已声明事件 | 一个 `INSERT` 成功，另一个读胜出行。不覆盖权威引用。谁持有分区不影响任务行数 | 未执行。物理唯一约束未建 |
| 同一事件出现在两个分区 | 仍是一个任务。两个分区各自的 offset 单独判断 | 未执行 |
| 任务已创建，Worker 尚未领取 | 代次保持 0。Consumer 的 rebalance 不领取它 | 未执行 |
| Worker 已领取，Consumer rebalance | 执行权仍看已提交代次和 `CURRENT`。分区换持有者只影响再次投递从哪里读 | 未执行 |
| 执行期间消息再次到达 | Create-or-Get 返回原任务。不新开尝试，不替换权威输入 | 未执行 |
| 执行失败后消息再次到达 | 不把再次投递当成新的执行权。是否进入 `RETRY_WAITING` 仍是 IR-08，不由 Consumer 改写 | 未执行 |
| 旧 Worker 失去执行权后写入 | 条件更新匹配不到就回滚。不得用消费组归属代替代次 | 未执行 |

## 9. 隔离路径的可执行性判断

06-04-26 第 7.4 节条件 B 要求：不建自动处理任务；原文和接入上下文进入已确认、可再读的隔离记录；恢复责任和读取路径已经设计。隔离记录不是任务，也不生成 `replayRequestId`。

IR-15 在台账中仍是待决策、P2。介质、保留策略和负责人都未选。因此：

- 条件 B 只是设计候选。
- IR-15 未决前，不能写成已经可执行。
- 不为了让 Consumer 继续跑而建临时隔离表、Inbox、Outbox、DLQ 或 Redis 锁。
- 条件 A 不成立且条件 B 又不可执行时，保持该分区的安全边界：不建自动任务，不提交越过未完成消息的 offset。其他分区不受这一分区暂停的影响。

06-04-09 第 3.4 节已说明，有稳定身份时任务行就是幂等记录，不另引入 Inbox。当前四个来源还没有这份身份，所以也不能用 Inbox 代替。

## 12. 已确认设计规则

下列规则来自已有文档，本轮只收口，不另立一套：

1. 无契约声明的稳定事件身份，不自动建任务。06-04-26 第 6、11 节。
2. 未提交某一条 offset 不会让 Kafka 停住该分区。已提交位置不得越过未完成消息。06-04-26 第 7.1、7.2 节。
3. MySQL 与 Kafka 没有跨系统本地事务。06-04-09 第 3.4 节。
4. `COMMIT` 已发送但结果不明、`COMMIT` 未发送即断连、唯一冲突后胜出读取未完成，三者分开。不确定时不插入、不提交 offset。06-04-19 第 6.3 至 6.5 节。
5. 消费组持有分区不是 Task 执行权。06-04-11 第 6、7 节。
6. 客户端版本仍是 BOM 中的 3.9.2 与 3.3.16，并且不在类路径上。Broker 4.1.2 是用户确认的外部环境。ADR-0001。

下列是本轮推导，不是 ADR：

- Consumer 不调用 Pipeline，不写 TaskAttempt，不写业务表。
- 接入装配放在 `app-worker`，Kafka 类型留在 `platform-messaging`。
- 多分区可以并行，单分区必须按连续前缀提交。
- 条件 B 在 IR-15 决定之前不可执行。

## 15. 结论与 IR-09 状态建议

建议保持台账中的「设计已明确 / 待验证」、P1，不关闭，也不改成已验证。

本调查确定的是职责和验收预期：Consumer 只处理投递和连续 offset；任务创建与执行权分开；没有稳定身份或事务结果不确定时，不提交越过未完成消息的位置；隔离路径受 IR-15 阻塞。这些预期都没有运行证据。

关闭 IR-09 至少还要同时满足：IR-02 的创建与恢复实验有执行记录；至少一个来源的稳定事件身份有契约，或明确该来源不进入自动消费；客户端按 BOM 版本进入 `platform-messaging` 之后，第 11 节矩阵有未改预期的执行记录；IR-15 若要启用条件 B，介质和恢复责任已经决定。当前都不满足。

不因此关闭 IR-02、IR-03、IR-07 或 IR-15。不把协议兼容写成消费验证通过。
