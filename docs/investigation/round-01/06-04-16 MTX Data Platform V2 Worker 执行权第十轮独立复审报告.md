## 3. G-01

文档审查通过。第 5.1 节第 6 步要求预期新代次只用不会静默回绕的精确整数，禁止用固定宽度整数做加法后再比较。Java 的 64 位有符号整数被明确写成不够。JDBC 读回值必须无损转换成同一个精确整数，截断、强制转换或降低精度造成的相等算失败并回滚。

比较写在插入之前。比较失败则回滚，第 7 步的 `INSERT` 不会执行。因此按文字顺序，不存在先留下 `CURRENT`、后发现溢出的已提交路径。回滚后已提交代次不变，写在同节的验收表里。该表标明未执行。

三种列类型只比较范围：有符号 `BIGINT` 的上限是 2^63-1，`BIGINT UNSIGNED` 的上限是 2^64-1，小数位为 0 的 `DECIMAL` 的精度未定。没有任何一种被接受。列类型未选定之前，文档写明不能执行「超出列范围」这一支。所以「最大值再加一必回滚」是选定列类型之后的规则，现在没有最大值可验。

未来 Java 实现的无损契约已经写明：精确整数加法不得回绕，JDBC 转换不得丢精度，64 位有符号整数不是已接受表示。这仍是设计要求，没有实现，也没有在 8.0.46 上核对驱动返回类型。

种类：文档规则完整。数据库语义待验证。并发测试未执行。代码未验收。

## 4. G-02

文档审查通过。第 5.2 节把恢复读取写成另一条连接上的新事务。原连接只能废弃或回滚，其返回值不能证明提交结果。恢复事务对任务行 `SELECT ... FOR UPDATE`，原事务仍持锁时必须等待，不得用普通一致性读的旧快照认定失败。拿到任务行锁后，同一事务再对尝试行加锁读。恢复事务不插入、不加代次、不恢复 `CURRENT`、不新建 `taskId`，自身也不调用 Pipeline。

第 7 节仍要求正常 Pipeline 的第一笔权威写入在同一事务里锁定任务行，并同时满足当前代次、`CURRENT`、`RUNNING` 和有效阻断为空。阻断收敛使用第 8 节自己的条件，不沿用内存代次。因此端口结果不是一张可以绕过围栏的长期凭证。

| 时序 | 文档结果 | 允许 Pipeline | 允许重做完整领取 | 允许把本次读取当成执行权 |
| --- | --- | --- | --- | --- |
| A. 原事务尚未 `COMMIT`，恢复事务开始 | 停在任务行锁等待。不用旧快照 | 否 | 否，直到锁释放后确认没有新代次 | 否 |
| B. 原事务最终 `COMMIT`，等待后读到 | 代次为预期新值，尝试为 `OPEN` / `CURRENT` | 只有这次锁定读确认之后，并仍受第 7 节或第 8 节约束 | 否 | 否。依据是锁定读到的已提交行 |
| C. 原事务最终 `ROLLBACK`，等待后读到 | 代次仍是旧值，没有本次新尝试 | 否 | 是。恢复事务结束之后另开第 5.1 节 | 否 |
| D. 恢复事务结束并释放锁之后，另一 Worker 取得更高代次 | 第 5.2 节的 F 行覆盖的是等待期间。结束后的竞态靠第 7 节：下一笔权威写入加锁时代次已变，整笔回滚 | 该旧代次的写入否 | 原调用方否 | 否 |
| E. 恢复事务锁等待超时 | 领取结果不确定 | 否 | 否 | 否 |
| F. 任务行读到，尝试行读取失败 | 归类表的「读回失败」为不确定。见 H-02 | 否 | 否 | 否 |

这些都是文档推演。没有并发实验。

## 5. G-03

文档审查不通过。计数语句已经写出，回滚规则也写出了，但它对锁范围的断言超过了 8.0 手册能够支持的范围。

语句是：

```sql
SELECT COUNT(*)
FROM task_attempt
WHERE task_id = :taskId
  AND ownership = 'CURRENT'
FOR UPDATE;
```

手册能确定的部分：

- `SELECT ... FOR UPDATE` 是加锁读。17.7.2.4 写明：对搜索遇到的索引记录，锁住这些行及相应索引项，效果与对这些行发出 `UPDATE` 相同。锁在事务提交或回滚时释放。普通一致性读忽略这些锁。语句必须处在显式事务中。
- 17.7.3 写明：加锁读锁的是扫描到的索引记录，不是引擎记住的那句 `WHERE`。没有合适索引而必须全表扫描时，每一行都会被锁住，并挡住其他会话向该表插入。唯一索引上的唯一查找只锁找到的记录，不锁间隙。其他查找和非唯一索引锁住扫描到的索引范围，用间隙锁或 next-key lock 挡住范围内的插入。
- 17.7.2.1 写明：InnoDB 默认隔离级别是 `REPEATABLE READ`。可重复读下，非唯一查找锁范围并含间隙。`READ COMMITTED` 下，加锁读只锁索引记录，不锁记录前的间隙，因此允许在已锁记录旁插入新行。该段对 `UPDATE`/`DELETE` 还写了不匹配行可以释放锁，以及 semi-consistent read。这两句的主语是 `UPDATE` 或 `DELETE`，不是 `SELECT ... FOR UPDATE`。
- 17.7.3 把「结果行与源行关系丢失、因而不能提前解锁」的例子给了 `UNION`，没有给 `COUNT(*)`。

手册没有回答、本复审也不猜测的部分：

- `COUNT(*) ... FOR UPDATE` 是否因为聚合而丢失源行关系，从而不按普通 `SELECT ... FOR UPDATE` 持有行锁。
- 在没有 `task_id` 索引、只有非唯一 `task_id` 索引、或唯一索引时，这句实际锁住的记录和间隙。
- 默认可重复读与读已提交下，另一个不先锁任务行的会话能否在计数之后、提交之前插入第二条 `CURRENT`。

06-04-11 第 16 节仍写隔离级别未选。没有 DDL，因此也没有 `task_id` 索引。在这两项选定并在 8.0.46 上执行之前，不能把锁范围写成已知事实。

第 5.1 节第 10 步写「这句再锁本任务的尝试行」。这句话把锁对象说成已经等于该 `task_id` 的尝试行。手册只保证锁的是扫描到的索引范围，并且该范围依赖索引和隔离级别。这是文档断言超出了手册证据。

同一段又写：计数不是物理唯一约束，不执行本检查的事务仍可能写入第二条 `CURRENT`，IR-02 不因此关闭。这一句与手册不冲突，并且必须保留。遵守协议的其他领取要先锁任务行。本事务从第 2 步起已经持有任务行锁，所以这些领取会等待。这是任务行锁的串行，不是 `COUNT(*)` 的唯一约束。

### H-01 P2 计数语句的锁范围被写成已经确定

种类：文档规则缺陷，同时是数据库语义待验证。不是已执行的并发测试。

证据：06-04-11 第 5.1 节第 10 步及其中的 `SELECT COUNT(*) ... FOR UPDATE`。17.7.2.4、17.7.3、17.7.2.1 如上。06-04-11 第 16 节写隔离级别未选。

触发条件：把这句当成「只锁本任务尝试行，并阻止一切并发插入 `CURRENT`」。

失败时序：隔离级别若是读已提交，手册允许在已锁记录旁插入。不先取得任务行锁的写入是否被这句挡住，手册没有对聚合加锁读作出结论。若实现据此省略任务行锁，计数为 1 之后仍可能出现第二条 `CURRENT`。本复审没有在 8.0.46 上证实或否定这条插入。

影响：计数仍可作为本语句所见行数的完整性检查，失败则回滚。它不能充当物理唯一约束，也不能在索引和隔离级别未定时空谈锁范围。遵守协议的领取仍由任务行锁串行，这一条不依赖该计数。

建议：删掉「再锁本任务的尝试行」这一断言，改成待 8.0.46 实测的锁范围。在实测前，唯一性只引用尚未建成的 IR-02，串行只引用任务行锁。

验收：在 8.0.46 上分别用可重复读和读已提交、有无 `task_id` 索引，记录这句实际锁住的记录和间隙，以及不持任务行锁的插入是否被挡住。未执行。

IR：不关闭 IR-02、IR-07。

| 条件 | 手册已写的锁 | 对本句的结论 |
| --- | --- | --- |
| 默认可重复读，非唯一范围查找 | 锁扫描到的索引范围，含间隙或 next-key lock | 若优化器走这种查找，范围内的插入会被挡。本句是否走这种查找，未证实 |
| 默认可重复读，唯一索引上的唯一查找 | 只锁找到的记录，不锁间隙 | `task_id` 加 `CURRENT` 不是已设计的唯一键。不能套用这一条 |
| 读已提交，加锁读 | 只锁索引记录，不锁间隙，允许在旁边插入 | 隔离级别未选。若将来选用，间隙插入按手册是允许的。本句是否先持有那些记录锁，未证实 |
| 没有合适索引 | 全表扫描会锁住每一行，并挡住对该表的插入 | 索引未设计。不能把这当成预期锁，也不能排除它 |
| `COUNT(*)` 聚合 | 手册没有单独规定 | 待 8.0.46 实测。不推断它等价于锁住全部匹配行，也不推断它不加锁 |

## 6. G-04

文档审查通过。第 6.1 节规定一次调用只有一个结果。不能确认提交还是回滚时，只能是领取结果不确定，不能改成未领到或数据库或事务错误。扫描不得把不确定降成未领到。不确定时不调用 Pipeline，也不用内存中的 `actualGeneration`。

| 情况 | 唯一结果 | 调用 Pipeline | 使用未确认代次 |
| --- | --- | --- | --- |
| 条件更新改变 0 行，且没有进入提交结果不明 | 未领到 | 否 | 否 |
| 提交已确认，阻断为空 | 已领到并可执行正常 Pipeline | 是，随后仍受第 7 节约束 | 否 |
| 提交已确认，阻断已在 | 已领到且只做 `FAILED` 收敛 | 否。只收敛 | 否 |
| `COMMIT` 前语句失败，并且回滚已被确认 | 数据库或事务错误 | 否 | 否 |
| 死锁错误完整返回 | 数据库或事务错误。整笔回滚只引用 InnoDB 语义，未在 8.0.46 核实 | 否 | 否 |
| 锁等待之后，回滚已被确认 | 数据库或事务错误。`innodb_rollback_on_timeout` 未选，超时本身不算已回滚 | 否 | 否 |
| `COMMIT` 成功但响应丢失 | 领取结果不确定 | 否 | 否 |
| `COMMIT` 是否成功无法确认 | 领取结果不确定 | 否 | 否 |
| 事务执行中连接断开 | 领取结果不确定。即使服务器后来回滚，断开当时也不得先归为错误 | 否 | 否 |
| 恢复查询失败 | 领取结果不确定 | 否 | 否 |
| 已确认提交之后 Pipeline 失败 | 领取结果不变 | 按原有重试或阻断规则，不把扫描当成新的执行权 | 否 |

死锁与断连的分界是错误有没有完整返回。锁等待与错误的分界是回滚有没有被确认。这两条写清之后，同一个异常不再同时落入两个结果。Pipeline 失败不改已返回的已领到结果，任务代次和尝试保持已提交状态。

死锁整笔回滚尚未在 8.0.46 上执行。这是待验证项，不使互斥规则本身缺失。
