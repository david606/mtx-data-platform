## 1. MySQL 8.0 事务能力

证据来自 MySQL 8.0 参考手册。8.0.46 属于该系列。本轮不引用 8.4 手册。这些语句没有在本仓库的 8.0.46 实例上执行。

| 能力 | 手册行为 | 对本设计的含义 | 章节 |
| --- | --- | --- | --- |
| autocommit | 默认开启。不在显式事务中时，每条语句自己提交。语句执行中的错误会回滚该语句，但不能再用 `ROLLBACK` 撤销已经自动提交的语句 | 观测和匹配结果若分成两条自动提交语句，崩溃会留下没有匹配结果的观测。必须用显式事务把同一次写出包在一起 | [15.3.1](https://dev.mysql.com/doc/refman/8.0/en/commit.html) |
| `COMMIT` / `ROLLBACK` | `COMMIT` 使当前事务的修改永久化。`ROLLBACK` 取消当前事务中尚未提交的修改。事务写入二进制日志发生在 `COMMIT` | 已提交的领域结果不能靠后一次 `ROLLBACK` 撤销。Kafka offset 和 Doris 写入不在这个事务里 | 同上 |
| 语句回滚与锁 | 重复键等错误只回滚失败语句。整个事务回滚才释放该事务的全部锁。单条语句回滚后，该事务已有的锁仍然保留 | 唯一冲突后可以在同一事务里读取胜出行，然后结束事务，不能改写胜出行 | [15.3.1](https://dev.mysql.com/doc/refman/8.0/en/commit.html)，[17.21.5](https://dev.mysql.com/doc/refman/8.0/en/innodb-error-handling.html) |
| 死锁与锁等待 | 死锁回滚整个事务，应用必须重试整个事务。锁等待超时默认只回滚当前语句；`--innodb-rollback-on-timeout` 才回滚整个事务 | 该参数尚未选定。恢复代码不能假设超时一定回滚整个事务 | [17.21.5](https://dev.mysql.com/doc/refman/8.0/en/innodb-error-handling.html) |
| `SAVEPOINT` | `ROLLBACK TO SAVEPOINT` 撤销保存点之后的修改，但不结束事务，也不释放保存点之后在内存中记录的行锁 | 它只作用于当前 MySQL 事务。不能用它撤销已经提交的结果、Kafka 消息或 Doris 写入。本轮不把保存点当作跨阶段恢复机制 | [15.3.4](https://dev.mysql.com/doc/refman/8.0/en/savepoint.html) |
| 隔离级别 | InnoDB 默认 `REPEATABLE READ`。该级别下，普通一致性读使用事务内第一次读的快照。`READ COMMITTED` 下，每一次普通一致性读使用自己的新快照。加锁读看当前已提交的行。手册不建议在同一事务混用普通读和加锁读 | 隔离级别仍未选定。失败方读取胜出行沿用 06-04-08：加锁读或新事务，不用更早的普通快照 | [17.7.2.1](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html) |
| 并发插入 | 插入成功对新行加排他记录锁。唯一冲突对已有索引记录加共享锁，两个等待者可能死锁。`ON DUPLICATE KEY UPDATE` 改为更新并加排他锁 | 不可变记录仍不用更新语句。死锁后重试整次 Create-or-Get | [17.7.3](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html) |

`ROLLBACK` 是数据库回滚。补偿是另一次已定义的业务动作，例如显式重放。二者不能混用。数据库事务也不能撤销 Kafka 消费位点或 Doris 写入。

## 2. 提交原则

1. 任务创建、快照固定、契约版本固定分成三次提交。不合成一个长事务。
2. 一条观测和它的匹配结果同一次提交。MappingResult 不是第二份权威记录。
3. 版本固定记录先提交。`NormalizedAmount` 另一次提交。先后关系不自动变成一个长事务。
4. 每个字段的结果独立提交。一个字段失败不删除其他字段已经提交的观测或标准化结果。
5. 任务生命周期只有 Pipeline 第 11 节那一个 `status`，不另设终态列。存在当前尝试时，终态单独提交，并在同一事务里结束这条尝试：`status`、该尝试的执行结果、执行权从 `CURRENT` 改为 `RELEASED` 一起提交或一起回滚。新的 `TaskAttempt` 不更新已经提交的 `status`。领取与当次尝试插入是另一个短事务，见下文第 8 节。`PENDING` 或 `RETRY_WAITING` 上的取消没有当前尝试，只把 `status` 改成 `CANCELLED`，不插入尝试，见第 3.3 节。下文“终态为空”是指 `status` 仍是 `PENDING`、`RUNNING` 或 `RETRY_WAITING`。
6. 有效阻断的登记和终态落库是两次提交，条件不同。登记只在 `status` 为 `RUNNING`、当前尝试为 `CURRENT` 且尚无有效阻断时写入阻断，`status` 保持 `RUNNING`。把 `status` 改成 `FAILED` 的更新要求该阻断已经记下，不再要求阻断为空。两次之间崩溃时，`status` 仍是 `RUNNING` 且阻断已在，结果只能是 `FAILED`。成功类终态才要求尚无有效阻断。迟到审计和完整性审计另一次提交，不改 `status`。进程内先读后写不是仲裁。具体条件见 [06-04-11](06-04-11%20MTX%20Data%20Platform%20V2%20Worker%20Task%20Ownership%20与并发执行控制专项设计.md)。
7. Kafka offset 与 Doris 写入都在 MySQL 事务之外。
8. 已提交的不可变内容只通过 06-04-08 的 Create-or-Get 复用。响应丢失时重试读取，不覆盖。
9. 不使用 JVM 本地锁作为跨 Worker 边界。
10. 不把整条 Pipeline 放进一个事务，也不把尚未执行的故障场景写成测试通过。

`RETRY_WAITING` 不是终态。哪些字段级失败可以进入它仍是 IR-08，本轮不选择。进入该状态的提交只改任务执行状态，不删除领域结果。

## 3. 分阶段边界

### 3.1 任务创建

来源已经声明稳定事件身份时，第一次提交只包含逻辑任务、权威 `rawPayloadRef` 和权威 `receivedAt`。显式重放则在同一次提交中写入新 `taskId` 和调用方的 `replayRequestId`。这样不会出现有重放任务却没有重放标识，或相反。

重复投递走 Create-or-Get。冲突后读取胜出行，不替换权威引用和权威 `receivedAt`，也不创建 `replayRequestId`。没有稳定事件身份的来源仍不能做这次幂等，见 IR-03。

`TaskAttempt` 不单独提交。它和任务领取、旧尝试被取代写在同一个短事务里，不修改已经提交的终态，也不清除已经登记的有效阻断。终态已经提交时，这个事务的条件不再成立。执行代次和租约的规则以 06-04-11 为准：创建任务时把代次写成 0，0 不是执行权；成功的领取把这个整数加一，首次领取得到 1。该列不得为 NULL，加一不得回绕。第一轮稿曾把尝试写成下一次独立提交，第 8 节说明为何收回。

快照固定是再下一次提交。身份是 `taskId` 加已经提交的不可变输入，内容是胜出 `snapshotId` 和 `parserVersion`。临时读取失败不提交新快照，按原任务重试。确定性校验失败停止该任务，不改读另一份快照。快照一旦提交，重试只读这一份。

契约版本是快照提交之后的另一次提交。只在已提交的 `snapshotId` 内解析。恰好一个且哈希相符才写入权威 `contractVersionId` 和 `contractBodySha256`。零个或多个是 `CONTRACT_VERSION_UNRESOLVED`，不写入权威版本，不产生字段结果，不降成 `UNMAPPED`。身份不一致和哈希不符同样不写入权威版本。临时读取没有得出候选数量时，不提交失败结论，仍用原任务和原快照重试。

### 3.2 字段、观测和标准化

字段结果按 `taskId + contractVersionId + fieldPath` 单独 Create-or-Get。失败字段不写 `ObservedAmount`。

尚无观测时，提取和匹配在事务外完成。同一次显式事务先对任务行做 `SELECT ... FOR UPDATE`，条件是当前执行代次、该代次尝试为 `CURRENT`、`status` 为 `RUNNING`、有效阻断为空，再写入该观测身份的观测内容和匹配结果。已有阻断时这次加锁失败，不得把收敛尝试写成正常提取。事务提交前，库里没有这条权威观测。提交后，二者同时可见。提交失败则整笔回滚，不留下没有匹配结果的观测。事务开始前单独读出的代次不能代替这次加锁。已有观测的恢复只按权威引用查询，不读正文，不重新解析，不重新匹配。字段结果、版本固定记录和 `NormalizedAmount` 各自的短事务使用同一锁条件。写前查询不是围栏。

一个字段的观测提交后，其他字段失败只影响那些字段自己的结果和后来的终态。不删除、不覆盖已提交观测。

标准化门禁失败不写版本固定记录，也不写 `NormalizedAmount`，观测保持原样。门禁通过后，版本固定记录单独提交。只有 `CREATED` 或 `ALREADY_EXISTS` 返回的版本才能用于下一次提交中的 `NormalizedAmount`。两次提交之间崩溃时，重试读取已固定版本，不改用新发布的规则。相同 `normalizationIdentity` 但内容不同是完整性异常，不覆盖。

Pipeline 写明不转换时 `conversionRuleVersion` 在逻辑上为空，并写明不能假设复合唯一索引已经处理空值。06-04-08 又写明唯一索引允许多个 NULL。本轮不把空版本改成某个哨兵值。该档结果的物理唯一性仍挂在 IR-02 和 IR-14，不影响“先固定、后写出”这两次提交的顺序。

当前没有已发布计算规则，不写计算结果，也不为它单设事务。将来若成为 Pipeline 权威写入，围栏与正常阶段相同：当前代次、该代次尝试为 `CURRENT`、`status` 为 `RUNNING`、有效阻断为空，并且在同一显式事务内持有任务行锁直到提交。现在不写这一行。

### 3.3 终态与审计

终态提交读取已经提交的字段结果、有效阻断和步骤状态。它使用任务行上的条件更新，使四个互斥终态只提交一次。同一事务更新当前代次那条尝试的执行结果，并把执行权改为 `RELEASED`。任一步失败则整笔回滚，不允许终态已落库而尝试仍是 `CURRENT`。`SUCCESS`、`PARTIAL_SUCCESS`、`ALL_FIELDS_FAILED`、`FAILED` 的计算规则仍以 Pipeline 第 11 节为准。`UNMAPPED` 和 `CONFLICT` 仍算字段成功。成功类终态把尝试结果写成 `SUCCEEDED`。`FAILED` 把尝试结果写成 `FAILED`。崩溃后仍是 `OPEN` 的尝试不写成这两种结果，只能等接管时写成 `INTERRUPTED`。

有效阻断的登记先于 `FAILED` 落库，但两句条件更新不是同一谓词。登记成功只表示任务行记下了有效阻断，`status` 仍是 `RUNNING`。随后的更新把 `status` 改成 `FAILED`，条件是 `status` 仍是 `RUNNING` 且有效阻断已经是这一条。因此阻断获胜之后，终态更新仍然匹配得到这一行。成功、部分成功和全部字段失败则要求有效阻断仍为空，并把 `status` 从 `RUNNING` 改成对应值。终态先提交时，后来的阻断登记匹配不到行，只新增迟到审计。阻断已登记而 `status` 尚未离开 `RUNNING` 时，不重做字段处理，直接按该阻断提交 `FAILED`。其他 Worker 用“`status` 为 `RUNNING` 且有效阻断非空”识别这种任务。第二条不同阻断身份在终态前不成为第二条有效阻断，拒绝审计单独提交。

没有任何一类审计必须和观测、标准化结果或终态放进同一个 MySQL 事务。有效阻断是参与终态的业务记录，不是审计。迟到审计、拒绝审计和完整性审计都独立提交。终态尚未提交时的依据不一致不写终态、不写有效阻断，也不写终态后的完整性审计。审计提交失败不回滚已经提交的观测、标准化结果或终态。普通应用日志不是这些审计行。审计身份仍是 Pipeline 第 11.1 节已有顺序，不新增错误码。

`CANCELLED` 已在状态表中。取消锁任务行，条件是终态仍为空且有效阻断仍为空。它不要求调用方持有执行代次，也不依赖 Worker 进程仍在运行。锁住之后按有没有当前尝试分开。`RUNNING` 且已有 `OPEN` / `CURRENT` 时，同一事务把这条尝试写成 `CANCELLED` 和 `RELEASED`，一步失败则整笔回滚。`PENDING` 还没有尝试，`RETRY_WAITING` 的上一条已经是 `FAILED` / `RELEASED`，这两种只更新任务终态，不插入尝试，也不改写历史行。有效阻断已经登记时匹配不到行，不写成 `CANCELLED`，终态仍由收敛路径提交 `FAILED`。两个取消、取消与领取、取消与领域写入、取消与阻断登记都锁同一任务行，胜出结果由条件更新决定。谁有权发起取消尚未定义。无论何种终态，提交后都不删除已提交领域结果。细节与 06-04-11 第 9 节相同。

### 3.4 Kafka

仓库没有 Kafka 客户端，也没有消费位点配置。MySQL `COMMIT` 不包含 offset。offset 提交也不包含 MySQL。

候选顺序是至少一次投递，而不是跨系统原子事务：

1. 先提交第 3.1 节的任务 Create-or-Get。
2. 此后才允许提交该消息的 offset。
3. offset 提交失败时，重复消息再次进入同一次 Create-or-Get，返回原任务。
4. 不允许在 MySQL 任务提交成功之前提交 offset。那样会在 MySQL 失败后丢掉唯一的重试入口。

没有稳定事件身份时，第 1 步还不存在。这类来源不能把 offset 提交写成已经安全。这仍是 IR-03。

Inbox 会把“消息已经处理”再存一份。来源契约已经声明稳定事件身份时，任务行就是这个幂等记录，不必再引入 Inbox 表或模块。Kafka 记录键是否等于该稳定身份，仓库没有证据，所以本轮不引入 Inbox。

Outbox 会把“待发送的下游动作”和权威写入放进同一次 MySQL 提交。当前权威是 MySQL 里的领域结果，Doris 是提交之后的副本。在 IR-17 仍禁止把 `WriterExecutionRecord` 当作已有实体时，本轮不新增 Outbox 表，也不把它写成已选择的实现。

### 3.5 Doris

Doris 4.0.7 只接收 MySQL 已经提交的不可变副本。复制在 MySQL 事务提交之后开始。写入失败、超时或没有收到响应，都不对 MySQL 执行 `ROLLBACK`。已经提交的事务也无法被这次失败回滚。

没有响应时，恢复入口是按 MySQL 权威结果再次复制。Doris 表模型和幂等协议都未设计，不能假设某次成功写入可以被客户端确认。暂时不可用时保留 MySQL 结果，稍后补写。对账以 MySQL 为准发现缺副本，不用 Doris 改 MySQL。

不持久化 `WriterExecutionRecord`。补写任务若以后需要记录，留给 IR-17，不在本轮造出该实体。

## 4. 事务边界总表

“需要事务”指需要一次显式 InnoDB 事务。默认 autocommit 只适合单语句且该语句本身就是完整权威写入的操作。下表的显式事务在 `COMMIT` 前对其他会话不可见。

| 阶段 | 操作 | 所属存储 | 是否需要事务 | 事务范围 | 提交成功后的权威状态 | 失败恢复方式 | 依赖事项 |
| --- | --- | --- | --- | --- | --- | --- | --- |

## 5. 故障注入矩阵

验证方式都是尚未执行的设计检查。本表不表示测试已经通过。

| 故障场景 | 已提交的数据 | 未提交的数据 | 重试入口 | 是否允许覆盖 | 预期最终状态 | 验证方式 |
| --- | --- | --- | --- | --- | --- | --- |
| `INSERT` 成功但响应丢失 | 该语句所属事务若已 `COMMIT`，胜出行已在 | 客户端尚未看到返回 | 同一 Create-or-Get | 否 | `ALREADY_EXISTS`，内容相同则复用 | 重试后仍只有一行，内容与首次写入相同 |
| 唯一键冲突 | 胜出事务已提交的那一行 | 失败语句已回滚 | 加锁读取胜出行 | 否 | 内容相同为已存在；不同为完整性异常 | 失败方不发 `UPDATE` |
| 两个 Worker 并发写入 | 先提交的一行 | 后一个插入语句 | 失败方读取胜出行 | 否 | 只留一行权威结果 | 两个返回值指向同一持久化内容 |
| 数据库死锁 | 死锁前其他事务已提交的行 | 被回滚的整个事务 | 从该次事务的第一条语句重做 | 否 | 重做后仍遵守 Create-or-Get | 不在已回滚事务里继续写 |
| 锁等待超时 | 已提交的胜出或无关行 | 默认只回滚超时语句。整事务是否回滚取决于尚未选定的服务器参数 | 先确认当前事务是否还在，再重试该语句或整个事务 | 否 | 不把超时变成覆盖 | 参数未定时两种恢复都要有明确分支 |
| MySQL 提交成功后进程崩溃 | 已 `COMMIT` 的任务、观测、版本或终态 | 崩溃点之后尚未开始的事务 | 从最后一条已提交记录继续，而不是从报文重头覆盖 | 否 | 已提交领域结果保持 | 重启后读取权威行再决定下一步 |

| Kafka offset 提交失败 | 已经提交的任务 Create-or-Get | offset 仍未前进 | 消息再次投递，进入原任务 | 否 | 不新建任务，不替换权威引用 | 仅当稳定事件身份已存在 |

| Doris 写入成功但响应丢失 | MySQL 权威结果。Doris 侧是否真有副本不能由丢失的响应证明 | 客户端没有成功回执 | 按 MySQL 结果再次复制 | 否，不改 MySQL | MySQL 保持。副本最终可补齐 | 对账以 MySQL 为源 |
| Doris 写入失败 | MySQL 权威结果 | Doris 副本 | 稍后按 MySQL 补写 | 否 | MySQL 不回滚 | 失败日志不是权威删除 |
| 审计写入失败 | 已提交的业务结果和终态 | 这一条审计 | 只用同一审计身份重试审计 | 否 | 终态不变。审计最终一条或不留下冲突的第二份 | 不因为审计失败重开任务 |

| 观测成功但标准化失败 | 观测和匹配结果 | 版本固定或标准化结果 | 从门禁或版本固定继续 | 否 | 观测保留。`UNMAPPED` 和 `CONFLICT` 本来就没有标准化结果 | 不删除观测，不重新匹配 |

不是每种故障都从原始报文重新执行。已经提交的观测、版本和终态都有自己的读取入口。

## 8. 与 06-04-11 的分工

06-04-09 维持事务边界和失败后的读取入口。06-04-11 维持执行代次、租约和尝试生命周期。两边使用同一组提交点。

第二轮相对第一轮稿的调整：

| 第一轮写法 | 第二轮写法 | 原因 |
| --- | --- | --- |
| 尝试单独提交 | 领取、插入尝试、取代旧尝试同一事务 | 分开提交会留下有执行权无尝试，或有尝试无执行权 |
| 终态和阻断都要求有效阻断为空 | 只有登记和成功类终态要求阻断为空。`FAILED` 要求阻断已经存在 | 否则阻断获胜后终态永远匹配不到行 |
| 领域写入不检查执行代次 | 每个权威写入事务内对任务行 `SELECT ... FOR UPDATE` | 事务外先读代次挡不住领取插进来 |

已经列出的故障场景都保留。第二轮新增的两行仍在。第三轮再补一条：终态事务提交后响应丢失时，重读终态和当前尝试。终态已写入且执行权已是 `RELEASED`，就按已提交处理，不新建尝试，也不把尝试留在 `CURRENT`。观测与匹配仍是一次提交。快照固定和契约版本固定同样先锁当前代次，并且有效阻断已存在时不得执行。Kafka 与 Doris 仍不进入 MySQL 事务。ADR-0004 的确定性失败仍不换快照。

第四轮只补对齐，不改上面三行的分工。正常 Pipeline 的快照、契约、字段结果、观测与匹配、版本固定和 `NormalizedAmount` 都在事务内要求当前代次、`status` 为 `RUNNING`、该代次尝试为 `CURRENT`、有效阻断为空。将来的计算结果沿用同一围栏，当前仍不写。取消在 `PENDING` 和 `RETRY_WAITING` 上只提交任务终态；运行中的取消才在同一事务释放当前尝试。`CURRENT` 仍是尝试行上的独立值，不能只凭代次相等认定。

第五轮不再使用单独的终态列。任务是否已经终态，只看 `status` 是不是五个终态值之一。正常 Pipeline 写入在第四轮条件上再要求该代次尝试为 `CURRENT`，并且 `status` 为 `RUNNING`。取消把 `status` 改成 `CANCELLED`，不另写一列。

第六轮不改提交点。Pipeline 第 11 节补上 `PENDING` 和 `RETRY_WAITING` 到 `CANCELLED`，条件与本文第 3.3 节相同。IR-09 的依赖列为 IR-01（已满足）、IR-02（未满足）、IR-03（未满足）和 IR-07（设计已明确、待验证）。没有单独的消费位点 IR。

第七轮不增加第三套阻断或终态条件。本文第 3.3 节和第 4 节与 06-04-11 第 8 节仍是同一协议。06-04-10 第 11.1 节里「不选择锁」的句子改为历史风险，并指向这一协议。创建任务的代次初值改为 0，领取在同一事务内加一。到期后的领取调用链写在 06-04-11 第 6.1 节。Pipeline 第 11 节的取消和阻断收敛没有另一套仲裁。这些仍不是 MySQL 并发验证。

第八轮不改阻断条件和取消条件。领取行改为先保存领取前状态，更新后读回实际代次，新尝试只写读回值。响应丢失的完整判定在 06-04-11 第 5.2 节。扫描批次里一个任务失败不撤销其他任务已经提交的领取。列类型和 `sql_mode` 仍未选，溢出行为仍未在 8.0.46 上执行。
