## 2. 当前已确认规则

- presence 只有七种。不增加第八种。
- `ABSENT` 是路径没有节点。`PRESENT_NULL` 是节点存在且值为 JSON null。二者不同。
- `EMPTY_STRING` 的字面量是空字符串。它不是缺失，也不是 null。
- `OTHER_TEXT` 的原文是“其他字符串”，例子是带单位的句子、空格数字、多个数字拼在一起。
- `NON_SCALAR` 的原文是数组或对象。不取第一项，不加总。出现在标量路径上时字段码是 `TYPE_MISMATCH`，不形成正常观测。
- `0`、`0.0`、`"0"`、`"0.00"` 都是 `NUMERIC_ZERO`，token 各自保留。空 `Money` 不是 0。
- 06-03-03-02 的字符串例子把 `rawText` 写成 `18.50`，JSON 引号不在 `rawText` 里。
- 提取不建 `Money`。标准化不改 `rawText`，失败不把观测改成 0。
- `UNMAPPED` 和 `CONFLICT` 保留观测，不进入标准化。ADR-0004 的契约版本失败不写观测，不降成 `UNMAPPED`。
- `PRESERVE_SOURCE`：不取绝对值，不丢负号，不把负数改成 0，也不因类型是退款就改成负数。
- 观测身份是 `rawPayloadRef + snapshotId + contractVersionId + fieldPath`。不含 `parserVersion`，也不含节点种类。标准化身份再加两个规则版本。没有发现节点种类与这四段冲突，因此不改身份。
- 已有观测的重试返回原观测，不重新解析覆盖字面量。
- 三个版本不合并。`normalizationRuleVersion` 尚未分配。没有封存的 `conversionRuleVersion`。

## 3. 四项决策的方案比较

### 3.1 JSON 节点种类和路径状态

【待确认】06-03-01 把 `NUMERIC_TEXT` 写成字符串。06-03-03-01 把非零 JSON 数字和整个十进制字符串都标成 `NUMERIC_TEXT`。提取表没有布尔值这一行。

节点种类和 presence 是两个维度。路径不存在不是节点。

| JSON 节点种类 | 含义 | 与 presence 的关系 |
| --- | --- | --- |
| `NUMBER` | JSON 数字节点 | 普通十进制可对应 `NUMERIC_ZERO` 或 `NUMERIC_TEXT`。指数数字见第 3.2 节，不能靠门禁倒推 presence |
| `STRING` | JSON 字符串节点 | 空字符串是 `EMPTY_STRING`。无符号十进制字符串可对应 `NUMERIC_ZERO` 或 `NUMERIC_TEXT`。其他字符串是 `OTHER_TEXT` |
| `NULL` | JSON null 节点 | presence 是 `PRESENT_NULL`。不是 `ABSENT` |
| `BOOLEAN` | JSON `true` 或 `false` | 提取表没有对应 presence。不是字符串，所以不是 `OTHER_TEXT`。不是数组或对象，所以不是 `NON_SCALAR` |
| `ARRAY` | JSON 数组 | presence 是 `NON_SCALAR`。`NON_SCALAR` 不区分数组和对象，所以节点种类仍然要单独记 |
| `OBJECT` | JSON 对象 | 同上，presence 是 `NON_SCALAR` |

`ABSENT` 只表示声明路径上没有节点。它没有上表中的任何一种节点种类。字段结果可以记下“路径不存在”，但不能把 `ABSENT` 写成第六或第七种 JSON 种类。

| 问题 | 方案 A：只保留 presence 和 rawText | 方案 B：七种 presence 不变，另记上表六种节点种类 |
| --- | --- | --- |
| `12` 与 `"12"` | presence 可相同，`rawText` 都是 `12`。节点差别丢失 | presence 仍可相同。种类分别是 `NUMBER` 和 `STRING` |
| `12.0` 与 `"12.0"` | 标度都可以是 1，节点差别丢失 | 标度规则不变，种类分开 |
| `0`、`0.0`、`"0"`、`"0.00"` | 【设计决定】都是 `NUMERIC_ZERO`，token 不合并 | 同样保留 token。`NUMBER` 与 `STRING` 再分开 |
| null 与缺失 | presence 已能分开 `PRESENT_NULL` 和 `ABSENT` | `NULL` 只用于真实 null 节点。缺失没有节点种类 |
| 空字符串 | presence 已是 `EMPTY_STRING` | 种类是 `STRING`，presence 仍是 `EMPTY_STRING` |
| `true`、`false` | 七种 presence 对不上 | 种类是 `BOOLEAN`。presence 仍无准确值，见下文 |
| 数组、对象 | 都是 `NON_SCALAR`，种类丢失 | 种类分开，presence 仍都是 `NON_SCALAR` |
| JSON 引号 | 【设计决定】现有例子不把引号放进 `rawText` | 引号仍不进入 `rawText` |
| 放在哪里 | 只有 presence 和 `rawText` | `RawAmountValue` 在提取时记下种类。字段码为 `OK` 并形成观测时，`ObservedAmount` 抄下同一不可变事实。不单独落库的提取对象结束之后，标准化只能读观测 |
| 观测身份 | 不加入四段身份 | 同样不加入。未发现与现有身份规则的冲突 |
| 历史数据 | 没有生产观测。按 A 写下之后不能从 `rawText` 恢复种类 | 从形成观测时就带上种类。不回填，也不重读报文 |
| Java | 成功解析无法知道节点是数字还是字符串 | 成功路径的事实输入必须带种类。拒绝路径可以不依赖种类，见第 7 节 |

布尔值的缺口：不增加 presence、也不把 `BOOLEAN` 塞进 `OTHER_TEXT` 或 `NON_SCALAR` 时，字段结果无法给出一个既有 presence。这不是方案 B 能单独关闭的。确认前不把 `true` 或 `false` 写成某种 presence。

【审查建议】推荐方案 B。`RawAmountValue` 保存提取时的节点种类。只有形成观测的路径，才把种类抄入 `ObservedAmount`。成功标准化读取的事实必须包含这个种类。种类不进入观测身份，也不进入标准化身份。`ABSENT` 不是节点种类。确认前不实现。

需要确认的问题：`12` 与 `"12"`、`12.0` 与 `"12.0"` 是否必须在观测上区分。若回答否，方案 A 就够用，字符串许可也无法按节点执行。布尔值的 presence 仍要另作设计修订，本推荐不代选。

### 3.2 科学计数法与 OTHER_TEXT

【已确认事实】06-03-03-01 第 6 节把 `OTHER_TEXT` 定义为其他字符串，不是“其他标量”，也不是“其他 JSON 数字”。06-03-03-04 不把 `1e2` 收成 `100`，也不改 `rawText`。同一份提取表又把非零 JSON 数字都标成 `NUMERIC_TEXT`。JSON 语法允许指数，`BigDecimal` 能解析指数，两者都不等于业务允许。

五个例子都是指数：`1e2`、`1E2`、`1.0e2`、`1e+2`、`1e-2`。`e` 与 `E`、显式 `+` 与省略 `+`，是同一种写法。节点种类都是 `NUMBER`。

| 方案 | 对 OTHER_TEXT 原文的影响 | 对 06-03-03-01 的修订 | 标准化 |
| --- | --- | --- | --- |
| 接受并定义数值和标度 | 不使用 `OTHER_TEXT` | 要把指数算进“十进制数字”，并新写标度。`1e2` 与 `1.0e2`、`1e-2` 的标度现在没有句子 | 不改 `rawText`。标度规则未写出前不能解析 |
| 拒绝且不转换成普通十进制 | 本身不指定 presence | 必须收窄“全部非零 JSON 数字”。只拒绝、不指定 presence，字段结果仍缺一个必填形态 | 不生成结果，不改 token |
| 把 JSON `NUMBER` 指数标成 `OTHER_TEXT` | 改变原义。`OTHER_TEXT` 不再只是其他字符串，而要包括非字符串的数字节点 | 第 6 节的“其他字符串”必须改成更宽的定义。只因为标准化门禁拒绝 `OTHER_TEXT`，不能推出这个归类 | 门禁会拒绝，但这是事后结果，不是分类依据 |
| 把 `OTHER_TEXT` 改成“其他标量文本” | 同样改变原义。布尔值仍不是文本，数组和对象仍是 `NON_SCALAR` | 明确修订第 6 节。指数数字可以落入新定义，布尔值仍然不行 | 同上一行，门禁拒绝不能代替定义 |
| 使用现有字段码 | 不改 `OTHER_TEXT` | 现有码只有 `TYPE_MISMATCH`、`PATH_NOT_UNIQUE`、`RAW_TEXT_UNRETAINABLE`。指数 token 可以完整保留，路径也可以唯一，它也不是数组或对象。三者都不准确 | 不形成正常观测，标准化看不到这条字面量 |

【已确认事实】在不增加 presence、不新造字段码、也不改写 `OTHER_TEXT` 原义的前提下，没有一种 presence 能准确表示“节点种类是 `NUMBER`，字面量是指数”。把它标成 `NUMERIC_TEXT` 会把指数当成十进制数字。把它标成 `OTHER_TEXT` 会把其他字符串改成也包含 JSON 数字。

职责仍分开：提取负责节点种类、presence 和 token。标准化不重新分类，不把指数收成普通十进制，也不为了得知种类而重读 JSON。

【审查建议】推荐拒绝转换成普通十进制，并且不把 JSON `NUMBER` 指数标成 `OTHER_TEXT`。节点种类记为 `NUMBER`，`rawText` 保留原 token。presence 在第 6 节修订前不代选。不推荐接受，因为会发明标度。不推荐现有字段码，因为三个码都不准确。确认前，提取表的“全部非零 JSON 数字”仍然写在设计稿里，Java 不能提前改分类。

需要确认的问题：是否修订 06-03-03-01，把 `OTHER_TEXT` 从“其他字符串”改成另一种定义。若不同意修订，指数数字的 presence 就仍然没有准确位置。本方案不代选那一格。

### 3.3 正负号

【设计决定】符号一旦进入金额值，就按 `PRESERVE_SOURCE` 保留。退款类型不因此变成负数。负优惠是否允许仍待业务确认。冲正没有已接受的 V2 符号规则，本方案不补。技术上能留下减号，不等于业务允许负金额。

| 输入 | 节点种类 | 语法 | 现有分类 | 符号 |
| --- | --- | --- | --- | --- |
| JSON 数字 `-12` | `NUMBER` | JSON 数字可以有减号 | 非零 JSON 数字行会标成 `NUMERIC_TEXT` | token 应留下 `-` |
| JSON 数字 `-0` | `NUMBER` | 语法合法，数值是 0 | “正好是 0”可能落入 `NUMERIC_ZERO`。稿件没有 `-0` | 不能改写成 `0` |
| 字符串 `"-12"`、`"-12.50"` | `STRING` | 字符串，不是 JSON 数字语法 | 06-03-03-04 第 15 节没有例子 | 若将来接受，减号留在 token |
| 字符串 `"+12"`、`"+0"`、`"+12.50"` | `STRING` | 不能作为 JSON 数字 | 正号不是已写的十进制数字。若保持 `OTHER_TEXT` 原义，这些是其他字符串 | 不能删掉 `+` |
| 字符串 `"-0"` | `STRING` | 字符串 | 没有例子 | 不能改成 `0` 或 `"0"` |

【审查建议】推荐：

- `NUMBER` 上的减号留在 token 里。`-12` 是否直接沿用非零 JSON 数字行，仍要写成设计修订后的句子，确认前不实现。
- `-0` 在确认前不写成已经是 `NUMERIC_ZERO`。
- 正号字符串在 `OTHER_TEXT` 仍只表示其他字符串时，可以讨论为其他字符串。这是字符串，不是 JSON 数字指数，所以不触犯第 3.2 节对 `NUMBER` 的限制。确认前仍不写成已批准分类。
- 减号字符串保持待确认，不归入 `NUMERIC_TEXT`。
- 不取绝对值，不丢符号，不把负数改成 0。负优惠、退款负数和冲正单独确认。

需要确认的问题：正号字符串是否就是 `OTHER_TEXT`；减号字符串是否属于数字文本；JSON 数字 `-0` 是否为 `NUMERIC_ZERO` 且 token 为 `-0`；负优惠和退款负数是否允许出现。

### 3.4 字符串数字许可的可表达性

【已确认事实】06-03-02-03 的 `amount_mapping_version` 有列 `source_data_type`，类型是 `VARCHAR(64)`，没有检查约束列出允许值。`mapping-version-v2` 的哈希顺序包含 `sourceDataType`，还包含资格、语义、证据、单位、币种、精度、`transformationPolicy` 和 `aggregationPolicy`。`transformationPolicy` 的检查约束只有 `NO_CONVERT`。资格只有现有五个值。这些列里没有一项的语义是“允许把字符串数字解析成金额”。

【已确认事实】06-03-02-02 的字段清单用 double、string、int、object 描述调查所见，并在 `package_bag_money_yuan` 的映射行写“字符串要先按契约允许的 `NUMERIC_TEXT` 解析。本规则未批准解析”。这是矩阵中的句子，不是 `mapping-version-v2` 的一个布尔字段，也不在正文哈希的字段名单里。

因此：

1. 当前映射正文没有可机器读取的字符串数字许可字段。
2. 不存在可填写的字段名、类型、语义和哈希范围。`sourceDataType` 参加哈希，但它没有被定义成这项许可，不能改称为现有许可字段。
3. 若要机器可读，就要增加映射正文属性。那不是给现有列补一个口头含义。
4. 增加属性会改变 `mapping-version-v2` 的值顺序。顺序一变，`bodySha256` 就变。已封存版本不能改正文。新正文是新的 `mappingVersion`。快照条目保存的是该版本的 `bodySha256`。新快照若引用新版本，条目哈希也不同。不能说增加正文属性却不改变快照所封存的正文。
5. 旧快照没有该属性。重放不得把它解释成“允许”，也不得解释成后来版本上的值。
6. 重放只读该观测 `snapshotId` 所封存的映射版本。许可事实只来自那一版正文。后发布的版本不回写旧观测。

| 方案 | 是否有可读取字段 | 哈希和快照 | ADR-0003 |
| --- | --- | --- | --- |
| 凡是十进制字符串都可标准化 | 不需要新字段。与 06-03-01、06-03-03-01 的“映射允许”句子冲突 | 不改当前 v2 顺序 | 不改变 `UNMAPPED`、`CONFLICT` 的保存 |
| 增加映射正文属性后再允许 | 新属性，不是现有字段 | 改变 `mapping-version-v2` 和 `bodySha256`。旧快照没有该属性 | 不修改 ADR-0003。未声明时观测可以存在，不产生 `Money` |
| 只继续使用现有资格 | 资格不回答字符串能不能解析 | 哈希不变，许可仍然无法读取 | 不修改 ADR-0003。冲突继续存在 |

JSON `NUMBER` 与 `STRING` 仍分开。06-03-03-01 的“映射没有允许之前，不能变成 `Money`”写在字符串那一行。没有句子把同一限制套到全部 JSON 数字。

【审查建议】推荐增加一项新的映射正文属性，而不是占用 `sourceDataType` 或资格枚举。未增加前，字符串节点不产生 `Money`。增加之后，只有新版本和新快照带有该属性；旧快照的重放视为许可事实不存在。不修改 ADR-0003 和 ADR-0004，不新增 `MappingEligibility`。确认前，06-03-03-04 的“门槛通过即解析”没有被撤销，代码不能选择其中一边。

需要确认的问题：是否接受新增正文属性和因此改变的 `mapping-version-v2` 哈希；旧快照缺少该属性时是否一律视为不允许字符串解析；JSON `NUMBER` 是否不需要同一属性。

## 4. 推荐方案与推荐理由

【审查建议】下面四项都未批准。指数 presence 和布尔 presence 甚至还没有推荐到具体枚举值。

| 决策 | 推荐 | 理由 |
| --- | --- | --- |
| 节点种类 | 方案 B，六种 JSON 种类，`ABSENT` 除外 | 引号不在 `rawText` 里。`NON_SCALAR` 分不开数组和对象。null 与缺失已经由 presence 分开，种类仍要避免把缺失写成 `NULL` |
| 科学计数法 | 拒绝收成普通十进制。不标成 `OTHER_TEXT` | `OTHER_TEXT` 原文只是其他字符串。现有字段码也不准确。presence 留待修订 06-03-03-01 |
| 正负号 | 减号留在 token。正号字符串可按其他字符串讨论。减号字符串和 `-0` 待确认 | 正号字符串没有改 `OTHER_TEXT` 的字符串原义。负金额业务允许性另计 |
| 字符串许可 | 新增映射正文属性，不占用现有列 | 哈希名单里没有这项语义。新增必然改变正文哈希和引用它的新快照 |

## 5. 每项推荐的代价和风险

- 方案 B 要求观测抄录节点种类。漏抄之后，成功解析没有输入，而且不允许重读 JSON 补齐。
- 布尔值和指数数字仍没有准确 presence。推荐方案 B 不关闭这两处缺口。
- 若以后把 `OTHER_TEXT` 改宽来容纳指数，就是在修订 06-03-03-01 的原义，不能写成“本来就是这样”。
- 新增映射属性会使已封存的 `mapping-version-v2` 与新正文不能共用一个哈希定义。旧快照不能被解释成已有许可。
- 四项都未确认。按推荐提前编码，会把本方案写成事实。

## 6. 提取阶段与标准化阶段契约

以下是候选契约，不是已批准接口。未确认的 presence 不在契约里填死。

### 6.1 提取

输入：

| 输入 | 必填 | 语义 |
| --- | --- | --- |
| 原始报文引用 | 必填 | 权威 `rawPayloadRef`。取不回原文是任务级阻断 |
| `snapshotId` | 必填 | 任务已经固定的快照。不改读最新快照 |
| `parserVersion` | 必填 | 与快照同一阶段固定。重试复用。不进入观测身份 |
| `contractVersionId` | 必填 | 只在该快照内确定。未确定则没有字段结果 |
| 契约声明的字段路径 | 必填 | 只读封存清单。不扫描报文猜金额 |

输出，每个声明路径一条：

| 输出 | 语义 |
| --- | --- |
| 路径状态 | 节点不存在时为 `ABSENT`。存在时不使用这个状态冒充节点种类 |
| 节点种类 | 方案 B 确认后，只使用 `NUMBER`、`STRING`、`NULL`、`BOOLEAN`、`ARRAY`、`OBJECT`。路径不存在时没有种类 |
| presence | 现有七种之一。布尔值和指数数字在设计修订前不能填 |
| rawText | 有字面量时保留 token，不含 JSON 引号。`ABSENT` 和 `NULL` 没有字面量。空字符串的字面量是空字符串 |
| 字段提取状态 | 现有 `fieldCode`：`OK`、`TYPE_MISMATCH`、`PATH_NOT_UNIQUE`、`RAW_TEXT_UNRETAINABLE` |
| 拒绝信息 | 只引用已有阻断码或已有字段码。不新造错误码 |

任务级阻断：报文无法解析、原文引用无效、契约版本无法确定、契约身份不一致、正文哈希不符、路径清单未定义、损坏或完整性失败。这些都不写字段结果和观测，不降成 `UNMAPPED`。

字段级失败：`TYPE_MISMATCH`、`PATH_NOT_UNIQUE`、`RAW_TEXT_UNRETAINABLE`。其他路径继续。这三种不形成正常观测。数组和对象按现行设计走 `NON_SCALAR` 与 `TYPE_MISMATCH`，节点种类仍可留在未落成观测的字段结果上。

### 6.2 标准化

输入分成两层。

拒绝路径的最小事实：字段码、presence、`mappingStatus`。判断三种禁止资格、语义和证据时，还要已抄录的资格、语义和证据。这些已够判断 `UNMAPPED`、`CONFLICT`、非数字形态和任务级完整性异常。节点种类可以不参与这类拒绝。

成功路径的完整事实：上述字段，加上观测上的节点种类、`rawText`、该快照目录中的类型生命周期，以及该快照所封存映射版本里的字符串许可属性。许可属性在第 3.4 节落地前不存在，成功路径就不能声称自己读到了许可。节点种类在观测形成时写入。标准化不重读 JSON 来补上缺失的种类。

| 输入 | 必填 | 语义 |
| --- | --- | --- |
| 不可变 `ObservedAmount` | 必填 | 只读已经抄下的事实 |
| 字段映射事实 | 必填 | 当次观测引用的那一版。不重新匹配 |
| 快照目录事实 | 必填 | 该观测引用的目录，不是今天的最新目录 |
| 节点种类 | 成功解析必填 | 来自观测。缺失则不能解析，不能回读报文 |
| 字符串许可 | 成功解析字符串时必填 | 只来自该快照封存的映射正文。旧正文没有这项时视为事实不存在 |
| `normalizationRuleVersion` | 仅结果构造时 | 门禁未过不得编造 |
| `conversionRuleVersion` | 仅在要求换算并已封存时 | 当前没有封存版本。不转换时为空 |

两个版本不是门禁函数的输入。顺序仍是先过门禁，再固定版本，再写结果。

输出三选一：

- 标准化成功结果：只在全部门禁通过、节点种类和许可事实齐全、且版本固定返回之后。当前不会发生。
- 字段级拒绝：形态不符、单位、币种、字面量、字符串许可不存在，或要求换算但没有转换版本。观测不改。其他字段继续。
- 任务级完整性异常：三种禁止资格、非 `部分确认` 的已映射语义、未排除的第二种解释，或运行时证据表禁止的证据出现在 `MAPPED` 上。不降成 `UNMAPPED`。

标准化不重新读取原始 JSON，不修改观测，不推断币种、单位、精度或舍入，不取绝对值。

## 7. 候选 Java 类及模块职责

这些类没有创建，也不是已批准接口。Core 包候选 `com.mtx.rdp.core.amount`。Transform 包候选 `com.mtx.rdp.transform.amount`。Transform 只依赖 Common 和 Core。Pipeline 只依赖端口。

| 类 | 模块 | 职责 | 输入及必填语义 | 输出 | 依赖 | 是否等待决策 | 对应测试 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `RawAmountValue` | Core | 提取时的内存事实 | 路径必填。presence 在能归入七种时必填。路径不存在时没有节点种类。有节点时种类必填。rawText 在缺失和 null 时无 | 不可变过程值 | 无基础设施 | 是。布尔值和指数的 presence 未定 | 第 9 节。现在不写 |
| `ObservedAmount` | Core | 不可变领域记录 | 四段身份必填。字段码 `OK` 时抄录 presence、rawText 和节点种类 | 观测。匹配结果在同一记录 | 不依赖 Transform | 是。身份不改 | 不可变、重试不覆盖、种类不靠重读 JSON |
| `ObservedAmountFacts` | Core | 只读输入 | 拒绝路径：字段码、presence、执行状态必填，种类可缺。成功路径：种类和 rawText 必填 | 无副作用 | 无 | 两层字段不能混成“现在就已经齐全” | 拒绝用例不要求种类。成功用例在决策前不能写成通过 |
| `AmountNormalizationGate` | Transform | 先做已写明的拒绝 | 拒绝路径的最小事实。是否要求换算必填 | 拒绝，或“还不能进入解析” | 只依赖 Core | 成功放行等待四项决策和许可属性 | 未识别、冲突、非数字形态、要求换算 |
| `NormalizationRefusal` | Core | 返回已有门禁 | 名称必须是已有句子 | 字段级或任务级拒绝 | 无 | 指数和布尔值还没有稳定原因名 | 只断言不生成结果 |
| `DecimalLiteralParser` | Transform | 只解析门禁放行后的 token | 必须先读到观测上的种类和 rawText。缺种类则不调用 | 未标度整数和标度，或失败 | 禁止 `double`。禁止重读 JSON | 是 | 待决策行不是通过标准 |
| `Money` | Core | 数值、币种、单位、标度 | 四项都必填。符号在数值里 | 不可变值。不写回观测 | 无 | 是 | 不生成。禁止默认 `CNY` |
| `NormalizedAmount` | Core | 逻辑结果 | 观测身份和两个已固定版本必填。不含节点种类，不含 `parserVersion` | 一条结果 | 版本固定记录尚不存在 | 是 | 不生成生产结果 |

调用顺序：提取写入 `RawAmountValue`。字段码为 `OK` 时，匹配形成 `ObservedAmount` 并抄下节点种类。`AmountNormalizationGate` 先用最小事实拒绝 `UNMAPPED`、`CONFLICT` 和已写明的非数字形态。只有门禁没有拒绝、且观测上已有种类时，才调用 `DecimalLiteralParser`。解析器不向报文补事实。然后才可能构造 `Money` 和 `NormalizedAmount`。当前两步成功都不会发生。

## 8. 完整调用流程

```text
权威原文引用
  -> 固定 snapshotId 与 parserVersion
  -> 只在该快照内确定 contractVersionId
       不能确定：任务阻断，无观测
  -> 按声明路径提取
       路径不存在：ABSENT，无节点种类
       有节点：记下六种种类之一
       能归入七种 presence 且字段码 OK：形成观测并抄录种类
       布尔值或指数数字：presence 未修订前不形成可标准化观测
       数组或对象：NON_SCALAR，TYPE_MISMATCH，不形成正常观测
  -> 匹配
       UNMAPPED 或 CONFLICT：保留观测，停止
       任务级完整性异常：不改读最新快照
       MAPPED：进入门禁
  -> 门禁用观测上已有事实，不重读 JSON
       拒绝：无结果，不改观测
       放行但种类或字符串许可缺失：仍无结果，不回读报文
       全部通过：才固定两个规则版本
       版本不能固定：不编造，无 NormalizedAmount
  -> 将来的 Pipeline 与 Writer
```

当前没有已发布映射。成功结果不会出现。
