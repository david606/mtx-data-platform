## 1. 目标、范围和非目标

目标是：`fieldCode = OK` 的路径在固定快照下得到 `UNMAPPED` 或唯一 `CONFLICT` 时，观测保持可追溯；后续补证据、审核和发布只产生新草稿或新快照，不改旧观测。

范围内：两种执行结果的保存、原因说明、候选与证据的读取、审核和发布的衔接、历史报文与新报文的差别、重放边界、异常和测试。

范围外：不新增执行状态，不重新定义 39 个类型，不把 `candidateDisposition` 写成执行结果，不设计标准化算法和计算规则，不新增 Maven 模块，不编写物理表。

## 2. 上游基线与已知差异

已确认事实：

- 执行侧 `mappingStatus` 只有 `MAPPED`、`UNMAPPED`、`CONFLICT`。定义侧生命周期是 `DRAFT`、`ACTIVE`、`RETIRED`。审核状态是 `NOT_SUBMITTED`、`IN_REVIEW`、`APPROVED`、`REJECTED`。这三组不能互相代替。
- `candidateDisposition` 只有 `SINGLE_CANDIDATE`、`MULTI_CANDIDATE`、`HOLD_UNIDENTIFIED`、`CONFLICTING_CANDIDATES`、`NO_AMOUNT`、`BLOCKED_BY_ELIGIBILITY`。它不写入观测。写成 `CONFLICTING_CANDIDATES` 不会自动变成已经发生的 `CONFLICT`。
- 没有命中时保存 `UNMAPPED`。映射引用和 `proposedType` 为空，`evidenceStatus = NONE`，`semanticStatus = 无法验证`，`Money` 为空。
- 恰好一条冲突决定时保存 `CONFLICT`，保留这一个 `conflictDecisionId`，`proposedType` 为空。不从候选里选择。
- 两条映射、一条映射加一条冲突、两条冲突决定，都是任务失败。不挑选，不降成 `UNMAPPED`，不改读最新快照。
- 窗口是左闭右开。`receivedAt` 是唯一业务时间。映射条目上的 `RETIRED` 仍参加匹配。
- 冲突决定创建后不可修改。要变化就新建决定。未通过审核的决定不能进入快照。`APPROVED` 还不是已经发布。
- 解除冲突时发布新快照：把冲突条目的右端点收到解除时刻，并在同一时刻开始一条新的映射窗口。旧决定、旧快照和旧观测都不改。
- 观测身份是 `rawPayloadRef + snapshotId + contractVersionId + fieldPath`。不含租户，不含业务对象标识。同一身份重试返回原观测。
- `UNMAPPED` 和 `CONFLICT` 不进入标准化。标准化成功也不是计算授权。人工审核不能绕过 06-03-03-04 的门禁。
- 类型 `RETIRED` 禁止新映射，不能回到 `ACTIVE`。已有观测保留原码。

已知差异，本文不修改上游：

1. 外部版本“未提供”对应零个或多个修订时，06-03-03-01 是提取阻断，06-03-02-03 第 8 节第 2 步写 `UNMAPPED`。提取已经阻断时，本文不生成观测。
2. 06-03-01 写只有 `ACTIVE` 能用于新观测。06-03-02-03 与 06-03-03-03 写 `RETIRED` 窗口仍按 `receivedAt` 命中。本文跟随后两份，并且不把这种命中当成重新激活类型。

## 3. 领域对象

| 对象 | 职责 | 不承担 |
| --- | --- | --- |
| `ObservedAmount` | 一次不可变观测，记录当次执行状态 | 审核结论、新映射正文 |
| `AmountMapping` | 一条映射定义及其版本 | 某一次报文是否命中 |
| `MappingConflictDecision` | 一次不能选定类型的不可变决定，含候选和证据 | 把候选标成 `ACTIVE` |
| `AmountMappingSnapshot` | 一次发布的不可变快照。`snapshotId` 就是批次 | 修改旧批次 |
| `NormalizedAmount` | 只有通过 06-03-03-04 全部门禁才形成 | 由 `UNMAPPED` 或 `CONFLICT` 直接生成 |
| `AmountCalculation` | 已批准计算规则的另一次执行 | 未识别笔数或冲突笔数 |

`UNMAPPED` 不是 `CONFLICT`。`CONFLICT` 不表示已经选了某个类型。审核通过不等于映射生效。新快照不覆盖旧观测。

## 4. UNMAPPED

### 4.1 何时保存

已确认事实：只有 `fieldCode = OK` 的路径进入正常匹配。没有命中映射也没有命中冲突时，保存一条 `UNMAPPED` 观测。`ALLOWED_AS_UNIDENTIFIED` 即使命中，执行状态仍是 `UNMAPPED`。今天没有已发布生产窗口，所以当前能形成的观测都在这一类，或者落在将来快照中的冲突类。不能产生 `MAPPED`。

三种提取失败码不形成正常观测，因此也不是未识别金额观测。整份提取阻断时不补造 `UNMAPPED`。

### 4.2 原因说明

设计决定：原因只解释已有门禁，不新增执行状态。一条观测仍然只有 `mappingStatus = UNMAPPED`。

| 已有情况 | 说明 |
| --- | --- |
| 快照中该契约版本和具体路径没有任何落入 `receivedAt` 的条目 | 未命中 |
| 草稿存在，但没有进入该快照 | 草稿不参加匹配 |
| 命中的资格是 `ALLOWED_AS_UNIDENTIFIED` | 仍是未映射，不是未识别类型已经生效 |
| `receivedAt` 等于某窗口右端点 | 该窗口不命中。若没有其他命中，就是未映射 |

这些说明可以出现在治理阅读结果里。它们不写回观测，也不代替 `presence`。

### 4.3 追溯

已确认事实：观测保留 `rawPayloadRef`、具体 `fieldPath`、`presence`、`rawText`、`snapshotId`、`contractVersionId`、`contractBodySha256` 和 `AmountSource`。来源里有平台、接口、消息类型、外部契约版本和 `receivedAt`。

设计决定：未识别治理只读这些引用。不从金额字段推断业务对象标识。取不回原文时不改写成另一份报文。

### 4.4 查询、筛选、统计和审核

设计决定：可以按 `mappingStatus = UNMAPPED`、`snapshotId`、`contractVersionId` 和具体 `fieldPath` 阅读观测。统计只数观测条数，不把这些条数当成营业额、实付或 `AmountCalculation`。审核发生在映射配置上，使用已有的 `approvalStatus`。审核不更新观测。

查询索引、保存多久和由谁操作，存储和权限都未设计，见第 11 节。

### 4.5 补证据、草稿、发布和后续报文

已确认事实：新规则从 `DRAFT` 开始。发布必须满足 06-03-02-03 第 13 节：类型在该目录中为 `ACTIVE`，资格不是三种禁止值，语义是 `部分确认` 且没有未排除的第二种解释，不是只靠 `E4`、`E5`、`E6`。`APPROVED` 之后还要发布成功，才有新的 `snapshotId`。

设计决定：补充契约或类型定义只产生新的草稿或新的目录版本。当前 0 个类型是 `ACTIVE`，所以现在不能发布生效映射。发布失败整笔回滚，旧快照不变。

新到达的报文在任务第一次开始时固定当时最新且校验通过的快照。已经开始的任务，包括重试，仍用原来的 `snapshotId`。因此新快照只影响之后新开始的任务。

历史 `UNMAPPED` 观测不修改。若要用新快照再处理同一原文，必须是另一次任务，形成新观测。调用方可以在插入时写入 `replayOfObservationId`。系统不按订单号自动寻找旧观测。旧观测的 `UNMAPPED` 保持不变。不重放也可以。没有新快照时，不为了治理去重跑旧快照。

## 5. CONFLICT

### 5.1 何时成立

已确认事实：运行时的 `CONFLICT` 只在该快照中恰好一条冲突决定的窗口含有 `receivedAt`，并且没有映射窗口同时命中。候选少于两条不能发布决定。决定保存 `conflictDecisionId`、契约版本、字段路径、每条候选的 `mappingVersionId`、冲突类型、原因、证据、作者、审核人和审核时确认的窗口。

多个草稿候选或 `candidateDisposition = MULTI_CANDIDATE` 只说明设计上不能选默认。它本身不是一条冲突观测。美团打包袋的分和元、淘宝 `totalPrice` 的两种旧解释、富智云 `expressAmt` 的两种运费，都是 06-03-02-02 的设计评估，现在全部是 `DRAFT`，没有已发布的冲突决定。

### 5.2 冲突观测字段

已确认事实：06-03-03-02 第 4.2 节规定观测必填 `mappingStatus`、`semanticStatus`、`evidenceStatus`、`extractionFieldCode`，以及身份、路径、形态、来源、快照和契约哈希。`mappingId` 在未命中或冲突未选定类型时为空。`mappingVersion` 只跟随 `mappingId`。`mappingEligibility` 只在命中映射版本时抄录，未命中时为空。`evidenceRef` 在没有依据时为空。`proposedType` 在冲突时为空。冲突决定上的多行证据算不算观测上的“一项依据”，上游没有写。06-03-03-02 第 6.3 节和 06-03-03-03 第 7 节只规定 `mappingStatus = CONFLICT`、唯一的 `conflictDecisionId` 和空的 `proposedType`。这两节没有规定冲突观测的 `semanticStatus`、`evidenceStatus` 和 `evidenceRef`。

决定头没有 `semanticStatus`。决定的证据是多行，每行有自己的 `evidenceStatus`。候选映射版本各自还有语义和证据。这些都不是观测上的一个字段。

设计决定：冲突观测按下面赋值。不新增执行状态，不写成 `MAPPED`，不生成 `NormalizedAmount`。

| 字段 | 赋值 | 依据 |
| --- | --- | --- |
| `mappingStatus` | `CONFLICT` | 已确认事实 |
| `conflictDecisionId` | 唯一命中的决定 | 已确认事实 |
| `mappingId` | 空 | 已确认事实。冲突没有选定映射 |
| `mappingVersion` | 空 | 已确认事实。没有 `mappingId` |
| `proposedType` | 空 | 已确认事实 |
| `mappingEligibility` | 空 | 已确认事实。没有命中映射版本 |
| `semanticStatus` | `无法验证` | 设计决定。见下面的语义边界 |
| `evidenceStatus` | `NONE` | 设计决定。见下面的证据边界 |
| `evidenceRef` | 空 | 设计决定。见下面的证据边界 |
| `extractionFieldCode` | `OK` | 已确认事实。失败码不形成观测 |
| `money` | 空 | 已确认事实。形成观测时不填金额 |

语义和证据分开处理，不因为其中一列取了某个值就推出另一列：

- 语义：不读取、不比较、不抄录任何一个候选的 `semanticStatus`。候选全部相同也不抄。`无法验证` 只表示这次执行没有形成可归到单一类型的语义结论。它不表示每个候选的语义都是 `无法验证`，也不改写候选版本。
- 证据：不从候选证据中选一条，也不从决定的证据行中选一条，即使只有一行，或者每一行等级相同。`NONE` 只表示观测上没有单一证据等级。`evidenceRef` 因此为空。决定上的证据行仍通过 `conflictDecisionId` 读取，每行保持自己的 `evidenceStatus`、`sourceReference` 和 `quotedNote`。`NONE` 不表示这些证据不存在，也不表示它低于 `E6`。

不新增第七种语义或第九种证据。候选差异留在决定和候选版本上，不压进观测。

### 5.3 候选差异与证据

已确认事实：候选正文留在各自的映射版本和证据行。决定只保存版本号和当时的 `candidateBodySha256`。还原时先核对哈希，再读那一版正文。缺行或哈希不一致就是快照损坏，任务失败，不挑选其中一个候选。

设计决定：治理阅读要同时看到候选之间的类型、资格、语义和证据差异，以及决定上的原因。阅读不选择候选，也不把差异写成 `proposedType`、`semanticStatus` 或 `evidenceStatus`。

### 5.4 封存前后的证据与新决定

已确认事实来自 06-03-02-03 第 7、8、10、13 节：

1. 创建决定之前，候选映射版本可以是草稿，证据写在该版本自己的证据行上。创建决定时，请求带上至少两个 `mappingVersionId` 和决定自己的 `evidences`。服务读取候选当前正文并计算哈希。这一步插入决定头、候选行和证据行，还不封存候选。
2. 决定创建后没有修改接口。要改变正文，包括追加证据，只能另建一条决定。
3. 发布事务才把尚未封存的候选版本和对应契约版本改为 `SEALED`。封存后该版本整行不能再改，证据也不能再追加。同一个 `mappingId` 的其他未封存版本可以继续编辑。新版本不会自动进入已经创建的决定。
4. 审核人必须是另一名操作者。只接受 `NOT_SUBMITTED`。`REJECTED` 不能进入快照。`APPROVED` 不封存候选，也不产生快照。
5. 发布冲突决定使用已有的发布接口。首次进入快照的窗口必须等于决定正文里审核确认的窗口，请求不能另传窗口。候选少于两条、哈希不一致或窗口重叠，整笔回滚。
6. 同一契约版本、同一字段的映射窗口和冲突窗口放在一起检查。后一段起点早于前一段终点，或前一段没有右端点又存在后一段，返回 `WINDOW_OVERLAP`。相邻窗口可以首尾相接，右端点属于后一段。以后的快照只能把已有冲突条目的右端点提前，不能改决定正文里的窗口。

设计决定：封存之后的新证据按下面处理。

| 步骤 | 处理 |
| --- | --- |
| 旧决定上的证据 | 不追加，不替换。旧决定、旧快照、旧观测保持原样 |
| 候选正文需要变化 | 新建映射版本。已封存版本返回 `VERSION_SEALED`。新版本不写入旧决定 |
| 新决定 | 用新的 `CREATE_CONFLICT_DECISION` 创建。候选只传当时的 `mappingVersionId`。新证据写在新决定自己的 `evidences`。服务重新计算候选哈希 |
| 审核 | 新决定从 `NOT_SUBMITTED` 开始。另一名操作者审核。驳回或证据不足都不发布 |
| 发布 | `APPROVED` 之后单独发布。发布成功才封存这次引用的尚未封存版本，并产生新快照。失败整笔回滚 |

新旧决定要进入同一字段的快照，只能使用上面已经存在的窗口规则：

- 不能在同一次冲突发布里同时关闭旧决定。关闭右端点是另一个发布动作，只提前条目右端点，不改旧决定。
- 父快照里旧冲突窗口若还没有右端点，或者新决定的确认窗口与它重叠，新决定不能发布。结果是 `WINDOW_OVERLAP`，没有新快照。
- 只有先发布一份把旧冲突右端点提前的快照，并且新决定审核确认的起点不早于该右端点，新决定才可能发布。发布请求不能改写这个确认窗口来避开重叠。
- 两条决定的窗口之间可以有空隙。空隙里没有其他命中时，执行结果是 `UNMAPPED`。本文不补一条覆盖空隙的窗口。
- 若新决定创建时写下的窗口无法满足上述规则，这条决定停留在未发布。不能修改它，也不能发明第二套覆盖规则。要换窗口，再创建另一条决定。

### 5.5 发布、解除和两类报文

已确认事实：新快照增加冲突条目时，第一次发布的窗口必须等于决定里审核确认的窗口。解除时，新快照把该冲突条目的右端点提前到解除时刻，并在同一时刻开始新的映射窗口。相邻窗口首尾相接，右端点属于后一段。

因此：

- 旧快照上的冲突观测保持 `CONFLICT`。
- 仍用旧快照重试的报文返回原观测。
- 新任务固定新快照后，`receivedAt` 仍小于解除时刻的，继续命中冲突窗口，新观测可以是 `CONFLICT`，并指向原来的决定。
- `receivedAt` 大于或等于解除时刻的，不再命中这段冲突窗口。若新映射窗口的其他发布条件成立，才可能是 `MAPPED`。当前没有这种已发布窗口。
- 历史报文如果任务已经固定了旧快照，不因为后来解除冲突就改读新快照。

类型在新快照目录中已是 `RETIRED` 时，不能把新映射发布成生效，也不能把该类型改回 `ACTIVE`。已有观测不修改。

## 6. 流程

### 6.1 未识别

```text
保存原文
  -> 提取
  -> 固定快照匹配
  -> 没有命中：UNMAPPED 观测
  -> 治理只读观测、原文引用和快照
  -> 补证据只写新草稿
  -> 另一名操作者审核
  -> 发布成功才有新快照
  -> 之后新开始的任务使用新快照
```

历史观测不自动重放。要重放必须新开任务并固定另一份快照，新观测可选指向旧观测。旧的 `UNMAPPED` 不改。

### 6.2 冲突

```text
保存原文
  -> 提取
  -> 固定快照匹配
  -> 恰好一条冲突决定：CONFLICT
  -> 观测按第 5.2 节赋值，不抄录候选语义或证据
  -> 读取决定上的候选和证据行，不选择
  -> 证据不足或驳回：不发布
  -> 封存后的新证据：新建决定，不改旧决定
  -> 审核通过但窗口重叠或发布失败：整笔回滚
  -> 发布成功：新快照
  -> 之后新开始的任务按新窗口处理
```

### 6.3 历史再处理

| 情况 | 结果 |
| --- | --- |
| 同一快照再次处理 | 返回已有观测。不改 `UNMAPPED` 或 `CONFLICT` |
| 更换快照 | 新观测。旧观测保持原匹配结果 |
| `receivedAt` 落在 `RETIRED` 映射窗口内，且该快照目录中的类型仍是 `ACTIVE` | 匹配仍可命中。这不重新激活类型，也不改旧观测 |
| 该快照目录中的类型已是 `RETIRED` | 不发布新映射，不把类型改回 `ACTIVE`。已有观测不修改 |
| 冲突已在新快照解除 | 旧快照上的冲突观测不变。新报文是否命中新映射，只看它自己的 `receivedAt` 和新快照窗口 |
| 原文取不回 | `PAYLOAD_REF_INVALID`。不生成观测，不改读最新报文 |

不能把历史观测改写成新的匹配结果。

## 7. Pipeline

| 模块 | 职责 |
| --- | --- |
| `platform-core` | 观测、冲突决定引用和端口 |
| `platform-transform` | 实现匹配。不选择候选，不执行审核 |
| `platform-pipeline` | 只调用 core 端口。不依赖 Transform 实现类 |
| `app-worker` | 装配并执行已经固定的快照 |
| `app-admin` | 配置草稿、审核和发布。与 Worker 互不依赖 |
| `platform-writer` | 写出已经形成的观测。不把未识别改成 0，不把冲突改成某个类型 |
| `platform-quality` | 不修改观测，也不把未识别登记成提取错误 |

审核通过不能跳过 06-03-03-04。`UNMAPPED` 和 `CONFLICT` 都没有标准化结果，也没有计算结果。

幂等沿用观测身份。配置命令仍只用 `amount_mapping_idempotency_request`。观测不写入那张表。物理唯一索引尚未实现。

## 8. 异常

| 情况 | 级别 |
| --- | --- |
| 未命中 | 字段。保存 `UNMAPPED`。其他字段继续 |
| 恰好一条冲突决定 | 字段。保存 `CONFLICT`。其他字段继续 |
| 多条映射、映射加冲突、两条冲突决定 | 任务失败。不挑选 |
| 决定或候选哈希不符 | 任务失败。不改读最新快照 |
| 审核驳回或证据不足 | 不发布。已有观测不变 |
| 发布失败 | 整笔回滚。没有新快照 |
| 原文取不回 | 任务在提取阶段阻断。不生成观测 |
| 标准化门禁未通过 | 不生成 `NormalizedAmount`。观测保留 |
| 标准化通过但没有生效计算规则 | 不生成 `AmountCalculation` |

同一任务里任务失败之后，其他字段已经写出的观测是否撤销，上游没有事务。本文不规定。已经写好的观测不被后来的失败改写。

## 10. 架构决策

| 决策 | 结论 |
| --- | --- |
| 是否新增执行状态 | 否 |
| 未识别观测是否保存 | 是 |
| 冲突是否在运行时选择候选 | 否 |
| 审核通过是否等于生效 | 否 |
| 新快照是否覆盖旧观测 | 否 |
| 未识别或冲突是否进入计算 | 否 |
| 是否自动重放历史观测 | 否。只有新任务固定新快照时才新建观测 |
| 是否新增模块 | 否 |
| 冲突观测是否抄录候选语义或证据 | 否。语义与证据的赋值见第 5.2 节 |
| 封存后的新证据是否写入旧决定 | 否。另建决定，窗口仍用已有规则 |

这些决定同时记在 ADR-0003。该记录待审查，不表示生产映射已经发布。

## 11. 风险与待确认

1. 未识别列表的保存期限、筛选权限和统计是否展示，都没有产品决定。统计不能当成经营指标。
2. 业务对象标识仍未知。治理不推断。
3. 观测身份的物理唯一索引未实现。
4. “未提供”在提取阻断和匹配 `UNMAPPED` 之间的上游差异仍在。
5. 冲突决定的查询界面和通知没有设计。
6. 同一任务中任务失败后，其他字段已写出的观测是否撤销，没有事务规则。
7. 冲突观测使用已有的 `无法验证` 和 `NONE`。治理如果把 `NONE` 读成“决定没有证据”，会漏掉决定上的证据行。查询产品尚未规定必须同时展示这些行。
