# 06-03-03-04 MTX Data Platform V2 金额标准化与约束校验设计

## 1. 设计目标与范围

目标是：在不覆盖 `ObservedAmount` 的前提下，规定一条观测要同时满足哪些已有条件，才允许形成一条可追溯的标准化结果；条件不足时保留原始观测，不生成标准金额。

范围内：对象边界、准入、字面量解析约束、单位与币种、精度与舍入、七种 `presence`、结果如何追溯和重放、Pipeline 位置、与 `AmountCalculation` 的分界、测试矩阵。

范围外：不修改 39 个类型编码，不把 `DRAFT` 改成 `ACTIVE`，不批准映射，不设计未识别金额的专门流程，不设计聚合公式，不新增 Maven 模块，不编写物理表，不补官方接口契约。

已确认事实：标准类型 38 个是 `DRAFT`，`AMT.FEE.DELIVERY` 是 `RETIRED`，0 个是 `ACTIVE`。06-03-02-02 的映射全部是 `DRAFT`，已确认生产映射数量是 0。转换策略只有 `NO_CONVERT`。当前仓库因此没有一条已经通过发布门槛的映射，现在不会写出标准化结果，也不会产生 `AmountCalculation`。这不表示将来一条已经发布、语义为 `部分确认` 的映射也不能标准化。

## 2. 上游基线与已知差异

已确认事实：

- `semanticStatus`、`evidenceStatus`、`mappingEligibility`、定义侧生命周期、执行侧 `mappingStatus` 是不同维度，不能互相代替。
- `MAPPED` 只表示这次执行引用了哪一版映射。它不表示语义已经确认，也不表示可以计算。
- 只有 `ALLOWED_IF_CONTRACT_DEFINES` 可以写成 `MAPPED`。`ALLOWED_AS_UNIDENTIFIED` 的执行状态是 `UNMAPPED`。`NOT_UNTIL_CONFIRMED`、`DISALLOWED`、`CONFLICT_ONLY` 在匹配引擎中是任务级快照完整性异常。
- `部分确认` 的定义是“有一个来源把这个词说清了，还不能当成全部平台或全部包含项已确认”。目录中没有“语义已确认且可以随意映射”的编码。`E1-A` 不表示业务已确认。`E4` 不能把语义升成已确认。
- 正负号约定全部是 `PRESERVE_SOURCE`。不因为类型是退款就改成负数，也不把负优惠取绝对值。
- 精度约束是 `NO_IMPLICIT_ROUNDING`。舍入只出现在计算规则里。当前没有生效的计算规则。
- 币种和单位都在金额实例上。类型不默认 `CNY`，也不默认元或分。单位或币种为 `UNKNOWN` 时，`calculationPermission` 必须是 `BLOCKED`。
- `unitEvidence = CONTRACT_DECLARED` 只来自契约或摘录已经写明的单位。DDL 注释不是这个值。团购八列固定按 `UNCONFIRMED` 设计，禁止写成 `FEN` 或 `YUAN`。
- 七种 `presence` 不合并。缺失、null、空字符串和数字 0 继续区分。
- 06-03-03-02 规定观测形成时 `Money` 保持为空。空不是 0。

上游没有写明的事：

1. 06-03-02-03 第 13 节把 `部分确认` 定为业务发布的语义门槛，并要求没有未排除的第二种解释。06-03-02-01 又写明 `部分确认` 不是全部平台或全部包含项已确认。本文同时遵守这两句：通过发布门槛的 `部分确认` 可以进入标准化，范围只限于当前契约已经写明的字段含义。
2. 证据沿用发布门槛，不另设等级制度：只靠 `E4`、`E5`、`E6` 不能发布，因此也不能据此标准化。上游没有再规定 `E1-A`、`E1-B`、`E2`、`E3` 的优先顺序。
3. 06-03-01 允许观测上存在可空的 `Money`。06-03-03-02 决定形成观测时不填写。本文不把标准化结果写回观测上的 `Money`。这不是修改那两份文档。

旧代码事实，不进入 V2 规则：

| 已读到的代码行为 | 证据 | 本文怎么用 |
| --- | --- | --- |
| 美团、淘宝用 `HALF_UP` 把元变成整数分 | 06-02-10 | 代码已确认。不是已批准舍入模式 |
| 京东、富智云订单金额遇到小数变成 `null`，不是截断 | 06-02-10 | 代码已确认。V2 不把失败改成空金额观测 |
| 京东售后 `cashMoney`、`refundUserMmoney` 的 `longValue()` 会截断小数 | 06-02-10，06-03-02-02 | 代码已确认。V2 不截断小数来凑整数 |
| 淘宝优惠取绝对值 | 06-02-10，06-02-04 | 代码已确认。负优惠是否允许仍待业务确认。V2 不取绝对值 |
| 美团承担为负时收成 0 | 06-02-10 | 代码已确认。V2 不把负数收成 0 |
| 富智云金额转换失败返回 `null`，随后 `COALESCE` 可能留下旧值 | 06-02-10 | 代码已确认。可能掩盖坏报文，待业务确认。V2 不沿用这个写入 |

| 已读计算路径未发现用 `double` 或 `new BigDecimal(double)` | 06-02-10 | 只覆盖已读路径，不能写成全仓库都不存在 |

四平台字段不能收成一个营业额。原系统列名不是标准类型编码。

## 3. 领域边界

| 对象 | 职责 | 持久化 |
| --- | --- | --- |
| `RawAmountValue` | 一次提取在内存中的形态和字面量 | 不单独落库。06-03-03-01 规定提取是纯函数 |
| `ObservedAmount` | 某次原文、契约版本和快照下的不可变观测，含 `presence`、`rawText` 和执行状态 | 一条观测记录。标准化不更新它 |
| `NormalizedAmount` | 准入全部通过之后的标准化结果。它引用观测，不替换观测 | 逻辑结果。是否建物理表未决定。本文不给 DDL |
| `AmountCalculation` | 已批准计算规则的另一次执行 | 本文不生成 |

关系是单向的：观测可以没有标准化结果。标准化结果必须指向一条已经存在的观测。计算结果必须另有批准规则，不能从标准化结果自动产生。

标准化不改 `rawText`、`presence`、`mappingStatus`、`proposedType`、`snapshotId` 和来源。解析器版本仍是 06-03-03-02 记下的实现前置待决事项。本文不设计解析器版本体系。

## 4. 准入规则

标准化只接受已经通过 06-03-02-03 第 13 节正式发布门槛的映射。门槛是：类型在该快照目录中为 `ACTIVE`；资格不是 `NOT_UNTIL_CONFIRMED`、`DISALLOWED`、`CONFLICT_ONLY`；语义是 `部分确认`，并且没有未排除的第二种解释；不是只靠 `E4`、`E5`、`E6`。`ALLOWED_AS_UNIDENTIFIED` 发布后的执行状态仍是 `UNMAPPED`，不进入标准化。

`部分确认` 只允许标准化当前契约已经写明的那个字段含义。它不提升为跨平台、跨字段或全部包含项的业务确认。`MAPPED` 只表示这次执行引用了哪一版映射，不是语义确认。标准化成功也不是计算授权。

字段级失败保留观测，不生成该字段的结果，其他独立字段继续。任务级异常不降成普通字段失败，不改读最新快照。本文不假设这些失败会回滚同一任务里已经写出的其他结果。

| 组合 | 处理 | 级别 |
| --- | --- | --- |
| `extractionFieldCode` 不是 `OK`，或 `presence` 不是 `NUMERIC_ZERO` / `NUMERIC_TEXT` | 没有可标准化的观测。不改成 0 | 字段 |
| `mappingStatus` 是 `UNMAPPED` 或 `CONFLICT` | 保留观测，不生成结果 | 字段 |
| `mappingStatus = MAPPED`，资格是 `ALLOWED_IF_CONTRACT_DEFINES`，语义是 `部分确认`，没有未排除的第二种解释，证据不是只靠 `E4`、`E5`、`E6`，类型在该快照目录中是 `ACTIVE` | 语义和发布门槛通过。仍须单独通过单位、币种、标度和是否转换。通过后只标准化契约写明的含义 | 字段继续检查 |
| 同上，但这次标准化会把含义用到契约没有写明的其他平台、其他字段或其他包含项 | 不生成结果。不扩大 `部分确认` | 字段 |
| `MAPPED`，但语义是 `待平台确认`、`待业务确认`、`待财务确认`、`存在冲突` 或 `无法验证` | 正式发布不会接受这种语义。出现在已发布映射上视为快照完整性异常 | 任务。不降成 `UNMAPPED`，不改读最新快照 |
| 仍有未排除的第二种解释 | 不满足发布门槛。不生成结果 | 任务。同上 |
| 证据只是 `E4`、`E5`、`E6` 之一或它们的组合，或是 `NONE` | 与发布门槛相同，不能据此标准化。不另排证据等级 | 若该映射已被写成 `MAPPED`，任务失败；若观测本身是 `UNMAPPED`，字段级不生成结果 |
| 资格是 `NOT_UNTIL_CONFIRMED`、`DISALLOWED` 或 `CONFLICT_ONLY` | 沿用 06-03-03-03。快照完整性异常 | 任务 |
| 类型不是该快照目录中的 `ACTIVE` | `DRAFT` 和 `RETIRED` 都不能在本文被改成 `ACTIVE`。当前 0 个 `ACTIVE` | 字段。不生成结果 |
| 单位识别失败，或币种不是契约已写明的值 | 不补成元、分或人民币。见第 6、8 节 | 字段 |
| 要求改变单位，但没有封存的转换规则版本 | 保持 `NO_CONVERT`。不生成换算后的结果 | 字段 |

当前仓库没有已发布映射，所以上表里“可以继续”的那一行现在不会写出结果。这是现状，不是把 `部分确认` 再禁掉。

## 5. 原始数值解析

已确认事实：提取不把字面量解析成 `Money`。`NUMERIC_TEXT` 的 `rawText` 保留原文。带空格的数字、带单位的句子和多个数字拼在一起是 `OTHER_TEXT`。提取不截断出其中的数字。

设计决定：将来如果准入全部通过，解析只读取观测上已经写下的 `rawText`。中间表示必须是十进制的未标度整数加标度，不能是二进制浮点。JDK 里的 `BigDecimal` 可以用字符串构造来表达这种十进制；`new BigDecimal(double)` 和任何先转成 `double` 的路径都不能使用。本文不把这个类写进工程依赖，也不编写解析代码。

| 输入 | 处理 |
| --- | --- |
| JSON 数字和整个字符串都是十进制数字 | 提取已分别标成 `NUMERIC_TEXT` 或 `NUMERIC_ZERO`。两者都保留原始 token。解析时不把 JSON 数字先变成浮点 |
| 整数和小数 | 标度来自字面量本身。`12` 与 `12.0` 数值可以相等，标度不同，不把它们改写成同一种写法 |
| 科学计数法 | 06-03-03-01 没有把它定义为十进制数字。不把 `1e2` 收成 `100`，也不改 `rawText` |
| 前后空格 | 已是 `OTHER_TEXT`。不自动 trim 后再解析 |
| 正负号 | `PRESERVE_SOURCE`。不取绝对值，不把负号丢掉。提取是否把带符号的字符串标成 `NUMERIC_TEXT`，上游没有例子，见第 15 节 |
| 非法字符 | 不删除字符，不修复 |
| 超长文本 | 提取阶段的 `RAW_TEXT_UNRETAINABLE` 不形成正常观测。标准化不保存截断后的字面量 |
| 非有限值 | 不把 `NaN` 或无穷当成金额。标准 JSON 数字不是这两种值 |
| 精度超出已批准标度 | 没有已批准的目标标度。标度与字面量不同不是失败。见第 7 节 |
| 空字符串 | `EMPTY_STRING`。不是 0，也不解析 |

解析失败只说明这一字段没有标准化结果。它不把观测改成 0，也不回写 `rawText`。

## 6. 单位转换

原始单位文字和规范单位分开。

- `declaredUnitText` 保存契约或摘录里的原始单位文字。没有就空着。它不换成 `FEN` 或 `YUAN`。
- `sourceUnit` 只有在明确规则把这份文字识别成已有的 `YUAN` 或 `FEN` 之后才有值。不能只凭字段名、平台名或数值大小识别。
- 识别失败时不生成标准化结果。
- 不发生转换时，结果上的 `Money.unit` 使用这个已确认的 `sourceUnit`。
- 将来要换成另一个单位，必须另有封存的转换规则版本。当前没有这种版本。
- 团购八个字段的单位仍是未确认。DDL 注释不是 `declaredUnitText` 的有效来源，也不能识别成 `FEN`。

| 情况 | 已有事实 | 转换 |
| --- | --- | --- |
| `YUAN` | 契约写明元时才可识别。美团 `phf_ssf`、`package_bag_fee`、`package_bag_money_yuan` 的文档写了元 | 没有封存规则时不换成别的单位。`Money.unit` 保持 `YUAN` |
| `FEN` | 契约写明分时才可识别。美团 `wmPoiReceiveCent`、`package_bag_money` 写了分。京东摘录 `orderBuyerPayableMoney` 写了分，但是摘录是否现行未确认 | 摘录未确认时不能识别成 `FEN` 再换算 |
| 其他币种的最小单位 | 上游没有给出非人民币的最小单位或比例 | 待确认。不假设都是百分之一 |
| 单位未知 | 美团 `total`、`shipping_fee`、`original_price` 的官方行没有写“元”。示例里的小数不能升成单位 | `declaredUnitText` 为空，`sourceUnit` 识别失败，不生成结果 |
| 单位不一致 | 同一打包袋有分和元两种字段，06-03-02-02 写明只能选一个来源，不能相加 | 不把两列换算后合并 |

不发生转换时，没有另一个目标单位。转换比例、转换精度和转换后校验都依附于尚未存在的封存规则。规则不存在而调用方又要求转换时，该字段失败：不生成结果，保留观测，不用 `null` 覆盖旧金额。

不能根据字段名里的 `Cent` 或 `Yuan` 补单位。团购八个 `DECIMAL(24,6)` 列的列宽是存储技术精度，不是业务单位，也不是业务允许的小数位。

## 7. 精度与舍入

五种精度不能混用。

| 概念 | 含义 | 没有已批准业务规则时 |
| --- | --- | --- |
| 原始字面量标度 | `rawText` 里小数点后的位数。`12` 是 0，`12.0` 是 1 | 保留。不补零，不改写成同一种 token |
| 业务允许精度 | 业务允许这个类型保留几位小数 | 上游没有规定。列为待确认。不擅自填写 |
| 目标精度 | 标准化之后必须对齐的小数位 | 上游没有规定。列为待确认。不擅自填写 |
| 存储技术精度 | 某一列能放下的位数，例如团购列的 `DECIMAL(24,6)` | 不是业务规则。不拿它拒绝或改写字面量 |
| 数值技术溢出 | 十进制表示无法在不改动数字的情况下容纳这个字面量，或出现非有限值 | 该字段失败。不舍入，不截断 |
| 业务数值范围 | 业务规定的最大值和最小值 | 上游没有规定。列为待确认。未定义不等于超限 |

不选择 `HALF_UP`、`DOWN` 或其他舍入模式。不截断。不补零来改变原始字面量。旧代码把 0.005 元进到 1 分，只是 06-02-10 的代码事实。

## 8. 币种与数值范围

币种缺失、未声明或 `UNKNOWN` 时不生成标准化结果，也不写成 `CNY`。单位已经识别成功也不能补币种。同一路径若有两份互相冲突的币种文字，该字段失败，不挑选。

零是 `NUMERIC_ZERO`，不是错误，也不是缺失。负数保留。没有已批准的业务最大值和最小值时，不因为数值很大或很小就判失败。只有第 7 节的技术溢出才是字段失败。存储列放不下，不等于业务范围超限。

类型与符号的关系只有 `PRESERVE_SOURCE`。退款类型不因此变成负数。负优惠不因此变成正数。

## 9. presence

| presence | 能否标准化 |
| --- | --- |
| `ABSENT` | 否。不是 0 |
| `PRESENT_NULL` | 否。不是空字符串，也不是 0 |
| `EMPTY_STRING` | 否。字面量是空字符串 |
| `NUMERIC_ZERO` | 只有第 4 节全部门禁都通过时才可以。通过前不生成结果。它与缺失不是同一事实 |
| `NUMERIC_TEXT` | 同上，并且字面量按第 5 节可以无修改地解析 |
| `OTHER_TEXT` | 否。不挖出其中的数字 |
| `NON_SCALAR` | 否。不加总，不取第一个元素。对象或数组在标量路径上同时是 `TYPE_MISMATCH`，本来就没有正常观测 |

## 10. NormalizedAmount

候选字段先评估，不全部采用。

| 候选 | 决定 | 理由 |
| --- | --- | --- |
| `normalizedAmountId` | 不在本文冻结生成算法 | 与 `observationId` 一样，算法未设计 |
| `observationId` | 采用 | 结果必须回到那条观测 |
| `amountTypeCode` | 采用，仅当准入通过 | 来自该观测已写入的 `proposedType`。不在标准化时另选类型 |
| 十进制数值、币种、单位、标度 | 采用为结果上的 `Money` 形状 | 沿用 06-03-01 的四项。不写回观测 |
| `sourceUnit` | 采用 | 由 `declaredUnitText` 按第 6 节识别。识别失败则没有结果。不发生转换时，`Money.unit` 等于它 |
| `normalizedUnit` | 暂不单独采用 | `NO_CONVERT` 下没有另一个目标单位。将来的规则版本若规定目标单位，再增加这一项 |
| `conversionRuleId`、`conversionRuleVersion` | 暂不采用为已存在的标识 | 没有封存的转换规则。不预建规则表 |
| `mappingId`、`mappingVersion`、`snapshotId` | 采用为引用 | 与观测上的当次匹配相同，不重新匹配 |
| `normalizationStatus` | 不新增枚举 | 现有状态已经能说明为何没有结果。再造一套状态会和执行状态、语义、资格重复 |
| `constraintResult` | 不新增错误码 | 返回给 Pipeline 的是哪一条已有门禁失败。是否把这次失败另存，待存储设计 |
| `normalizedAt` | 采用为结果形成时间 | 不代替 `receivedAt`，也不改观测的 `observedAt` |

逻辑幂等身份是：

```text
normalizationIdentity =
    observationIdentity
  + normalizationRuleVersion

observationIdentity =
    rawPayloadRef
  + snapshotId
  + contractVersionId
  + fieldPath
```

`observationIdentity` 沿用 06-03-03-02，不把业务对象或解析器版本加进去。标准化规则版本还没有设计。在它出现之前，唯一已经封存的策略是 `NO_CONVERT`，没有转换规则标识。同一观测在这个策略下重复处理，不得生成第二条结果；门禁失败时重复处理仍然没有结果。

将来规则版本变化，必须新建结果，不能覆盖旧结果，也不能覆盖观测。

解析器版本仍是 Java 实现前必须先完成的事项。本文不设计这套体系。已经形成的观测不被重新解析覆盖。尚未形成观测时，不能声称换解析器后字面量相同。

物理唯一索引和并发控制留待存储设计。它们是实现前必须具备的条件。本文不声称现在已经有物理幂等能力。

当前仓库没有已发布映射，所以上面的身份现在不会被一条生产结果占用。

失败是否另存，仍待存储设计。失败不能写进 `ObservedAmount`。Pipeline 仍能拿到字段级失败原因，见第 11、12 节。

## 11. 状态与异常

不扩展 `mappingStatus`、`semanticStatus`、`evidenceStatus`、`mappingEligibility` 或 `presence`。

| 情况 | 级别 | Pipeline 得到什么 |
| --- | --- | --- |
| 单位、币种、标度、第二种含义超出契约、形态或未映射 | 字段 | 该字段没有结果，并标明是哪一条已有门禁。观测不更新。其他独立字段继续 |
| `MAPPED` 上出现三种禁止资格、非 `部分确认` 的语义、未排除的第二种解释，或只靠 `E4`、`E5`、`E6` | 任务 | 快照完整性异常。不改写成字段失败，不降成 `UNMAPPED`，不改读最新快照 |
| 快照不可用 | 任务 | 失败。不使用部分条目 |
| 技术上无法按原数字容纳字面量 | 字段 | 不舍入。不把它说成业务范围超限 |
| 同一报文一个字段失败 | 字段 | 不自动阻断其他字段各自的准入 |
| 重试 | 不覆盖观测 | 同版本已有结果则返回原结果。没有结果则仍然没有 |

不假设尚未设计的事务会撤销同一任务中其他字段已经写出的结果。已经写好的观测保持不变。

## 12. Pipeline

顺序是：保存原文，提取，按固定快照匹配，标准化与约束校验，只有准入通过才写出标准化结果。计算不在这一步。

| 模块 | 职责 |
| --- | --- |
| `platform-core` | 标准化端口、请求和结果模型 |
| `platform-transform` | 实现准入和解析约束。不写存储，不调用质量模块 |
| `platform-pipeline` | 只调用 core 端口。不依赖 Transform 实现类 |
| `app-worker` | 装配实现 |
| `platform-writer` | 只写出已经形成的结果。不推断单位，不把失败改成 0，不执行业务计算 |
| `platform-quality` | 不修改观测，也不把未确认关系改写成标准化错误 |

请求引用一条 `ObservedAmount` 和它的 `snapshotId`。每个字段的返回要么是一条逻辑结果，要么是字段级失败原因。任务级异常单独返回，不能被记成某个字段的普通失败。异常不删除原文，不更新观测。

逻辑幂等见第 10 节。今天没有物理唯一索引。标准化规则版本未设计时，重复调用不生成第二条 `NO_CONVERT` 结果。

## 13. 与 AmountCalculation 的边界

标准化成功只表示：这条观测在某一版明确规则下得到了一个未改写原文的十进制值。它不是计算授权。

进入 `AmountCalculation` 至少还要同时满足：

- 已经有标准化结果；
- `calculationPermission` 不是 `BLOCKED`；
- 存在一条已经生效的 `AmountCalculationRule`；
- 该规则自己的语义、证据和批准状态允许执行；
- 聚合策略不是把本条结果拿去和别的金额相加，除非那条策略和规则都已经生效。

当前没有生效计算规则。单位或币种未知时权限保持 `BLOCKED`。`FORBIDDEN` 的类型不能把多笔收成合计。因此本文不生成正式计算结果。

## 15. 风险与待确认

1. `部分确认` 可以进入标准化，但只限于当前契约写明的字段。它仍然不是跨平台业务确认。当前没有已发布映射，所以这条规则现在不会写出记录。
2. `E1-A`、`E1-B`、`E2`、`E3` 之间没有更细的标准化排序。本文只复用“只靠 `E4`、`E5`、`E6` 不能发布”。
3. 带正负号的字符串是否在提取时就是 `NUMERIC_TEXT`，06-03-03-01 没有例子。
4. 非人民币的最小货币单位和比例没有依据。
5. 业务允许精度、目标精度、业务最大值和最小值没有依据。未定义时不判失败，也不擅自填数。
6. 转换规则的正文、版本和封存方式没有设计。本文不预建。
7. 失败记录是否持久化，待存储设计。字段级原因必须能返回给 Pipeline，即使尚未落库。
8. 结果的物理唯一索引和并发控制是实现前置条件，现在没有。
9. 解析器版本管理、重放策略和兼容性策略是 Java 实现前置待决事项。
10. 京东摘录里的“分”、富智云摘录是否现行，06-03-02-02 仍待平台确认。不能提前识别成 `FEN` 再换算。
11. 负优惠是否允许，06-02-10 待业务确认。V2 不取绝对值。
12. 旧代码把失败写成 `null` 或留下旧金额，是否可接受，待业务确认。V2 不沿用。
13. 同一任务中，任务级失败之后其他字段已经写出的标准化结果是否撤销，上游没有事务。本文不规定。
