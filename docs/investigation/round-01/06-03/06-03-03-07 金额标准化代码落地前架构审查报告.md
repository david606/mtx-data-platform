## 4. 十进制解析审查

【设计决定】提取阶段只做形态分类，不建立 `Money`，不改 `rawText`。标准化阶段只读取观测上已经写下的 `rawText`。两段不能并成一个解析器。

| 项 | 结论 |
| --- | --- |
| JSON 数字的原始字面量 | 【设计决定】06-03-03-01：非零 JSON 数字的 `rawText` 保留 JSON 字面量。06-03-03-04：解析时不先变成浮点。如何在提取时拿到未丢失的 token，提取稿没有给出解析器算法 |
| `12` 与 `12.0` | 【设计决定】数值可以相等，标度分别是 0 和 1。不改写成同一种 token，不补零 |
| `NUMERIC_ZERO` 与 `NUMERIC_TEXT` | 【设计决定】数字 0、字符串按十进制看正好是 0，都是 `NUMERIC_ZERO`，并保留各自 token，例如 `0`、`0.0`、`"0.00"`。非零才是 `NUMERIC_TEXT`。空 `Money` 不是 0 |
| 前后空格 | 【设计决定】带空格的数字是 `OTHER_TEXT`。标准化不 trim 后再解析 |
| 科学计数法 | 【待确认】06-03-03-04 写明 06-03-03-01 没有把科学计数法定义为十进制数字，不把 `1e2` 收成 `100`。同一份提取表又把“非零 JSON 数字”全部标成 `NUMERIC_TEXT`。标准 JSON 数字可以带指数。两边没有共同规则 |
| 正负号 | 【设计决定】结果约定是 `PRESERVE_SOURCE`：不取绝对值，不丢负号，不因退款类型改号。【待确认】带正负号的字符串是否属于 `NUMERIC_TEXT`，06-03-03-01 没有例子。06-03-03-04 第 15 节已标出。本文不把它写成提取规则 |
| 非法字符 | 【设计决定】不删除、不修复。字符串不是十进制数字时，提取记 `OTHER_TEXT` |
| 超长字面量 | 【设计决定】提取阶段 `RAW_TEXT_UNRETAINABLE` 不形成正常观测，不保存截断 token。标准化不解析截断字面量 |
| 避免二进制浮点 | 【设计决定】初稿禁止 `double`、`new BigDecimal(double)` 和任何先转成 `double` 的路径。中间表示是十进制未标度整数加标度 |
| 解析失败不改观测 | 【设计决定】失败只说明该字段没有标准化结果。不把观测改成 0，不回写 `rawText` |

【待确认】冲突有两处，本文不选边：

1. 06-03-01 第 3.1a 节把 `NUMERIC_TEXT` 定义为“值是字符串，内容像数字”。06-03-03-01 第 6 节把非零 JSON 数字也标成 `NUMERIC_TEXT`。JSON 数字和数字字符串是两种节点。
2. 06-03-01 写“只有 `NUMERIC_ZERO` 或映射明确允许的 `NUMERIC_TEXT` 才可能产生 `Money`”。06-03-02-02 对个别字段写“本规则未批准解析”。06-03-03-04 则写：形态已是 `NUMERIC_TEXT` 且第 4 节门槛通过后，按第 5 节无修改解析。是否还要一条单独的“允许把字符串当数字”映射许可，三份稿没有合成一条规则。

【审查建议】解析器的安全边界只能是：输入已经由上游标成 `NUMERIC_ZERO` 或 `NUMERIC_TEXT`，并且 `rawText` 是上游已经确认的十进制 token。下面这些输入现在没有确认语法，解析器不能接受，也不能在标准化阶段改回提取分类：

- 带 `+` 或 `-` 的字符串。
- 带指数的 token，包括已经被提取标成 `NUMERIC_TEXT` 的 JSON 数字 `1e2`。
- 前后空格、单位句子、多个数字。它们应停在 `OTHER_TEXT`。
- 只有小数点、前导小数点、尾随小数点。稿件没有例子。
- 任意长度的数字。初稿把“技术上无法按原数字容纳”定为字段失败，但没有给出位数或数值界限。JDK `BigDecimal` 可以表示很长的十进制，不能用它的容量代替这条尚未定义的界限。
- 用无限制的 `new BigDecimal(String)` 直接解析。它会接受指数和正号，超出初稿已经写明的拒绝项。

【审查建议】因此现在不能实现一个会返回 `Money` 的解析器。可以保留的实现边界只是拒绝，不是成功解析。提取分类仍由 06-03-03-01 负责；标准化不能补做分类。

## 5. 单位、币种、精度和舍入审查

【设计决定】`declaredUnitText` 是契约或摘录里的原始单位文字，没有就空着。`sourceUnit` 只有明确规则把该文字识别成 `YUAN` 或 `FEN` 之后才有值。不转换时，结果上的 `Money.unit` 等于这个 `sourceUnit`。`unitEvidence = CONTRACT_DECLARED` 只来自契约或摘录已经写明的单位。DDL 注释不是这个值。

【已确认事实】团购八字段在 06-03-02-01 固定按 `UNCONFIRMED` 设计，禁止写成 `FEN` 或 `YUAN`。列宽 `DECIMAL(24,6)` 是存储技术精度。

【设计决定】币种缺失、未声明或 `UNKNOWN` 时不生成结果，也不写成 `CNY`。单位识别成功也不能补币种。同一路径两份冲突币种文字时该字段失败，不挑选。

【设计决定】精度约束是 `NO_IMPLICIT_ROUNDING`。不选择 `HALF_UP`、`DOWN` 或其他舍入模式。不截断，不补零，不把负数取绝对值，不把负数收成 0。旧代码里的这些行为只是 06-02 调查事实。

【设计决定】没有业务最大值和最小值时，不因为数值很大或很小而失败。存储列放不下不等于业务超限。

| 逻辑 | 分级 | 理由 |
| --- | --- | --- |
| 不按字段名、平台名或数值大小推断单位 | 现在可以写成拒绝 | 初稿第 6 节已写明 |
| 不默认 `CNY` | 现在可以写成拒绝 | 初稿第 8 节已写明 |
| 不把团购八字段按 DDL 注释认成元或分 | 现在可以写成拒绝 | 06-03-02-01 已写明 |
| 不使用未经批准的舍入、截断、补零、取绝对值、负数改零 | 现在可以写成拒绝 | 初稿第 7、8 节已写明 |
| 不把存储列宽当成业务精度 | 现在可以写成拒绝 | 初稿第 7 节已写明 |
| 不把未定义的业务最值判成超限 | 现在可以写成“不得因此失败” | 初稿第 7、8 节已写明。前提是调用方没有另传一个自造上限 |
| 把某段 `declaredUnitText` 识别成 `YUAN` 或 `FEN` | 必须等待明确识别表 | 初稿要求“明确规则”。美团若干字段的文档用词不是已经发布的映射 |
| 读取币种文字 | 必须等待字段落点 | 初稿要求契约写明的值，没有规定文字放在观测的哪一列 |
| 元与分按 100 换算 | 必须等待封存的转换规则版本 | 当前没有这种版本。`NO_CONVERT` 不是换算许可 |
| 非人民币最小单位 | 必须等待业务或平台依据 | 初稿第 15 节写明上游没有比例 |
| 业务允许精度、目标精度、业务最值 | 必须等待业务确认 | 未定义时不得填数，也不得判失败 |
| 负优惠是否允许出现 | 必须等待业务确认 | 即使允许性未决，已写明的动作仍是保留符号，不是取绝对值 |

## 6. 三个版本的职责与待决项

【设计决定】三个版本不合成一个字段。`parserVersion` 不进入 `normalizationIdentity`。本文不新分配版本号，也不设计注册算法。

| 版本 | 现有定义 | 是否已分配 | 是否能开始实现 | 缺失决策 |
| --- | --- | --- | --- | --- |
| `normalizationRuleVersion` | 【设计决定】标准化规则版本。`NO_CONVERT` 不是这个版本号。未分配时，同一观测在“不转换、且转换版本为空”这一档只有一个逻辑结果 | 【待确认】尚未分配。台账 IR-14 仍是待决策 | 【审查建议】不能开始生产标准化，也不能编造版本号。只返回“未分配、不生成生产结果”才不越权 | 谁分配、何时发布、未分配在记录里如何表示。空值不能改成哨兵 |
| `conversionRuleVersion` | 【设计决定】转换规则版本。不转换时为空。没有封存规则就没有这个版本 | 【待确认】没有封存规则，因此没有版本 | 【审查建议】不能实现元分转换。调用方要求转换时，该字段失败 | 规则正文、比例、封存方式和空版本的物理表示。06-04-23 将空版本与 `NOT NULL` 唯一索引的冲突标为 A-01N，决定前不建索引 |
| `parserVersion` | 【设计决定】06-03-03-02 第 4.3 节：不增加该字段，不设计版本体系，并把它列为进入 Java 实现之前必须完成的事项。06-03-03-06 只规定一次任务内首次固定、重试复用，且不进入观测身份 | 【待确认】注册、发布、兼容和历史重放都未设计。台账 IR-11 仍是待决策 | 【审查建议】不能开始报文提取器，也不能声称换解析器后字面量不变。它不阻塞“读取已经写下的 `rawText`、并且只做拒绝”的判断，但阻塞任何会重新解析报文的实现 | 版本标识如何登记，重放任务如何固定当时的解析器 |

【审查建议】阻止生产标准化的是：`normalizationRuleVersion` 未分配、没有已发布映射、没有封存转换规则。阻止独立解析器开发的是：`parserVersion` 体系未设计，加上第 4 节的十进制语法和符号分类未决。不要把解析器版本写入标准化身份。

## 7. 结果身份和幂等边界

【设计决定】身份公式沿用初稿第 10 节：

```text
normalizationIdentity =
    observationIdentity
  + normalizationRuleVersion
  + conversionRuleVersion

observationIdentity =
    rawPayloadRef
  + snapshotId
  + contractVersionId
  + fieldPath
```

【设计决定】观测不可变。标准化结果引用观测，不覆盖观测，不改 `rawText`、`presence`、`mappingStatus`、`proposedType`、`snapshotId`。相同逻辑身份不得形成第二份结果。新的规则版本形成新结果，旧结果保留。失败不写入 `ObservedAmount`。字段级原因返回 Pipeline。

【已确认事实】物理唯一索引、锁、事务和并发证明都没有实现。06-03-03-04、06-03-03-06 和 06-04-19 都把它们留在存储设计。空的 `conversionRuleVersion` 不能改成哨兵后再放进 `NOT NULL` 唯一索引。因此“同一档只有一个逻辑结果”不是已经实现的物理幂等。

【审查建议】本轮不设计表、DDL、事务、锁或持久化适配器。Pipeline 第 8 节的 `versionFixKey` 含观测身份、`taskId` 和标准化阶段，用来固定一次尚未确定的版本。它不是 `normalizationIdentity`。两个键不要合并。
