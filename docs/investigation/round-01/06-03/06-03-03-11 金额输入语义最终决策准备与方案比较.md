## 2. JSON 金额提取语义

节点种类和 presence 是两维。`ABSENT` 表示声明路径上没有节点，不是 `NUMBER`、`STRING`、`NULL`、`BOOLEAN`、`ARRAY`、`OBJECT` 之一。依据是 06-03-03-10 第 3.1 节，以及 06-03-03-01 第 6 节“路径没有这个节点”。

| JSON 节点 | 现行 presence | 现行 fieldCode | 形成观测 |
| --- | --- | --- | --- |
| 无节点 | `ABSENT` | `OK`。第 9 节写明这是正常形态 | 是 |
| `NULL` | `PRESENT_NULL` | `OK` | 是 |
| `STRING` 空串 | `EMPTY_STRING` | `OK` | 是 |
| `NUMBER` 或十进制 `STRING`，数值为 0 | `NUMERIC_ZERO`。token 不合并 | `OK` | 是 |
| 非零 `NUMBER` | `NUMERIC_TEXT`。第 6 节没有排除指数 | `OK` | 是 |
| 整个字符串是十进制数字 | `NUMERIC_TEXT`。映射未允许前不能变成 `Money` | `OK` | 是 |
| 其他字符串 | `OTHER_TEXT` | 第 9 节第 190 行只写形态，没有失败码。第 188 行又把 `OTHER_TEXT` 列为 `TYPE_MISMATCH` 可以记下的形态 | 只有最终是 `OK` 才形成 |
| `ARRAY`、`OBJECT` | 都是 `NON_SCALAR` | `TYPE_MISMATCH` | 否 |
| `BOOLEAN` | 第 6 节没有行 | 四个现有码都贴不准 | 未定 |
| 指数 `NUMBER` | 第 6 节字面会落入 `NUMERIC_TEXT`；第 5 节的标准化稿又不把它当十进制 | 四个现有码都不表示“指数拒绝” | 未定 |

`rawText` 不包含 JSON 引号。06-03-03-02 的字符串例子是 `18.50`。因此数字节点 `12` 和字符串节点 `"12"` 的 presence 与 `rawText` 可以相同。种类要不要另记，仍是方案 B，不是已批准字段。

### 2.1 布尔值

`true` 和 `false` 不是字符串，所以不是 `OTHER_TEXT`。不是数组或对象，所以不是 `NON_SCALAR`。06-03-03-01 第 9 节第 188 行要求“不是金额标量”时留下实际形态并使用 `TYPE_MISMATCH`。布尔值没有一个已命名的形态可填。

| 候选 | 结果 | 代价 |
| --- | --- | --- |
| 增加第八种 presence | 可以有形态名 | 抵触 06-03-03-01 第 14 节“七种 presence 不扩展”。若再配 `OK`，观测落入 ADR-0003 的不可覆盖范围 |
| 新增字段码 | 可以不形成观测，ADR-0003 的保存义务不触发 | 第 10 节把 `fieldCode` 封在四码里。新码仍要填 presence |
| 不形成正常观测，沿用 `TYPE_MISMATCH` | 与数组、对象的观测边界相同 | 第 188 行要求记下真实 presence。不修订这句话，布尔字段结果无法成立 |

【审查建议】不增加 presence，不新增字段码。布尔值的字段结果记下节点种类 `BOOLEAN` 和字面量 `true` 或 `false`，presence 栏不适用，`fieldCode` 使用现有 `TYPE_MISMATCH`，不形成 `ObservedAmount`。这要求把第 188 行改成：布尔值用节点种类表达，不伪造七种 presence。确认前这只是建议。

### 2.2 指数数字

`1e2`、`1E2`、`1.0e2`、`1e+2`、`1e-2` 的节点种类都是 `NUMBER`。`1e-2` 的数值不是 0。把它们标成 `OTHER_TEXT` 会把 06-03-03-01 第 6 节的“其他字符串”改成也包含 JSON 数字。`TYPE_MISMATCH`、`PATH_NOT_UNIQUE`、`RAW_TEXT_UNRETAINABLE` 分别对应非标量或类型不符、路径不唯一、字面量无法完整保存。指数 token 可以完整保留，路径也可以唯一，节点也是数字。三个码的原义都不准确。

| 候选 | 对第 6 节 | 标准化 |
| --- | --- | --- |
| 保持 `NUMERIC_TEXT` 且 `OK` | 第 117 行不用改 | 会形成观测。06-03-03-04 第 9 节把 `NUMERIC_TEXT` 放在可进入标准化的一侧，门禁只看 presence 时放行，拒绝只能发生在解析步骤。标度没有定义 |
| 不形成观测，且不指定 presence | 必须把指数移出第 117 行 | 标准化看不到字面量。没有准确字段码 |
| 把 `OTHER_TEXT` 改成其他标量文本 | 第 119 行和第 117 行都要改 | 布尔值仍不是文本 |

【审查建议】不把指数收成普通十进制，不标成 `OTHER_TEXT`，不占用三个字段码的原义。与布尔值共用同一种字段结果：节点种类 `NUMBER`，`rawText` 保留原 token，presence 不适用，`fieldCode` 为 `TYPE_MISMATCH`，不形成观测。这同样要修订第 9 节，写明该用法只表示“这个数字字面量不是已定义的十进制金额”，并收窄第 6 节第 117 行。业务是否允许指数金额，不由这条技术分类代替。

### 2.3 正负号

06-03-03-04 第 5、8 节已经写明：符号进入金额值后按 `PRESERVE_SOURCE` 保留，不取绝对值，不把负数改成 0，也不因退款类型改成负数。负优惠是否允许仍是 06-03-03-04 第 15 节的待确认项。

| 输入 | 节点 | 【审查建议】 | 仍须业务确认 |
| --- | --- | --- | --- |
| JSON `-12` | `NUMBER` | 沿用非零 JSON 数字行：`NUMERIC_TEXT`，`OK`，token 保留 `-` | 允许解析不等于允许负金额业务 |
| JSON `-0` | `NUMBER` | token 保持 `-0`，确认前不写成 `NUMERIC_ZERO` | `-0` 是否视为零金额 |
| `"-12"`、`"-12.50"` | `STRING` | 确认前不归入 `NUMERIC_TEXT`，不进入标准化 | 减号字符串是否属于数字文本 |
| `"+12"`、`"+0"` | `STRING` | 它们是其他字符串。若第 2.4 节把 `OTHER_TEXT` 定为 `OK`，则形成观测且不标准化 | 无单独的正号业务含义。`+` 不能从 token 删除 |

### 2.4 其他字符串的字段码

第 9 节第 188 行和第 190 行并列。带单位文本和前后空格的 presence 已是 `OTHER_TEXT`，06-03-03-04 第 5 节禁止 trim 后再解析，第 9 节禁止把 `OTHER_TEXT` 标准化。该节没有写 `OTHER_TEXT` 本来就没有观测。`NON_SCALAR` 则写明没有正常观测。

【审查建议】带单位文本和前后空格使用 `fieldCode = OK`，形成观测，由标准化门禁拒绝。第 188 行的 `TYPE_MISMATCH` 只用于数组、对象，以及第 2.1、2.2 节建议的布尔值和指数。这样观测是否形成有一句确定的话。

形成观测之后，同一身份的重试返回原观测，不覆盖 `presence` 和 `rawText`。依据是 ADR-0003 的不可覆盖，以及 06-03-03-02 第 4.3 节。未形成观测时没有观测身份；解析器以后变化，重提可能不同。

## 3. Mapping 字符串许可与版本模型

### 3.1 现行正文没有这项许可

`mapping-version-v2` 的值顺序在 06-03-02-03 第 1014 行：版本名、`mappingVersionId`、`mappingId`、`mappingVersion`、`contractVersionId`、`platform`、`fieldPath`、`sourceDataType`、`candidateAmountTypeCode`、`candidateDisposition`、`mappingEligibility`、`semanticStatus`、`evidenceStatus`、`unitConstraint`、`currencyConstraint`、`precisionConstraint`、`transformationPolicy`、`aggregationPolicy`、证据列表。审核状态不进入哈希。

这些字段回答不了“允许把字符串数字解析成金额”：

- `sourceDataType` 是 `VARCHAR(64)`，没有允许值约束。06-03-02-02 把 `package_bag_money_yuan` 的调查类型写成 `string`，这不是哈希里的布尔许可。
- `transformationPolicy` 的检查约束只有 `NO_CONVERT`。它表示不换算，不表示解析字符串。
- 五种 `mappingEligibility` 管的是类型能不能被指到。`MAP-MT-BAG-YUAN` 已是 `ALLOWED_IF_CONTRACT_DEFINES`，备注仍写未批准解析。
- `semanticStatus` 和证据等级表示确认进度和出处。同一行可以是 `部分确认`，解析仍然未批准。

`contract-version-v3` 的值顺序在第 1008 行，含 `payloadFormat` 和金额路径，不含字符串解析许可。`payloadFormat` 只表示整份报文按 JSON 读取。

两句现有文字的主语不同。06-03-02-02 第 273 行写“按契约允许的 `NUMERIC_TEXT` 解析”。06-03-03-01 第 118 行写“映射没有允许之前，不能变成 `Money`”。06-03-01 又写只有 `NUMERIC_ZERO` 或映射明确允许的 `NUMERIC_TEXT` 才可能产生 `Money`。06-03-03-04 第 9 节在门槛通过后仍按字面量解析。这四句并存。本报告不把其中一句当成已经胜出。

契约级开关覆盖该契约版本上的全部字符串路径，分不开整数路径和字符串路径。映射级属性可以只写在一条映射版本上。

### 3.2 三种候选

已封存正文不能原地修改。06-03-02-03 第 1012 行写明：已经按 v2 算出的哈希不能改用 v3 重算。`snapshot-v2` 第 1020 行只保存 `bodySha256` 文本，不展开正文。因此新字段必须使用新的编码名。06-03-03-10 第 11 节第 3 点写成“修订 `mapping-version-v2` 字段顺序”。本报告不采用这句。插入旧顺序会使已有哈希对不上。

规范编码里布尔的类型字节是 `04`。第 978 行写明当前业务字段没有布尔值，编码先保留。NULL 是 `00`，空字符串是 `0100000000`。三者不能互相代替。

原任务重试不换 `snapshotId`。显式重放是新任务，固定当时的最新已发布快照，新观测不覆盖旧观测。依据是 ADR-0004 第 123–129 行和 ADR-0003。校验失败后能否改选另一份快照，仍是 ADR-0004 的待决事项，三种方案都不另写选择规则。

| 项 | 方案 A：映射布尔 | 方案 B：映射枚举 | 方案 C：契约三态 |
| --- | --- | --- | --- |
| 位置 | 映射正文 | 映射正文 | 契约正文 |
| 候选名与类型 | `stringNumericTextAllowed`，布尔 | `numericTextParsePolicy`，字符串 | `stringNumericTextDecision`，字符串 |
| 允许值 | 真、假 | `DENY`、`ALLOW_DECIMAL_STRING` | `DENY`、`ALLOW`、`NOT_DECIDED` |
| 新正文的缺省 | 假 | `DENY` | `DENY` |
| NULL | 新编码拒绝。不能读成允许 | 新编码拒绝 NULL 和空字符串 | 新编码拒绝。旧编码没有该字段，空列不是 `NOT_DECIDED` |
| JSON `NUMBER` | 不约束 | 不约束 | 不约束 |
| JSON `STRING` | 真才允许十进制字符串 | 只有 `ALLOW_DECIMAL_STRING` 允许 | `ALLOW` 才允许。同一契约版本的字符串路径共用 |
| 哈希 | 参加新编码 | 参加新编码。编码名固定后，再增加枚举值只改内容、不改顺序，仍然是新的 `bodySha256` | 参加新的契约编码。若还要进入材料指纹，那是另一套编码，本报告不把它算进这一项 |
| 新版本 | 新 `mappingVersion`，编码名候选 `mapping-version-v3` | 同左 | 新 `contractVersionId`，编码名候选 `contract-version-v4`。映射改挂新契约时才增加 `mappingVersion` |
| 新快照 | 要被 Worker 读到就发布新快照。`snapshot-v2` 的字段顺序可以不变，条目里的哈希文本变 | 同左 | 新契约进入快照条目后发布新快照 |
| 旧快照 | 许可事实不存在。不把缺失重算成假 | 不把缺失重算成 `DENY` | 仍按该行原来的 `body_encoding` 校验，不补三态 |
| 显式重放 | 新任务固定含新映射版本的快照后才读到真或假。原任务重试仍用旧快照 | 同左 | 新任务固定含新契约的快照后才读到三态 |

【审查建议】采用方案 B。许可放在映射正文，与 06-03-03-01 第 118 行的主语一致，也能把整数路径和字符串路径分开。使用新编码名 `mapping-version-v3`，不改写 `mapping-version-v2`。新正文缺省 `DENY`。旧快照读作许可事实不存在，不重算成 `DENY`。JSON `NUMBER` 不受该枚举约束。未写入新正文前，字符串节点不产生 `Money`。方案 A 会第一次使用尚未用过的布尔类型字节。方案 C 更贴近 06-03-02-02 第 273 行的“契约允许”，粒度却是整份契约。

## 4. 金额模型端到端一致性

七个名字都不是已实现类。Core 持有模型和结果，Transform 做纯判断和解析并只依赖 Common 与 Core，Pipeline 只调用 Core 端口。这个方向与 ADR-0002 一致。06-03-03-02 把提取和匹配的执行放在 Transform，类型仍放在 Core。Pipeline 不因此依赖 Transform 的类。

调用链：

1. 契约版本无法确定：任务阻断，无字段结果，无观测，不写成 `UNMAPPED`。依据是 ADR-0004。
2. 提取产生内存中的 `RawAmountValue`。路径不存在时没有节点种类。
3. 只有 `fieldCode = OK` 才匹配并形成 `ObservedAmount`。`UNMAPPED` 和 `CONFLICT` 保留观测并停止。依据是 ADR-0003。
4. `AmountNormalizationGate` 只读已经抄下的事实。
5. 门禁未拒绝，且观测上已有节点种类和所需许可时，才调用 `DecimalLiteralParser`。
6. `Money` 的数值、币种、单位、标度都必填。
7. 两个规则版本固定返回之后才可能有 `NormalizedAmount`。当前没有已发布映射，这一步不会发生。

拒绝路径判断 `UNMAPPED`、`CONFLICT` 和非数字形态时，字段码、presence 和 `mappingStatus` 够用。判断资格、语义和证据时，还要观测上已经抄录的那三项。第二种解释和证据组合没有可读取字段，这条任务级句子现在无法执行。它不阻塞输入语义分类，留在第 12 节。

成功路径现在不够。06-03-03-02 第 4.2 节的逻辑字段有 `presence` 和条件必填的 `rawText`，没有节点种类。方案 B 若不先把种类写入这张表，提取对象结束后，种类只可能靠 `rawPayloadRef` 再读 JSON。06-03-03-10 禁止用这次重读补齐或覆盖观测。因此种类必须在观测形成时写入，不能等标准化再发现。

字符串许可不能从当前快照读到，因为 `mapping-version-v2` 没有该字段。旧快照在新编码发布后仍然没有该字节。

`ABSENT` 配 `OK` 是已写明的组合，门禁因 presence 不是两种数字形态而拒绝，不把缺失改成 0。布尔值和指数若按第 2 节建议不形成观测，标准化不会去读一条不存在的观测。若表决改成 `NUMERIC_TEXT` 加 `OK`，指数会穿过“非数字形态”这道门，拒绝只能放在解析器。

## 5. 跨模型一致性检查

三份调查的冲突按下面方式收口。收口仍是【审查建议】。

| 冲突 | 收口 |
| --- | --- |
| 06-03-03-09 仍把指数的拒绝形态写成可以是 `OTHER_TEXT`；06-03-03-10 第 3.2 节写明该归类改变原义 | 以 06-03-03-01 第 6 节的“其他字符串”和 06-03-03-10 第 3.2 节为准。决策表不再把 `OTHER_TEXT` 列为指数的推荐 |
| 06-03-03-10 第 11 节要求修订 `mapping-version-v2` 的字段顺序；06-03-02-03 第 1012 行禁止用新顺序重算旧哈希 | 采用新编码名。不改已定义的 v2 顺序 |

## 7. 推荐方案及替代方案

【审查建议】一次确认时采用第 6 节推荐列：方案 B 的节点种类、布尔值和指数不形成观测、正号与其他字符串形成 `OTHER_TEXT` 观测、JSON 减号留在十进制数字 token 中、减号字符串和 `-0` 暂不归入数字形态、字符串许可用映射枚举和新编码名。

可以整组改选，不必拆成多轮调查：

- 节点种类改选方案 A。代价是以后无法按节点执行字符串许可，`"12"` 与 `12` 在观测上相同。
- 指数改选“`NUMERIC_TEXT` 加 `OK`，解析器拒绝且不改 `rawText`”。代价是门禁放行，拒绝点后移，并且与“未定义为十进制数字”并列，直到 06-03-03-04 第 9 节写明解析失败。
- 许可改选方案 C。代价是同一契约版本的字符串路径共用一态，并使用新的契约编码名，而不是 `mapping-version-v3`。
- 许可改选方案 A。代价是第一次把业务字段编成类型字节 `04`。

不在推荐中的做法：增加第八种 presence，新增 `MappingEligibility`，把 `sourceDataType` 口头改成许可，把指数标成 `OTHER_TEXT`，用新字段顺序重算旧哈希，标准化重读 JSON。

## 8. 需要业务负责人确认的事项

1. 负优惠、退款负数、冲正是否允许出现。JSON `-12` 即使按 `NUMERIC_TEXT` 留下减号，也不代替这项确认。
2. JSON `-0` 是否视为零金额。
3. 减号字符串是否属于数字文本。
4. 指数金额是否允许被当成十进制金额。推荐的技术分类是不进入标准化；若业务要求接受，必须另定标度，不能只改字段码。
5. 字符串金额在映射未声明允许时，是否一律不能产生 `Money`。推荐是不能。
6. `"+12"` 是否就是其他字符串，而不是数字文本。

平台字段口径、类型从 `DRAFT` 改为 `ACTIVE`、业务精度和最值，不在本次输入语义里表决。
