## 2. JSON 金额提取语义

节点种类和 presence 是两维。`ABSENT` 表示声明路径上没有节点，不是 `NUMBER`、`STRING`、`NULL`、`BOOLEAN`、`ARRAY`、`OBJECT` 之一。依据是 06-03-03-10 第 3.1 节，以及 06-03-03-01 第 6 节“路径没有这个节点”。

| JSON 节点 | 现行 presence | 现行 fieldCode | 形成观测 |
| --- | --- | --- | --- |
| 无节点 | `ABSENT` | `OK`。第 9 节写明这是正常形态 | 是 |
| `NULL` | `PRESENT_NULL` | `OK` | 是 |
| `STRING` 空串 | `EMPTY_STRING` | `OK` | 是 |
| `NUMBER` 或十进制 `STRING`，数值为 0 | `NUMERIC_ZERO`。token 不合并 | `OK` | 是 |
| 非零 `NUMBER` | `NUMERIC_TEXT`。第 6 节没有排除指数 | `OK` | 是 |
| 整个字符串是十进制数字 | `NUMERIC_TEXT`。映射未允许前不能变成 `Money` | `OK` | 是 |
| 其他字符串 | `OTHER_TEXT` | 第 9 节第 190 行只写形态，没有失败码。第 188 行又把 `OTHER_TEXT` 列为 `TYPE_MISMATCH` 可以记下的形态 | 只有最终是 `OK` 才形成 |
| `ARRAY`、`OBJECT` | 都是 `NON_SCALAR` | `TYPE_MISMATCH` | 否 |
| `BOOLEAN` | 七种 presence 都对不上。不伪造 `OTHER_TEXT` 或 `NON_SCALAR` | 【审查建议】布尔分支，`TYPE_MISMATCH`，见第 2.1 节 | 否 |
| 指数 `NUMBER` | 第 6 节落入 `NUMERIC_TEXT`。标准化不收成普通十进制 | 【审查建议】`OK`，形成观测，解析器拒绝 | 是，见第 2.2 节 |

`rawText` 不包含 JSON 引号。06-03-03-02 的字符串例子是 `18.50`。因此数字节点 `12` 和字符串节点 `"12"` 的 presence 与 `rawText` 可以相同。种类要不要另记，仍是方案 B，不是已批准字段。

### 2.1 布尔字段结果使用独立分支

【已确认事实】06-03-03-01 第 10 节规定每条字段结果都含 `presence`。第 14 节写明七种 presence 不扩展，异常用字段码表达。`fieldCode` 只有 `OK`、`TYPE_MISMATCH`、`PATH_NOT_UNIQUE`、`RAW_TEXT_UNRETAINABLE`。06-03-03-02 第 4.2 节规定 `ObservedAmount.presence` 必填。第 5.3 节规定只有 `fieldCode = OK` 进入正常匹配并可以形成观测；`TYPE_MISMATCH` 不形成观测。数组和对象已经有诚实形态：`NON_SCALAR` 加 `TYPE_MISMATCH`。布尔值不是字符串，所以不是 `OTHER_TEXT`；不是数组或对象，所以不是 `NON_SCALAR`。

现行“每条结果都有 presence”因此盖不住布尔值。下面两种结构都能留下字段结果，都不增加第八种 presence，都不新增字段码，都不改观测四段身份。

| 候选 | 结构 | 调用方怎么分支 | 代价 |
| --- | --- | --- | --- |
| A. 两种字段结果 | `MORPHOLOGICAL` 必须带七种 presence 之一。`BOOLEAN_NON_AMOUNT` 没有 presence 栏，必须带节点种类 `BOOLEAN` 和适用性 `NOT_AN_AMOUNT_SCALAR` | 先读 `resultBranch`。匹配和观测只接受 `MORPHOLOGICAL` 且 `fieldCode = OK` | 06-03-03-01 第 10 节从一张平表改成分支。观测字段不变 |
| B. 平铺适用性字段 | 字段名 `morphologyApplicability`，取值只有 `HAS_PRESENCE` 与 `BOOLEAN_NON_AMOUNT`。`HAS_PRESENCE` 时 presence 必填且为七种之一。`BOOLEAN_NON_AMOUNT` 时不得填写 presence | 先读适用性，再决定能不能读 presence | presence 在同一条记录上有时必填、有时必须缺席，调用方仍要防空。观感接近把 presence 改成可空 |

【审查建议】采用候选 A。普通字段继续必须填写七种 presence 之一。布尔值不进入这张平表。

`BOOLEAN_NON_AMOUNT` 的完整字段：

| 字段 | 约束 |
| --- | --- |
| `resultBranch` | 固定 `BOOLEAN_NON_AMOUNT` |
| `fieldPath` | 必填，声明路径展开后的具体路径 |
| `jsonNodeKind` | 必填，只能是 `BOOLEAN` |
| `booleanApplicability` | 必填，只能是 `NOT_AN_AMOUNT_SCALAR`。这是适用性，不是第八种 presence |
| `literal` | 必填，只能是 `true` 或 `false` |
| `fieldCode` | 固定为已有的 `TYPE_MISMATCH` |

这条分支没有 `presence`、`rawText` 金额字面量和 `declaredUnitText`。它不进入正常金额匹配，也不形成 `ObservedAmount`。原因是 06-03-03-02 第 5.3 节只让 `fieldCode = OK` 形成观测，而 `ObservedAmount.presence` 必填，这条分支又没有可抄录的 presence。观测四段身份因此不会出现布尔路径。

`MORPHOLOGICAL` 的完整字段：

| 字段 | 约束 |
| --- | --- |
| `resultBranch` | 固定 `MORPHOLOGICAL` |
| `fieldPath` | 必填 |
| `jsonNodeKind` | 有节点时必填，取 `NUMBER`、`STRING`、`NULL`、`ARRAY`、`OBJECT`。路径不存在时为空，不得写成 `NULL` |
| `presence` | 必填，且只能是现有七种之一 |
| `rawText` | `ABSENT` 与 `PRESENT_NULL` 没有。其余形态保留所见 token，不含 JSON 引号 |
| `declaredUnitText` | 可空。材料没写就空着 |
| `fieldCode` | 现有四码之一。数组和对象为 `TYPE_MISMATCH`。`PATH_NOT_UNIQUE` 与 `RAW_TEXT_UNRETAINABLE` 仍按 06-03-03-02 第 5.3 节，本轮不改它们的保存方式 |

合法组合：

| 分支 | 节点 | presence 或适用性 | fieldCode | 形成观测 |
| --- | --- | --- | --- | --- |
| `MORPHOLOGICAL` | 无 | `ABSENT` | `OK` | 是 |
| `MORPHOLOGICAL` | `NULL` | `PRESENT_NULL` | `OK` | 是 |
| `MORPHOLOGICAL` | `STRING` | `EMPTY_STRING`、`NUMERIC_ZERO`、`NUMERIC_TEXT` 或 `OTHER_TEXT` | `OK` | 是 |
| `MORPHOLOGICAL` | `NUMBER` | `NUMERIC_ZERO` 或 `NUMERIC_TEXT` | `OK` | 是 |
| `MORPHOLOGICAL` | `ARRAY` 或 `OBJECT` | `NON_SCALAR` | `TYPE_MISMATCH` | 否 |
| `BOOLEAN_NON_AMOUNT` | `BOOLEAN` | `NOT_AN_AMOUNT_SCALAR` | `TYPE_MISMATCH` | 否 |

禁止的组合：布尔分支填写任一 presence；形态分支缺少 presence；布尔分支使用 `OK`；用 `OTHER_TEXT` 或 `NON_SCALAR` 表示 `true` 或 `false`。确认前这是审查建议。修订 06-03-03-01 第 10 节之后，调用方才能按分支实现。

### 2.2 指数数字形成观测

`1e2`、`1E2`、`1.0e2`、`1e+2`、`1e-2` 的节点种类都是 `NUMBER`，数值都不是 0。06-03-03-01 第 6 节把非零 JSON 数字写成 `NUMERIC_TEXT`，并保留数字字面量。06-03-03-04 第 5 节不把 `1e2` 收成 `100`，也不改 `rawText`。第 5 节同时写明解析失败不把观测改成 0，也不回写 `rawText`。后一句以观测已经形成为前提。不能从“不允许标准化”推出“不允许形成观测”。

| 候选 | 原始事实 | 与第 6 节 | 与解析失败不改观测 | 任务结束后 | ADR-0003 |
| --- | --- | --- | --- | --- | --- |
| A. `NUMERIC_TEXT`，`OK`，形成观测，解析器拒绝 | `rawText` 留在观测上，例如 `1e2`。不改成 `100` | 符合非零 JSON 数字行 | 符合。拒绝发生在 `DecimalLiteralParser`，观测保持原 token | 观测身份一旦写下，重试返回原观测，不因后来的解析器变化而改写 | 不修改。观测可以是 `UNMAPPED` 或 `CONFLICT`，今天不会是 `MAPPED`。不生成 `NormalizedAmount` |
| B. `TYPE_MISMATCH`，不形成观测 | 内存字段结果里可以暂时留下 token。06-03-03-02 第 4.3 节规定这个对象不单独落库 | 必须收窄第 6 节，把指数移出非零 JSON 数字 | 没有观测可供“解析失败不改观测”适用 | 分类事实随任务结束消失。再次提取依赖原文仍能取回，并且 06-03-03-02 第 4.3 节第 4、5 点写明：尚未形成观测时，解析器变化后重提可能不同。身份不含 `parserVersion` | 不触发 ADR-0003 的保存，因为没有观测。这不是 ADR 要求取消观测 |

【审查建议】采用候选 A。五个指数样例都是 `NUMBER`、`NUMERIC_TEXT`、`OK`，形成 `ObservedAmount`，`rawText` 保留原 token。标准化门禁按 presence 放行后，解析器拒绝，不产生 `Money` 或 `NormalizedAmount`，不改观测。业务是否允许指数金额仍待确认；未允许时解析器保持拒绝。不把它们标成 `OTHER_TEXT`。

### 2.3 正负号与负零

三件事分开：

1. JSON 数字的数值是否为 0。06-03-03-01 第 6 节按“数值正好是 0”决定是不是 `NUMERIC_ZERO`。
2. 原始 token 是什么。同一行要求保留 token，所以 `0`、`0.0` 和 `-0` 不是同一个字面量。
3. 业务是否给负零单独含义。这只影响以后能不能把它当作零金额使用，不决定 presence。

【已确认事实】数字 0 与字符串 `"0"` 都是 `NUMERIC_ZERO`，token 各自保留。符号进入金额值后按 `PRESERVE_SOURCE` 保留。负优惠是否允许仍是 06-03-03-04 第 15 节的待确认项。

【审查建议】JSON `-0` 的数值是 0，presence 为 `NUMERIC_ZERO`，节点种类为 `NUMBER`，`fieldCode` 为 `OK`，`rawText` 为 `-0`，形成观测。不改写成 `0`。负零有没有特殊业务含义，标为待业务确认，不把技术分类留空。

| 输入 | 节点 | 技术分类 | 待业务确认 |
| --- | --- | --- | --- |
| JSON `-12` | `NUMBER` | `NUMERIC_TEXT`，`OK`，token 保留 `-`，形成观测。解析器可以留下负号 | 技术解析成功后仍要业务准入，见第 2.3 节后半。未准入时不构造 `Money` |
| JSON `-0` | `NUMBER` | `NUMERIC_ZERO`，`OK`，token 为 `-0`，形成观测 | 负零是否在计算或展示上单独处理 |
| `"-12"`、`"-12.50"` | `STRING` | 第 6 节没有把带减号的字符串写成十进制数字。确认前不归入 `NUMERIC_TEXT`，不进入标准化 | 减号字符串是否属于数字文本 |
| `"+12"` | `STRING` | 未归类。不是已确认的十进制数字文本，也还没有被批准为 `OTHER_TEXT` | 正号非零字符串是否属于数字文本。若属于，presence 是 `NUMERIC_TEXT`，不是 `NUMERIC_ZERO` |
| `"+0"` | `STRING` | 未归类。数值是 0，但不能提前写成 `NUMERIC_ZERO` 或 `OTHER_TEXT` | 正号零字符串是否属于数字文本。若属于，按已确认的“数值正好是 0”归入 `NUMERIC_ZERO`，不能写成 `NUMERIC_TEXT` |

JSON `-12` 再分成五层，避免把解析器能力和业务许可写成一件事：

1. 语法。JSON 数字可以带减号。`-12` 不是 0，也不是指数。06-03-03-01 第 6 节的非零 JSON 数字行覆盖它，presence 为 `NUMERIC_TEXT`，`rawText` 为 `-12`。
2. 技术解析。`DecimalLiteralParser` 若被调用，未标度整数保留负号。不取绝对值，不删减号，不把负数改成 0。这是 `PRESERVE_SOURCE`，依据是 06-03-03-04 第 5、8 节。
3. 进入 `Money`。数值、币种、单位、标度都还要齐。负号本身不是这四项已经齐备的证据。
4. 业务语义。负优惠、退款是否必须为负、冲正符号都未确认。06-03-03-04 第 15 节第 11 点只确认 V2 不取绝对值。
5. 类型是否允许负值。当前没有 `ACTIVE` 类型声明负值许可。本报告不按类型名补这条规则。

【审查建议】技术解析成功不等于业务准入成功。解析器可以返回带负号的未标度整数。构造 `Money` 之前增加一道负金额准入：准入事实不存在时，不构造 `Money`，也不构造 `NormalizedAmount`。观测上的 `-12` 保持不变。这道准入不在 `DecimalLiteralParser` 里面，避免解析器支持负数就被当成生产标准化已经允许。JSON `-0` 仍按上一节是 `NUMERIC_ZERO`，token 为 `-0`，不走这道负值准入。

### 2.4 其他字符串的字段码

第 9 节第 188 行和第 190 行并列。带单位文本和前后空格的 presence 已是 `OTHER_TEXT`，06-03-03-04 第 5 节禁止 trim 后再解析，第 9 节禁止把 `OTHER_TEXT` 标准化。该节没有写 `OTHER_TEXT` 本来就没有观测。`NON_SCALAR` 则写明没有正常观测。

【审查建议】带单位文本和前后空格使用 `fieldCode = OK`，形成观测，由标准化门禁拒绝。第 188 行的 `TYPE_MISMATCH` 只用于数组、对象，以及第 2.1 节的布尔值。指数按第 2.2 节形成观测，不使用 `TYPE_MISMATCH`。

形成观测之后，同一身份的重试返回原观测，不覆盖 `presence` 和 `rawText`。依据是 ADR-0003 的不可覆盖，以及 06-03-03-02 第 4.3 节。未形成观测时没有观测身份；解析器以后变化，重提可能不同。

### 2.5 失败字段在任务结束后

【已确认事实】当次提取的内存字段结果可以带具体路径、形态分支上的 presence、布尔分支上的字面量、节点种类和 `fieldCode`。06-03-03-01 第 8 节写明提取是纯函数，提取结果不单独落库。06-03-03-02 第 4.3 节写明任务结束后 `RawAmountValue` 不靠自己的存储继续存在。第 5.3 节把失败码留在当次字段结果上，不写入观测，并写明是否另存独立记录仍待存储设计决定。本文不建表，不新增模块，也不引入收件箱、发件箱或死信队列。

任务结束后的追溯分成三层：

| 层 | 能留下什么 | 限制 |
| --- | --- | --- |
| 已形成的观测 | presence、rawText、匹配结果。采用节点种类时还有种类 | ADR-0003 禁止覆盖。解析器后来变化也不改这些字段 |
| 未形成观测的失败字段 | 当次内存结果。进程结束后没有已批准的失败记录 | 06-03-03-02 第 4.3 节第 4 点：重提可能得到不同分类。这就是指数若走 `TYPE_MISMATCH` 会丢失已分类 token 的原因 |
| 原文 | `rawPayloadRef` 指向当时报文。加上路径可以再次定位节点 | 06-03-03-01 第 14 节写明保存产品未定，怎样长期取回原文仍待确认。再次提取只用于核对，不覆盖已有观测 |

## 3. Mapping 字符串许可与版本模型

### 3.1 现行正文没有这项许可

`mapping-version-v2` 的值顺序在 06-03-02-03 第 1014 行：版本名、`mappingVersionId`、`mappingId`、`mappingVersion`、`contractVersionId`、`platform`、`fieldPath`、`sourceDataType`、`candidateAmountTypeCode`、`candidateDisposition`、`mappingEligibility`、`semanticStatus`、`evidenceStatus`、`unitConstraint`、`currencyConstraint`、`precisionConstraint`、`transformationPolicy`、`aggregationPolicy`、证据列表。审核状态不进入哈希。

这些字段回答不了“允许把字符串数字解析成金额”：

- `sourceDataType` 是 `VARCHAR(64)`，没有允许值约束。06-03-02-02 把 `package_bag_money_yuan` 的调查类型写成 `string`，这不是哈希里的布尔许可。
- `transformationPolicy` 的检查约束只有 `NO_CONVERT`。它表示不换算，不表示解析字符串。
- 五种 `mappingEligibility` 管的是类型能不能被指到。`MAP-MT-BAG-YUAN` 已是 `ALLOWED_IF_CONTRACT_DEFINES`，备注仍写未批准解析。
- `semanticStatus` 和证据等级表示确认进度和出处。同一行可以是 `部分确认`，解析仍然未批准。

`contract-version-v3` 的值顺序在第 1008 行，含 `payloadFormat` 和金额路径，不含字符串解析许可。`payloadFormat` 只表示整份报文按 JSON 读取。

两句现有文字的主语不同。06-03-02-02 第 273 行写“按契约允许的 `NUMERIC_TEXT` 解析”。06-03-03-01 第 118 行写“映射没有允许之前，不能变成 `Money`”。06-03-01 又写只有 `NUMERIC_ZERO` 或映射明确允许的 `NUMERIC_TEXT` 才可能产生 `Money`。06-03-03-04 第 9 节在门槛通过后仍按字面量解析。这四句并存。本报告不把其中一句当成已经胜出。

契约级开关覆盖该契约版本上的全部字符串路径，分不开整数路径和字符串路径。映射级属性可以只写在一条映射版本上。

### 3.2 三种候选

已封存正文不能原地修改。06-03-02-03 第 1012 行写明：已经按 v2 算出的哈希不能改用 v3 重算。`snapshot-v2` 第 1020 行只保存 `bodySha256` 文本，不展开正文。因此新字段必须使用新的编码名。06-03-03-10 第 11 节第 3 点写成“修订 `mapping-version-v2` 字段顺序”。本报告不采用这句。插入旧顺序会使已有哈希对不上。

## 4. 金额模型端到端一致性

七个名字都不是已实现类。Core 持有模型和结果，Transform 做纯判断和解析并只依赖 Common 与 Core，Pipeline 只调用 Core 端口。这个方向与 ADR-0002 一致。06-03-03-02 把提取和匹配的执行放在 Transform，类型仍放在 Core。Pipeline 不因此依赖 Transform 的类。

调用链：

1. 契约版本无法确定：任务阻断，无字段结果，无观测，不写成 `UNMAPPED`。依据是 ADR-0004。
2. 提取产生内存字段结果。形态分支带七种 presence 之一。布尔分支没有 presence。路径不存在时没有节点种类。
3. 只有形态分支且 `fieldCode = OK` 才匹配并形成 `ObservedAmount`。布尔分支在这里停止。`UNMAPPED` 和 `CONFLICT` 保留观测并停止。依据是 ADR-0003。
4. `AmountNormalizationGate` 只读已经抄下的事实。它不把 JSON 减号当成语法失败。
5. 门禁未拒绝，且观测上已有节点种类和所需许可时，才调用 `DecimalLiteralParser`。负数的未标度整数保留负号。
6. 负金额准入读取业务许可。许可不存在时，不构造 `Money`，不改观测。
7. `Money` 的数值、币种、单位、标度都必填。负号不代替业务许可。
8. 两个规则版本固定返回之后才可能有 `NormalizedAmount`。当前没有已发布映射，这一步不会发生。

拒绝路径判断 `UNMAPPED`、`CONFLICT` 和非数字形态时，字段码、presence 和 `mappingStatus` 够用。判断资格、语义和证据时，还要观测上已经抄录的那三项。第二种解释和证据组合没有可读取字段，这条任务级句子现在无法执行。它不阻塞输入语义分类，留在第 12 节。

成功路径现在不够。06-03-03-02 第 4.2 节的逻辑字段有 `presence` 和条件必填的 `rawText`，没有节点种类。`rawText` 不含引号，所以观测上的 `12` 与 `"12"` 不能靠字面量区分 JSON `NUMBER` 和 JSON `STRING`。

字符串许可若在标准化阶段执行，标准化必须能区分这两种节点。区分事实如果只留在当次内存字段结果里，任务结束后该结果不存在，标准化就无法再做这个判断。把 `jsonNodeKind` 写入观测是候选 `K1`，不是已批准决定。不写入完整 `jsonNodeKind` 时，仍必须有一种在观测形成时抄下、之后不再改变、并且不重新读取原始 JSON 的替代事实，否则标准化阶段的字符串许可无法执行。重新读取 JSON 的 `K3` 与 06-03-03-10 已写明的“不重读 JSON”冲突。它不是与 `K1` 并列的普通可选项；没有单独论证并修订该约束之前，不能把它标成 `CONFIRMED`。

字符串许可不能从当前快照读到，因为 `mapping-version-v2` 没有该字段。旧快照在新编码发布后仍然没有该字节。字段缺失、显式 `NOT_DECIDED`、显式 `DENY`、显式 `ALLOW` 是四种事实。旧 v2 快照是字段缺失，不能被重新解释成显式 `DENY` 或显式 `NOT_DECIDED`，这也不使它自动获得字符串解析许可。

`ABSENT` 配 `OK` 是已写明的组合，门禁因 presence 不是两种数字形态而拒绝，不把缺失改成 0。指数按第 2.2 节形成观测后，门禁会放行 `NUMERIC_TEXT`，拒绝放在解析器，观测上的 token 保持不变。JSON `-12` 的解析器可以成功并保留负号；没有业务准入时停在 `Money` 之前。布尔分支和数组、对象不形成观测，标准化不去读一条不存在的观测。它们的分类事实在任务结束后只依赖第 2.5 节的原文再提取，而那一次再提取不是稳定的历史记录。

## 7. 推荐方案及替代方案

【审查建议】一次确认时可以采用：布尔值使用 `BOOLEAN_NON_AMOUNT` 分支且不形成观测；指数形成 `NUMERIC_TEXT` 观测并由解析器拒绝；JSON `-12` 形成观测并由解析器保留负号，没有业务准入时不构造 `Money`；JSON `-0` 形成 `NUMERIC_ZERO` 观测且 token 为 `-0`；空格和带单位文本形成 `OTHER_TEXT` 观测。字符串许可的审查建议仍是映射枚举和新编码名，但旧快照只表示许可事实不存在。`"+12"` 与 `"+0"` 不在这组建议里代选。`jsonNodeKind` 写入观测的 `K1` 也只是候选，不是已批准决定。

可以整组改选，不必拆成多轮调查：

- 节点种类改选只留内存。代价是标准化阶段无法区分 `"12"` 与 `12`。在第 4 节的执行点下，它与 `B1`、`B2`、`B3`、`B4` 都不可组合。见第 13.7 节。
- 指数改选不形成观测。代价是分类 token 随任务结束消失，只能依赖尚未定案的原文再提取，并与 06-03-03-01 第 6 节的非零 JSON 数字行冲突。
- 许可改选方案 C。代价是同一契约版本的字符串路径共用一态，并使用新的契约编码名，而不是 `mapping-version-v3`。
- 许可改选方案 A。代价是第一次把业务字段编成类型字节 `04`。

不在推荐中的做法：增加第八种 presence，新增 `MappingEligibility`，把 `sourceDataType` 口头改成许可，把指数标成 `OTHER_TEXT`，用新字段顺序重算旧哈希，标准化重读 JSON。

## 8. 需要业务负责人确认的事项

1. 负优惠、退款负数、冲正是否允许出现，以及哪些金额类型允许负值。JSON `-12` 即使解析成功并留下减号，也不代替这项确认。未确认时不构造 `Money`。
2. JSON `-0` 在计算或展示上是否有特殊含义。技术分类已经建议为 `NUMERIC_ZERO` 且 token 为 `-0`，这项确认不推翻 presence。
3. 减号字符串是否属于数字文本。
4. 指数金额是否允许被解析成十进制金额。技术分类建议形成观测并保留 token；未允许时解析器拒绝。若业务要求接受，必须另定标度。
5. 字符串金额在字段缺失、显式 `NOT_DECIDED` 或显式拒绝时，是否一律不能产生 `Money`。这三者必须与显式允许分开。旧快照缺失不得自动当成允许，也不得写成显式 `NOT_DECIDED`。只有显式允许且其余门禁通过后，才继续考虑构造 `Money`。
6. `"+12"` 是否属于非零数字文本。若属于，presence 是 `NUMERIC_TEXT`。
7. `"+0"` 是否属于数字文本。若属于，数值为零，presence 只能是 `NUMERIC_ZERO`。

平台字段口径、类型从 `DRAFT` 改为 `ACTIVE`、业务精度和最值，不在本次输入语义里表决。

上列事项的选项、影响范围和未决后果见第 13 节 `11-BIZ-01` 至 `11-BIZ-12`。本节不记录确认结果。

## 9. 需要架构负责人确认的事项

1. 标准化阶段若要执行字符串许可，用什么不可变事实区分 JSON `NUMBER` 与 JSON `STRING`。写入 `jsonNodeKind`、只留在当次内存、或改抄另一种不重读 JSON 的事实，都还是待确认选项。缺失时种类为空。已形成观测的 presence 保持必填。种类不进入四段身份。
2. 布尔值是否采用 `BOOLEAN_NON_AMOUNT` 分支，而不是平铺的可缺席 presence。不增加第八种 presence。
3. 普通 `OTHER_TEXT` 的字段码是否为 `OK`。指数是否按 `NUMERIC_TEXT` 形成观测。
4. 字符串许可放在映射还是契约，以及新正文缺字段如何处理。缺字段可以编码成拒绝值，也可以使新编码失败。显式 `NOT_DECIDED` 只在契约三态里由已存在的字段值表达。旧快照缺失不能改写成 `DENY`、`NOT_DECIDED` 或允许。
5. JSON `NUMBER` 是否不受该枚举约束。
6. 第二种解释和证据组合仍无字段。本次不设计该字段。

上列事项的选项、影响范围和未决后果见第 13 节 `11-ARC-01` 至 `11-ARC-07`。第 6 点不进入本次确认。本节不记录确认结果。
