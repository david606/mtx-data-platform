## 2. 已确认规则

这些规则已经写明，方案比较不能放宽：

- 提取不把字面量解析成 `Money`，不改写 `rawText`。
- 七种 `presence` 不增加第八种。`ABSENT` 和 `PRESENT_NULL` 没有字面量。
- 带空格的数字、带单位的句子、多个数字拼在一起是 `OTHER_TEXT`。不 trim，不挖出数字。
- `NUMERIC_ZERO` 保留各自 token，例如 `0`、`0.0`、`"0.00"`。空 `Money` 不是 0。
- 标准化只在观测已经形成后读取 `rawText`。失败不把观测改成 0，不回写字面量。
- `UNMAPPED` 和 `CONFLICT` 不进入标准化。ADR-0004 的契约版本失败不产生观测。
- 正负号约定是 `PRESERVE_SOURCE`：不取绝对值，不丢负号，不把负数改成 0。负优惠是否允许仍待业务确认。
- `parserVersion`、`normalizationRuleVersion`、`conversionRuleVersion` 是三个字段。前一个不进入观测身份，也不进入标准化身份。
- 已有观测重试返回原观测，不重新解析覆盖字面量。

## 3. 方案比较

### 3.1 JSON 数字与数字字符串

现有原文：

- 06-03-01 第 3.1a 节：`NUMERIC_TEXT` 是“值是字符串，内容像数字，尚未按数值解析”。
- 06-03-03-01 第 6 节：非零 JSON 数字是 `NUMERIC_TEXT`，`rawText` 保留 JSON 数字字面量；整个字符串是十进制数字时也是 `NUMERIC_TEXT`。数值正好为 0 的数字节点和字符串都是 `NUMERIC_ZERO`。
- 06-03-03-02 的例子把字符串 `18.50` 的 `rawText` 写成 `18.50`，不带 JSON 引号。

当前冲突：同一 presence 同时被写成“字符串”和“JSON 数字或字符串”。若 `rawText` 不保留引号，数字节点 `12` 和字符串节点 `"12"` 的字面量看起来相同，presence 也相同，节点种类就丢了。

| 比较项 | 方案 A：都归入现有 `NUMERIC_TEXT` 或 `NUMERIC_ZERO`，只保留 token | 方案 B：presence 仍只用现有七种，另记节点种类，同时保留 token |
| --- | --- | --- |
| 类型语义 | 数字节点和字符串节点在分类上相同。06-03-01 的“字符串”表述被放宽 | 节点种类是提取事实。presence 仍只回答零、非零数字文本、其他文本 |
| 原始字面量 | 两边都要求不改 token。A 若不记引号，两种节点的 `rawText` 会相同 | 节点种类和 token 一起保存。token 仍可以不带引号 |
| presence 的职责 | presence 同时表示节点种类和数字形态，但实际区分不开 | presence 不承担节点种类。不新增第八种形态 |
| 与提取模型的兼容 | 与 06-03-03-01 的表一致，与 06-03-01 的句子不一致 | 要给提取结果增加一个现有表里没有的字段。presence 表本身可以不改 |
| 历史数据 | 当前没有生产观测。若将来只存 A，已经写下的观测无法再分出节点种类 | 尚未写观测。若采用 B，以后的观测从形成时就带节点种类，不需要回填 |
| 解析器复杂度 | 标准化只看 presence 和 token。字符串许可和数字节点许可无法分开 | 标准化可以规定只解析某一种节点。多一个输入字段，少一类歧义 |
| 重放 | 换解析器后若节点种类变了，A 的已存 token 看不出来 | 已存观测带有当时的节点种类。重放不覆盖它 |

【审查建议】更倾向方案 B 的方向：不新增 presence，增加节点种类事实。理由是 06-03-03-02 的例子已经把引号留在 JSON 语法里，而不是留在 `rawText`。只靠方案 A 不能同时满足“保留节点差别”和“rawText 不带引号”。这不是批准。确认前两种方案都不写进代码。

需要业务负责人确认的具体问题：数字节点和去掉引号后的数字字符串，是否必须在观测上分成两种事实。

### 3.2 科学计数法

现有原文：06-03-03-04 第 5 节写明 06-03-03-01 没有把科学计数法定义为十进制数字，不把 `1e2` 收成 `100`，也不改 `rawText`。06-03-03-01 第 6 节又把“非零 JSON 数字”全部标成 `NUMERIC_TEXT`。JSON 文本语法允许指数。语法合法不是业务允许。

| 比较项 | 明确拒绝 | 明确接受 |
| --- | --- | --- |
| JSON 语法 | 报文仍可包含 `1e2`。拒绝的是金额分类，不是把报文改成非法 JSON | 语法允许的指数被当成金额数字 |
| 提取分类 | 指数 token 不能进入 `NUMERIC_TEXT` 或 `NUMERIC_ZERO`。它可以是 `OTHER_TEXT`，或沿用无法完整按原数字理解时的字段失败。本文不新造错误码 | 必须改写 06-03-03-01，把指数算进“十进制数字” |
| 标准化解析 | 即使 token 已经写在观测上，也不把它收成普通十进制，不改 `rawText` | 要定义 `1e2`、`1.0e2`、`100` 的标度是否相同。当前没有这个定义 |
| rawText | 两种方案都保留原文。拒绝方案明确禁止改写成 `100` | 接受方案若把值收成 `100`，就违反现行“不改 rawText” |
| 精度与标度 | 不产生标度。`12` 与 `12.0` 的标度规则用不上 | 指数的标度没有现成句子。不能用 `BigDecimal` 的负标度代替业务标度 |
| 历史兼容 | 没有生产观测。拒绝方案与标准化初稿第 5 节一致，与提取表的“全部 JSON 数字”不一致 | 接受方案要同时改提取表和标准化第 5 节，否则重放时两边分类不同 |

【审查建议】更倾向明确拒绝：提取不把指数标成 `NUMERIC_TEXT` 或 `NUMERIC_ZERO`，标准化遇到这种 token 不生成结果、不改写字面量。理由是接受方案会发明标度，并直接抵触标准化初稿已经写下的“不收成 100”。拒绝方案仍要改提取表里“全部非零 JSON 数字”这半句，所以现在也不能当已批准规则。

需要确认的具体问题：带指数的 JSON 数字是 `OTHER_TEXT`，还是该字段没有正常观测。两种拒绝都不新造错误码。

### 3.3 带正负号字符串

必须分开的例子：

| 字面量 | JSON 数字节点 | JSON 字符串节点 |
| --- | --- | --- |
| `-12` | 语法上可以是数字 | 可以是字符串 |
| `+12` | 语法上不是 JSON 数字 | 只能是字符串 |
| `-0` | 语法上可以是数字，数值是 0 | 可以是字符串 |
| `+0` | 语法上不是 JSON 数字 | 只能是字符串 |
| `-12.50` | 语法上可以是数字 | 可以是字符串 |
| `+12.50` | 语法上不是 JSON 数字 | 只能是字符串 |

现有原文：06-03-03-01 没有这些例子。06-03-03-04 第 15 节已把“带正负号的字符串是否为 `NUMERIC_TEXT`”标为待确认。`PRESERVE_SOURCE` 只约束已经进入金额值之后的符号，不证明这些字符串属于数字形态。负优惠是否允许是另一件业务事。技术上能解析，不等于业务允许出现负金额。

| 比较项 | 方案 S1：只把无符号十进制算作数字文本；正号字符串不是数字文本 | 方案 S2：可选正负号属于数字文本；零仍按数值是否为 0 分类 |
| --- | --- | --- |
| 提取分类 | `+12`、`+0`、`+12.50` 是 `OTHER_TEXT`。负号字符串仍没有例子，S1 也不把它们写成已经是 `NUMERIC_TEXT` | 六个例子都能进入 `NUMERIC_TEXT` 或 `NUMERIC_ZERO`。这要扩大“十进制数字”的定义 |
| JSON 数字节点上的减号 | S1 不取消 06-03-03-01 已有的“JSON 数字”行。`-12` 作为数字节点时 token 保留减号。`-0` 是否“数值正好是 0”仍要单独确认 | 数字节点和字符串使用同一套符号规则 |
| 标准化 | 未分类成两种数字形态的 token 不解析。已保留的减号不被去掉 | 解析器必须接受正号，并且不能把 `+12` 改写成 `12` |
| 业务负金额 | 两种方案都不取绝对值，不把负数改成 0。业务是否允许负优惠仍待确认 | 同左。S2 只增加技术分类，不表示负金额已被业务允许 |
| 历史与重放 | 没有生产观测。S1 不把尚未举例的正号写进历史 token | 一旦按 S2 写下观测，以后收紧回 S1 会让同一报文的 presence 变化。已有观测仍不能覆盖 |

【审查建议】更倾向 S1 作为下一步讨论稿：正号不写入当前“十进制数字”；JSON 数字节点上的减号继续留在 token 里，直到 `-0` 的零值分类被单独写明；带减号的字符串继续保持 06-03-03-04 第 15 节的待确认，不在本报告里归入 `NUMERIC_TEXT`。这不是批准。

需要确认的具体问题有三个：正号字符串是否永远是 `OTHER_TEXT`；减号字符串是否属于数字文本；JSON 数字 `-0` 是 `NUMERIC_ZERO` 还是别的形态。第三个问题确认前，不把 `-0` 写成 0 的同一种 token。

### 3.4 parserVersion 的两种工作

| 问题 | A. 从原始报文读 JSON 并形成字段结果 | B. 对已经写下的 `rawText` 做标准化 |
| --- | --- | --- |
| 是否依赖 `parserVersion` | 【设计决定】依赖。任务第一阶段把它和 `snapshotId` 一起固定，重试复用 | 【审查建议】不依赖。输入已经是观测上的 token 和 presence。换解析器不能改这个 token |
| 是否重读原始报文 | 尚无观测时要读。已有观测时先返回原观测，恢复前不读报文字节 | 不允许为了标准化再解析 JSON |
| 重试如何稳定 | 同一任务用首次固定的 `parserVersion`。尚未形成观测时，不能声称换解析器后字面量相同 | 稳定来自已存 `rawText` 和两个规则版本。解析器升级不触发重算 |
| 历史观测能否重解析 | 【设计决定】不能覆盖。核对提取若与已存字面量不一致，不改观测 | 不能。标准化失败也不改观测 |
| 是否进入观测身份 | 【设计决定】不进入 | 不进入 |
| 是否进入标准化身份 | 不进入 | 【设计决定】不进入。身份只加 `normalizationRuleVersion` 和 `conversionRuleVersion` |

【已确认事实】06-03-03-02 把解析器版本的注册、发布、兼容和重放列为进入报文解析 Java 实现之前的事项。本文不设计版本号怎么分配。A 因此仍不能实现。B 的拒绝判断可以不读报文，但成功解析仍被第 3 节的未决语法挡住。

## 4. 推荐意见

【审查建议】汇总如下。每一条都等待确认，不能当作 ADR 或设计稿修订。

1. 节点种类与 presence 分开记，不新增 presence。未确认前不实现。
2. 科学计数法在提取和标准化两边都拒绝收成普通十进制，且不改 `rawText`。拒绝形态用现有 `OTHER_TEXT` 或现有字段失败表达，不新造错误码。提取表的“全部 JSON 数字”尚未按此收窄。
3. 正号字符串先不归入数字文本。减号字符串保持待确认。JSON 数字上的减号保留在 token 中。不取绝对值，不把负数改成 0。
4. 标准化只消费观测，不重读 JSON，不修改字面量。`parserVersion` 只约束报文提取，不进入两条金额身份，也不并入两个规则版本。

## 7. 完整输入输出契约

以下是候选契约，不是已批准接口。

提取阶段：

- 输入：已经保存的原文、任务上已经固定的 `snapshotId` 和 `parserVersion`、该快照内已经确定的 `contractVersionId`。契约版本未确定时没有字段结果，也没有观测。
- 节点识别：只看契约声明路径上的节点。数组或对象是 `NON_SCALAR`。JSON null、空字符串、缺失互相区分。
- token：有字面量时按看到的文本保留。不先变成 `double`。不把指数收成普通十进制。引号是否进入 `rawText`，现有例子是不进入；节点种类若要保留，不能只靠去掉引号后的 token。
- 分类：只使用现有七种 presence 和现有字段码。指数、正号、减号字符串在确认前不能由本报告指定 presence。
- 不能生成正常字段结果：整份契约版本或报文阻断；`TYPE_MISMATCH`、`PATH_NOT_UNIQUE`、`RAW_TEXT_UNRETAINABLE`。这些路径不写 `ObservedAmount`。

标准化阶段：

- 输入：一条已经形成的观测，以及该观测引用的快照目录事实。不重新读取 JSON，不使用 `parserVersion` 改写 token。
- 只读取观测上的 `rawText`、presence、字段码和匹配事实。
- 不允许修改原始字面量，不允许把结果写回观测。
- 可以继续的分类，仍只限于设计稿已经写明的条件：字段码 `OK`，presence 为 `NUMERIC_ZERO` 或 `NUMERIC_TEXT`，执行状态 `MAPPED`，并且其余门禁通过。`UNMAPPED` 和 `CONFLICT` 停止。
- 解析失败：该字段没有标准化结果。观测保持原样。不新造错误码。
- 版本无法确定：不编造 `normalizationRuleVersion` 或 `conversionRuleVersion`，不生成结果。
