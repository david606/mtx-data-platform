## 3. 冻结的现有语义

本轮不把下面的规则改成新规则。

有效阻断：一个任务最多一条。它参与终态。拒绝审计失败不撤销它。拒绝审计不是第二条有效阻断。06-04-11 第 8 节，Pipeline 第 11.1 节。

拒绝审计的首次写入条件：终态尚未提交，已经有一条有效阻断，另一条不同 `blockIdentity` 被拒绝。身份和四个内容字段保持这次仲裁的原始值。它不参与终态。失败不改阻断、任务状态、尝试执行权和已提交领域结果。

迟到审计的首次写入条件：终态已经提交，该 `blockIdentity` 还没有任何既有记录。不改已提交终态和领域结果。

重复：同一身份、同一内容按既有种类幂等返回。同一身份、不同内容是 `BLOCK_CONTENT_CONFLICT`，不覆盖。已有拒绝审计和已有有效阻断都不因任务后来进入终态而改类。

由此可以直接推出，并且现行文档已经这么写：分类看的是第一次成功写入时有没有终态、有没有有效阻断、有没有同身份记录。它不看 `receivedAt`、Worker 本地时钟、日志时间，也不在终态提交之后回头改写种类。

## 4. 权威发生时点的四个候选

### 4.1 候选 A：最终审计记录成功提交才算发生

拒绝仲裁可以已经在调用栈里完成，但审计 `INSERT` 尚未成功时，库里没有这个事件。Worker 在提交前崩溃，其他进程看不到被拒绝身份。Pipeline 第 11.1 节要求待处理责任不能只留在内存里，所以只承认最终审计行，又允许终态先提交，跨进程恢复就没有可恢复的发生时点。终态后的第一次 `recordTaskBlock` 还会按现行首次写入写成迟到审计。候选 A 描述的是「没有别的事实时，现行规则实际承认的唯一持久化时点」。它满足不了 06-04-34 的恢复目标。

### 4.2 候选 B：仲裁结果确定时即发生

若「确定」只在内存，它不能作为跨进程依据。Pipeline 已把即时重试限制为调用方还活着并且已经收到失败结果。内存事件不得记成已持久化。没有另一次成功 `COMMIT`，候选 B 和候选 A 在崩溃之后是同一种丢失。

### 4.3 候选 C：独立的拒绝责任事实成功提交时发生

Pipeline 第 11.1 节把「与权威任务协调状态一致的持久化待处理记录」列为未选定的候选，不是已有实体。最终审计行和这份责任事实不是必然同一行。

责任事实自己的 `COMMIT` 成功，只说明这一行已经持久化。它不能自动证明写入时 Task 尚未终态，也不能自动证明当时的有效阻断仍是 A。调用方在事务外读到的 `RUNNING` 不是这个证明。06-04-11 第 7 节已经写明，事务外先读再在另一个事务里写，中间的其他事务可以先提交，那不是围栏。现行拒绝审计还不锁任务行，所以现有文档没有这条证明。候选 C 若要让该行充当终态前分类，必须先满足第 4.5 节的加锁条件。该条件待决策，不是已有实现。

在该条件已经满足、并且这次 `COMMIT` 已确认的前提下，恢复才可以按该行补写，不按恢复当时的任务状态重判。`COMMIT` 结果不明时，沿用 06-04-09：不记成已发生，也不记成确定未发生。读不完整不得当成没有这件事实。它需要自己的逻辑身份才能幂等。物理唯一约束仍是 IR-02，现在没有。任务行锁不能代替这个唯一约束。它会多一个窗口：责任已提交、审计未提交、两边都可能结果不明。保留和清理属于 IR-15，本轮不定。这不是 Outbox 或 Inbox。06-04-09 没有引入那两个组件。

### 4.4 候选 D

没有文档支持的第四种组件。把终态推迟到拒绝审计提交之后，会改掉 Pipeline 第 11.1 节「审计是否完成与任务终态是两个状态」，也会改掉 06-04-11 第 7 节「拒绝审计不并入终态事务」。第 8 节的 `FAILED` 落库只要求阻断已经是这一条，正文没有写它等待拒绝审计。把等待补进第 8 节是对已冻结规则的修订问题，不是已有机制。本轮不采用。第 4.5 节也不把终态改成等待责任事实。

### 4.5 责任事实与 Task 终态的并发序列化边界

这里分开四件事。已经写在 06-04-11、06-04-09 和 06-04-19 里的，是现有约束。候选 C 还要额外满足的加锁次序，是待决策条件。责任事实这张行本身尚未批准。下面任何顺序都还没有 MySQL 8.0.46 并发实验。

现有约束：

- 领取、阻断登记、成功类终态、`FAILED` 收敛、进入 `RETRY_WAITING` 和 `RUNNING` 取消，先对任务行 `SELECT ... FOR UPDATE`，校验放在持锁之后，提交前不释放这把锁。既改任务又改尝试时，先锁任务行，再动尝试行。06-04-11 第 7 节。这就是 Task-first。
- 这组「先锁任务、再改尝试」不套到只追加、不改尝试执行权的拒绝审计和迟到审计。同一节的拒绝审计行写明不锁任务行，也不要求调用方仍是 `CURRENT`。
- 06-04-19 第 6 节把任务行锁限于 B 类。拒绝审计和迟到审计不套用 B 类围栏。A 类从「不锁定一条 `RUNNING` 任务」开始。
- 成功类终态的条件是有效阻断为空。`FAILED` 的条件是有效阻断等于已登记的那一条。06-04-11 第 8 节。因此已经提交的 `SUCCESS` 不能同时带着有效阻断。这是终态条件，不是拒绝责任事务已经和终态互斥的证明。
- 两个都要这把任务行锁的事务会排队。先持锁的一方提交之后，后一方才继续，并且看到先提交的行。06-04-11 第 7 节用这一点约束领取和旧代次写入。手册依据是加锁读在提交或回滚时释放。该排队没有覆盖不取这把锁的拒绝审计。
- 隔离级别仍未选定。普通一致性读不能充当随后写入的围栏。06-04-11 第 7 节。事务外缓存的 `RUNNING` 不能带进下一次事务。

候选 C 若要让责任行证明「终态前、阻断仍为 A」，还需要下面的条件。现有文档没有这段协议，所以整段待决策，不能写成已经存在的实现：

1. 责任事实事务先锁任务行，不先锁尝试行，也不修改尝试的执行结果或执行权。
2. 持锁之后重新读取 `status` 和有效阻断。不使用本次事务开始前缓存的 `RUNNING`。
3. 只有重新读到尚未终态、且有效阻断仍是 A，才插入身份 B 和四个内容字段。
4. 这把锁保持到该事务 `COMMIT` 或回滚。插入成功还不是 `COMMIT` 成功。
5. 本事务不修改 Task 终态、有效阻断和领域结果。终态仍由 06-04-11 第 8 节自己的事务提交。
6. 条件不成立则整笔回滚，不留下一条声称「终态前」的责任行。终态已经提交时，这次到达按迟到审计处理，不创建终态前责任事实。

在这六条被接受之前，不能说责任事实 `COMMIT` 自动证明终态前发生。

#### 场景 A：责任事实事务先取得任务行锁

若第 4.5 节的待决策条件成立，顺序可以是：责任事务取得任务行锁，持锁重读，确认尚未终态且阻断仍为 A，插入身份 B，`COMMIT` 成功后释放锁。终态事务也要这把锁，所以它必须等到责任事务结束，再按当时已提交的行做自己的检查。06-04-11 只证明了「两边都取这把锁时，后一方等待」。它没有证明责任事务会取这把锁。因此场景 A 是候选 C 的条件，不是当前实现。没有 8.0.46 实验证明终态事务一定会等到责任事务完成。

#### 场景 B：终态事务先取得任务行锁

终态事务先锁任务行、按第 8 节检查状态和阻断、提交 `SUCCESS` 或 `FAILED`、再释放锁。这一段是现有设计，仍然待验证，但不是本轮新造的事实。

责任事务若在锁释放后才取得同一把锁，必须重新读取当前 `status` 和有效阻断。不得用更早缓存的 `RUNNING` 插入终态前责任事实。终态已经提交、且该身份还没有任何已提交记录时，现行首次写入仍是迟到审计。Pipeline 第 11.1 节，06-04-19 第 3 节。

现有拒绝审计不取任务行锁。因此「随后取得锁并重读」还不是拒绝责任的现行步骤。把它写成责任事务的必做步骤，属于场景 A 的同一项待决策。未持锁就插入，不能引用场景 B 的重读。

#### 场景 C：责任事实与 `SUCCESS` 并发

已经证明的只有终态条件：`SUCCESS` 要求有效阻断为空；带着有效阻断 A 的已提交行不能是 `SUCCESS`。06-04-11 第 8 节。拒绝责任若要声称「当时阻断是 A，且 Task 尚未终态」，必须和这次 `SUCCESS` 使用同一条任务行锁，使两个 `COMMIT` 有唯一先后。先提交 `SUCCESS` 的一方释放锁之后，责任事务重读到的就不再是「尚未终态且阻断为 A」，于是不得创建终态前事实。先提交责任事实的一方释放锁之后，`SUCCESS` 仍要自己的阻断为空条件，不会把已有阻断改成空。

当前文档没有这把共同的锁。拒绝审计明确不锁任务行。06-04-19 也不把它放进 B 类。所以互斥待决策。不能用「`SUCCESS` 的 `WHERE` 要求阻断为空」代替这次加锁：那个条件阻止的是带阻断的 `SUCCESS`，阻止不了一笔不持锁、又使用旧 `RUNNING` 的责任插入。

#### 场景 D：`COMMIT` 结果不确定

责任事实和最终审计各自提交。一边的结果不明，不能用来推断另一边。06-04-09 第 4 节把审计写成独立事务。第 5 节的故障矩阵都未执行。

| 情况 | 现有约束 | 对责任事实的用法 |
| --- | --- | --- |
| `COMMIT` 尚未发送 | 06-04-11 第 7 节：连接中断不猜测提交结果。06-04-19 第 6.1 节把「尚未发送 `COMMIT`」和已经发送分开。该节的重做步骤属于 A 类和 B 类，没有责任事实专用协议 | 不得记成已发生，也不得记成确定未发生。不完整读取不得当成没有这行 |
| `COMMIT` 已发送但响应丢失 | 06-04-09 第 2 节：响应丢失时重试读取，不覆盖。第 8 节第三轮：终态事务提交后响应丢失时，重读终态和当前尝试，不新建尝试。这些读取步骤没有写成责任事实的协议 | 同一原则：先完整读取。读不完就停止，不伪造分类，不另写一条迟到审计来收场 |
| `COMMIT` 已确认，随后 Worker 崩溃 | 06-04-09 第 5 节：从最后一条已提交记录继续。已提交行保留 | 只有第 4.5 节的加锁条件也已满足时，这行才是终态前分类。否则一行已经提交，仍不能自动当成终态前事实 |
| 结果不明期间，另一 Worker 提交终态 | 终态事务会锁任务行。若责任事务当时仍持有同一把锁，后一方等待。这个「若」尚未被现有拒绝审计证明 | 终态可以按自己的条件先提交。不明期间不得把没读到责任行当成「没有拒绝」，也不得用终态结果改写尚未确认的分类 |

不引入 Redis 锁、Inbox、Outbox 或 DLQ。任务行锁如果以后被选为这条边界，它仍只串行同一任务上的这两笔事务，不代替 IR-02 的唯一约束，也不把恢复执行者写成 `CURRENT`。

## 5. 时间线

下面每一行都按现行规则回答。没有已提交的拒绝分类时，「是否允许写成迟到审计」说的是现行首次写入，不是本轮已经批准的补写。候选 C 的责任事实现在还不存在，对应行标成假设。

### 5.1 第二个身份被拒绝，尚未产生持久化记录时 Worker 崩溃

任务可仍是 `RUNNING`。有效阻断 A 已经提交。拒绝事件未持久化。最终审计未持久化。这次没有拒绝侧的 `COMMIT`。恢复只能读到阻断 A 和任务行，读不到身份 B。没有可重试的持久化请求。不得把不存在的 B 写成迟到审计，也不得伪造拒绝审计。不得改变 Task 或 Attempt。风险是事件丢失。

### 5.2 拒绝责任事实 `INSERT` 之后、`COMMIT` 之前崩溃

任务可仍是 `RUNNING`。有效阻断 A 已在。现行文档没有责任事实这一行；若按候选 C 假设这次 `INSERT` 属于尚未发送 `COMMIT` 的事务，拒绝事件是否已持久化不确定。最终审计未持久化。`COMMIT` 未发送，不得把断连记成已提交或已回滚。恢复在完整读完之前没有可依据的身份 B。不确定期间不允许重试插入另一份内容，也不允许写成迟到审计来收场。不得改变 Task 或 Attempt。风险是事件可能尚未发生，以后也可能重复插入。

### 5.3 `COMMIT` 已发送，响应丢失

任务可仍是 `RUNNING`。有效阻断 A 已在。拒绝事件是否持久化不确定，要看这次提交的是责任事实还是最终审计。最终审计同样不确定。`COMMIT` 结果不明。06-04-09 把已发送但没有结果，和尚未发送分开。恢复必须完整读取对应身份之后才知道有没有行。不明期间不第二次插入不同内容。不得改成迟到审计来代替这次不明提交。不得改变 Task 或 Attempt。把不明记成失败会丢事件，记成成功又可能重复。

### 5.4 责任事实 `COMMIT` 已确认，最终审计尚未写入

仅在候选 C 下才可能有这行。现行能力里它不存在。最终审计未持久化。责任事实的 `COMMIT` 已确定，只表示该行已持久化；审计的 `COMMIT` 还没有。若这行是在第 4.5 节的任务行锁下、持锁重读到尚未终态且阻断仍为 A 之后提交的，恢复可以读到身份、四个内容字段和当时的阻断，并按拒绝分类补写。不得因为任务后来进入终态而改成迟到审计。若不满足该加锁条件，已确认的 `COMMIT` 仍不能自动证明终态前发生，恢复不得把它当成拒绝分类来源。不得改变 Task 或 Attempt。风险是审计行还没有。责任行在 `COMMIT` 已确认时不丢，但它的分类效力待决策。

### 5.5 责任事实提交之后，任务进入 `FAILED`

任务已经是 `FAILED`。有效阻断仍是 A，并且与该终态是同一条。06-04-11 第 8 节。终态的 `COMMIT` 已确定。最终审计可能尚未写入。恢复能读到终态和阻断 A。责任事实只有在第 5.4 节所说的加锁提交已经确认时，才是可恢复的拒绝分类；这时补写仍保持拒绝，不按当前 `FAILED` 重判。没有那份已串行化的事实时，现行首次写入会是迟到审计。`FAILED` 事务不等待责任事实，这一点保持不变。终态已提交，不得再改 Task 或 Attempt。这就是第 6.1 节。

### 5.6 任务已经是 `SUCCESS`，恢复才发现先前的拒绝责任

任务是 `SUCCESS`。成功类终态要求有效阻断为空。06-04-11 第 8 节。拒绝审计的前提是当时已经有有效阻断，所以随后能成立的终态只是带同一条阻断的 `FAILED`。已经提交的 `SUCCESS` 与「提交责任事实时有效阻断为 A」不能同时成立，但只有两边通过同一任务行锁分出先后，才能阻止那条矛盾行被写出来。这把共同的锁尚未证明，见第 4.5 节场景 C。

不能用当前 `SUCCESS` 证明终态前发生过拒绝，也不能用事务外缓存的 `RUNNING` 在 `SUCCESS` 提交之后补一条终态前责任事实。没有已串行化的事实时，新身份的首次写入是迟到审计。不得把终态改成带阻断的 `SUCCESS`，也不得凭 `SUCCESS` 补写拒绝审计。若库里出现声称终态前已有阻断的责任行，而当前行是无阻断的 `SUCCESS`，这是完整性异常。本轮不规定新的错误码。用当前状态或旧缓存推断，会把没有发生的拒绝写成拒绝审计。

### 5.7 最终审计 `INSERT` 成功，但 `COMMIT` 结果不确定

任务不因这次审计而改变，可以仍是 `RUNNING`，也可以已经终态。有效阻断不改。若走候选 C，责任事实可以已经在；最终审计是否持久化不确定。`COMMIT` 不明。恢复在完整读到该审计身份之前不能判断。允许的重试是读完之后、内容相同才按已有记录确认。不得另写一条迟到审计来代替这次不明提交。不得改变 Task 或 Attempt。可能已经有一行，也可能还没有。

### 5.8 最终审计成功，责任完成状态更新失败

任务和有效阻断都不改。拒绝事件已经由审计行持久化。最终审计已持久化，它的 `COMMIT` 已确定。完成标记的更新结果不明。恢复读到的是审计行。同一内容只做幂等确认，不新增。不得写成迟到审计。不得改变 Task 或 Attempt。风险是标记和审计行不一致，不得因此再插一行。只更新标记而没有审计行，不算完成。

### 5.9 两个恢复进程并发补写同一拒绝审计

任务和有效阻断都不改。拒绝事件是否已持久化，取决于责任事实或审计行有没有先提交。最终审计在逻辑上应是一条。先提交的一方 `COMMIT` 确定，后写的一方要读到这一行。Pipeline 第 11.1 节和 E2E-117 要求同一身份、同一内容只留一条，一方 `REJECT_AUDIT_RECORDED`，另一方 `REJECT_AUDIT_ALREADY_RECORDED`。允许后写者按同一内容重试。不得各写一种分类，包括不得一条拒绝、一条迟到。不得改变 Task 或 Attempt。IR-02 的物理唯一约束未验证，现在不能保证数据库只留一行。

### 5.10 原 Worker 消失，其他 Worker 接管恢复

任务状态不因原进程消失而改变。有效阻断不改。只有已经提交的事实可以交接。最终审计同样只认已提交的行。未提交的内存仲裁没有 `COMMIT`。接手者读不到原进程内存。没有事实就不允许补写，也就没有可重试的拒绝请求。分类只来自已提交事实；没有事实时不得写成迟到审计来冒充这次拒绝。不得把接手者写成原尝试的 `CURRENT`，也不得改 Task 或 Attempt。没有事实则事件无法接手，等于丢失。

### 5.11 同一身份已有拒绝审计，扫描仍看到未完成责任

任务可以已经终态。有效阻断不改。拒绝事件已持久化，最终审计也已持久化，两边的 `COMMIT` 都已确定。恢复读到的是这条拒绝审计。同一内容允许幂等重试，返回 `BLOCK_IDENTITY_REJECTED` 和 `REJECT_AUDIT_ALREADY_RECORDED`。E2E-116，未执行。不得改成迟到审计。不得改变 Task 或 Attempt。可能重复调用，不应产生第二行。未完成标记与已存在的审计行不一致时，按第 5.8 节收口，不另插。

### 5.12 已有拒绝审计的身份再次以不同内容提交

任务和有效阻断都不改。原拒绝事件和原审计都已持久化，`COMMIT` 已确定。恢复读到的是原四个内容字段。不允许用新内容重试覆盖。不得把这次写成迟到审计。返回 `BLOCK_CONTENT_CONFLICT`，不覆盖。不得改变 Task 或 Attempt。不新增行，也不丢失原行。

## 6. 分类冲突

### 6.1 场景一：终态前拒绝，终态后才补写

步骤 1 至 3 是现行仲裁：`RUNNING`，已有阻断 A，身份 B 被拒绝。步骤 4「拒绝责任事实持久化成功」不是现行能力。06-04-34 已写，这个身份此时只在调用里。步骤 5 的 `FAILED` 按 06-04-11 第 8 节是登记之后的另一笔事务，条件只是阻断仍是 A。第 7 节写明拒绝审计不并入这笔记终态的事务，并且不锁任务行。现行规则因此可以先提交 `FAILED`，不等待 B 的审计。步骤 6 的恢复进程在现行数据里发现不了 B。

在假设步骤 4 的事实已经成功提交、并且该提交满足第 4.5 节的任务行锁条件时：

- B 应当仍是拒绝审计。分类来自持锁重读后提交的「终态前、相对阻断 A、身份 B、四个内容字段」，不是来自恢复时任务已经是 `FAILED`，也不是来自事务外缓存的 `RUNNING`。
- 普通 `recordTaskBlock` 不够。终态已提交且 B 还没有审计行时，现行返回是 `LATE_BLOCK_RECORDED`。Pipeline 第 11.1 节。
- 因此需要单独的恢复补写语义：只消费这份已经串行化的责任事实，写出拒绝审计，不重新仲裁。
- 必须保留事实里的身份、四个内容字段和当时的有效阻断身份。不读取恢复时的任务状态来改类。

若步骤 4 没有成功提交，或者提交时没有持有任务行锁并重读，现行规则回答不了「B 仍是拒绝审计」。那时不存在可恢复的 B，已提交的行也不能自动当成终态前事实。这就是 R-02 仍待决策的原因，不是已经选定要增加责任事实。第 4.5 节的加锁条件同样待决策。

### 6.2 场景二：终态后才首次到达

任务已是 `SUCCESS`。身份 C 首次到达。没有终态前提交过的拒绝责任事实，也没有 C 的审计行。C 是迟到审计。

与场景一的 B 区分，不能只看当前任务状态。两个场景在恢复时都可以已经终态。区分点只能是：是否存在一次更早的、在任务行锁下重读并成功提交的分类事实，写明该身份在终态前被拒绝。没有这份事实，C 不得补写成拒绝审计。终态事务先提交之后才到达的身份，按迟到审计处理，不得再用旧的 `RUNNING` 创建终态前责任事实。`receivedAt`、Worker 时钟和日志时间都不是这份事实。

## 7. 恢复写入语义

不决定 Java 方法名。需要分开的是语义，不是模块。

| 语义 | 何时 | 分类依据 | 不得做的事 |
| --- | --- | --- | --- |
| 正常阻断仲裁 | 终态尚未提交 | 当时没有有效阻断则可能成为有效阻断；已有有效阻断且是另一身份，则拒绝 | 不把拒绝写成第二条有效阻断 |
| 拒绝审计首次写入 | 终态尚未提交，且本次仲裁已经确定拒绝 | 同一次调用中的身份和四个内容字段 | 失败不回滚已提交阻断 |
| 已有拒绝责任的恢复补写 | 责任事实已经按第 4.5 节持锁重读并成功提交，最终审计还没有同内容的行。此时任务可以已经终态 | 只读该事实。不重新按当前终态分类。不使用事务外缓存的 `RUNNING` | 不把该行写成迟到审计，不改 Task、Attempt、有效阻断。未满足第 4.5 节时，不得把该行当成拒绝分类来源 |
| 迟到审计首次写入 | 终态已提交，且该身份没有任何已提交的拒绝责任或审计行 | 当前终态加上「没有更早的拒绝事实」 | 不得因为调用者自称为恢复而改成拒绝审计 |
| 已有记录的幂等确认 | 同身份记录已在 | 既有种类和既有内容 | 内容不同则冲突，不覆盖，不改类 |

恢复补写必须携带、并且只能来自已提交事实的不可变项：被拒绝的 `blockIdentity`、四个内容字段、仲裁时的有效阻断身份，以及「持有任务行锁并重读时，终态尚未提交、有效阻断仍是这一条」。恢复进程自行推断的值，以及事务外缓存的任务状态，不能充当来源。只看到责任行已经 `COMMIT`，还不够。

不需要原 Worker 的 `executionGeneration` 或 `taskAttemptId` 作为身份或授权。Pipeline 已写明它们不进入阻断身份和内容。授权是这份已提交的拒绝事实，加上调用没有改任务执行权。原尝试已经不是 `CURRENT`，也不取消这项授权。没有这份事实，就没有恢复授权。

责任事实与审计完成的关系：两边各自提交，各自处理 `COMMIT` 是否确定。审计行成功提交且内容与一份已经满足第 4.5 节的责任事实一致，责任即为完成。只更新一个完成标记却没有审计行，不算完成。标记更新失败而审计行已在，不另插一行。内容不一致是完整性异常，不覆盖。不新增错误码。责任事实的结果不明，不能用审计行的结果来代替，反过来也不行。

## 9. 结论

1. 推荐的权威发生时点是：在持有任务行锁、并重读到「终态尚未提交、有效阻断仍为当时那一条」之后，一次成功 `COMMIT` 固定被拒绝身份和四个内容字段。内存仲裁不是这个时点。责任行的 `COMMIT` 本身不能自动证明终态前发生。这是调查建议，不是批准的新表，也不是已经实现的加锁协议。
2. 在现有规则里，唯一已经能充当拒绝分类的，是终态前提交成功、并且此后不再改类的拒绝审计行。它提交之后，任务再进入终态，种类保持拒绝。E2E-116，未执行。现行拒绝审计不锁任务行，所以这一行的 `COMMIT` 同样还没有和第 4.5 节一样的并发证明。
3. 是否再要一份独立的拒绝责任事实：现行文档没有这行。只有在允许 `FAILED` 先于拒绝审计提交、又仍要求终态后补写保持拒绝分类时，才必须另有这份事实。即便如此，它还要满足第 4.5 节的任务行锁条件，否则不能证明发生在终态前。Pipeline 把这类待处理记录列为未选。本轮不批准它，也不把它写成 Outbox。
4. 终态后的恢复补写，只有在第 1 点的事实已经按第 4.5 节提交时才保持拒绝审计。分类读该事实，不读恢复时的任务状态，也不读事务外缓存。
5. 终态后首次到达、且没有这份事实的新身份，仍是迟到审计。终态事务先拿到任务行锁时，后续不得再用旧的 `RUNNING` 创建终态前责任事实。
6. 普通 `recordTaskBlock` 的现行返回不够完成第 4 点。恢复补写需要单独语义。本轮不命名接口。
7. 尚未解决的是：这份事实与最终审计是否同一行、它的逻辑身份和物理唯一约束、它是否取任务行锁并保持到自己的 `COMMIT`、它和终态事务的先后如何读取、两个 `COMMIT` 各自不明时如何确认、两个恢复者并发，以及保留策略。加锁条件待决策。物理约束挂在 IR-02。保留挂在 IR-15。都没有 8.0.46 并发实验。
8. Pipeline 第 11.1 节若要支持终态后的拒绝补写，需要后续修订：在「终态已提交且该身份尚无记录则是迟到审计」之外，写明已按任务行锁提交的拒绝分类事实优先于当前终态。06-04-11 第 7 节的首次写入两行也要同样区分，并且要决定拒绝侧是否进入现在明确排除它的任务行锁。本轮不改这两份文档。另一项可选修订是让终态等待未完成的拒绝审计，那会改变「两个状态」和现有的 `FAILED` 条件。两项都未选。第 4.5 节不改变 Task-first，也不让终态事务改去等待责任事实。
9. R-02 仍待决策。发生时点的定义有调查建议。责任事实与终态的互斥没有充分证据。实现路径不能收成唯一方案。
10. IR-10 保持待决策、P1。不修改台账。IR-02、IR-07、IR-09 和 IR-15 也不关闭。
