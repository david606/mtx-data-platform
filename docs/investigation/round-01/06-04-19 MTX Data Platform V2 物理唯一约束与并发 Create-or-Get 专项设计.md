# 06-04-19 MTX Data Platform V2 物理唯一约束与并发 Create-or-Get 专项设计

本文把已经冻结的逻辑身份整理成 MySQL 8.0.46 上的候选物理唯一约束，并写明跨 Worker 的 Create-or-Get。它是候选设计，不是 DDL，不是已接受 ADR，也没有在 MySQL 8.0.46 上执行。

基线是 `3d7e310c7ba7f41ad81919b9c5c011b051d40cde`。起稿时不修改 Pipeline、06-04-08、06-04-09、06-04-11、台账或 ADR。IR-02 仍是待决策、P0，不关闭。

针对 [06-04-20](06-04-20%20MTX%20Data%20Platform%20V2%20IR-02%20物理唯一约束与并发%20Create-or-Get%20独立架构复审报告.md) 的 L-01、L-02、L-03，本文改正了适用范围，补上冲突决定，并把「胜出记录读取未完成」从「提交结果不确定」里分开。随后又把 `COMMIT` 尚未发送时的连接中断与已经发送的 `COMMIT` 分开。第 6.5 节覆盖五种断连子场景，并写明唯一冲突后确认缺行不进入第 6.3 节。针对 [06-04-21](06-04-21%20MTX%20Data%20Platform%20V2%20IR-02%20第十六轮定点独立复审报告.md) 的 M-01，超时错误未完整返回单独成一种已知事实，不并入 `INSERT` 执行期间断连。不改 06-04-20 和 06-04-21，不改 ADR-0003 的业务规则，不关闭 IR-02、IR-03、IR-07 或 IR-09。这些改正没有执行 SQL，也没有并发测试。

## 2. IR-02 的边界

台账写明：观测身份是 `rawPayloadRef + snapshotId + contractVersionId + fieldPath`。标准化另有 `normalizationIdentity` 和 `versionFixKey`。物理索引、锁、隔离级别和 DDL 留待存储设计。先查后插会留下两条有效观测。关闭条件是把已有逻辑身份落成唯一约束，并规定并发失败方读取胜出记录。台账不指定索引类型。

本文不做的事：

- 不发明来源事件身份，也不把 Kafka offset、`rawPayloadRef` 或 `receivedAt` 写成任务幂等键。那是 IR-03。
- 不证明 offset 可以安全提交。
- 不关闭 IR-07 或 IR-09。执行权文字和事务提交点仍待验证。
- 不把任务行锁、`CURRENT` 计数、代次或普通查询索引写成物理唯一约束。
- 不引入 Redis 锁、Inbox、Outbox 或 DLQ。
- 不把 Doris 写成事务幂等存储。ADR-0005 的分析副本不回写权威。

已有文档冲突，本轮只记录：

| 冲突 | 证据 | 影响 |
| --- | --- | --- |
| 身份列必须 `NOT NULL`，但不转换时 `conversionRuleVersion` 为空，且不得改成哨兵 | 06-04-08 第 1 节与第 6 节；06-04-09 第 3.4 节；06-03-03-04 的逻辑身份 | `normalizationIdentity` 的物理唯一索引现在不能同时满足两边。见第 5 节 |
| 06-04-08 第 2、4 节写当时不设计租约和执行权 | 06-04-11 已有租约和执行权候选 | 尝试唯一键仍只按 `taskAttemptId`。租约不进入该键。不改 06-04-08 |

## 4. 四类机制

| 机制 | 已有规定回答的问题 | 不能代替 |
| --- | --- | --- |
| 逻辑身份 | 哪一组字段表示同一条业务记录 | 物理上阻止第二行 |
| 物理唯一约束 | 两个事务不能各提交一行相同的完整身份 | 执行权、来源事件身份、offset |
| 查询索引 | 加快查找 | 唯一性。普通索引允许重复键 |
| 完整性检查 | 提交前发现本事务看见的行数或内容不符 | 其他不遵守协议的插入。`COUNT(*)` 不是唯一约束 |

## 5. 物理唯一约束候选

能直接写出约束条件的，仍受列宽、字符集和排序规则限制。06-04-08 已写明：字符集未定时不能创建物理索引。本轮不指定字符集、排序规则、列类型或列宽。

候选共同规则，均来自 06-04-08，本轮不放宽：

- 身份列 `NOT NULL`。允许 NULL 的唯一索引可以有多行 NULL。
- 唯一性覆盖完整列，不用前缀索引。
- 不使用 `INSERT IGNORE` 或 `ON DUPLICATE KEY UPDATE`。后者会更新旧行。
- 不分区。分区列必须进入每一个唯一键，现有身份里没有已经证明的分区键。
- 不把哈希列当成领域身份。

| 实体 | 候选唯一键 | 本轮能否写成可执行约束 | 原因 |
| --- | --- | --- | --- |
| ObservedAmount | 四段观测身份，全部 `NOT NULL` | 条件具备后可以。现在不能执行 | 列宽和排序规则未定。键长是否超过 3072 字节待实测 |
| ExtractedFieldResult | 三个独立字段，全部 `NOT NULL` | 同上 | Pipeline 要求按字段比较，不串成一个序列化字符串 |
| 版本固定记录 | `versionFixKey` 的三段，全部 `NOT NULL` | 表是否独立未决 | 阶段标记是已有的「标准化」，不另造阶段 |
| NormalizedAmount | `normalizationIdentity` 的全部组成 | 暂不能完成 | 空的 `conversionRuleVersion` 与 `NOT NULL` 冲突，见下节 |
| ConflictDecision | `conflictDecisionId`，`NOT NULL` | 标识列宽和生成算法未定前不能执行 | 与 `MappingConflictDecision` 是同一记录。正文、证据、窗口和 `bodySha256` 都是内容，不进入这条唯一键。新决定用新标识 |
| TaskExecutionContext | 每个非重放 `taskId` 一份胜出上下文 | 可以落在任务行，不一定独立成表 | 第一次选哪份快照仍是 IR-04 |
| Snapshot | `snapshotId` | 标识列宽未定 | 不决定尚未关闭的快照选择 |
| ContractVersion | `contractVersionId` | 标识列宽未定 | 正文哈希是内容列，不进入唯一键 |
| Task 稳定事件 | 来源已声明的全部身份字段 | 暂不能设计 | IR-03。未声明的来源不建这条约束，也不建任务 |
| ReplayRequest | `replayRequestId` | 暂不能设计 | 生成算法未定 |
| TaskAttempt | `taskAttemptId` | 标识算法未定前不能执行 | 不把 `taskId` 做成尝试表的唯一键。租约、代次、`ownership` 都不进入该键 |
| `blockIdentity` | `taskId`、阻断码、阻断主体 | 物理列未冻结 | 不把 `taskAttemptId` 放进键 |
| 每任务一条有效阻断 | 不建成过滤唯一索引 | 不采用 | MySQL 8.0 的 `UNIQUE` 没有带 `WHERE` 的部分索引。名额仍由任务行条件和 06-04-11 的锁保证 |
| 完整性审计 | 第 11 节已经列出的四段 | 列表的物理列未冻结 | 键列表必须能按字段比较。默认序列化不能当身份 |
| RawPayload 字节 | 不建 | 不设计 | 介质未选 |
| 权威引用 | 不建全局唯一 | 不设计 | 它是任务行上的不可变列 |
| MappingResult、ProcessingErrorRecord、计算结果、Doris | 不建权威唯一 | 不设计 | 已有文档明确没有这套身份，或身份未冻结 |

索引字段顺序只影响最左前缀查询，不改变「全部列一起唯一」。本轮不把某一种顺序写成必须。查询索引可以另建，但不得代替上表的唯一键。

### 5.1 空转换版本

已有规定：不转换时 `conversionRuleVersion` 在逻辑上为空。不能假设复合唯一索引已经处理空值。06-04-08 写明唯一索引允许多个 NULL。06-04-09 写明不把空版本改成哨兵，该档结果的物理唯一性挂在 IR-02 和 IR-14。

本轮建议：在 IR-14 选定一种 `NOT NULL` 且不是新业务版本号的表示之前，不为 `normalizationIdentity` 生成可执行的唯一索引。不在本文挑选哨兵字符串。逻辑上「不转换且转换版本为空只保留一个结果」仍然有效，但现在没有物理约束。

### 5.2 哈希

已有规定：领域身份不用哈希代替。审计和阻断的幂等也不使用摘要。若列宽以后被证明放不进 3072 字节，本轮只保留 06-04-08 的限制：可以另有固定长度的技术摘要列，但冲突或读取时仍比较全部逻辑字段。摘要相同而原字段不同，不是同一业务身份，不能当成 `ALREADY_EXISTS`。

待决策，本轮不选：摘要算法、规范化编码、字段边界、字符编码、摘要列是否建立。只写「使用 SHA-256」不能关闭这个问题。

### 5.3 历史数据

当前仓库没有这些表，也没有生产数据清理步骤。索引建立前若已有重复逻辑身份，唯一索引会创建失败。那是以后执行 DDL 时的前置检查，本轮不写清理脚本。

### 5.4 冲突决定与冲突观测

已有规定，本轮不改：

- ADR-0003 的 `MappingConflictDecision` 与 06-04-08 的 ConflictDecision 是同一逻辑记录。不建两个实体，也不选定物理表名。
- 身份是决定自己的 `conflictDecisionId`。该列候选要求 `NOT NULL`，并做完整列唯一。生成算法现有文档没有给出，本轮不设计。
- `contractVersionId`、`fieldPath`、候选、冲突类型、原因、证据、作者、审核人、审核结论、审核确认的窗口和 `bodySha256` 是决定正文。`bodySha256` 用来发现正文被改，不是第二条身份。
- 决定创建后不可修改。封存后不在旧决定上追加证据。正文或证据要变化时，另建一条新标识的决定，不覆盖旧行。
- `APPROVED` 只表示审核通过。它不发布快照，也不让映射生效。
- 运行时不从多个冲突候选里选择类型、语义或证据来代替这条决定。
- `taskAttemptId` 不进入决定身份。现有设计没有这条要求。

与 `CONFLICT` 观测的边界：观测身份仍是四段 `rawPayloadRef + snapshotId + contractVersionId + fieldPath`。恰好命中一条已发布决定时，观测行保存该 `conflictDecisionId`，`proposedType` 为空，并且不生成 `NormalizedAmount`。观测引用决定，不回写决定。两条记录不合并。决定未发布或命中不止一条时，按 06-03-03-05 处理，不在本文改成另一种观测。

## 6. Create-or-Get 协议

本轮建议，与 06-04-08 第 3 节和 06-04-09 第 1 节一致。出现在第 3 节或第 5 节，不等于这条唯一约束已经可以执行。列宽、字符集、排序规则或生成算法未定的身份，只保留候选，不在本轮插入。

任务行锁只属于下面的 B 类。它不是 A 类的前置条件。

### 6.1 A 类：通用不可变记录

适用于已经具备完整逻辑身份、并且将来能建立完整列唯一约束的不可变记录。当前能归入这一类、但还不能执行 DDL 的是：

| 记录 | 身份 | 现在能否执行 |
| --- | --- | --- |
| 已发布 Snapshot | `snapshotId` | 不能。列宽未定。发布快照行本身不要求先有一条 `RUNNING` 任务 |
| 已封存 ContractVersion | `contractVersionId` | 不能。列宽未定。封存契约行本身不要求先有一条 `RUNNING` 任务 |
| ConflictDecision，即 `MappingConflictDecision` | `conflictDecisionId` | 不能。生成算法和列宽未定。这是配置决定，不是某次尝试的领域结果 |
| ReplayRequest | `replayRequestId` | 不能。生成算法未定 |
| 已声明稳定事件身份的 Task | 来源契约声明的身份字段 | 不能。IR-03 未给出字段前不建任务。创建时尚不存在可锁的任务行 |

迟到审计和拒绝审计沿用 06-04-11：只追加审计，不要求调用方仍是 `CURRENT`，也不改任务终态。它们不套用 B 类围栏。完整性审计的物理列仍未冻结。

基本协议：

1. 开启显式事务。不锁定一条 `RUNNING` 任务。
2. 可选地先按完整身份查询。这一步不是正确性边界。
3. 按完整逻辑身份做普通 `INSERT`，带上不可变内容。不使用会更新旧行的语句。若该语句执行期间连接中断，且客户端没有收到完整结果，进入第 6.5 节的「`INSERT` 执行期间断连」子场景，不进入第 6.3 节。不推断这条语句是否已经执行。
4. `INSERT` 明确成功时，本事务还没有提交。语句成功不是事务已提交。连接仍然可用，就在同一连接上发送 `COMMIT`。只有 `COMMIT` 成功返回，才是 `CREATED`，调用方采用刚写入的行。`COMMIT` 尚未发送且连接仍可用时，不另开连接插入。若在发送 `COMMIT` 之前连接断开，进入第 6.5 节的「插入已成功」子场景，不进入第 6.3 节。
5. `INSERT` 明确返回唯一冲突时，失败语句回滚，该事务已取得的锁仍保留。这次不是提交结果不确定。在同一事务里用覆盖完整身份的唯一索引做加锁读，读当前已提交的胜出行。不用更早的普通一致性读快照。
6. 内容相同则返回 `ALREADY_EXISTS`，结束事务，不对胜出行发 `UPDATE`。
7. 内容不同则返回已有的完整性异常，原行保持，不新增错误码。
8. 唯一冲突已经明确返回，但胜出记录没有读完、读不完整或不能比较时，停止。状态只叫胜出记录读取未完成。不返回 `ALREADY_EXISTS`，不叫提交结果不确定，不再 `INSERT`，不更新胜出行。恢复只按第 6.4 节，不进入第 6.3 节。
9. 死锁错误完整返回，并且整笔事务回滚已经确认：从本类第 1 步重做。不锁任务行。错误没有完整返回时，不能把整笔回滚当成已经发生，不按本步重做，不插入，也不进入第 6.3 节。不能把这次 `INSERT` 说成一定成功或一定失败。`COMMIT` 尚未发送而连接已经断开时，进入第 6.5 节的「死锁错误未完整返回」子场景。
10. 锁等待超时的三种客户端事实不能合并。`innodb_rollback_on_timeout` 未选。超时不是提交结果不确定，也不是唯一冲突。
    - 超时错误完整返回，并且连接仍可用：按默认只知道当前语句回滚，不知道整笔事务已经回滚。只有整笔回滚随后被确认，才从第 1 步重做。尚未确认时不重新插入。
    - 超时错误完整返回之后，整笔回滚确认之前连接断开：客户端知道发生了锁等待超时，也知道默认只回滚当前语句。不能据此认定整笔事务已经回滚。进入第 6.5 节的「超时错误完整返回后断连」，不进入第 6.3 节。
    - 错误响应没有完整返回，并且 `COMMIT` 尚未发送时连接断开：客户端不能确认发生了锁等待超时，不能确认当前语句已经回滚，也不能确认整笔事务已经回滚。进入第 6.5 节的「超时错误未完整返回后断连」。这不是「`INSERT` 执行期间断连」，不进入第 6.3 节，不重做，不重新插入。

### 6.2 B 类：Task 归属的 Pipeline 领域结果

适用于必须受 Worker 执行权约束的权威写入。06-04-11 第 7 节已经列入：任务上的快照固定、任务上的契约版本固定、`ExtractedFieldResult`、观测与匹配、版本固定记录、`NormalizedAmount`，以及将来若成为权威写入的计算结果。

这和 A 类的 Snapshot 行、ContractVersion 行不是同一次写入。任务上下文是把已经存在的 `snapshotId` 或 `contractVersionId` 固定到该任务上，所以要锁任务行。发布快照或封存契约版本本身走 A 类。

同一显式事务内先做下面的校验，全部通过才插入：

1. `SELECT` 该任务行 `FOR UPDATE`。
2. 调用方代次等于已提交的 `executionGeneration`。
3. 该代次的尝试为 `CURRENT`。
4. `status` 为 `RUNNING`。
5. 不存在有效阻断。

锁不到符合条件的行就回滚，不插入。写前查询不是围栏。

通过之后，插入、唯一冲突和内容比较使用第 6.1 节第 2 至 7 步。唯一冲突后的第一次胜出读取仍在这一笔事务内完成，然后结束事务，不更新胜出行。读取没有完成时进入第 6.4 节，不进入第 6.3 节。

死锁错误完整返回且整笔回滚已确认时，从本类的任务行锁定重新开始。不从一次没有锁的插入开始，也不沿用内存中的代次或上一次事务里的校验结果。错误未完整返回时不重做，也不把 `INSERT` 说成一定成功或一定失败。`COMMIT` 尚未发送而连接已断开时，走第 6.5 节，不走第 6.3 节。任务行锁或后续语句上的锁等待，与第 6.1 节第 10 步使用同一组三种事实。超时错误没有完整返回时，归第 6.5 节的「超时错误未完整返回后断连」，不归死锁子场景，也不取得执行权。

B 类任何一次新的领域 `INSERT`，包括死锁确认回滚后的重做，以及第 6.3 节确认缺行后的重新插入，都必须在那个新事务里同时满足：

1. 重新 `SELECT` 任务行 `FOR UPDATE`，并且这把锁保持到本事务结束。
2. 重新读取并校验 `executionGeneration`，不沿用内存代次。
3. 该代次的尝试仍是 `CURRENT`。
4. `status` 仍是 `RUNNING`。
5. 有效阻断仍为空。

任一项失败就回滚，不插入。只读取已经提交的行并比较内容时，不取得执行权，也不把任务写成成功。A 类的重做和重新插入都不增加任务行锁。第 6.4 节和第 6.5 节在确认缺行时不允许插入，所以这两节现在没有 B 类的新领域写入。

旧代次覆盖不了新代次的领域结果：旧代次拿不到当前代次的任务行锁。`ALREADY_EXISTS` 只表示领域行的身份和不可变内容与胜出行相同。它不是任务终态成功。终态仍走 06-04-11 第 8 节自己的条件。

`NormalizedAmount` 在第 5.1 节的空版本有决定之前，即使走了这道围栏，也不能靠唯一索引保证只有一行。围栏不因此取消。

任务创建不走本类。稳定事件身份未定前，A 类的任务行也不执行。

### 6.3 提交结果不确定

只用于 `COMMIT` 已经发送，但结果无法确认：响应丢失，或连接在 `COMMIT` 期间断开。`COMMIT` 尚未发送时的五种断连都留在第 6.5 节，不进入本节。唯一冲突已经返回，也不进入本节。超时错误没有完整返回，也不进入本节。

废弃原连接。原连接上的回滚返回值不能证明服务器已经提交或已经回滚。

另一条连接上的新事务按完整逻辑身份加锁读权威记录。不用一次普通查询没有看见行来推断可以插入。

- A 类不锁任务行。读到行之后比较不可变内容：相同则 `ALREADY_EXISTS`，不同则完整性异常，都不更新原行。只有这次加锁读确认没有该行，才允许重新插入。
- B 类先在该新事务里锁定任务行，用来等待原事务释放这把锁。不等待结束，不能把领域行当成不存在。拿到锁之后先按完整身份读取领域行。读到行则只比较不可变内容：相同为 `ALREADY_EXISTS`，不同为完整性异常。这次比较不取得新的执行权，也不要求 `status` 仍是 `RUNNING`。只有确认没有该行，并且代次、`CURRENT`、`RUNNING` 和有效阻断为空仍然全部通过，才允许在同一事务里重新插入。没有该行但校验失败时回滚，不插入。不沿用内存中的代次或未提交内容。

恢复读取失败、不完整或不能归类时，继续保持提交结果不确定：不再插入，不把任务写成成功。

本节不用于第 6.4 节，也不用于第 6.5 节。

### 6.4 胜出记录读取未完成

只用于 `INSERT` 已经明确返回唯一冲突，而胜出行的读取或内容比较还没有完成。本事务的插入没有成功。这不是提交结果不确定。

同一事务里的那次读取失败后，结束该事务，不再 `INSERT`，不更新任何行。随后的恢复使用另一条连接和新事务，按完整逻辑身份加锁读。

- 读取失败、不完整或不能比较：继续保持胜出记录读取未完成。不插入，不把没看见行当成没有行。
- 加锁读确认记录存在，且不可变内容相同：`ALREADY_EXISTS`。不更新。
- 加锁读确认记录存在，且不可变内容不同：已有的完整性异常。原行保持，不新增错误码。
- 加锁读确认记录不存在：不改判为提交结果不确定，也不使用第 6.3 节的重新插入。结果保持为「唯一冲突后确认缺行」。不插入，不更新，不把任务写成成功。现有 ADR 和 06-04-08、06-04-09、06-04-11 没有规定这一情况的业务分类。在单独决定之前，它是待决策，不新增错误码。

B 类做上述恢复读取时，不因为读取本身取得执行权。本节没有重新插入，所以这次恢复不新做一次领域写入。

### 6.5 COMMIT 未发送，事务结果未完成

本节用于 `COMMIT` 还没有发送，原连接已经断开，客户端不能再在原事务上提交或回滚。这不是提交结果不确定，不进入第 6.3 节。

五个子场景共用这一状态。它们的已知事实不同，不能写成同一种 SQL 结果：

| 子场景 | 客户端已经知道的事实 | 客户端不能据此认定的事 |
| --- | --- | --- |
| `INSERT` 执行期间断连 | 这次调用是 `INSERT`，但没有收到该语句的完整结果 | 不能认定 `INSERT` 已经执行，也不能认定它没有执行，不能认定原事务已经回滚 |
| `INSERT` 已明确成功后、发送 `COMMIT` 前断连 | 该 `INSERT` 语句已经成功返回 | 语句成功不是事务已经提交。未提交的行对其他会话不可见 |
| 死锁发生，错误响应没有完整返回，并且连接中断 | 不能把这次当作「死锁错误完整返回且整笔回滚已确认」 | 不能认定整笔事务已经回滚，不能按第 6.1 节第 9 步重做。不能把 `INSERT` 说成一定成功或一定失败 |
| 超时错误完整返回后断连 | 已经收到完整的锁等待超时错误。按默认只说明当前语句回滚。`innodb_rollback_on_timeout` 仍未选定 | 不能把这次超时当成整笔事务已经回滚。断连之后整笔状态仍未确认 |
| 超时错误未完整返回后断连 | 没有收到完整错误响应，并且 `COMMIT` 尚未发送 | 不能确认发生了锁等待超时，不能确认当前语句已经回滚，不能确认整笔事务已经回滚。不能把本行改写成「`INSERT` 执行期间断连」 |

共同处理：

- 废弃原连接。该连接的回滚返回值不能证明服务器已经回滚。原事务可能仍在执行，也可能仍占着锁、等待服务器清理。
- 未确认原事务结束之前，不重新插入。
- 不用一次普通查询没有发现记录，推断原事务已回滚或可以重新插入。
- 另一条连接上的新事务只按完整身份做加锁读。加锁读仍在等待时，等待本身不是缺行。这次等待若超时，整笔回滚仍未确认，不插入，也不进入第 6.3 节。
- 加锁读失败或不完整：保持本节状态，不插入。
- 加锁读完成并看见行：比较不可变内容。相同则 `ALREADY_EXISTS`，不同则完整性异常。都不更新。看见行只说明这条身份已有提交记录，不把原事务补写成已经提交，也不取得执行权。
- 加锁读完成并确认没有行：不进入第 6.3 节，不重新插入。现有 ADR 和 06-04-08、06-04-09、06-04-11 没有证明「`COMMIT` 尚未发送时，新连接确认缺行就等于原事务已经结束」。五个子场景都是待决策，不新增错误码。超时错误未完整返回后断连也使用上面这些读取边界，不另放宽。

A 类做上述读取时不锁任务行。B 类这次只比较已有行，不取得执行权，也不把任务写成成功。决定允许整次重做之前，两类都不插入。若以后允许重做，A 类从第 6.1 节第 1 步开始，不增加任务行锁；B 类必须在新事务中重新锁定任务行，重新校验代次、`CURRENT`、`RUNNING` 和有效阻断为空，并且把任务行锁保持到该事务结束。不得沿用内存代次或旧事务中的校验结果。

## 7. 并发与恢复矩阵

下列「是否重试」都指整次 Create-or-Get，不是忽略异常后继续。全部待实测。

| 序号 | 时序 | 重试 | 先读权威行 | 可以再插入 | 可以更新已有行 | 完整性异常 | 提交结果不确定 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 两个 Worker 都先查到没有行 | 插入由唯一约束裁决 | 冲突的一方必须读 | 只有胜出插入可以留下 | 否 | 内容不同才是 | 否 |
| 2 | A 已提交，B 再插入 | B 不把冲突当成失败后忽略 | 是 | 否 | 否 | 内容不同才是 | 否 |
| 3 | A 已插入未提交，B 插入 | B 等待 A 的锁 | A 结束后再分类 | A 回滚后 B 可以成为胜出 | 否 | 尚未比较 | 否。仍在等待 |
| 4 | A 插入后整笔回滚，B 随后执行 | B 按新插入处理 | 可选 | 是。A 没有留下行 | 否 | 否 | 否 |
| 5 | 唯一冲突后读到胜出行且内容相同 | 否。返回 `ALREADY_EXISTS` | 已经读到 | 否 | 否 | 否 | 否 |
| 6 | 唯一冲突已返回，胜出行读取失败 | 否。保持第 6.4 节。不进入第 6.3 节 | 必须。新连接、新事务、按完整身份加锁读 | 否。确认缺行也待决策，不插入 | 否 | 只有读到行且内容不同才是 | 否 |
| 7 | `COMMIT` 已发送但响应丢失，或 `COMMIT` 期间连接断开 | 先按第 6.3 节加锁读 | 是 | 只有第 6.3 节确认没有该行。B 类还要重新通过执行权校验 | 否 | 读到后内容不同才是 | 在读完并分类之前是 |
| 8 | `INSERT` 明确成功，尚未发送 `COMMIT`，连接仍可用 | 否。在原事务提交或回滚 | 尚未需要 | 否。不另开连接插入 | 否 | 否 | 否 |

## 8. 与执行权的分工

| 机制 | 解决 | 不解决 |
| --- | --- | --- |
| 任务行锁 | 遵守协议的领取、终态和领域写入对已有任务行排队。新代次提交后，旧代次的下一笔权威写入加锁失败 | 两个会话同时插入一个尚不存在的任务。同一观测身份的第二行。绕过协议的写入 |
| 物理唯一约束 | 同一完整逻辑身份不能有两行已提交记录 | 谁持有执行权。来源事件是不是同一个。offset 能否提交 |
| Create-or-Get | 冲突后读胜出行，内容相同则复用，不同则留下原行 | 把冲突解释成任务成功 |
| `executionGeneration` | 已提交且大于 0 的代次才是执行权。旧代次不能再写 | 观测四段身份的唯一 |
| `CURRENT` 计数 | 本事务提交前看见的 `CURRENT` 是不是 1。不是则回滚 | 物理唯一。锁范围仍未在 8.0.46 证实 |

B 类领域写入与任务行锁在同一个事务里。唯一冲突发生在这个事务之内时，第一次读取胜出行也在这个事务里，然后结束事务，不更新胜出行。这次读取没有完成时走第 6.4 节：不提交领域行，不提交成功终态，不再插入。第 6.3 节只处理已经发送的 `COMMIT`。第 6.5 节处理 `COMMIT` 尚未发送时的五种断连，子场景的已知事实仍然分开。超时错误未完整返回后断连不是提交结果不确定，也不是已确认的死锁整笔回滚，也不改名为 `INSERT` 执行期间断连。这些状态不互相改名。

B 类恢复后若要重新插入，必须在新事务中重新锁定任务行，重新校验代次、`CURRENT`、`RUNNING` 和有效阻断为空，并把任务行锁保持到该事务结束。不沿用内存代次或旧事务的校验结果。A 类不增加这道任务行锁。只比较已有行不取得执行权。超时错误未完整返回后的读取同样不取得执行权；它现在不允许插入，所以也不绕过这道围栏。这不改变 06-04-11 已经确定的领取、终态和执行权规则。第 6.4 节和第 6.5 节确认缺行时仍然不插入。

不允许旧代次覆盖新代次的结果：旧代次拿不到当前代次的任务行锁。这只约束 B 类。不允许因为唯一冲突就判定任务成功：`ALREADY_EXISTS` 只复用已有不可变行。终态仍走 06-04-11 第 8 节自己的条件。

## 14. 结论

已有规定足够列出观测、字段结果、版本固定、标准化、快照、契约版本、冲突决定、阻断和审计的逻辑身份。`ConflictDecision` 与 `MappingConflictDecision` 是同一条决定。本轮建议是：A 类不可变记录用普通 `INSERT` 加完整列唯一索引，不先锁 `RUNNING` 任务；B 类领域结果仍先完成 06-04-11 第 7 节的执行权校验，重新插入时也要重做这道围栏。冲突后加锁读胜出行，内容不同则保持原行。胜出读取未完成、`COMMIT` 未发送的事务结果未完成，以及提交结果不确定是三种状态。第 6.5 节的五个子场景只共用「`COMMIT` 尚未发送且连接已断」，不共用同一种 SQL 结果。超时错误没有完整返回时，不能写成已经发生锁等待超时或当前语句已经回滚。只有 `COMMIT` 已经发送而结果无法确认时才进入第 6.3 节，并且只有该节确认没有行才可以重新插入。第 6.4 节和第 6.5 节确认缺行都不插入。

暂不能设计的是：来源事件身份、重放标识算法、空转换版本的物理表示、审计列表的物理列，以及 `CURRENT` 的部分唯一索引。

实施准入：不允许执行 DDL，不允许开始 Java，不允许创建或接受 ADR，不允许把 IR-02 标成已关闭。下一步是选定列宽、字符集和空版本表示，然后在 MySQL 8.0.46 上做第 12 节的实验。实验之前，跨 Worker 的先查后插仍然不能保证只有一行。
