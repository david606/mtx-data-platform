# 06-04-19 MTX Data Platform V2 物理唯一约束与并发 Create-or-Get 专项设计

本文把已经冻结的逻辑身份整理成 MySQL 8.0.46 上的候选物理唯一约束，并写明跨 Worker 的 Create-or-Get。它是候选设计，不是 DDL，不是已接受 ADR，也没有在 MySQL 8.0.46 上执行。

基线是 `3d7e310c7ba7f41ad81919b9c5c011b051d40cde`。本轮不修改 Pipeline、06-04-08、06-04-09、06-04-11、台账或 ADR。IR-02 仍是待决策、P0，不关闭。

## 2. IR-02 的边界

台账写明：观测身份是 `rawPayloadRef + snapshotId + contractVersionId + fieldPath`。标准化另有 `normalizationIdentity` 和 `versionFixKey`。物理索引、锁、隔离级别和 DDL 留待存储设计。先查后插会留下两条有效观测。关闭条件是把已有逻辑身份落成唯一约束，并规定并发失败方读取胜出记录。台账不指定索引类型。

本文不做的事：

- 不发明来源事件身份，也不把 Kafka offset、`rawPayloadRef` 或 `receivedAt` 写成任务幂等键。那是 IR-03。
- 不证明 offset 可以安全提交。
- 不关闭 IR-07 或 IR-09。执行权文字和事务提交点仍待验证。
- 不把任务行锁、`CURRENT` 计数、代次或普通查询索引写成物理唯一约束。
- 不引入 Redis 锁、Inbox、Outbox 或 DLQ。
- 不把 Doris 写成事务幂等存储。ADR-0005 的分析副本不回写权威。

## 4. 四类机制

| 机制 | 已有规定回答的问题 | 不能代替 |
| --- | --- | --- |
| 逻辑身份 | 哪一组字段表示同一条业务记录 | 物理上阻止第二行 |
| 物理唯一约束 | 两个事务不能各提交一行相同的完整身份 | 执行权、来源事件身份、offset |
| 查询索引 | 加快查找 | 唯一性。普通索引允许重复键 |
| 完整性检查 | 提交前发现本事务看见的行数或内容不符 | 其他不遵守协议的插入。`COUNT(*)` 不是唯一约束 |

## 5. 物理唯一约束候选

能直接写出约束条件的，仍受列宽、字符集和排序规则限制。06-04-08 已写明：字符集未定时不能创建物理索引。本轮不指定字符集、排序规则、列类型或列宽。

候选共同规则，均来自 06-04-08，本轮不放宽：

- 身份列 `NOT NULL`。允许 NULL 的唯一索引可以有多行 NULL。
- 唯一性覆盖完整列，不用前缀索引。
- 不使用 `INSERT IGNORE` 或 `ON DUPLICATE KEY UPDATE`。后者会更新旧行。
- 不分区。分区列必须进入每一个唯一键，现有身份里没有已经证明的分区键。
- 不把哈希列当成领域身份。

| 实体 | 候选唯一键 | 本轮能否写成可执行约束 | 原因 |
| --- | --- | --- | --- |
| ObservedAmount | 四段观测身份，全部 `NOT NULL` | 条件具备后可以。现在不能执行 | 列宽和排序规则未定。键长是否超过 3072 字节待实测 |
| ExtractedFieldResult | 三个独立字段，全部 `NOT NULL` | 同上 | Pipeline 要求按字段比较，不串成一个序列化字符串 |
| 版本固定记录 | `versionFixKey` 的三段，全部 `NOT NULL` | 表是否独立未决 | 阶段标记是已有的「标准化」，不另造阶段 |
| NormalizedAmount | `normalizationIdentity` 的全部组成 | 暂不能完成 | 空的 `conversionRuleVersion` 与 `NOT NULL` 冲突，见下节 |
| TaskExecutionContext | 每个非重放 `taskId` 一份胜出上下文 | 可以落在任务行，不一定独立成表 | 第一次选哪份快照仍是 IR-04 |
| Snapshot | `snapshotId` | 标识列宽未定 | 不决定尚未关闭的快照选择 |
| ContractVersion | `contractVersionId` | 标识列宽未定 | 正文哈希是内容列，不进入唯一键 |
| Task 稳定事件 | 来源已声明的全部身份字段 | 暂不能设计 | IR-03。未声明的来源不建这条约束，也不建任务 |
| ReplayRequest | `replayRequestId` | 暂不能设计 | 生成算法未定 |
| TaskAttempt | `taskAttemptId` | 标识算法未定前不能执行 | 不把 `taskId` 做成尝试表的唯一键。租约、代次、`ownership` 都不进入该键 |
| `blockIdentity` | `taskId`、阻断码、阻断主体 | 物理列未冻结 | 不把 `taskAttemptId` 放进键 |
| 每任务一条有效阻断 | 不建成过滤唯一索引 | 不采用 | MySQL 8.0 的 `UNIQUE` 没有带 `WHERE` 的部分索引。名额仍由任务行条件和 06-04-11 的锁保证 |
| 完整性审计 | 第 11 节已经列出的四段 | 列表的物理列未冻结 | 键列表必须能按字段比较。默认序列化不能当身份 |
| RawPayload 字节 | 不建 | 不设计 | 介质未选 |
| 权威引用 | 不建全局唯一 | 不设计 | 它是任务行上的不可变列 |
| MappingResult、ProcessingErrorRecord、计算结果、Doris | 不建权威唯一 | 不设计 | 已有文档明确没有这套身份，或身份未冻结 |

索引字段顺序只影响最左前缀查询，不改变「全部列一起唯一」。本轮不把某一种顺序写成必须。查询索引可以另建，但不得代替上表的唯一键。

### 5.1 空转换版本

已有规定：不转换时 `conversionRuleVersion` 在逻辑上为空。不能假设复合唯一索引已经处理空值。06-04-08 写明唯一索引允许多个 NULL。06-04-09 写明不把空版本改成哨兵，该档结果的物理唯一性挂在 IR-02 和 IR-14。

本轮建议：在 IR-14 选定一种 `NOT NULL` 且不是新业务版本号的表示之前，不为 `normalizationIdentity` 生成可执行的唯一索引。不在本文挑选哨兵字符串。逻辑上「不转换且转换版本为空只保留一个结果」仍然有效，但现在没有物理约束。

### 5.2 哈希

已有规定：领域身份不用哈希代替。审计和阻断的幂等也不使用摘要。若列宽以后被证明放不进 3072 字节，本轮只保留 06-04-08 的限制：可以另有固定长度的技术摘要列，但冲突或读取时仍比较全部逻辑字段。摘要相同而原字段不同，不是同一业务身份，不能当成 `ALREADY_EXISTS`。

待决策，本轮不选：摘要算法、规范化编码、字段边界、字符编码、摘要列是否建立。只写「使用 SHA-256」不能关闭这个问题。

### 5.3 历史数据

当前仓库没有这些表，也没有生产数据清理步骤。索引建立前若已有重复逻辑身份，唯一索引会创建失败。那是以后执行 DDL 时的前置检查，本轮不写清理脚本。

## 6. Create-or-Get 协议

本轮建议，与 06-04-08 第 3 节和 06-04-09 第 1 节一致。适用于第 5 节能建立唯一约束的不可变记录。任务创建在 IR-03 有身份之前不执行。标准化结果在第 5.1 节的空版本问题有决定之前，不能靠本节保证只有一行。

领域结果写入还要先满足 06-04-11 第 7 节：同一显式事务里锁定任务行，调用方代次等于已提交代次，尝试为 `CURRENT`，`status` 为 `RUNNING`，有效阻断为空。然后才插入。锁不到符合条件的行就回滚，不插入。

步骤：

1. 开启显式事务，并完成上述任务行锁定与校验。
2. 可选地先按完整身份查询，减少冲突。这一步不是正确性边界。
3. 普通 `INSERT` 完整身份和不可变内容。不使用会更新旧行的语句。
4. 插入成功则提交。返回 `CREATED`。调用方采用刚写入的行。
5. 唯一冲突时，失败语句回滚，该事务已取得的锁仍保留。用覆盖完整身份的唯一索引做加锁读，读当前已提交的胜出行。不用更早的普通一致性读快照。
6. 内容相同则返回 `ALREADY_EXISTS`，结束事务，不对胜出行发 `UPDATE`。
7. 内容不同则返回已有的完整性异常，原行保持，不新增错误码，不把任务写成成功。
8. 死锁则整个事务回滚。从任务行锁定开始重做整次 Create-or-Get。
9. 锁等待超时默认只回滚当前语句。`innodb_rollback_on_timeout` 未选。超时本身不是整笔回滚。只有整笔回滚被确认后，才从第 1 步重做。否则按提交结果不确定处理。
10. 提交响应丢失或连接在提交期间断开：废弃原连接，其回滚返回值不能证明服务器结果。另一条连接上的新事务按完整身份加锁读。读到行则按第 6、7 步分类。确认没有该行之后，才允许新一次插入。读取失败、不完整或不能归类时保持不确定：不再插入，不把任务写成成功，不用内存中的代次或未提交内容。

唯一冲突不是成功。`ALREADY_EXISTS` 只表示身份和不可变内容都与胜出行相同。它不表示任务终态成功，也不授权旧代次覆盖新代次。旧代次在第 1 步就会因任务行条件失败而回滚，到不了覆盖。

## 7. 并发与恢复矩阵

下列「是否重试」都指整次 Create-or-Get，不是忽略异常后继续。全部待实测。

| 序号 | 时序 | 重试 | 先读权威行 | 可以再插入 | 可以更新已有行 | 完整性异常 | 提交结果不确定 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 两个 Worker 都先查到没有行 | 插入由唯一约束裁决 | 冲突的一方必须读 | 只有胜出插入可以留下 | 否 | 内容不同才是 | 否 |

## 8. 与执行权的分工

| 机制 | 解决 | 不解决 |
| --- | --- | --- |
| 任务行锁 | 遵守协议的领取、终态和领域写入对已有任务行排队。新代次提交后，旧代次的下一笔权威写入加锁失败 | 两个会话同时插入一个尚不存在的任务。同一观测身份的第二行。绕过协议的写入 |
| 物理唯一约束 | 同一完整逻辑身份不能有两行已提交记录 | 谁持有执行权。来源事件是不是同一个。offset 能否提交 |
| Create-or-Get | 冲突后读胜出行，内容相同则复用，不同则留下原行 | 把冲突解释成任务成功 |
| `executionGeneration` | 已提交且大于 0 的代次才是执行权。旧代次不能再写 | 观测四段身份的唯一 |
| `CURRENT` 计数 | 本事务提交前看见的 `CURRENT` 是不是 1。不是则回滚 | 物理唯一。锁范围仍未在 8.0.46 证实 |

领域写入与任务行锁在同一个事务里。唯一冲突发生在这个事务之内时，读取胜出行也在这个事务里，然后结束事务，不更新胜出行。读取失败则整个结果不确定，不提交领域行，也不提交成功终态。

不允许旧代次覆盖新代次的结果：旧代次拿不到当前代次的任务行锁。不允许因为唯一冲突就判定任务成功：`ALREADY_EXISTS` 只复用领域行。终态仍走 06-04-11 第 8 节自己的条件。

## 13. 关闭条件

IR-02 同时满足下面各项才可以另案关闭。现在一项都没有完成：

3. 空转换版本的表示已经由 IR-14 决定，并且对应的标准化唯一索引已创建，或者明确该档在决定之前禁止写出第二行的物理方案已经批准。

5. 没有把任务行锁、`CURRENT` 计数或先查后插写成已经满足第 1 项。

## 14. 结论

已有规定足够列出观测、字段结果、版本固定、标准化、快照、契约版本、阻断和审计的逻辑身份。本轮建议是：不可变记录用普通 `INSERT` 加完整列唯一索引，冲突后加锁读胜出行，内容不同则保持原行，提交结果不明则换连接再读。

暂不能设计的是：来源事件身份、重放标识算法、空转换版本的物理表示、审计列表的物理列，以及 `CURRENT` 的部分唯一索引。

实施准入：不允许执行 DDL，不允许开始 Java，不允许创建或接受 ADR，不允许把 IR-02 标成已关闭。下一步是选定列宽、字符集和空版本表示，然后在 MySQL 8.0.46 上做第 12 节的实验。实验之前，跨 Worker 的先查后插仍然不能保证只有一行。
