## 2. 执行权模型摘要

现行候选把任务生命周期收成一个 `status`，取值是 Pipeline 第 11 节的八个状态。终态不是第二列。`CANCELLED` 是生命周期结束，不是四种处理终态之一。

执行权的线性化点是新领取事务的 `COMMIT`。租约只用 MySQL `NOW()` 决定别的 Worker 何时可以尝试领取。代次相等不等于仍持有执行权，因为终态、`RETRY_WAITING` 和运行中取消都不增加代次，只把当时的 `CURRENT` 写成 `RELEASED`。

正常 Pipeline 权威写入要在同一个显式事务里锁住任务行，直到提交，并同时满足：代次等于已提交代次、该尝试为 `CURRENT`、`status` 为 `RUNNING`、有效阻断为空。阻断登记和 `FAILED` 落库是两句不同的条件更新。取消不要求调用方持有代次，但要求 `status` 尚未终态且有效阻断为空。

这些规则都还不是已接受 ADR。06-04-11 第 16 节写明没有 DDL，也没有 8.0.46 并发测试。

### R-01 P1 阻断与终态的数据库仲裁在两份现行文档里相反

具体问题：06-04-10 仍写终态与阻断没有数据库级仲裁、本轮不选择锁。06-04-11 第 8 节已经规定两句条件更新。仓库没有一句声明第 11.1 节作废。

证据：06-04-10 第 11.1 节：「下面的交错还没有数据库级仲裁」「06-04-09 没有证明这种读写会被 InnoDB 排成一个结果。本轮不选择锁」。06-04-11 第 8 节表：登记要求 `status` 为 `RUNNING` 且有效阻断为空；成功类终态同样要求阻断为空；`FAILED` 要求阻断已经等于这一条。

触发条件：实现者按 06-04-10 第 11.1 节，在事务外先读「尚无阻断、尚未终态」，再插入阻断。

失败时序：Worker A 提交 `SUCCESS`。Worker B 仍按读到的旧事实插入有效阻断。任务行上出现成功类 `status` 加有效阻断。06-04-11 第 8 节把这个组合标成不允许，但旧句没有强制再读。

影响：终态被一条迟到阻断在事实上改写，或恢复程序把已成功任务再收敛成 `FAILED`。

建议：在 06-04-10 第 11.1 节追加现行规则指向 06-04-11 第 8 节，并写明先前「不选择锁」只属于该轮当时。不要把 06-04-10 的旧句留成可实现的第二套协议。

验收：同一任务上，终态先提交时，后到的另一条阻断只能成为迟到审计，任务 `status` 不变。两个会话在 8.0.46 上交错执行。本报告没有做这次实验。

### R-02 P1 首次领取的「代次加一」在创建任务不写代次时没有可执行语义

具体问题：创建任务「不写执行代次」。领取又要求「代次加一」，并且「代次必须增加，否则原值更新会被当成没有改变」。

证据：06-04-11 第 3.1 节创建行与首次领取行；第 5 节第 1 点和第 5 节对 [MySQL 8.0 15.2.17](https://dev.mysql.com/doc/refman/8.0/en/update.html) 的引用。本审查没有在 8.0.46 上执行语句。MySQL 里对 NULL 做加一，结果仍是 NULL。若创建时该列是 NULL，`SET executionGeneration = executionGeneration + 1` 不会产生一个新的非空代次，改变行数也可以是 0。文档没有规定初值，也没有规定首次领取改用赋值而不是加一。

触发条件：第一个 Worker 领取刚创建的 `PENDING` 任务。

失败时序：条件更新改变 0 行，事务按第 5 节回滚，不插入尝试。任务永远停在 `PENDING`。或者实现者自行把 NULL 当成 0，与「不写执行代次」分裂成两种实现。

影响：单 Worker 的第一次领取就可能无法开始。这发生在多 Worker 竞态之前。

建议：规定创建时是否写入数值初值。首次领取的语句必须让该列变成一个确定的新值，并且改变行数按 15.2.17 得 1。不要在审查报告里代选 0 或 1。

验收：两个会话同时领取同一条 `PENDING`。恰好一个代次被写成确定值，恰好一条 `OPEN` / `CURRENT`。另一会话改变 0 行且没有尝试行。未执行。

IR：影响 IR-07 的实现前提。不把它改成已验证。

整改状态：06-04-11 第 5.1 节采用方案 A，创建时写 0，成功领取加一。伪 SQL 未在 MySQL 8.0.46 上执行。列类型仍未选。本项不改为已验证。

### R-03 P1 租约到期后没有指定谁来调用领取

具体问题：执行权要等新领取提交才切换。文档没有指定哪个现有模块发现到期并调用这次领取。

证据：06-04-11 第 6 节只定义到期后可以尝试领取。第 10 节写「到期后新代次把旧尝试写成 `INTERRUPTED`」。[scheduling.md](../../architecture/scheduling.md) 写当前没有调度适配层，不要在两个应用里创建 Quartz `Scheduler`，调度放在哪个现有模块仍待设计。Kafka 消费只负责接入，06-04-10 没有把分区再分配定义成执行权接管。

触发条件：持有 `RUNNING` 的 Worker 进程退出，租约到期，没有下一次业务消息，也没有下一次 Cron。

失败时序：任务行保持 `RUNNING`，尝试保持 `OPEN` / `CURRENT`，代次不变。这符合第 3.1 节「崩溃且租约到期」在没有新领取时的预期。缺失的是新领取永远不会被调用。已登记阻断的任务同样停在「有阻断、尚未 `FAILED`」。

影响：崩溃恢复在文档上有条件更新，在运行上没有入口。单实例重启也要靠某个未写出的循环再次进入领取。

建议：在现有十模块里指定调用方，只调用 06-04-11 第 5 节的领取，不新建模块，也不把 Quartz API 放进 Pipeline。调用方未指定前，不能把崩溃恢复写成已经可运行。

验收：杀掉唯一的 Worker 后，不依赖人工 SQL，到期任务被另一次领取接上。有阻断的只进入 `FAILED`。未执行。

IR：IR-07 仍待验证。本项是验证之前还缺的运行入口。

整改状态：06-04-11 第 6.1 节和 `docs/architecture/scheduling.md` 的「到期接管」写出候选调用链。Quartz 未集成，ADR 未创建。本项不改为已验证。

### R-04 P1 任务和领域结果都还没有物理唯一约束

具体问题：并发 Create-or-Get 在没有唯一索引时不能保证只有一行。这是 IR-02 的原问题，执行权设计没有把它变成已建约束。

证据：06-04-02 IR-02 状态是待决策。06-04-11 第 15 节写「06-04-08 的 Create-or-Get 未改。唯一约束仍未建成」。06-04-09 第 6 节写 IR-02 仍待决策，本设计依赖它的唯一约束。06-04-11 第 3.1 节创建行把重复投递的正确性放在 06-04-08 的加锁读胜出行上。没有唯一索引时，两个插入都可以成功，加锁读没有胜出可讲。

触发条件：同一稳定身份的两条投递同时创建任务。或两个任务为同一观测身份同时插入。

失败时序：两个事务都 `INSERT` 成功。随后各自分到不同 `taskId`，或同一观测身份留下两行。领取和围栏只能保护已经创建出来的那一行，不能把两行并回去。

影响：重复权威任务或重复观测。执行代次无法修补创建阶段已经分裂的身份。

建议：先按 06-04-08 已有的逻辑身份做物理唯一约束，并保持「插入后加锁读胜出行、不覆盖」。列宽和排序规则仍不要在本审查里另选。

验收：两个会话对同一身份并发插入，最终一行，失败方读到胜出行且内容相同才复用。未执行。

IR：不关闭 IR-02。IR-09 依赖它，且该依赖未满足。

### R-05 P1 没有稳定来源身份时，普通任务和 offset 都还不能安全开始

具体问题：四个已核对来源都没有可进入任务唯一约束的稳定事件身份。当前安全状态是不建普通任务、不提交 offset。执行权协议从领取才开始，覆盖不到这一步。

证据：06-04-10 第 7 节和第 9 节；06-04-02 IR-03 为「部分确认 / 待决策」。offset、订单号、消息种类、`rawPayloadRef`、`receivedAt` 和载荷哈希都被写成不是该身份。隔离介质未选，所以「先隔离再提交 offset」也不能执行。

触发条件：无身份消息重复到达，或实现者为了分区继续消费而先提交 offset。

失败时序：先提交 offset，MySQL 里没有任务也没有可再读的隔离记录，消息不能重试。或者用订单号建成两个任务，代次分别领取，写出两套观测。

影响：丢消息，或重复权威结果。这不是领取竞态能补上的。

建议：保持 06-04-10 的否定结论。身份未声明的来源不建任务、不提交 offset。不要在执行权实现里临时造键。

验收：无身份消息投递两次，任务表零行，该分区 offset 不前进。有身份时先见 MySQL 提交，再允许提交 offset，重复投递回到原 `taskId`。未执行。

IR：不关闭 IR-03。

### R-06 P2 隔离级别和锁等待超时参数都未选

证据：06-04-11 第 7 节末段；06-04-09 第 1 节对死锁和 `innodb_rollback_on_timeout` 的引用。锁等待超时默认只回滚当前语句，事务和其余锁可以还在。

触发条件：Pipeline 写入等不到任务行锁。

失败时序：调用方把超时当成整笔已回滚，随后用同一连接提交，或在锁还持有时开始下一句。围栏的「整笔回滚」就不成立。

影响：一次短事务变成未定义的半开事务。不直接造出第二个代次，但会破坏「失败则整笔重试」的恢复。

建议：实现前要么选定该参数，要么在代码里显式处理「只回滚语句」和「回滚整笔」两种分支。不要假定超时等于死锁。

验收：构造锁等待超时，确认没有带着旧代次提交领域行。未执行。

IR：不改变 IR-09 的待验证状态。

### R-07 P2 租约比较依赖尚未统一的会话时区

证据：06-04-11 第 6 节。`NOW()` 使用会话时区。比较的不是 Worker 墙上时钟。

触发条件：两个 Worker 连接的 `time_zone` 不同，一个写入 `leaseExpiry`，另一个用自己的 `NOW()` 判断是否到期。

失败时序：租约在一个会话里尚未到期，在另一个会话里已经到期。后者领取成功，前者仍可能持有锁并提交当前代次的写入。这不破坏「新代次提交后旧写入失败」，但会让接管早于设计者以为的到期时刻，或让续租与领取的先后偏离预期。

影响：接管时机不稳定。执行权仍以代次提交为准，所以这不是第二套执行权，但运维上的租约长度不再有单一含义。

建议：所有执行权连接使用同一个会话时区，并把它写成运行约束。不要用 Worker 本地时钟代替 `NOW()`。

验收：两个不同时区的会话对同一到期列判断不一致的用例被禁止，或被证明不会发生。未执行。

IR：已写在 IR-07 的风险里。不关闭。

### R-08 P2 改变行数的 JDBC 语义未验证

证据：06-04-11 第 16 节。第 5 节要求改变行数不是 1 就回滚。MySQL 8.0 15.2.17 统计的是实际变化的行。JDBC 驱动可能另报匹配行数。本审查没有查驱动，也没有跑查询。

触发条件：重复终态或重复取消。`status` 已经是目标值，语句匹配到行但没有改值。

失败时序：驱动返回 1，调用方把它当成第一次成功，再插入审计或再释放一次尝试。

影响：重复副作用。任务终态本身因条件没变而不应被覆盖。

建议：实现时固定使用「实际变化行数」，并用「值已相同」的重复提交做回归。未验证前不要把客户端返回值当成 15.2.17 的返回值。

验收：第二次相同终态更新在应用里被当成 `ALREADY_FINALIZED`，不插入第二条尝试。未执行。

IR：不关闭 IR-07。

### R-09 P2 一条 CURRENT 只有事务约定，没有物理唯一性

证据：06-04-11 第 4.2 节第 5 点写只有领取事务插入 `CURRENT`，并在同一事务改掉旧的 `OPEN`。第 16 节写这些列没有 DDL。

触发条件：领取事务被拆成两次提交，或另有一条路径也插入 `CURRENT`。

失败时序：旧尝试仍是 `CURRENT`，新尝试也是 `CURRENT`。两个代次的写入都通过「尝试为 `CURRENT`」这一条，只剩任务行上的代次还能挡住旧代次。若写入只检查尝试行、不锁任务行，两套权威结果都能提交。

影响：执行权分裂。现行围栏若被完整实现，任务行代次仍能挡住旧代次。缺的是第二道物理约束。

建议：DDL 时考虑同一 `taskId` 只允许一条 `CURRENT`。在那之前，任何写入都不能只看尝试行。

验收：并发领取后 `CURRENT` 行数为 1。未执行。

IR：不关闭 IR-07。

### R-10 P2 取消的数据库规则已齐，调用者仍未定义

证据：Pipeline 第 11 节和 06-04-11 第 9 节对三种取消的事务一致。06-04-02 IR-21 仍是待决策。06-04-11 写明不能把任意 Worker 都当成已经有权取消。

触发条件：任何一个能连上任务表的进程执行第 9 节的条件更新。

失败时序：数据库会正确地把无阻断的 `PENDING` 改成 `CANCELLED`。错在谁被允许发出这条语句。并发本身不会产生两个终态，因为第二笔改变 0 行。

验收：未授权调用不能执行该更新。两个合法取消只有一个把 `status` 从非终态改成 `CANCELLED`。未执行。

IR：不关闭 IR-21。

### R-11 P2 自动进入 RETRY_WAITING 没有允许清单，也没有写明清单为空时禁止进入

证据：06-04-11 第 4 节和 06-04-02 IR-08。崩溃被明确排除。哪些字段级失败可以进入，仍待确认。

触发条件：实现者把契约解析失败或已登记阻断也放进 `RETRY_WAITING`。

失败时序：确定性失败不走阻断和 `FAILED`，任务回到 `RETRY_WAITING` 后再次领取，形成另一代，仍用原快照。这和 ADR-0004「确定性失败不换快照」不冲突，但会把本应终止的任务反复执行。

影响：重复执行。已提交观测按 Create-or-Get 不应被覆盖，所以不是直接的第二行观测，而是任务永不终态。

建议：在允许清单出现之前，写明不得进入 `RETRY_WAITING`。不要在本审查里挑选失败类别。

验收：未列入清单的失败不会把 `status` 改成 `RETRY_WAITING`。未执行。

IR：不关闭 IR-08。

### R-12 P2 分区再分配没有写成执行权或 offset 的操作步骤

证据：06-04-10 第 7 节写 offset 不是业务身份，任务提交成功后才可以提交 offset。同文场景 22 只写「分区暂停后恢复」，没有写消费者被撤销分配后，已经领到的代次和尚未提交的 offset 各自怎么办。06-04-11 没有把分区所有权当成执行权。

触发条件：再分配发生时，旧消费者已经创建或领取任务，尚未提交 offset。新消费者从该分区继续读。

失败时序：文档能够推出的只有：无身份则两边都不得提交 offset，也不得建任务。有身份则重复投递走 Create-or-Get。文档没有写旧消费者是否必须停止后续领域写入。若它已经持有代次，再分配本身按现行模型不应撤销代次。这一点是推断，不是 06-04-10 的原句。

影响：实现者可能把「失去分区」当成「失去执行权」，在新代次尚未提交时放弃本代次，或相反，在失去分区后仍然提交 offset。

建议：补一句操作约束：分区再分配不修改 `executionGeneration`；已领取的写入仍走第 7 节围栏；offset 仍只在任务或可再读隔离记录提交之后提交。这不是新的消息组件。

验收：再分配过程中旧代次的领域写入要么在新代次前提交并保留，要么在新代次后回滚。offset 不先于 MySQL。未执行。本场景在矩阵中标为设计证据不足。

IR：不关闭 IR-03、IR-09。

### R-15 P3 续租条件使用了比 RUNNING 更宽的「终态仍为空」

证据：06-04-11 第 3 节把「终态为空」定义成 `PENDING`、`RUNNING` 或 `RETRY_WAITING`。第 6 节续租只要求代次匹配、终态仍为空、到期时刻晚于 `NOW()`。进入 `RETRY_WAITING` 后再续租，不会把已 `RELEASED` 的尝试改回 `CURRENT`。下一次领取 `RETRY_WAITING` 也不看租约是否已延长。

## 6. Task 与 TaskAttempt

三个维度在文字上是分开的。

| 维度 | 存放 | 取值 |
| --- | --- | --- |
| 任务生命周期 | 任务 `status` | 八个 Pipeline 取值 |
| 尝试结果 | 尝试行 | `OPEN`、`SUCCEEDED`、`FAILED`、`CANCELLED`、`INTERRUPTED` |
| 尝试执行权 | 尝试行的另一列 | `CURRENT`、`SUPERSEDED`、`RELEASED` |

审查过的非法组合，现行条件是否挡住：

| 组合 | 结论 |
| --- | --- |
| `status` 已终态且尝试仍为 `CURRENT` | 终态事务把两者写在一起。未提交则两者都不变。按文字挡住 |
| 尝试已 `RELEASED` 且 `status` 仍为 `RUNNING` | 释放只发生在终态、`RETRY_WAITING` 或运行中取消。这些都会同时改 `status`。按文字挡住 |
| 新代次已提交但旧 `OPEN` 未变成 `SUPERSEDED` | 领取把这两步放在同一事务。按文字挡住。见 W-014 |
| 两条 `CURRENT` | 只有领取插入，且先改旧 `OPEN`。没有物理唯一索引。见 R-09 |
| `PENDING` 终态却带一条为取消而建的尝试 | 第 9 节禁止。按文字挡住 |

`RETRY_WAITING` 是任务 `status`，不是尝试结果。尝试在进入该状态时已经是 `FAILED` / `RELEASED`。

## 7. MySQL 事务与围栏

必须与任务行锁处在同一显式事务、并且提交前不释放锁的写入：

| 写入 | 额外条件 | 依据 |
| --- | --- | --- |
| 快照固定、契约固定、字段结果、观测与匹配、版本固定、`NormalizedAmount` | 当前代次、`CURRENT`、`RUNNING`、阻断为空 | 06-04-11 第 7 节；06-04-09 第 4 节对应行 |
| 将来的计算结果 | 同上。当前不写 | 06-04-09 第 3.2 节 |
| 阻断登记 | 当前代次、`CURRENT`、`RUNNING`、阻断为空。不改 `status`，不释放 | 第 8 节第一句 |
| 成功类终态 | 同上，并同时 `SUCCEEDED` / `RELEASED` | 第 8 节第三句 |
| `FAILED` | 当前代次、`CURRENT`、`RUNNING`、阻断等于已登记的一条。不写正常领域行 | 第 8 节第二句 |
| 进入 `RETRY_WAITING` | 与成功类终态相同的围栏，尝试改为 `FAILED` / `RELEASED` | 第 3.1 节 |
| 运行中取消 | 不要求调用方代次。`status` 为 `RUNNING`、阻断为空，同时 `CANCELLED` / `RELEASED` | 第 9 节 |

可以独立提交的写入，以及理由：

| 写入 | 理由 |
| --- | --- |
| 任务创建 | 与快照、契约分成三次提交，避免长事务。重复创建的正确性依赖 R-04 的唯一约束，目前不成立 |
| 各字段的领域短事务彼此分开 | 一个字段失败不删除其他字段已提交结果。每个短事务自己再围栏 |
| 版本固定与 `NormalizedAmount` | 先后两次提交。崩溃后读已固定版本，不改用新规则 |
| 迟到审计、拒绝审计 | 不修改已提交 `status` 和领域行 |
| Kafka offset、Doris 复制 | 不在 MySQL 事务内。失败不回滚 MySQL |

提取和匹配被要求在观测事务开始前完成，避免把外部调用放进持有任务行锁的事务。这能缩短锁时间。若实现把外部调用放进该事务，领取和取消会被拖住。文档已经禁止这种放法，没有测试守住它。

锁顺序是先任务行，再领域插入。两个任务插入同一观测身份时，可能在唯一索引上死锁。06-04-09 第 1 节已要求死锁后重试整笔 Create-or-Get。这覆盖了该风险的恢复，没有消除死锁本身。未实测。

本审查没有核对某条具体 SQL 在 8.0.46 上的锁类型，也没有选择隔离级别。加锁读看最新已提交行，这一点只引用了 06-04-11 已引的手册句子，不是本轮实验结果。

## 8. Kafka 与 MySQL 的失败窗口

跨系统没有原子事务。现行顺序是：有稳定身份时，先提交任务 Create-or-Get，然后才可以提交 offset。offset 失败则再次投递回到原任务。任务失败或尚未提交时提交 offset，消息不能再读。无身份时连第一步都不存在，分区不得前进。

06-04-10 没有把再分配写成执行权撤销。W-020 因此是证据不足，不是已经证明的安全场景。

Doris 在 MySQL 提交之后复制。失败不回滚 MySQL。这与执行权无关，也不在本轮改写成新的写入账本。
