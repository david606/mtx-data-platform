## 2. 已有约束

Pipeline 第 4.2 节已经分开三种身份：接入事件身份、任务幂等身份、内部 `taskId`。非重放任务的幂等身份等于来源契约已经声明的稳定接入事件身份。`taskAttemptId` 只表示一次尝试。显式重放必须新建 `taskId`，并带调用方给出的 `replayRequestId`。普通重复投递不能创建 `replayRequestId`。

同一稳定事件再次到达时，返回原 `taskId`，不替换第一次保存的权威 `rawPayloadRef` 和权威 `receivedAt`。本次新引用不进入原任务的观测身份。观测身份仍是 `rawPayloadRef + snapshotId + contractVersionId + fieldPath`，不加 `taskId`、`parserVersion` 或 `tenantId`。

没有稳定事件身份时，不能用金额、`rawPayloadRef`、`receivedAt` 或报文字节哈希拼键。相同业务事件可以有不同字节，不同业务事件也可以有相同内容。

ADR-0004 继续要求先固定 `snapshotId`。原任务重试使用原快照。确定性解析失败不降成 `UNMAPPED`。新快照重新处理必须是显式重放任务。

06-04-09 的候选顺序是：MySQL 任务 Create-or-Get 提交成功之后才提交 Kafka offset。Kafka、MySQL、Doris 没有跨系统本地事务。06-04-08 的 Create-or-Get 仍是普通插入、唯一冲突后读取胜出行、内容不同则完整性异常、不覆盖权威输入。列宽、字符集、排序规则和 DDL 仍属 IR-02。

## 3. 来源身份调查

### 3.1 京东创建新订单消息

SRC-03 于 2026-11-23 读到京东零售开放平台页面。目录是秒送 / 秒送订单 / 创建新订单消息，消息标识 `orderCreated`。触发条件原文是：客户支付订单后，推送创建新订单消息。页面更新时间写 2025-12-25 13:19:44。

消息体只有四列，且都标成不可空：

| 字段 | 页面描述 | 本轮能确认的身份含义 |
| --- | --- | --- |
| `venderId` | 分发标识。示例栏写“页面写不会下发” | 字段名存在。是否随消息下发、是否标识商户，未确认 |
| `billId` | 消息单据 ID。示例 `10003129` | 是这页上的单据号。不是已经证明的事件 ID，也没有和订单号分开 |
| `statusId` | 订单状态 ID。示例 `32000` | 状态值。不能单独区分两次业务事件 |
| `timestamp` | 时间戳。示例 `2025-10-16 13:23:30` | 时间文字。页面没有把它定义成事件版本或递增序号 |

该页没有金额字段，也没有重试、乱序、补发、历史重放或编号回收的说明。trade-flow 的金额来自订单详情，不是这则消息。查询摘录和本页是不是同一契约，06-03-01 仍标为待确认。因此 `billId` 不能进入任务唯一约束。

### 3.2 美团已确认订单推送

SRC-02 读到的页面是“APP方URL 推送已确认订单”，HTTP POST form。接口说明是：美团向 APP 方推送订单状态为已确认的订单。摘录下来的是金额、打包费和对账字段。订单号、门店号、应用号、消息号、事件号、版本号都没有出现在这份证据里。

trade-flow 回调事件名是 `managedCancelAndConfirmOrder`。R-09 和 06-03-01 写明不能证明它就是这一页。所以即使以后在别的资料里看到订单号，也不能回写成这一页已经声明了稳定事件身份。

这一页只证明“已确认订单”这一种推送的部分金额字段。它没有证明创建、取消、退款是不同事件，也没有证明网络重试是否复用某个消息号。

### 3.3 淘宝闪购订单消息目录

SRC-01 读到的是订单服务消息列表，不是某一条消息的字段页。已读到的消息码包括 217（订单生效）、12（商户接单）、14（订单被取消）、18（订单完结）、30–39（退单相关）、223（预订单备餐提醒）。这些码区分的是消息种类。同一种类会覆盖许多订单，所以消息码不是事件 ID。

不同消息码在目录文案上像是同一订单的不同业务事件，但没有字段证明某一次 14 和某一次 217 如何关联，也没有证明同一次 217 的重试身份。

### 3.4 富智云订单、支付与团购

06-03-01 第 4.4 节的订单金额来自仓库摘录，证据等级是 E1-B，本轮没有打开对应官方页。摘录字段是金额名，不是事件身份声明。

## 4. 重复、修正与重放

在身份未被契约声明之前，下面五类不能互相替代，也不能统称重复订单。

| 类别 | 判定所需证据 | 当前四份资料 |
| --- | --- | --- |
| 同一事件的重复投递 | 来源声明同一事件身份，重试复用该身份 | 没有这份声明 |
| 同一订单的新业务事件 | 订单实体身份与事件身份分开，且新事件使用新身份 | 淘宝目录只说明消息种类不同。京东本页只有一种消息。没有订单号与事件号的对照 |
| 同一事件的报文修正或补发 | 来源声明同一身份下正文可以变化，或声明必须使用新身份 | 未确认 |
| 显式重放 | 调用方给出 `replayRequestId` 的 V2 命令 | 这是 V2 规则，不是来源推送 |
| 无法判断是否重复 | 缺少稳定身份，或身份与正文互相冲突 | 当前资料都落在这里 |

## 5. 统一身份模型

候选表达只是适配器以后要填的接口，不是已经批准的字段组合。每个来源保留原始字段名和证据映射，不要求四家使用相同的原始列名。

| 候选组成 | 是否公共必需 | 当前证据 |
| --- | --- | --- |
| `sourceSystem` | 用来隔开不同来源，避免字段值相撞 | 适配器可以填写已登记的来源名。它本身不是来源报文里的事件号 |
| `sourceContractId` | 同一来源的不同契约必须分开 | 06-03-02-02 已有契约编号。京东消息和京东查询仍不能合并 |
| 来源声明的事件身份各字段 | 只有契约写明稳定且能区分不同业务事件时才进入身份 | 四份资料都没有这样的声明 |
| `sourceEventVersion` | 仅当来源真实提供并写明语义 | 京东 `timestamp` 和 `statusId` 都不是这项 |
| 商户、门店、应用、消息种类 | 只有证据证明事件号离开该范围会重复时才进入身份 | 全部未确认 |
| 订单号、金额、时间、报文字节哈希、`rawPayloadRef`、`receivedAt` | 不进入身份。订单号至多标识订单实体 | 禁止用它们拼键 |

公共必需项目前只有一条否定结论：没有经契约声明的稳定事件字段时，不能建立 `sourceEventIdentity`。平台专属字段必须等该契约补齐后再映射。辅助校验可以保留原始字段供审计，但辅助字段不参与任务唯一约束。

不同平台避免相撞的前提，是身份里带有已经登记的来源和契约，而不是假设某个字段名全局唯一。同一平台的不同消息种类是否要分开作用域，现在没有证据，不能预先规定。

原始身份字段应当能被追溯。保留期限和物理列仍是 IR-15、IR-02，本轮不设计表。

`taskId` 和 `replayRequestId` 的生成算法仍未设计。即使将来某个来源补齐了事件身份，内部标识怎么生成也还要单独决定。这是 IR-03 不能关闭的另一个原因。

## 6. 没有稳定身份时的策略

四个候选都还不是已接受决策。

| 策略 | 行为 | 能否去重 | 当前是否采用 |
| --- | --- | --- | --- |
| A 不建立来源级去重 | 每次接收分配只代表本次接收的内部接入记录，允许因此产生两个任务 | 不能。不得宣称已有来源级去重 | 不采用。业务尚未接受重复任务 |
| B 来源补充稳定事件身份 | 来源增加跨重试不变、且能区分同一订单多个事件的身份。旧协议缺字段时拒绝自动处理 | 可以，但要等契约版本声明语义 | 这是以后能够自动处理的前提。当前没有这样的契约 |
| C 业务级幂等协议 | 用事件版本或递增序号等被正式承诺的协议代替事件号 | 只有语义被证明能区分多个事件才可以 | 不采用。`订单号 + 时间` 没有这份承诺 |
| D 隔离和人工恢复 | 原始消息和接入上下文先可靠保存，自动金额处理暂停，人工决定是否建任务 | 隔离本身不是去重 | 行为上需要，但保存位置尚未选定，所以还不能执行 |

可自动进入 Task Create-or-Get 的条件：该来源契约已经声明稳定接入事件身份，作用域明确，重试复用规则明确，身份字段可按非空值比较，并且空值、格式错误和同身份异文都有契约语义。当前没有来源满足。

必须停止自动建任务的条件：身份缺失、空字符串、超出该契约声明的格式、无法判断是重复投递还是新事件、或者同一声明身份对应无法解释的不同正文。

允许降级成“每次接收一个独立任务”的条件：业务方书面接受重复任务，并且接入记录明确写着它不是来源事件身份。这项接受还不存在。

不允许提交 Kafka offset 的条件：既没有提交成功的任务 Create-or-Get，也没有提交成功的、可再次读出原始消息的隔离记录。不能为了让分区继续消费而先提交 offset。

需要人工介入的条件：来源没有契约、身份冲突、隔离记录要恢复成任务，或分区因上述原因停住。恢复责任人尚未指定，不能在本文里虚构。

## 7. Kafka 身份与 offset

| 标识 | 语义 | 是否业务身份 |
| --- | --- | --- |
| `sourceEventIdentity` | 来源契约声明的业务事件身份 | 是。当前没有来源已经声明 |
| `taskId` | V2 逻辑任务 | 否 |
| `taskAttemptId` | 一次执行尝试 | 否 |
| `replayRequestId` | 显式重放命令 | 否 |
| `topic` / `partition` / `offset` | 一次 Kafka 投递的位置 | 否 |
| Kafka record key | 分区路由候选 | 否。没有契约证明前不等于事件身份 |
| `rawPayloadRef` | 第一次接受时保存的原文引用 | 否 |
| `receivedAt` | 第一次接受时保存的业务时间 | 否 |

topic、partition 和 offset 只定位一次投递。同一 offset 的再次投递仍要靠 MySQL 里的任务身份判断，不能靠 offset 相等代替唯一约束。不同 offset、不同分区或不同主题也可以携带同一个来源事件。分区键和顺序要求本轮不选。

有稳定身份时，沿用 06-04-09 的候选顺序：

1. 接收 Kafka 消息。
2. 按该来源契约提取并校验事件身份。校验失败则不建任务。
3. 保存原始消息和接入引用。原文介质和保留期限仍是 IR-15，不能假设与 MySQL 任务行同一次提交。
4. 用稳定身份做 Task Create-or-Get。
5. 确认该 MySQL 事务已经提交。
6. 此后才提交 offset。
7. offset 提交失败时，再次投递回到原 `taskId`，不替换权威引用。

第 3 步若使用尚未选定的对象存储，它和 MySQL 不是一个本地事务。任务行提交成功但原文尚未保存时，不能把这条消息当成已经可重放的权威原文。06-04-09 已要求观测读取使用权威 `rawPayloadRef`。原文保存失败时，本次不提交 offset，任务行是否应当出现，要等 IR-15 选定介质后再定。本轮不把“先建任务、后补原文”写成已经安全。

没有稳定身份时，只写“不提交 offset”会让该分区停住。可选办法如下，都还不是实现决定。

| 方案 | 是否丢原文 | 是否产生重复任务 | 分区是否停住 | 能否恢复 | 是否打乱来源顺序 | 是否需要新设施 |
| --- | --- | --- | --- | --- | --- | --- |
| 暂停该分区，等身份契约或人工处置 | 消息仍留在 Kafka，尚未消费的不丢 | 暂停期间不会新建任务 | 会，直到恢复消费 | 恢复前必须先有身份规则或逐条人工决定 | 暂停本身不重排已有消息 | 不新增模块。运行上要有人负责恢复 |
| 原始消息先落入可再读的隔离记录，提交成功后再提交 offset | 取决于隔离保存是否真正提交。保存产品未选 | 隔离记录不是任务。恢复时若没有事件身份，仍可能建成两个任务 | 保存成功后分区可以继续 | 可以按隔离记录恢复。恢复动作本身尚未定义 | 后面的消息会越过被隔离的消息，顺序不再等于处理顺序 | 需要一处持久保存。它不是 Inbox，也不是新模块，但是 IR-15 未选介质之前不能实施 |
| 给每条消息造一个只代表本次接收的接入号，并自动建任务 | 可以随任务引用保存，介质仍未选 | 会。重复回调就是两个任务 | 不会 | 能找到两次接收，不能把它们合成一个来源事件 | 不依赖去重，所以也不保护事件顺序 | 不新增模块，但业务尚未接受重复任务 |
| 直接提交 offset，不保存消息 | 会丢 | 不会建任务，也无法补建 | 不会 | 不能恢复 | 该消息从顺序中消失 | 否。本方案不采用 |

候选运行边界是：身份不成立时暂停自动建任务。分区继续前进的前提，是隔离记录已经提交并且可以从中读回原始消息。这个前提现在不成立，所以当前安全状态是该消息所在分区不能前进。由此造成的积压是运行风险，不是把消息丢掉的理由。

不引入 Inbox。任务行只在稳定身份存在时承担去重。不引入 Outbox 或 DLQ 产品。隔离若以后需要物理记录，名称和表都留给后续决策。

## 8. MySQL Create-or-Get

| 来源 | 可以进入任务唯一约束的字段 | 能否保证 NOT NULL | 作用域 | 没有稳定身份时 |
| --- | --- | --- | --- | --- |
| 京东 `orderCreated` | 没有。`billId` 未证明是事件身份 | 页面写四列不可空，但不能因此建约束 | 未确认 | 不能建 |
| 美团该推送页 | 没有摘录到身份字段 | 不适用 | 未确认 | 不能建 |
| 淘宝闪购目录 | 消息码不是事件身份 | 不适用 | 未确认 | 不能建 |
| 富智云旧路径 | 没有来源契约字段 | 不适用 | 旧表键不是这里的作用域 | 不能建 |

显式重放不使用来源事件身份做唯一约束。它使用调用方给出的 `replayRequestId`，指向一个新的 `taskId`。普通重复投递不写这个标识。生成算法未定，所以重放唯一约束也还不能落成 DDL。

同一来源身份若已被契约声明，正文不同仍不覆盖权威 `rawPayloadRef` 和权威 `receivedAt`。这是完整性异常，不是更新。身份尚未声明时，不创建任务行，也就没有可覆盖的权威输入。

哈希可以在以后作为技术校验，不能代替来源身份，也不能用来绕开索引长度。

## 9. 隔离与人工恢复

隔离的行为契约是：

- 原始消息和接入上下文要能再次读到。接入上下文至少包括来源名、契约编号、topic、partition、offset、接收时间和校验失败原因。这些是候选字段，不是已建表。
- 不把隔离记录写成 `taskId`，不生成 `replayRequestId`。
- 不提交 offset，除非上一节里“保存已提交且可再读”的前提已经成立。当前前提不成立。
- 恢复时由人工或后续已批准规则决定：补齐身份后按 Create-or-Get 建任务，或明确接受一次独立接收。没有这个决定之前，不自动恢复。
- 恢复后的重复投递仍按当时已经成立的身份处理。身份仍不成立时，不能靠恢复动作把两条消息合成一个来源事件。

分区暂停的风险是消费滞后和需要人工恢复。恢复责任、告警和保留期限都未指定。

## 11. 与 06-04-09 的关联风险

### 11.1 有效阻断与终态

06-04-09 写的是两次短提交：有效阻断先提交，终态另一次提交，中间崩溃后重试 `finalizeTask`。Pipeline 第 11.1 节的协调边界是逻辑顺序，不是已经证明的数据库锁、条件更新或隔离级别。

因此下面的交错还没有数据库级仲裁：

1. Worker A 读到尚无有效阻断。
2. Worker B 也判断终态尚未提交。
3. A 提交终态。
4. B 随后提交一条本应参与终态的阻断。

若第 4 步没有再次读取已经提交的终态，就可能出现终态已经提交、阻断却被写成有效阻断。06-04-09 没有证明这种读写会被 InnoDB 排成一个结果。本轮不选择锁、租约、条件更新或隔离级别，也不修改 06-04-09。

这项留在 IR-07 和 IR-09：Worker 所有权尚未定义，终态与阻断的跨 Worker 顺序也尚未验证。它不由本轮的来源身份设计关闭。

### 11.2 无法校验的消息与分区

安全目标是：不丢原始消息，不把无法识别的消息建成伪装成来源去重的任务，不在 MySQL 权威结果缺失时提交 offset。

当前运行风险是分区停住和积压。隔离保存可以解除停住，但介质、保留和恢复负责人都属于后续决策。没有这些决定时，继续消费并提交 offset 不符合安全目标。

## 12. IR-03 建议

不关闭。状态保持部分确认、待决策。

已经确认的只有：Pipeline 的身份分工，以及四份现有资料都没有声明可直接用于任务唯一约束的稳定事件身份。POS 堂食和淘宝团购还没有对应契约。

不因此关闭 IR-02、IR-07、IR-09、IR-10、IR-15、IR-17、IR-19。
