## 3. R-01 复审

文档冲突已经消除。06-04-10 第 11.1 节写明「不选择锁」只描述来源身份设计当时，现行条件指向 06-04-11 第 8 节，并与 06-04-09 第 3.3 节、第 4 节使用同一组谓词。Pipeline 第 11 节仍规定有效阻断已登记时不能写成 `CANCELLED`，最终只收敛为 `FAILED`。没有第三套终态条件。

现行协议不是一句孤立的 `SELECT ... FOR UPDATE`。登记、成功类终态和 `FAILED` 都要在显式事务里锁住任务行，条件失败则整笔回滚，锁保持到 `COMMIT` 或 `ROLLBACK`。

| 动作 | 锁与条件 | 成功后 | 失败 |
| --- | --- | --- | --- |
| 登记阻断 | 代次匹配，尝试为 `CURRENT`，`status` 为 `RUNNING`，阻断为空。同一事务写阻断记录 | `status` 仍是 `RUNNING`，尝试仍是 `OPEN` / `CURRENT` | 匹配不到则回滚，不留下有效阻断 |
| `SUCCESS`、`PARTIAL_SUCCESS`、`ALL_FIELDS_FAILED` | 同上，并且计算不是阻断。同一事务把尝试写成 `SUCCEEDED` / `RELEASED` | `status` 进入对应成功类终态 | 阻断已在、代次已变或尝试已不是 `CURRENT` 时整笔回滚 |
| `FAILED` | 代次匹配，尝试为 `CURRENT`，`status` 为 `RUNNING`，阻断等于已登记的那一条。同一事务把尝试写成 `FAILED` / `RELEASED` | 一个 `FAILED` | 阻断尚未写下时回滚，不制造没有阻断的 `FAILED` |
| `CANCELLED` | 锁同一任务行。`status` 仍是 `PENDING`、`RETRY_WAITING` 或 `RUNNING`，且阻断为空。不要求调用方持有代次 | 有 `CURRENT` 时同一事务写成 `CANCELLED` / `RELEASED` | 阻断已在则改变 0 行，不覆盖成 `CANCELLED` |

取消不检查代次，这是 06-04-11 第 9 节已经写明的差别，不是又一套阻断仲裁。成功类三个终态共用「阻断为空」这一条，没有各自另写锁范围。

五个要求的时序，按上述条件可以串行成一个结果：

1. 成功类终态先提交：后到的登记要求 `status` 仍是 `RUNNING`，匹配不到。06-04-10 第 11.1 节和 06-04-11 第 8 节都规定只能写迟到审计，不改 `status`。
2. 阻断先提交：成功类终态要求阻断为空，回滚。此后 06-04-11 第 5 节只允许 `FAILED` 收敛，不允许重新提取或写观测。
3. 阻断与正常 Pipeline 写入：两边都要求当时阻断为空，并持有任务行锁到各自事务结束。写入先提交则领域结果保留，登记仍可能成功，之后终态只能是 `FAILED`。登记先提交则写入回滚。
4. `FAILED` 事务失败：06-04-09 第 4 节写明任一步失败则整笔回滚，行保持「`RUNNING` 且阻断已在」。同一代次在租约内按第 8 节重读后重试整笔终态事务。租约到期后，第 6.1 节的扫描再次领取，新尝试仍只做收敛。
5. 多个 Worker 收敛：只有领取提交的那一代满足 `CURRENT`。另一边改变 0 行，再读到 `FAILED` 且尝试已 `RELEASED` 时返回 `ALREADY_FINALIZED`，不插入第二套结果。

这些是文档上的确定胜者。没有在 MySQL 8.0.46 上交错执行。R-01 不再作为两套现行规则的 P1，也不改为已验证。

## 4. R-02 复审

第 5.1 节已经选定方案 A，并拒绝把初值留给实现者。

| 检查项 | 文档结论 | 伪 SQL 是否表达 |
| --- | --- | --- |
| 创建后为 0，0 不是执行权 | 第 3.1 节和第 4.2 节写明。重复 Create-or-Get 不把已增大的代次改回 0 | 创建语句不在第 5.1 节。领取 `WHERE` 使用读到的整数 |
| 首次领取得到 1 | 0 加一 | `SET execution_generation = execution_generation + 1`，在读到 0 且更新成功时得到 1 |
| 重试领取和到期接管 | 都从已提交正整数加一，不另写赋值 | 同一句 `UPDATE`。差别只在 `WHERE` 的 `status` 和租约 |
| 代次、插入、取代同一事务 | 第 5 节和第 5.1 节规则 8。06-04-09 领取行同样要求三者同一事务 | `START TRANSACTION` 到 `COMMIT` 之间含这三步 |
| 一步失败整笔回滚 | 规则 5、6、7。InnoDB 未提交事务在回滚后对其他会话不可见。这是语义核对，不是实测 | 插入失败和取代行数不符写的是回滚。行数判断在注释中，见 F-03 |
| 提交响应丢失 | 新值且尝试为 `OPEN` / `CURRENT` 则停止。两处都还是旧值才整笔重试 | 重读不在伪 SQL 中。第三态没有动作，见 F-02 |
| 重复 `CURRENT` | 只有领取插入。第二次领取要等行锁，条件失败则不插入 | 没有唯一约束。提交前若跳过行数检查，事务内可以留下两条，见 F-03 |
| 任务代次与尝试代次 | 规则要求新尝试代次等于提交后的任务代次 | 任务用 SQL 加一，尝试用调用方参数加一。两边没有读回比对，见 F-01 |
| 溢出 | 规则 10 要求失败并回滚，不得变成 0、负数或 NULL | 伪 SQL 没有溢出分支。列类型和 `sql_mode` 都未选，见 F-01 |

`SELECT ... FOR UPDATE` 先锁住任务行。随后的 `UPDATE` 仍带完整 `WHERE`：代次等于读到的值，并且 `status` 是 `PENDING` 或 `RETRY_WAITING`，或者 `status` 是 `RUNNING` 且 `lease_expiry <= NOW()`。同一事务持有这把锁时，别的会话不能先改这一行。因此 `SELECT` 是加锁，真正拒绝不该领取的行的是 `UPDATE` 的 `WHERE`。`SELECT` 本身没有这组过滤，过滤写在它后面的注释里。注释若被忽略，只要 `UPDATE` 的 `WHERE` 还在，错误领取仍然匹配不到行。

三种路径共用这句更新：

- `PENDING` 且代次为 0：更新应改变 1 行，取代应影响 0 行，插入代次 1。
- `RETRY_WAITING`：历史行应保持 `FAILED` / `RELEASED`，取代影响 0 行，代次加一。
- `RUNNING` 且租约已到期：取代必须影响 1 行，然后代次加一。第 6.1 节第 7 步只覆盖这一条路径，不覆盖前两条。

`NULL` 不会被这句 `UPDATE` 领走。`WHERE execution_generation = :observedGeneration` 在 SQL 里不会让 NULL 等于 NULL。调用方若把 NULL 当成 0，列上仍是 NULL，同样匹配 0 行。这和规则 9 一致。没有执行该语句。

JDBC 行数口径对本句领取更新没有额外的成败分支。成功时代次、所有者和到期时刻都会变化，MySQL 8.0 的改变行数和匹配行数都是 1。匹配不到时两者都是 0。因此「驱动报告匹配行数还是改变行数」不改变第 5.1 节这次 `UPDATE` 的判断。它仍然影响把列写成原值的重复终态和重复阻断登记：那里改变行数是 0，匹配行数可以是 1。该差别仍是 06-04-13 的 R-08，本轮没有查驱动。

原 R-02「NULL 加一无法形成第一代」在选定 0 之后不再成立。下面 F-01 至 F-03 是这套伪 SQL 仍未闭合的部分。

边界上的预期结果：

| 边界 | 文档给出的结果 |
| --- | --- |
| 两个 Worker 同时扫描同一行 | 一个代次提交。另一个改变 0 行 |
| 扫描后、领取前续租成功 | 到期条件失败，不产生新代次 |
| 扫描后被取消或进入其他终态 | 领取 `WHERE` 不再包含该 `status` |

| Quartz 重复触发或延迟触发 | 重复触发仍由条件更新仲裁。延迟期间旧代次保持有效，直到新领取提交。没有 misfire 或重叠策略，见 F-04 |

## 6. 新问题

### F-01 P2 代次溢出和两端加一没有写进可失败的语句

具体问题：规则 10 要求加一不能保存时整笔失败。伪 SQL 却让任务行执行 `execution_generation + 1`，让新尝试使用调用方的 `:observedGeneration + 1`。提交前没有读回任务代次，也没有要求它等于尝试代次。

证据：06-04-11 第 5.1 节规则 10 和伪 SQL 的 `UPDATE`、`INSERT`。同节写明列类型不选定。06-04-11 第 16 节仍写没有 DDL。

触发条件：列类型和 `sql_mode` 都未选，而当前值加一超出该类型。本复审没有执行溢出语句，不声称 8.0.46 会截断、报错或回绕。

失败时序：任务行按服务器算术保存一个值，尝试行按调用方算术写入另一个值，然后 `COMMIT`。或者服务器把语句当成成功，调用方却已经得到另一个整数。规则 10 的失败分支没有出现在语句里。

影响：不能说「代次溢出可靠失败」，也不能说伪 SQL 本身保证任务代次与尝试代次相同。在不溢出且两边类型一致时，同一把行锁下两个加一才是同一个数。

建议：选定列类型之前，在同一事务、提交前读回任务代次，必须等于新尝试代次；不相等则回滚。溢出语句以该类型在 8.0.46 上的实际错误或截断为准，不在类型未定时空写最大值。

验收：构造一个加一不能保存的值。事务回滚，任务代次不变，没有新的 `CURRENT`。未执行。

IR：不关闭 IR-07。

### F-02 P2 提交响应丢失的重读没有第三态

具体问题：第 5.1 节只规定两支。代次已是预期新值且尝试为 `OPEN` / `CURRENT`，则停止。任务代次和尝试都还是旧值，才整笔重试。其余读到的组合没有动作。

证据：06-04-11 第 5.1 节末段。第 6.1 节把领取响应丢失指向这一段。

触发条件：Worker A 的领取已经提交，响应丢失。在 A 重读之前，租约到期，Worker B 的领取已提交，A 的尝试变成 `INTERRUPTED` / `SUPERSEDED`，任务代次已大于 A 预期的新值。

失败时序：A 既不能走「停止」，也不满足「两处都是旧值」。文档没有写这时必须停止且不得插入。若实现者改成只重试 `INSERT`，会在已经存在的新代次旁边再写一条 `CURRENT`。若实现者把整笔领取再执行一次，第 5.1 节的 `WHERE` 会因新租约未到期而匹配 0 行，这一条路径是安全的，但文档没有把它指定为第三态的唯一动作。

影响：响应丢失后的恢复还不是封闭判定。同一事务的原子提交没有被否定；缺口在重读之后的动作。

建议：除两支已写明的结果外，其余组合一律停止，不插入尝试，不加代次。只有重读确认代次和尝试都未改变时，才重做整笔领取。

验收：先提交一代并取代上一条，再让原调用方按丢失响应重读。它不得再插入 `CURRENT`。未执行。

IR：不关闭 IR-07、IR-09。

### F-03 P2 取代行数依赖更新前的状态，伪 SQL 却先改状态

具体问题：`PENDING` 和 `RETRY_WAITING` 的取代必须影响 0 行，到期的 `RUNNING` 必须影响 1 行。这个判断使用的是领取前的 `status`。伪 SQL 先把 `status` 更新成 `RUNNING`，行数规则只写在后面的注释里。

证据：06-04-11 第 5.1 节规则 7 与伪 SQL 注释「领取前是 PENDING 或 RETRY_WAITING」。第 5 节正文要求改变行数不是 1 就回滚，这句话指的是任务行更新，不是取代语句。

触发条件：实现按更新之后的任务行判断。此时三条路径的 `status` 都已经是 `RUNNING`。

失败时序：首次领取或重试领取把取代语句按 1 行检查，实际影响 0 行，于是回滚。任务停在原来的 `PENDING` 或 `RETRY_WAITING`，没有 `CURRENT`。到期接管若误用 0 行规则，则会在旧尝试仍是 `CURRENT` 时提交新尝试。注释被忽略时，后者才会在提交后留下两条 `CURRENT`。

影响：第 5.1 节的正文规则是对的，伪 SQL 不能脱离「领取前」这三个字单独实现。这不是另一套代次初值。

建议：在 `UPDATE` 任务行之前保存 `status`。插入之后、提交之前用保存下来的值检查取代行数。不要读取已经被改成 `RUNNING` 的行来做这个判断。

验收：同一套代码分别领取 `PENDING`、`RETRY_WAITING` 和到期的 `RUNNING`。前两者提交后只有一条新的 `CURRENT`，旧的 `FAILED` 行不变。第三者恰好把一条旧 `OPEN` 写成 `SUPERSEDED`。未执行。

IR：不关闭 IR-07。

### F-04 P2 到期扫描有归属，没有失败分类和端口结果

具体问题：第 6.1 节指定了模块和十条顺序，也写了扫描失败后下次再扫、条件失败时改变 0 行。它没有定义执行权端口返回什么，也没有分开这些失败：扫描查询失败、单个任务死锁、领取已提交但随后的 Pipeline 或收敛失败、适配进程在事务中退出。Quartz 的重复触发、延迟触发和同一进程内两次扫描重叠，只间接靠领取条件更新兜底，没有适配自己的规则。

证据：06-04-11 第 6.1 节。scheduling.md「到期接管」同样写候选归属和未集成，没有失败分类。第 5 节有领取后的三行分流表，但没有写成端口结果。

触发条件：一次扫描读到多行，其中一行死锁，另一行领取已经提交。或者同一个 Worker 里两次触发重叠。

失败时序：文档没有说死锁的那一行是否阻止后面的标识继续领取，也没有说进程退出时未提交事务必须回滚后由下次扫描接手。重叠扫描在数据库上仍会排队，不会靠进程内锁防止重复领取。因此正确性没有被推翻，可运行的适配协议还不完整。

影响：不能把「调用链已写明」延伸成 Quartz 集成设计已经完成。不需要新增模块，也不把扫描移到 Admin。

建议：在现有端口上写明三个结果：未领到、已领到并进入正常 Pipeline、已领到并只做 `FAILED` 收敛。单个任务失败不回滚同一次扫描里已经提交的其他领取。进程退出只放弃未提交事务。重复和延迟触发不另写执行权。

## 8. 生命周期与交叉核对

Task 与 TaskAttempt 的分工没有被第七轮推翻。任务只看一个 `status`。尝试的执行结果和 `CURRENT` / `SUPERSEDED` / `RELEASED` 仍是另一套。`CURRENT` 不由代次相等推导。创建时的 0 没有 `CURRENT`。

仍成立的组合是：领取提交后恰好一条新 `CURRENT`，旧的 `OPEN` 在同一事务变成 `SUPERSEDED`。终态、进入 `RETRY_WAITING` 和运行中取消把当时的 `CURRENT` 写成 `RELEASED`，不加代次。`PENDING` 取消不插入尝试。这些都要求实现遵守同一事务。F-03 指出伪 SQL 的行数检查若用错状态，会在提交前回滚，或者在注释被忽略时留下两条 `CURRENT`。没有物理唯一索引，这一点仍是 06-04-13 的 R-09，等级仍是 P2。

取消与领取、取消与阻断仍锁同一任务行。先提交的条件更新决定结果。有效阻断存在时取消匹配 0 行。Pipeline 第 11 节的三条取消转换与 06-04-11 第 9 节相同。

租约到期不撤销旧代次。旧 Worker 在新领取提交前可以完成已经持有行锁的写入。新代次提交后，旧代次再加锁时条件失败。06-04-09 第 5 节仍保留这一故障行。

06-04-09 与 06-04-11 的提交点一致：领取三者同一事务，正常写入持锁到提交，阻断登记与 `FAILED` 使用不同谓词，终态与 `RELEASED` 同一事务。06-04-09 没有复写 F-02 的两支重读，执行权文档承担这段规则，不构成第三套提交点。
