本轮原文不编写物理表，也不把建议写成当时已经接受的设计。ADR-0005 接受之后，以该决策而不是本节最初的开放选型为准。

## 2. 现有存储职责回顾

06-04-04 已经划分四类职责，并明确这不是四种已经选定的产品。

| 职责 | 权威内容 | 已经写明的边界 |
| --- | --- | --- |
| 事务型元数据 | Task、TaskAttempt、TaskExecutionContext、Snapshot、ContractVersion、ConflictDecision、ReplayRequest、AuditRecord、RawPayloadReference | 要能表达唯一性和创建或返回已有记录。索引、锁和隔离级别尚未设计 |
| 金额处理结果 | ExtractedFieldResult、ObservedAmount 及其一次写出的匹配结果、版本固定记录、NormalizedAmount | 逻辑上独立于任务状态。物理上可以与元数据使用同一种产品。字段结果只有一份权威 |
| 原始报文正文 | RawPayload | `rawPayloadRef` 只是引用。介质未选。不是 OLAP 副本 |
| 分析副本 | Doris 中尚未设计的 ODS、DWD、DIM、DWS、ADS | 只复制已经提交的不可变结果。不承担任务终态、配置发布、审计权威和原文读取 |

需要“插入已有身份时返回原记录、且不覆盖原内容”的对象是：已声明稳定事件身份的 Task、ReplayRequest、已发布 Snapshot、已封存 ContractVersion、ConflictDecision、ObservedAmount、NormalizedAmount、版本固定记录、ExtractedFieldResult、AuditRecord。内容不一致时，现行规则是完整性异常或不覆盖，不是更新原行。

本轮没有发现必须回头改正 ADR 或 06-04-04 职责划分的错误。下面的产品差异是新的比较约束，不改那些已审查正文。

## 3. MySQL 与 PostgreSQL 对比

### 3.1 能力分层

| 能力 | 官方文档中的产品能力 | 本仓库当前实际能力 | 尚未验证 |
| --- | --- | --- | --- |
| 事务和唯一约束 | 两种产品都有事务引擎和唯一索引 | 无数据库、无驱动、无表 | 隔离级别、锁等待和死锁在本项目并发下的表现 |
| 创建或返回已有记录 | 语义不同，见 3.2 | 无适配代码 | 不可变记录的冲突后读取是否与 Pipeline 契约一致 |
| JSON | 两种产品都有 JSON 类型 | 未使用 | 契约正文和报文是否需要 JSON 查询 |
| 大字段 | 上限不同，见 3.2 | 无报文容量统计 | 真实报文是否适合放进关系库 |
| Spring Boot 3.5.16 | JDBC 自动配置认识 MySQL 和 PostgreSQL 驱动 | 应用没有数据源依赖 | 驱动、连接池和 JDK 25 的实际连通 |
| MyBatis-Plus 3.5.18.1 | 代码生成文档把 MySQL、PostgreSQL 列为内建数据库类型 | 只在依赖管理中登记，未进入类路径 | 其保存接口在键冲突时会不会更新不可变行 |

Spring Boot 3.5 文档用 `jdbc:mysql` 作为示例地址。那是文档示例，不是 MTX 的选型。未设置数据源地址时，Spring Boot 会尝试自动配置嵌入式数据库。正式元数据库不能依赖这条测试路径。

### 3.2 产品差异

| 维度 | MySQL 8.4 手册 | PostgreSQL 19 手册 | 对 MTX 的含义 | 证据 |
| --- | --- | --- | --- | --- |
| 默认隔离 | InnoDB 默认 `REPEATABLE READ`，并提供四种标准隔离级别 | 默认 `Read Committed`，另有 `Repeatable Read` 和 `Serializable` | 两边默认值不同。本轮不选隔离级别。移植时不能假设默认行为相同 | 官方文档 |
| 唯一冲突 | 重复的唯一键或主键使普通 `INSERT` 失败。`INSERT ... ON DUPLICATE KEY UPDATE` 在冲突时更新旧行。受影响行数 1 表示插入，2 表示更新，0 表示更新成原值；连接若带 `CLIENT_FOUND_ROWS`，最后一种变成 1 | `ON CONFLICT DO NOTHING` 不插入。`DO UPDATE` 更新冲突行。`DO SELECT` 配合 `RETURNING` 返回已有行，并可加行锁。发布说明写明 `DO SELECT` 是 19 的新增能力 | 金额和配置记录需要的是返回已有行且不改内容。MySQL 这条语句的定义是更新。PostgreSQL 19 的 `DO SELECT` 更接近该契约，但项目没有选定 19，也没有验证驱动 | 官方文档。项目使用情况为尚待验证 |
| 多唯一索引 | 手册建议避免在有多个唯一索引的表上使用 `ON DUPLICATE KEY UPDATE`，因为冲突可能只更新其中一行 | `ON CONFLICT` 可以指定冲突目标。推断失败会报错 | 一个表若同时有任务身份和另一组唯一键，不能靠未指定目标的更新语句处理 | 官方文档，架构推导 |
| 并发插入 | InnoDB 对重复主键加排他记录锁，对重复唯一键加排他 next-key 锁 | `Read Committed` 下，`DO NOTHING` 可能因为尚未进入本语句快照的并发事务而不插入。`DO UPDATE` 和 `DO SELECT` 会等待对方提交后再处理冲突行 | 先查后插不能代替唯一约束。没有唯一索引时，两种产品都不能保证只留下一条权威记录 | 官方文档，架构推导 |
| JSON | `JSON` 列使用二进制内部格式，按键或下标读取子元素。文档大小不能超过 `max_allowed_packet` | `json` 保留原文文本。`jsonb` 使用分解后的二进制格式，不保留空白、键顺序和重复键，并支持索引。官方建议一般使用 `jsonb` | 身份字段应是普通列。JSON 只适合尚未结构化的附加内容。契约正文哈希已经是权威，不需要靠 JSON 键顺序保证等价 | 官方文档，架构推导 |
| 大字段 | `LONGBLOB` 的长度上限是小于 2^32 字节，另受 `max_allowed_packet` 和内存限制。行内其他列合计仍受 65,535 字节限制，BLOB 只占其中的指针开销 | 单个字段上限 1 GB。较大的变长值可以放到行外的 TOAST 表，堆元组里保留指针 | 没有报文大小样本前，不能判断大字段是否可用。PostgreSQL 的 1 GB 字段上限是硬限制，不是本项目的容量规划 | 官方文档。报文规模为尚待业务确认 |
| 索引 | BLOB/TEXT 索引必须指定前缀长度。分区表不支持全文索引 | `jsonb` 可建 GIN 等索引。分区表上的索引实际落在各分区 | 观测身份、任务身份和审计身份用完整列的唯一索引。不把报文正文或大段 JSON 当作唯一索引列 | 官方文档，架构推导 |
| 分区与唯一性 | 分区表达式中的每一列都必须出现在每一个唯一键中。分区 InnoDB 表不支持外键。单表分区上限 8192 | 分区表的唯一约束或主键必须包含全部分区键列，且分区键不能是表达式。原因是每个分区索引只能保证分区内唯一 | 按时间分区时，若时间不是逻辑身份的一部分，两种产品都不能用分区唯一索引保证全局只有一条观测或一条任务。历史归档不能牺牲这条唯一性 | 官方文档，架构推导 |
| 库与 Schema | `CREATE SCHEMA` 是 `CREATE DATABASE` 的同义词 | Schema 是同一数据库内的命名空间。官方分区文档另有继承子表，那不是本轮要使用的拆分方式 | “不同 Schema”在两种产品里不是同一件事。MySQL 的另一个库名不是另一套事务产品 | 官方文档 |
| 备份恢复 | 手册包括逻辑导出 `mysqldump`、物理与增量策略，以及用二进制日志做时间点恢复 | 手册包括 SQL 导出、文件系统备份，以及 WAL 连续归档和时间点恢复 | 两种产品都有官方恢复路径。本仓库没有备份作业，也没有验证恢复顺序 | 官方文档。项目恢复为尚待验证 |
| 监控 | 8.4 手册有 Performance Schema 和服务器状态变量 | 19 手册有统计视图和日志维护 | 仓库没有接入任一监控。运维复杂度取决于以后的托管方式，本轮没有实测 | 官方文档。项目使用为尚待验证 |
| 许可 | 8.4 导言写明双许可：GNU GPL 开源使用，或向 Oracle 购买商业许可。企业版是单独的商业发行 | PostgreSQL License，允许使用、复制、修改和分发，不收取许可费。页面写明不计划改用其他许可证。许可文本同时写明发行方不提供维护义务 | 开源许可不等于已经购买支持，也不等于本项目已经完成安全补丁流程。两种许可风险不同，但都还不是选型结论 | 官方文档。支持合同为尚待业务确认 |
| 扩展 | 两者都能做复制。分区唯一键规则限制按时间拆分权威表 | 同左。单表和单字段还有附录中的硬上限 | 没有事件量和并发样本，不能估算节点数。按非身份列分片会拆开全局唯一约束 | 尚待业务确认，架构推导 |

Spring Boot 3.5.16 的 `DatabaseDriver` 同时列出 `MYSQL` 和 `POSTGRESQL`。3.5 参考文档的数据源示例包含 MySQL JDBC 地址，连接池构建器也列出 PostgreSQL 的非池化数据源。同一版本 BOM 管理 `com.mysql:mysql-connector-j:9.7.0` 和 `org.postgresql:postgresql:42.7.11`。这些坐标没有进入 MTX 模块依赖。BOM 中有驱动版本，只说明以后若引入 starter 时由该 BOM 管理版本，不说明已经连通，也不说明 PostgreSQL 19 或某一 MySQL 服务器版本已经通过 JDK 25 验证。

MyBatis-Plus 官方代码生成说明把 MySQL 和 PostgreSQL 列为内建 `dbType`，并提到 PostgreSQL 需要 schema 名。3.5.18 变更记录包含识别 PostgreSQL 分区表的修复，3.5.18.1 的发布日期与 ADR-0001 的记录一致。该框架尚未进入类路径。接入前要单独核对保存方法，避免键冲突时改写不可变行。本轮没有做这项核对。

### 3.3 对逻辑实体的约束

这些约束两种产品都要满足。满足方式依赖以后选定的语句，不依赖现在指定产品。

| 对象 | 存储必须保证的行为 | 不适合的产品用法 |
| --- | --- | --- |
| Task | 来源已声明稳定事件身份时，冲突返回原 `taskId`，保留第一次的权威 `rawPayloadRef` 和 `receivedAt` | 用冲突更新改写权威引用或接收时间 |
| ReplayRequest | 同一个调用方标识返回已有重放任务 | 把普通重复投递写成新的重放标识 |
| Snapshot、ContractVersion | 发布或封存后不改内容。哈希不符是失败，不是更新 | 用 UPSERT 刷新已发布批次或契约正文 |
| ConflictDecision | 变化时插入新决定 | 更新原决定或追加证据 |
| TaskExecutionContext | 原任务重试读取已固定的快照和契约版本 | 失败方用自己的候选覆盖胜出记录 |
| ObservedAmount | 四段身份冲突时返回原观测和原匹配结果 | 更新 `mappingStatus`、金额、`presence` 或 `rawText` |
| 版本固定记录、NormalizedAmount | 固定记录先成功。相同标准化身份和相同内容返回原结果 | 覆盖规则版本或标准化结果 |
| ExtractedFieldResult | 同一键只保留一份权威。内容不一致是完整性异常 | 在元数据库和金额库各写一份，或冲突时覆盖 |
| AuditRecord | 相同身份和相同内容不另插。内容冲突不覆盖，也不重开任务 | 用日志表代替审计，或为了补写而删除原记录 |

06-03-02-03 里的 MySQL 表仍只是“若配置库采用 MySQL”的建议。本比较不把那些表提升为已批准模型，也不为 PostgreSQL 补一套对应的表。

## 4. 元数据与金额结果的存储组合

比较三种组合。金额结果包括 ExtractedFieldResult、ObservedAmount、版本固定记录和 NormalizedAmount。MappingResult 不单独存放。

### 4.1 同一种产品、同一个数据库

任务、配置、审计和金额结果使用同一个数据库实例中的同一组可提交数据。记录仍然按 Pipeline 第 9 节分开，任务状态更新不覆盖观测。

| 方面 | 评估 |
| --- | --- |
| 事务 | 一次本地事务可以同时提交有依赖的记录，例如版本固定记录和标准化结果。失败则一起回滚。这不表示所有阶段必须合成一个长事务 |
| 唯一约束 | 同一数据库内的唯一索引可以执行第 3.3 节的身份 |
| 故障 | 一个备份和一套恢复点覆盖这些权威。恢复后不需要先对齐两个产品 |
| 查询 | 按标识读取任务和它引用的观测，不必做跨产品查询 |
| 运维 | 一套容量、权限和监控。库变大后的归档压力也集中在这里 |
| 证据 | 架构推导。06-04-04 已把“同一种事务产品”写成早期建议，本轮维持该建议，仍不是 Accepted |

### 4.2 同一种产品、不同 Schema

这个选项不能脱离产品解释。

PostgreSQL 的 schema 位于同一个数据库中。跨 schema 可以出现在同一个本地事务里，权限可以分开。唯一约束不跨 schema。若元数据和金额结果各放一个 schema，仍必须约定只有一个权威位置，不能两边各写一份字段结果。备份默认会带上整个数据库，除非导出时显式排除。这是官方 schema 模型加上架构推导，项目尚未验证跨 schema 事务。

MySQL 8.4 中 schema 与 database 是同义词。另一个库名仍是同一个服务器上的另一个目录式命名空间，不是另一套事务产品，也不是 PostgreSQL schema 的对应物。把它称作“不同 Schema”不能证明已经拆开故障域。同一实例上的两个库是否在一条事务中提交，本仓库尚未验证。

因此，不同 Schema 可以在 PostgreSQL 上用作权限和命名边界。它不能当作两种产品，也不能用来回避 IR-09。MySQL 上不应把这个选项写成已经成立的拆分方案。

### 4.3 不同数据库产品

金额结果使用与元数据不同的数据库产品，包括把金额权威放到 Doris。

| 方面 | 评估 |
| --- | --- |
| 事务 | 仓库没有批准跨存储的本地事务。Kafka 客户端也未进入模块依赖，不能把消息提交和两套数据库绑定成一个事务 |
| 唯一约束 | 每边可以有自己的唯一索引，但不能原子地保证“版本固定成功且标准化结果写出”或“观测和匹配结果一次写出” |
| 故障 | 一边已提交、另一边失败时，需要补偿和重读规则。这些规则属于 IR-09，尚未决定 |
| 查询 | 管理端同时看任务和金额时要跨产品组装。一致性是读时拼接，不是一个提交点 |
| 运维 | 两套备份、两套权限和两条恢复链路。恢复顺序错了会把副本当成权威 |
| 证据 | 仓库事实加上架构推导 |

Doris 继续只接收已提交副本。分析副本失败不回滚权威结果，权威结果也不以 Doris 成功为准。这是已审查设计，不是本轮新选择。

### 4.4 组合结论

早期仍建议同一种具备事务和唯一约束的产品、同一个数据库保存元数据和金额结果。理由是当前没有跨存储原子提交。字段结果即使和任务放在同一产品，权威仍然只有一份。

这个建议的退出条件是 IR-09 先写明每个写入的提交点和失败后读取哪一边。在此之前不拆产品。不同 Schema 只在未来产品确实把 schema 当作数据库内部命名空间时再考虑，并且不改变“一份权威”的规则。

## 5. 原始报文介质比较

`rawPayloadRef` 是任务第一次保存的引用标识，进入观测身份。RawPayload 是该引用指向的不可变字节。两者不是同一个存储对象。引用留在事务型元数据中。正文读不到时，已有观测仍按引用恢复；没有观测时沿用 `PAYLOAD_REF_INVALID`，不产生观测。

仓库没有报文大小、增长率、并发读取量或保留期限的统计。下表不填写这些数字。

| 维度 | 对象存储 | 关系库大字段 | 共享文件系统 |
| --- | --- | --- | --- |
| 适用性 | 按不可变对象键存放字节，和任务行分开 | 正文与引用可以在同一次事务中写入 | 只有所有 Admin 和 Worker 进程都能看到同一份持久挂载时才可能使用 |
| 不可变 | 依赖产品的写一次或对象锁定能力。本轮没有选定产品，不能把某一云厂商的锁定功能写成已具备 | 行可以被有权限的更新语句改写。不可变要靠权限和禁止更新，产品不会自动按观测身份禁止更新 | 文件可以被覆盖。写一次命名约定不是文件系统的强制约束 |
| 内容哈希 | 可以在写入时计算，并把哈希与引用一起放在元数据中复核 | 同左。哈希存在元数据或报文记录中，不只写应用日志 | 同左 |
| 读取 | 已有观测的恢复不读正文。未命中观测时按权威引用读。延迟和并发取决于具体产品，本轮没有实测 | 大字段会进入关系库备份和缓存。MySQL 对超大结果有包大小限制，PostgreSQL 单字段上限 1 GB | 读取延迟取决于挂载和磁盘，本仓库没有这种挂载 |
| 引用完整性 | 没有跨产品外键。引用可能先于正文，或正文已归档而引用还在 | 同一数据库里可以用同一事务减少“有引用无正文”。这仍然不是已批准的外键设计 | 没有数据库外键 |
| 生命周期 | 归档和冷数据是产品能力，天数未定 | 正文使事务库备份变大。归档要单独设计，不能删除仍被无观测任务需要的正文 | 归档就是搬文件，容易和引用脱节 |
| 备份 | 与元数据不是一个恢复点。要能按引用找回当时字节 | 可随事务库备份一起恢复，代价是备份体积和恢复时间包含全部正文 | 文件备份与数据库备份也不是一个恢复点 |
| 安全 | 访问凭证、加密和审计依赖所选产品 | 跟随数据库权限和加密。当前没有选定加密方案 | 跟随操作系统权限。独立部署的两个应用不容易共享 |
| 证据 | 架构推导。产品能力为尚待选定后核验 | 官方大字段上限加上架构推导 | 架构推导。当前模块没有共享文件契约 |

对象存储在这里指一类按键读取不可变字节的介质，不是某一个已批准的供应商。关系库大字段指第 3 节两种产品各自的二进制大类型，不是已经选择把正文放进元数据库。

在拿到报文大小分布之前，两种介质都保留。不把 Doris 当作原文权威，也不因为存在 `rawPayloadRef` 就断定正文在关系库。共享文件系统不适合作为两个独立部署应用的正文权威，除非以后另有部署决策证明它们共享同一持久卷，并且写一次约束能够强制执行。

## 6. 存储适配器模块归属

ADR-0002 的依赖事实：

| 约束 | 仓库事实 |
| --- | --- |
| Core 不依赖 JDBC、MyBatis 或具体数据库客户端 | 已接受 |
| Pipeline 只依赖 common 和 core | 已接受。编排通过存储无关端口 |
| Admin 只依赖 common、core、messaging | 已接受。Admin 不依赖 Worker，也不依赖 Writer |
| Worker 负责装配执行实现 | 已接受。Worker 可以依赖 writer、pipeline 等 |
| 不增加第十一模块，不引入 `platform-persistence` | 已接受 |

Admin 发布配置和任务管理需要元数据端口。Worker 执行金额链路也需要这些端口，以及金额结果端口。两边不能通过 Writer 共享实现，因为 Admin 不能依赖 Writer。Core 里的端口不能带具体数据库类型。

| 放置位置 | 是否符合当前依赖 | 评估 |
| --- | --- | --- |
| `platform-core` 或 `platform-common` | 不符合 | 会把 JDBC 或数据库客户端带进禁止依赖存储实现的模块 |
| `platform-pipeline` | 不符合 | Pipeline 不访问具体存储。Admin 也不依赖 Pipeline |
| `platform-writer` | 不符合 Admin 的依赖 | Writer 负责已形成结果的写出，不负责配置发布和任务终态。Admin 不能为了复用适配器去依赖它 |
| `platform-messaging` | 依赖名单允许两个应用依赖它，但职责不符合 | 该模块是消息适配。把数据库客户端放进去会把存储和消息绑成同一个发布单元。当前也没有 Kafka 客户端 |
| `app-admin` 与 `app-worker` 各自装配 | 符合当前矩阵 | 端口放在 Core。两个应用各自实现适配器。可以开始存储接入而不改 ADR。代价是两份实现必须保持同一套冲突后读取规则 |
| 新增双方都能依赖、且允许持有 JDBC 的模块 | 不符合当前 ADR | 只有新的 ADR 修改“不增加第十一模块”或放宽某个现有模块后才可能。本轮不提出模块名，不修改依赖 |

本轮建议：物理模型确定之前，不新增模块。若实现阶段要求一份共享适配器源码，把该要求写成独立决策，选项只记录为“修订 ADR-0002 的依赖边界”。在那份决策接受之前，符合当前架构的做法是 Core 端口加两个应用各自装配。

## 7. 备份、恢复和容量约束

下列项目没有业务证据，本轮不赋值：RPO、RTO、保留天数、报文容量、日事件量、峰值并发、法规保留年限、冷热存储比例。

| 清单项 | 可以确定的要求 | 需要确认的参数 |
| --- | --- | --- |
| 元数据备份 | Snapshot、ContractVersion、ConflictDecision、Task、执行上下文、审计和权威引用必须能按同一次提交点恢复 | 备份周期、保留的备份份数、RPO、RTO |
| 金额结果备份 | 与元数据同产品时，进入同一次事务库备份。拆产品后必须单独备份，并服从第 4.3 节的恢复顺序 | 是否拆产品尚未决定，所以不设第二套周期 |
| 原始报文备份 | 按权威引用能找回当时字节。正文备份点可以晚于引用，但未形成观测的任务在正文不可读时不能产生观测 | 报文大小分布、在线保留、归档介质、删除条件 |
| Doris 重建 | 从已经提交的权威结果重建分析副本。不用 Doris 反向修复任务、配置或观测 | 分层模型和重建窗口尚未设计 |
| 恢复顺序 | 先恢复事务权威，再核对引用能否定位正文，最后重建 Doris。不能先恢复分析副本并把它当成权威 | 各步骤的允许中断时间 |
| 一致性校验 | 逻辑身份只有一条有效记录；观测带有同一次写出的匹配结果；版本固定记录先于标准化结果；冲突决定未被原地修改；审计内容冲突没有覆盖原记录 | 校验频率和允许的修复动作。本轮不规定自动修复 |
| 历史归档 | 被观测引用的快照、契约版本和观测不能删除后改写。分区或归档不能丢掉全局唯一性 | 归档后是否仍算在线权威 |
| 保留期限 | 06-04-04 已列各对象的不可删除条件 | 天数、法规依据、无引用草稿能否删除 |
| 容量监控 | 事务库、正文介质和 Doris 分开计量 | 告警阈值、增长样本 |
| 故障恢复目标 | 权威恢复完成后，已有观测不依赖再次读取正文；没有观测的任务仍按原文是否可读决定能否提取 | RPO、RTO，以及正文延迟于元数据时是否允许暂停新提取 |

关系库与 Doris 没有共同事务。恢复演练在选定产品和备份工具后才能执行，当前不能声称已经验证。

## 8. 稳定事件身份及重复投递约束

| 问题 | 评估 | 证据 |
| --- | --- | --- |
| 唯一性作用域 | 稳定事件身份只在来源契约已经声明时才是非重放任务的幂等身份。作用域属于该来源契约，不是平台替所有来源规定的全局键。不同来源即使字符串相同，也不能在没有契约证据时并成一个任务 | 仓库事实，架构推导 |
| 没有稳定身份 | 不使用金额、`rawPayloadRef` 或 `receivedAt` 拼键。该来源不具备跨投递幂等，直到契约声明身份 | 仓库事实 |
| 同一身份、不同报文 | 回到原 `taskId`。不替换第一次保存的权威引用和权威 `receivedAt`，不用本次新引用构造观测身份或读取原文，不创建 `replayRequestId` | 仓库事实 |
| 报文哈希 | 它可以复核已经保存的权威字节是否被改写。它不是任务幂等键，不是观测身份，也不能把本次不同报文写成新任务。契约正文哈希是另一件事，沿用 `contractBodySha256` | 架构推导。哈希字段是否强制保存仍是 06-04-04 的“若存在” |
| 普通重复投递与显式重放 | 普通重复投递沿用原任务。显式重放由调用方给出 `replayRequestId`，创建新 `taskId` 和新观测，不覆盖旧观测。存储不能在重复投递时自动生成重放标识 | 仓库事实 |
| 统一事件键 | 本轮不设计。来源字段名、编码和唯一范围都没有契约样本 | 尚待业务确认 |

同一稳定身份再次出现不同报文时，是否额外产生一条不改变原任务的告警或审计，现有错误码没有对应项。本轮不新增错误码。若业务要求可见告警，另行确认，不能用它改变任务归属。

P-03、P-06 和 R15 仍按台账保持未决。存储选型不决定身份不一致与哈希不符同时发生时的单一错误码，不决定来源身份与原文记录不一致的归类，也不决定失效快照能否跳过。

## 9. 推荐方案与不推荐方案

MySQL 8.0.46 与 Doris 4.0.7 已由 ADR-0005 接受。第 1 条记录的是该决策，不是本评估文件新做的选型。同库存放、报文介质和适配器归属仍是建议，不是另一份 Accepted 决策。06-04-02 里除 IR-01 外的状态不由本节改写。

有条件的建议。产品版本已由 ADR-0005 接受，下列各项不再把产品选择留作开放项：

1. 事务型元数据的目标服务器版本是 MySQL 8.0.46。PostgreSQL 不是当前目标。8.0.46 的语句行为尚未在本仓库验证，不能用第 3 节的 8.4 手册代替这次验证。驱动、字符集、排序规则、隔离级别和生产支持条件仍待决定。8.0.46 的生命周期风险见 ADR-0005。
2. 在 IR-09 关闭前，金额结果与元数据使用同一种事务产品的同一个数据库。逻辑记录保持分开，字段结果只保留一份权威。
3. 原始报文继续并列调查对象存储和关系库大字段。引用与正文分开保存。调查项是报文大小分布、保留期限和读取并发，不编造容量。
4. 适配器端口放在 Core。在新的依赖决策接受之前，由 Admin 和 Worker 各自装配实现。
5. Doris 4.0.7 只重建和查询已提交副本。五层模型仍待设计，缺少表不表示分层方向取消。客户端版本未锁定。

不推荐：

| 方案 | 原因 |
| --- | --- |
| 把 MySQL 8.4 手册行为写成 8.0.46 已验证能力，或把目标版本改成 8.4 | ADR-0005 锁定的是 8.0.46。8.4 比较材料保留在第 3 节，不能代替该版本的验证。升级到 8.4 LTS 需要另一次兼容性评估 |
| 用 `ON DUPLICATE KEY UPDATE` 或会更新旧行的通用保存方法处理观测、快照、冲突决定和标准化结果 | 官方语义包含更新。现行规则是返回原记录或不覆盖 |
| 把 PostgreSQL 19 的 `DO SELECT` 当成已经可用的项目能力 | 该语法是 2026-11-19 发布的版本新增的。项目未选定版本，也未验证驱动 |
| 为了分类不同而把金额结果拆到另一个数据库产品 | 没有跨存储原子提交。会提前做 IR-09 尚未允许的补偿 |
| 在 MySQL 上用“不同 Schema”声称已经拆库 | 官方定义里 schema 就是 database |
| 按不在逻辑身份中的时间列做分区，并指望分区唯一索引保证全局幂等 | 两种产品都要求唯一键包含分区键 |
| 把正文、任务状态或审计权威放进 Doris | 与已审查的 OLAP 边界冲突 |
| 把共享文件系统当作两个独立应用的默认正文介质 | 没有共享卷决策，覆盖语义也不能保证不可变 |
| 新增 `platform-persistence` 或让 Core 依赖 JDBC | 直接违反 ADR-0002 |
| 设计全来源统一事件键 | 没有来源契约证据 |
| 写入 RPO、RTO 或保留天数 | 没有业务证据 |

## 11. 下一阶段物理模型设计的前置条件

进入物理模型和 DDL 之前，至少要满足：

1. 事务型产品版本已由 ADR-0005 接受为 MySQL 8.0.46。本文件的比较不能代替该决策，也不能把 8.4 手册写成 8.0.46 已验证能力。驱动和隔离级别仍未选定。
2. 金额结果是否与元数据同库有明确结论。若不同库，IR-09 的提交点和失败读取先写明。
3. 原文介质有明确结论，并核对 `rawPayloadRef` 与正文定位方式。容量未知时可以先决定“不把正文放进事务行”，但不能编造大小。
4. 每个第 3.3 节对象的逻辑身份对应一条不覆盖原内容的唯一约束策略。分区方案先证明不会放宽该唯一性。
5. 来源契约提供稳定事件身份的字段和唯一性作用域。没有该证据的来源保持不能跨投递幂等。
6. 适配器归属沿用第 6 节的当前矩阵，或先接受一份修改依赖的 ADR。
7. 备份清单中的 RPO、RTO 和保留天数由业务确认后再写入运行设计。物理模型可以预留归档边界，但不能写死天数。
8. Doris 物理模型仍排在权威写入规则之后。五层表不进入这一阶段的 DDL。

这些条件满足之前，不创建数据库，不编写 DDL，也不把任何表结构写成已批准设计。
