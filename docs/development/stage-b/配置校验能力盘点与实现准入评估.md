## 2. 当前配置体系概览

当前运行配置只有两个 Spring Boot 应用各自的一份 `application.yml`。`docs/development/local-build.md` 第 71 行写明：两个应用配置进程名、`mtx.rdp.role`、统一控制台日志和进程内健康状态，没有数据库、Kafka 或业务接口配置。`README.md` 第 50 行写明 `spring.main.web-application-type` 为 `none`，不启动嵌入式 HTTP 服务，骨架没有业务 Controller、Kafka 监听、数据库配置或 Pipeline。

配置值进入进程有两条已能核对的路径：

- classpath 上的 `application.yml`。
- Spring 环境覆盖。`AdminApplicationTest.rejectsWorkerRoleOnAdminProcess` 用 `--mtx.rdp.role=worker` 覆盖角色。环境变量是否被项目单独约定：UNKNOWN。仓库没有列出对应环境变量名。

`AdminRuntimeProperties` 和 `WorkerRuntimeProperties` 只绑定 `mtx.rdp.role`。它们没有校验注解，也没有 Java 默认值。真正的进程名和角色校验在 `StartupChecklist.check`，由 `AdminProcessStartup.run` 与 `WorkerProcessStartup.run` 在应用启动后调用。

## 7. 模块归属与依赖边界

`StartupChecklist` 位于 `platform-common`。它不依赖 Spring。这与 ADR-0002 中 common 不依赖框架的约束一致。

两个应用负责读取 Spring 环境并调用该函数，同时做健康检查。健康检查使用 Actuator，不能放进 `platform-core`。

`platform-core` 现在只有契约版本唯一性解析。配置属性类在 `app-admin` 和 `app-worker`，没有放进 core。没有发现需要新增模块或基础设施依赖才能完成配置校验的缺口。

与 ADR-0001 至 ADR-0005 没有新的冲突。ADR 不定义这组进程配置的校验表。把调查稿里的映射配置提前做成 core 校验器，才会越出已接受范围。本文不建议这样做。

## 9. 实施准入结论

当前不具备新的配置校验实现准入。

原因：仅有的纯逻辑规则已经实现；尚未实现的配置语义要么没有规则，要么仍挂在未决的金额、快照、身份或基础设施事项上。本文不从这些缺口里补一条默认规则。

## 10. 阻断项和后续建议

- 不要把 `StartupChecklist` 再实现一次，也不要为了 Stage B 把它从 `platform-common` 搬到 `platform-core`。
- 不要为 `web-application-type`、日志格式或健康详情单独发明取值范围。
- 映射配置、金额配置和任务配置的校验，等对应设计冻结并且有明确的必填、格式和错误表达之后再单独立项。
- 健康检查继续留在两个应用。它不是 Stage B 纯函数。

若以后要做的是新的配置对象，前置条件是：配置项、来源、是否可空、错误表达和时点都写进已接受文档。在那之前没有最小实现任务。
