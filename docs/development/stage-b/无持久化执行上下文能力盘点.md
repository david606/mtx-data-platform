## 3. 字段与生命周期

Pipeline 第 4 节把下列字段标为建议，不是 Java 类，也没有全部进入观测：

| 字段 | 文档给出的含义 | 来源与空值 | 生命周期 |
| --- | --- | --- | --- |
| `processingId` | 一次金额处理的执行标识 | 算法未设计 | 未定 |
| `taskId` | 逻辑任务标识 | 生成算法未设计。第 4.2 节写它依赖存储设计 | 一个逻辑任务一个标识 |
| `taskAttemptId` | 一次尝试 | 技术重试可以新建。算法仍看 IR-07 | 尝试级，不是上下文身份 |
| `rawPayloadRef` | 权威原文引用 | 第一次接受时保存。后到的引用不替换它 | 不可变任务输入 |
| 来源平台、接口、消息类型、事件号、消息号 | `AmountSource` | 空消息类型保留空字符串 | 不可变任务输入 |
| `snapshotId`、`parserVersion` | 第一阶段胜出值 | Worker 候选只是提议 | 第一阶段成功后不可改写 |
| `contractVersionId`、`contractBodySha256` | 第二阶段权威版本和正文哈希 | 必须属于已胜出快照 | 第二阶段成功后不可改写 |
| `receivedAt` | 窗口判断的业务时间 | 权威值来自第一次接受 | 不可变任务输入 |
| `normalizationRuleVersion` | 标准化规则版本 | 未分配时不编造。不在任务开始时确定 | 不属于两阶段上下文。IR-14 待决策 |
| `conversionRuleVersion` | 转换规则版本 | 不转换时为逻辑空值。不用 `NO_CONVERT` 填充 | 不属于两阶段上下文。物理表示未选 |
| `businessObjectType`、`businessObjectId` | 可选业务对象 | 来源未设计时为空。不从金额字段推断 | 不进入观测身份 |

`tenantId` 不进入必填项。Pipeline 第 4 节写明不单造租户字段。

第 4.1 节给出三种逻辑状态，并写明状态名不是已经存在的枚举：

| 状态 | 已持久化内容 | 下一步 |
| --- | --- | --- |
| 未固定 | 没有本任务的上下文 | 只允许第一阶段 |
| 快照已固定 | 胜出 `snapshotId` 和 `parserVersion` | 只允许第二阶段。禁止提取 |
| 契约已固定 | 再加 `contractVersionId` 和 `contractBodySha256` | 才允许查询观测 |

文档写明不能从“未固定”直接进入“契约已固定”，提取开始前两阶段都必须已经可靠持久化。一个非重放 `taskId` 只有一份上下文。多个 Worker 不靠 JVM 本地锁。`createOrGetSnapshot` 与 `createOrGetContract` 被明确写成不是已经存在的 Java 接口。

版本信息有，但分属不同阶段，而且 `parserVersion` 的登记仍是 IR-11。执行权和租约不属于这份上下文。写入围栏在 `06-04-11` 第 7 节，依赖任务行锁、代次、`CURRENT`、`RUNNING` 和有效阻断为空。

## 6. IR-10 与物理分支的继承

这两件事不合并。

台账 IR-10 的问题是审计记录的物理存储、保留和跨进程恢复尚未选型。状态是待决策。该行没有 `TaskExecutionContext`。`06-04-40` 至 `06-04-59` 讨论的是责任事实、定义 B、规则 C、D6 与 D7。集成审查 INT-03 写明定义 B 与规则 C 的架构决议栏仍空，空白不是批准。本轮不改这些结论，也不把审计身份放进执行上下文。

`TaskExecutionContext` 的物理约束分支不在 IR-10。它在 IR-02 的实验文档中：

- `06-04-23` 第 6.2 节：逻辑身份是每个非重放 `taskId` 一份。分支 A 嵌入任务行，分支 B 独立成表。决定前 A-12 没有可执行结构。唯一索引不授予执行权。
- `06-04-24` 第 8.1 节：两种实验不能合成一个结论。A-12 待补、未执行，阶段 A 不执行。第 10 节把承载标为待决策，推荐值是“不选”。

本轮继承这个“不选”的结论。无持久化的内存对象不是这两个分支的最终设计，也不能提前决定 Worker 执行权。

## 7. 模块边界

当前 POM 与 ADR-0002 一致：

- `platform-common` 不依赖其他内部模块，也没有业务上下文类型。
- `platform-core` 只依赖 `platform-common`。现有契约类型不依赖 Spring、JDBC、Kafka 或 MyBatis。
- `platform-pipeline` 只依赖 `platform-common` 与 `platform-core`，没有实现代码。
- `platform-transform` 与 `platform-quality` 同样只有允许的依赖，没有上下文代码。

没有反向依赖，也不需要新模块。Pipeline 第 10 节把上下文模型建议放在 `platform-core`，但同文第 14 节第 14 点写明本阶段不实现 Java。在字段和持久化语义闭合前，不把这句建议当成实现许可。
