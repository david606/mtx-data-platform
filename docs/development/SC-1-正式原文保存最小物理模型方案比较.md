## 1. 已经接受的约束

- 第一版只保存原始报文字节和 `rawPayloadRef`。
- 不增加接收时间、来源平台、连接器、接收通道、Kafka topic、partition、offset。不得用内部字段、辅助表或隐式元数据把它们加回来。
- 原文和引用在 MySQL 同一事务保存。明确提交成功后按引用读回，并逐字节比较。
- 相同字节再次保存是另一笔保存，不自动去重。
- `rawPayloadRef` 不是业务事件身份、投递身份或幂等键。
- 临时建表例外只覆盖这一张 SC-1 正式原文表：允许插入、按引用读取和读回核验。禁止删除、归档、自动清理、定时清理和未授权覆盖。
- IR-15 保持未决。Java、DDL、开发服务器操作分别授权。这次比较不授予其中任何一项。

不得用作 `rawPayloadRef` 的值：数据库自增 ID、业务订单号、Kafka offset、内容哈希。`java.util.UUID.nameUUIDFromBytes` 由输入字节派生，属于内容派生标识，同样不得使用。

## 2. rawPayloadRef 如何生成

JDK 25 的 `java.util.UUID` 公开工厂是 `randomUUID`、`nameUUIDFromBytes` 和 `fromString`。没有 v7 工厂。`randomUUID` 是类型 4。本轮没有做碰撞实验。下面的碰撞说法都是概率，不是数学上的绝对不碰撞。

| | UUIDv4 | UUIDv7 | 16 字节安全随机数 |
| --- | --- | --- | --- |
| 标记 | 推荐 | 候选 | 候选 |
| 随机性 | 122 位随机，另有版本和变体位 | 时间戳之外仍有随机位。同一毫秒内的随机位少于 122 位 | 128 位随机 |
| 碰撞 | 生成量远小于 2^61 时，撞上的概率很低，但不是零。主键冲突时这一笔插入失败，不得覆盖已有行 | 同样不是零。时间有序不消除碰撞 | 空间比 v4 略大，仍然不是零 |
| 是否依赖时间 | 否 | 是。含 Unix 毫秒时间戳 | 否 |
| 是否泄露创建时间 | 否 | 是。持有引用的人可以读出大约的生成时间 | 否 |
| 生成成本 | 一次强随机数 | 一次时钟读取加随机数 | 一次强随机数 |
| Java | `UUID.randomUUID()` 已在 JDK 25 | 标准库没有工厂。要自行排位，或增加未经批准的库 | `SecureRandom` 已在 JDK。没有标准文本形式 |
| 物理长度 | 16 字节 | 16 字节 | 16 字节 |
| 能否长期交给调用方 | 能。规范文本形式是 36 个字符的十六进制，带连字符 | 文本形式同样存在，但引用本身带有时间 | 能交给调用方，但十六进制或 Base64 都要另定一种规范，否则读回时对不上 |

推荐 UUIDv4。调用方看到的是规范文本。数据库保存 16 字节。文本和字节是同一个引用的两种表示，不是两条身份。

不推荐 UUIDv7。它把生成时间放进唯一会长期交给调用方的值里。第一版已经排除接收时间，并禁止用隐式元数据把时间加回来。索引上的顺序插入是 v7 的好处，见第 6 节，不足以推翻这个排除。

不推荐裸随机数。它不泄露时间，也没有现成的文本规范。在 v4 已经满足「不带时间、JDK 可生成、16 字节」时，不必再发明一种编码。

## 3. 引用的物理类型

[06-04-61](../investigation/round-01/06-04-61%20MTX%20Data%20Platform%20V2%20MySQL%20字符身份比较语义与唯一索引键长专项调查.md) 的相关事实：未指定字符集时服务器会落到 `utf8mb4` / `utf8mb4_0900_ai_ci`，项目没有采用；字符列会受客户端字符集转换影响；`VARBINARY` 不做这层字符转换。本轮不把该默认排序规则用于引用。

| | `BINARY(16)` | `VARBINARY(16)` | 字符型 UUID |
| --- | --- | --- | --- |
| 标记 | 推荐 | 候选 | 不推荐 |
| 存储 | 固定 16 字节 | 值最长 16 字节，另有长度前缀。短值也能写入 | 带连字符时至少 36 个字符。`utf8mb4` 下按最大字节数估算键长，远大于 16 |
| 比较 | 按 16 个字节 | 按字节，尾部的 `0x00` 有意义 | 取决于排序规则。默认 `utf8mb4_0900_ai_ci` 不区分大小写。项目未批准任何字符排序规则 |
| 索引 | 整列 16 字节，不需要前缀索引 | 整列也可以建。短值和长值会成为不同键 | 未定排序规则和列宽时，不能把字符唯一索引写成可建 |
| JDBC | `byte[16]`。写入前必须恰好 16 字节 | 同样用字节数组。类型本身允许更短的值 | 字符串。驱动可能按连接字符集转换 |
| 对外表示 | 与库内分离。库内是 16 字节，调用方拿到规范文本 | 同左，但库内容易混进短值 | 库内和对外容易写成同一串字符，转换风险留在库里 |

推荐 `BINARY(16)`。较短的写入会被补零，所以 Writer 在接触数据库之前必须拒绝不是 16 字节的值。这个拒绝是明确失败，不插入。

不推荐字符列。DEV_ONLY 的 `VARCHAR(64)` 不能当作正式引用列。

## 4. 引用唯一约束

优先评估的最小模型是：一行只有引用和正文，用引用定位这一行。

| | `PRIMARY KEY (raw_payload_ref)` | 另设自增主键，再加 `UNIQUE KEY` |
| --- | --- | --- |
| 标记 | 推荐 | 不推荐 |
| 行如何定位 | 引用就是聚集索引 | 自增或 InnoDB 隐藏行号才是聚集索引，引用是二级唯一索引 |
| 是否多一个定位值 | 否 | 是。该值不得返回给调用方冒充 `rawPayloadRef` |
| 与已接受语义 | 唯一的是这一次生成的引用，不是正文，也不是业务事件 | 同样可以做到不唯一约束正文，但多出一个物理定位 |

技术事实：InnoDB 表必有聚集索引。不设主键时，它会自己生成隐藏行号。把引用设成主键，就不需要这套隐藏定位，也不需要自增列。

不建内容哈希唯一约束、前缀索引、投递位置唯一约束。相同字节可以有多行。主键冲突只表示两个引用值撞上，处理是这一笔明确失败，不覆盖已有正文。

[持久化物理模型专项设计](持久化物理模型专项设计调查与方案比较.md) 写过原文引用「不做全局唯一」，以及「不在 MySQL 建正文唯一约束」。这里的主键只约束引用值，不约束正文字节，也不把引用变成业务事件的全局身份。该调查文件没有改写，不能把本推荐当成它已经同意的技术主键。

## 5. 原文字节列

MySQL 8.0 文档中的列上限是：`BLOB` 为 65535 字节，`MEDIUMBLOB` 为 16777215 字节，`LONGBLOB` 为 4294967295 字节。这是类型上限，不是本项目已经能够写入的大小。本轮没有查询开发服务器。

| | `BLOB` | `MEDIUMBLOB` | `LONGBLOB` |
| --- | --- | --- | --- |
| 标记 | 上限已知后才选择 | 上限已知后才选择 | 不推荐现在接受 |
| 理论上限 | 64KiB 减 1 | 16MiB 减 1 | 4GiB 减 1 |
| 协议 | 语句和结果都要放进包。手册记载的 `max_allowed_packet` 默认是 64MiB。服务器和连接器上的实际值都没有测量 | 同左。超过实际包大小时，类型上限没有意义 | 类型允许的大小远大于默认包大小 |
| 内存 | 调用方已经持有输入。读回比较至少还要再拿到一份字节 | 同左。尺寸上去之后，两份字节会压到 Worker 堆 | 不能从类型上限推出堆放得下 |
| 流式读写 | 驱动可以用流。比较仍要覆盖全部字节，流式不能省掉调用方手里的那一份 | 同左 | 同左。流式不是接受 4GiB 的理由 |
| 上限放在哪一层 | 批准了最大字节数之后，Worker 在开始事务之前拒绝超限。拒绝是明确失败，不插入 | 同左。列类型是第二道上限，不能代替批准的业务上限 | 同左 |

不能因为 `LONGBLOB` 的类型上限大，就认为应用、驱动和数据库都能承受。DEV_ONLY 使用了 `LONGBLOB`，那是测试表，不是正式类型决定。

推荐：先按第 6 节定出单条最大字节数，再从三者里选能够放下该上限的最小类型。现在不推荐接受 `LONGBLOB`。

## 6. 单条最大字节数

当前没有已批准的业务最大报文长度。本文件不假设一个数。

决策方法：

1. 只统计第一版真实调用方会提交的原始字节长度，包括空数组。本轮没有采集，也没有连接服务器。
2. 尚未列入的未来平台不参与这个数。要覆盖新平台时，另行批准提高上限，不预先写成 4GiB。
3. 批准的上限必须同时低于实际的包大小和 Worker 能同时放下输入与读回副本的堆。包大小以当时的服务器和连接器配置为准，不用未测量的手册默认值代替。
4. 超限在开始 MySQL 事务之前明确拒绝，不写入。不得截断，不得压缩后冒充原文，不得拆成多行。
5. 提高上限是另一次决定。若新上限超过当前列类型，还要另一次 DDL 授权。不得在没有授权时改列。

## 8. 风险与限制

- UUIDv4 做主键时，插入位置分散，聚集索引会产生页分裂。这是不把时间写进引用的代价。本文件不因此改推 UUIDv7。
- 碰撞概率不是零。撞上时不得覆盖。该笔是明确失败，正文没有被这一笔写下。
- 没有接收时间列，也不能从 v4 引用读出时间。人工核对仍然没有查找键。这是已接受的成本。
- 表只增不删，直到保留策略另有决定。IR-15 未决。增长不是删除的理由。
- 读回要再持有一份字节。上限若只按列类型估算，会低估堆和包的限制。
- `BINARY(16)` 对短值补零。写入路径必须先拒绝非 16 字节。
- 持久化调查里的「尚无技术主键」仍然写在那份文件里。本推荐没有改它，也还不是已批准主键。

## 9. 尚需用户决定

1. 是否接受 UUIDv4，而不接受 UUIDv7 或裸随机数。
2. 是否接受库内 `BINARY(16)`，调用方拿到规范文本。
3. 是否接受引用作为唯一主键，不另设自增主键。
4. 是否接受现在不选 `LONGBLOB`，等最大字节数确定后再选最小够用的二进制类型。
5. 单条最大字节数。本文件不代填。
6. 是否接受同表、只有上述两列。
7. 表名、字段名和正式库名。

空数组是否允许保存，仍是授权草案里待批准的规则，不是本文件新决定的。

## 12. 为什么本轮不能生成可执行 DDL

最大字节数、列类型、表名、字段名和库名都还没有用户决定。临时建表例外只划定了以后可以讨论的操作，它不是 DDL 执行授权。写出 `CREATE TABLE` 会把推荐方案变成看起来已经可以执行的语句。本轮因此不给出这种语句，也不连接服务器，也不创建表。
