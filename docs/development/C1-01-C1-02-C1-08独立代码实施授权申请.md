## 4. C1-01 显式确认键解析

两个键分别解析，再组合成确认状态。组合结果不得盖住单键已经得出的非法原因。不自动 trim，不忽略大小写，不接受别名。不新增生产环境信号，也不推定配置优先级。

`mtx.rdp.runtime-mode` 只接受精确的 `local-simulation` 与 `production`。

| 输入 | 单键结果 |
| --- | --- |
| 键不存在 | `NOT_SET` |
| 空字符串 | `INVALID` |
| 纯空白字符串 | `INVALID` |
| 精确等于 `local-simulation` 或 `production` | 该值 |
| 其他值，包括前后空格、不同大小写和别名 | `INVALID` |

`mtx.rdp.dev-only-acknowledged` 只接受精确的 `true` 与 `false`。键不存在按未确认处理，不是 `INVALID`。

| 输入 | 单键结果 |
| --- | --- |
| 键不存在 | 未确认 |
| 空字符串 | `INVALID` |
| 纯空白字符串 | `INVALID` |
| 精确等于 `true` 或 `false` | 对应布尔值 |
| 其他值，包括 `1`、`0`、`yes`、`no`、前后空格和不同大小写 | `INVALID` |

两个单键都不是 `INVALID` 时，组合结果是：

| `runtime-mode` | `dev-only-acknowledged` | 组合结果 |
| --- | --- | --- |
| `NOT_SET` | 未确认或 `false` | `NOT_CONFIRMED` |
| `NOT_SET` | `true` | `INCOMPLETE` |
| `local-simulation` | 未确认或 `false` | `INCOMPLETE` |
| `local-simulation` | `true` | `ACKNOWLEDGED` |
| `production` | 未确认或 `false` | `PRODUCTION_SELF_DECLARED` |
| `production` | `true` | `CONFLICT` |

任一键为 `INVALID` 时，组合结果是 `INVALID`，同时保留该键自己的非法结果。另一键的取值不把它改成 `INCOMPLETE`、`ACKNOWLEDGED` 或 `CONFLICT`。

`ACKNOWLEDGED` 只表示操作者显式确认完整。它不是可信非生产证明，也不是 `DEV_ONLY` 对象创建许可。`PRODUCTION_SELF_DECLARED` 只是自我声明。解析结果不得用来创建模拟存储或演示清单，也不得作为开启 C1-02、C1-08 运行时对象的条件。

- 允许修改的现有文件：`platform-common` 中的 `StartupChecklist` 或其同包测试 `StartupChecklistTest`。若解析不放进 `StartupChecklist`，新类型的类名待实施前确认，包名仍是已有的 `com.mtx.rdp.common`。
- 允许新增的职责：一个不依赖 Spring 的纯解析。输入能区分键不存在、空字符串、纯空白和原始文本。输出保留每个键的单键结果，以及上表的组合结果。
- 待实施前确认：是否给 `AdminRuntimeProperties` 和 `WorkerRuntimeProperties` 增加这两个字段。若增加，缺省不得变成已确认，`AdminProcessStartup` 和 `WorkerProcessStartup` 不得用结果创建对象或写清单。
- 禁止修改：两个 `application.yml`，`platform-core`，`platform-pipeline`，`platform-connector`，`platform-writer`，`platform-transform`，`platform-quality`，`platform-messaging`。不新增第三方依赖。
- 单元测试：覆盖两个键的单键规则，以及上表全部组合。至少包括空字符串、纯空白、前后空格、大小写不同，以及 `1`、`0`、`yes`、`no`。任一键非法时，断言组合结果是 `INVALID`，并且仍能看出是哪一个键非法。测试名写明这是确认行为，不是生产识别，也不是创建许可。不启动 Spring。
- 架构测试：`ModuleArchitectureTest` 的依赖预期保持不变。`platform-common` 仍不得依赖 Spring 或其他内部模块。
- 启动测试：现有 `AdminApplicationTest`、`WorkerApplicationTest` 的未命名启动仍然成功。若启动器读到两个键都成立，进程可以启动，但不得因此出现新的模拟对象或演示输出。
- 可以证明：代码能按精确文本区分 `NOT_SET`、`NOT_CONFIRMED`、`INCOMPLETE`、`ACKNOWLEDGED`、`PRODUCTION_SELF_DECLARED`、`CONFLICT` 和 `INVALID`，并且非法原因没有被组合结果盖住。
- 不能宣称：进程不在生产环境，安全门已通过，A13 已验收，或运行时可以创建 `DEV_ONLY` 对象。

## 5. C1-02 虚构来源与原文模拟存储

只放在 `platform-connector`。虚构来源只产生标明虚构的测试数据。内存存储保存完整虚构报文字节，并用本次对象生命周期内产生的引用读取。读取分开三种结果：命中、引用不存在、存储不可用。存储关闭后，已发出的引用不可用。不实现恢复、Replay 或跨进程持久化。这些字节不是 IR-15 的介质，也不是审计。

06-04-01 第 9 节仍禁止持久化 Java、Pipeline 业务 Java 和 Worker 执行。本任务申请的是不可恢复的进程内测试对象，不申请持久化实现，也不进入 Pipeline。若审查认为它仍落入该节的持久化禁令，则 C1-02 不实施。本文不改 06-04-01。

- 允许新增的位置：`platform-connector/src/main/java` 与 `platform-connector/src/test/java`。仓库里还没有这个模块的 Java 包。包名待实施前确认，不在本文起类名。
- 允许新增的职责：虚构来源，以及一个内存存储。实现可以放在 `platform-connector/src/main/java`。它不注册 Spring Bean，不提供运行时工厂、启动装配器或生产调用入口。
- 调用路径：构造、写入、读取和关闭只允许出现在本模块的单元测试中。`app-worker`、`app-admin`、`platform-pipeline` 以及其他模块不增加调用点。Worker 启动路径不创建、不装配、不使用该存储。配置键和测试专用的生产入口都不能绕过这条限制。验收要检查四件事：`platform-connector/src/main/java` 里没有应用运行时调用者；`app-worker` 和 `app-admin` 没有该存储的引用或装配；Spring Bean 定义中没有该存储；单元测试直接构造对象并验证行为。不声称这个 Java 类型在技术上无法被其他代码构造。
- 允许的依赖变更：仅为测试增加 `org.junit.jupiter:junit-jupiter`，`scope` 为 `test`，不写版本，与 `platform-common` 的现有写法相同。同时只把 `ModuleArchitectureTest` 里 connector 的预期依赖补上这一条。不增加其他依赖，不改变依赖方向。若审查不接受这条测试依赖，C1-02 停写，因为该模块当前无法编译 JUnit 测试。
- 禁止：应用启动路径创建、装配或使用该存储；运行时工厂和启动装配器；文件、数据库、网络、Kafka、跨进程通信、持久化、恢复、Replay、Task 或 Pipeline；调用 `resolve`；修改 `WorkerProcessStartup` 或 `WorkerApplication` 去引用它。
- 单元测试：直接构造后读回同一份完整报文；引用不存在；关闭后不可用。测试不启动 Spring。
- 架构测试：除上述测试依赖外，connector 仍只依赖 common 和 core。
- 启动测试：现有 `WorkerApplicationTest` 仍然只证明进程能启动。不把存储类型注册成 Spring Bean。两个确认键都成立时，Worker 上下文里也没有该存储。
- 可以证明：这个内存对象能按引用工作。
- 不能宣称：应用运行时已经保存报文，IR-15 已选定，Admin 能读取，生产安全门已通过，或 Pipeline 禁令已解除。

## 6. C1-08 Admin 独立演示清单

只放在 `app-admin`。清单每条都同时标出 `DEV_ONLY`、演示数据、非正式结果。条目只描述 Admin 自己的虚构数据，至少能表达成功、失败、未配置、阻断四种演示状态。这些状态不是 Worker 的实际结果。

- 允许新增的位置：`app-admin/src/main/java/com/mtx/rdp/admin` 与 `app-admin/src/test/java/com/mtx/rdp/admin`。新类型的类名待实施前确认。包名使用已经存在的 `com.mtx.rdp.admin`。
- 允许新增的职责：一份不依赖 Spring 的静态清单。它可以放在 `app-admin/src/main/java`。不注册 Spring Bean，不提供运行时诊断入口。
- 禁止修改：`AdminProcessStartup` 不得调用或输出这份清单。Admin 启动时不得输出它。不增加 HTTP、Controller、页面、模板或 `spring-boot-starter-web`。不依赖 `app-worker`。不读取 Worker 的日志、状态、内存或阶段记录。不把清单叫做管理页面。
- 单元测试：A11-1。不启动应用，不使用 `@SpringBootTest`。测试直接检查静态清单的文本，其中有四种演示状态和上述三个标记。
- 源码检查：确认启动类、配置和其他运行时入口都没有调用该清单。这项检查通过，也不等于 A11-2 通过。
- 架构测试：`app-admin` 的依赖集合保持 `ModuleArchitectureTest` 的现有预期。
- 启动测试：现有 `AdminApplicationTest` 在不启动 Worker 时仍然成功。A11-2 保持 BLOCKED。信号未验收前，两个确认键都成立也不输出清单。应用日志里出现这份清单是失败，不是通过。
- 可以证明：A11-1 的清单内容属于 Admin 自己。源码检查能看出启动路径没有调用它。
- 不能宣称：A11-1 通过等于 A11-2 通过，管理页面已交付，应用已经输出清单，或 Worker 状态已同步。
