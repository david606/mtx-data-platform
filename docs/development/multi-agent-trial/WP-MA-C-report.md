## 5. 问题之间的依赖关系

稳定事件身份未决定时，任务唯一约束没有可写入的来源字段，Create-or-Get 不能作为去重依据，条件 A 的第一项不成立。offset 安全提交挂在 IR-03 上，所以 IR-09 的消费部分不能单独关闭。

原文介质未决定时，条件 A 的「可再读」不能证明。此时即使将来补来身份，06-04-26 第 7.4 节也不允许把先建任务、后补原文写成已经安全。06-04-28 第 5 节进一步要求：原文不能再读时，不创建可安全执行或可恢复的任务。因此原文存储决策同时挡住 Task 创建和 offset 前进。

异常隔离未定义时，条件 B 不能代替条件 A。无身份来源既不能建自动处理任务，也不能靠提交 offset 越过当前记录。06-04-10 与 06-04-26 关于「不提交是否使分区停住」的冲突，决定实现者不能把「未提交」本身当成已经停止后续处理。后续业务停止、连续前缀和提交位置是另一组尚未实现的规则。

IR-02 的物理唯一约束、唯一冲突后的胜出读取，以及 `COMMIT` 结果不确定时的恢复，决定并发创建会不会产生两个权威任务。06-04-28 第 13 节 C-02 把这组实验标为关闭 IR-09 的前提。消费端不能用 JVM 内的先查后插代替它。

Task 行出现并且 MySQL 提交已确认，只满足接入侧的一部分。代次 0 不是执行权。领取、围栏和 Pipeline 写入属于 IR-09 的执行部分，不由 Consumer 完成。Kafka rebalance 也不接管执行权。

客户端能否进入 `platform-messaging`，依赖实现任务的明确批准，以及第 8 节的 Broker 实验仍未做。协议表的条件确认不能提前代替这些实验。

## 6. 需要业务确认的事项
