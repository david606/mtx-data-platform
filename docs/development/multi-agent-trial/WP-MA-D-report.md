### 3.2 Create-or-Get 的三支在现行 06-04-19 中分开

同一文件第 6.1 节把普通 `INSERT` 的明确成功与事务提交分开：`INSERT` 明确成功时本事务还没有提交；只有 `COMMIT` 成功返回才是 `CREATED`。唯一冲突明确返回时，失败语句回滚，这次不是提交结果不确定；在同一事务里按完整身份加锁读胜出行。第 6.3 节只用于 `COMMIT` 已经发送但结果无法确认。第 6.4 节只用于 `INSERT` 已经明确返回唯一冲突，而胜出行的读取或内容比较还没有完成，并写明这不是提交结果不确定。第 6.5 节用于 `COMMIT` 还没有发送且原连接已经断开，并写明不进入第 6.3 节。第 7 节矩阵把插入成功、唯一冲突后读胜出行、提交结果不确定分成不同行。第 14 节写：胜出读取未完成、`COMMIT` 未发送的事务结果未完成，以及提交结果不确定是三种状态；只有 `COMMIT` 已经发送而结果无法确认时才进入第 6.3 节。

`docs/investigation/round-01/06-04-23 MTX Data Platform V2 IR-02 MySQL 8.0.46 物理唯一约束与并发实验方案.md` 第 1 节和第 18 节写：A 类与 B 类、第 6.3 节、第 6.4 节和第 6.5 节仍然分开。E 组只对应第 6.3 节，D 组只对应第 6.4 节，F 组覆盖第 6.5 节的五种断连。

### 3.3 谁在事务边界之后回读

文档没有指定 Java 类、恢复进程或新模块来做这次回读。回读主体是原调用连接，或该调用方另开的一条连接。

`docs/investigation/round-01/06-04-19 MTX Data Platform V2 物理唯一约束与并发 Create-or-Get 专项设计.md`：

- 第 6.1 节第 5 步：唯一冲突已经明确返回时，第一次读胜出行在同一事务内，用覆盖完整身份的唯一索引做加锁读。这次仍在原连接上，位于事务结束之前。
- 第 6.2 节：B 类领域结果的第一次胜出读取仍在这一笔事务内完成，然后结束事务，不更新胜出行。读取没有完成时进入第 6.4 节。B 类的任务行锁只约束需要执行权的权威写入；A 类不先锁一条 `RUNNING` 任务。
- 第 6.4 节：同一事务里的读取失败后，结束该事务。随后的恢复使用另一条连接和新事务，按完整逻辑身份加锁读。这次读取不取得执行权。加锁读确认记录不存在时，结果保持为「唯一冲突后确认缺行」，不使用第 6.3 节的重新插入。该分类在决定之前是待决策。
- 第 6.3 节：`COMMIT` 已经发送但结果无法确认时，废弃原连接。另一条连接上的新事务按完整逻辑身份加锁读。A 类不锁任务行。B 类先锁定任务行，再按完整身份读取领域行；内容比较不取得新的执行权。只有确认没有该行，B 类还要重新通过代次、`CURRENT`、`RUNNING` 和有效阻断为空，才允许在同一事务里重新插入。恢复读取失败、不完整或不能归类时，继续保持提交结果不确定，不再插入。
- 第 6.5 节：`COMMIT` 尚未发送而连接已断开时，另一条连接上的新事务只按完整身份做加锁读。加锁读完成并确认没有行时，不进入第 6.3 节，不重新插入。五个子场景的已知事实不合并。

空 `conversionRuleVersion` 不得改成哨兵，证据见下一小节。围栏和回读协议都不把空转换版本写成一个新的业务版本号。
