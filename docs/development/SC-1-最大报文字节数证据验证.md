## 1. 已经批准的引用物理模型

这些是已批准决定：

- 引用算法是 UUIDv4。它是平台生成的原文保存记录引用。每次成功保存生成独立引用。
- 不使用业务订单号、Kafka offset、业务事件身份、投递身份或正文哈希生成引用。相同正文再次保存仍生成新引用。
- 数据库字段是 `BINARY(16)`。`raw_payload_ref` 直接作为主键。不增加自增主键。
- 不增加正文哈希唯一约束，不增加投递位置唯一约束，不用字符型 UUID 做数据库主键。
- 对外可以使用 UUID 规范文本。转换成 16 字节时，下标 0 到 7 是 `mostSigBits`，下标 8 到 15 是 `leastSigBits`，都是高位在前。还原用同一顺序。写入前长度必须恰好为 16。禁止依赖 MySQL 补零或隐式转换。后续 Java 测试必须覆盖文本、字节、再回到同一文本，以及写入后再读回的字节一致。本轮不写 Java。

正文列类型没有批准。最大报文字节数没有批准。

## 3. 测量结果

测量口径：

- 字符数按 Java 文本块去掉与结束分隔符相同的前导空格之后的码元个数。
- UTF-8 字节数是这段文本的 UTF-8 编码长度。无 BOM。换行是 LF。
- 这不是实际传输的原始字节。线上报文可能是另一种编码、另一种换行，或根本不是这份文本。
- 原文保存层以后保存的是收到的原始字节。本轮没有收到线上字节，所以没有「实际传输长度」可记。

## 5. MySQL、JDBC 和应用约束

本轮没有连接 MySQL，没有读取服务器参数。

| 项 | 记录 | 标记 |
| --- | --- | --- |
| `BLOB` | 类型上限 65535 字节 | 技术估算。来自 MySQL 8.0 文档，不是 8.0.46 上的实测 |
| `MEDIUMBLOB` | 类型上限 16777215 字节 | 同上 |
| `LONGBLOB` | 类型上限 4294967295 字节 | 同上 |
| `max_allowed_packet` | 手册默认 64MiB。开发服务器和连接器上的实际值未知 | 待环境验证。默认值不是该环境的配置 |
| JDBC 驱动 | `app-worker` 依赖 `com.mysql:mysql-connector-j`，版本由 Spring Boot 3.5.16 的 BOM 管理，模块 POM 不写版本。本轮没有执行 Maven，具体驱动版本未解析 | 待核对 |
| `setBytes` / `getBytes` | 驱动把字段放进 `byte[]`，整段进入协议包 | 技术资料上的行为，不是本环境实测 |
| 流式读写 | 驱动提供按流写入和读取的 API。流式不能取消调用方已经持有的那一份输入 | 同上 |
| 读回比较 | 输入一份，读回再一份时，堆上大约是两倍正文，再加驱动缓冲。逐块比较可以避免第二份完整数组，但输入本身仍在 | 技术估算 |
| Worker 堆 | 仓库的 `app-worker` 资源里没有 `-Xmx` 或堆配置 | 待环境验证 |
| 单条与多份 | 单条上限是一次保存的原始字节。C1 的调用方串行，保存路径不同时做多笔。比较期间仍会同时持有输入和读回。进程里若另外留下多份正文，不在这条串行约束里，本轮没有这种缓存设计 | 已接受的串行约束，加上技术估算 |

类型上限大，不表示包大小和堆放得下。`LONGBLOB` 的类型上限远大于手册默认包大小。

## 6. 三种上限方案

A、B、C 分开。A 是真实完整报文的观测最大值，当前没有。B 是基础设施估出来的可支持上限，包大小和堆未测，所以 B 还不是一个数。C 是要用户批准的业务最大字节数。不能用 A 或 B 代替 C。

| | `MEDIUMBLOB` 范围内封顶 | `LONGBLOB` 加应用层上限 | 按真实样本分布取更保守的数 |
| --- | --- | --- | --- |
| 标记 | 候选 | 候选 | 现在做不到 |
| 理论容量 | 不超过 16777215 字节 | 类型到 4294967295 字节，实际由应用上限和包大小卡住 | 取决于样本。现在没有完整报文 |
| 应用能否支持 | 只有 C 小于类型上限，并且小于实际包和堆能放下的读回比较，才支持 | 同左。类型本身不提供支持证明 | 无分布就不能取分位 |
| 包大小 | 若环境仍是 64MiB 默认，类型上限小于该默认值。实际配置未测，不能把「小于默认包」写成已经满足 | 类型上限大于默认包。不设应用上限就会在包或堆上失败 | 同左 |
| JDBC | C 未定之前不强制流式。C 大到两份字节放不进已知堆时，再决定流式比较 | 更可能需要流式。堆未知，所以这仍是待环境验证 | 无 |
| 内存 | 串行路径上主要是一份输入加一份读回 | 若 C 接近包大小，压力集中在这一笔，不是多笔并发 | 无 |
| 超限 | 事务开始前拒绝。不写入 | 同左。列类型宽，不能代替这次拒绝 | 同左 |
| 新平台 | C 不能预先写成 16MiB 来覆盖未知平台。新平台超出 C 时另批 | 列类型宽一些，应用上限仍要另批才能提高 | 新样本到了再重算，仍要用户批 C |

推荐：现在不选 `LONGBLOB`，也不把 `MEDIUMBLOB` 写成已经够用。先有 C，再选能放下 C 的最小类型。这是推荐方案，不是批准。

## 7. 超限行为建议

推荐在持久化之前用原始字节的长度做判断。超限则这次保存明确失败，不开始写入事务，因此没有半成品行。

不截断，不用压缩结果代替原始字节，不拆成多行。

本轮不新增错误码，不新增审计表。失败如何向调用方归类，留到后续决定。在那之前，只要求结果是明确失败，不是不确定，也不是成功引用。
