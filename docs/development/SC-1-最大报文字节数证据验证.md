## 1. 已经批准的引用物理模型

这些是已批准决定：

- 引用算法是 UUIDv4。它是平台生成的原文保存记录引用。每次成功保存生成独立引用。
- 不使用业务订单号、Kafka offset、业务事件身份、投递身份或正文哈希生成引用。相同正文再次保存仍生成新引用。
- 数据库字段是 `BINARY(16)`。`raw_payload_ref` 直接作为主键。不增加自增主键。
- 不增加正文哈希唯一约束，不增加投递位置唯一约束，不用字符型 UUID 做数据库主键。
- 对外可以使用 UUID 规范文本。转换成 16 字节时，下标 0 到 7 是 `mostSigBits`，下标 8 到 15 是 `leastSigBits`，都是高位在前。还原用同一顺序。写入前长度必须恰好为 16。禁止依赖 MySQL 补零或隐式转换。后续 Java 测试必须覆盖文本、字节、再回到同一文本，以及写入后再读回的字节一致。本轮不写 Java。

正文列类型没有批准。最大报文字节数没有批准。

## 5. MySQL 官方资料

本轮没有连接 MySQL 8.0.46，没有读取开发环境的变量。下面的类型上限和手册默认值都不是该环境的配置。

| 事实 | 手册说法 | 来源 | 标记 |
| --- | --- | --- | --- |
| `BLOB` 值的最大长度 | 长度 `L` 满足 `L < 2^16`，所以值本身最多 65535 字节。存储还要加 2 字节长度前缀 | [13.7 Data Type Storage Requirements](https://dev.mysql.com/doc/refman/8.0/en/storage-requirements.html) 的 String Type Storage Requirements | 已验证事实。是类型容量，不是实测写入 |
| `MEDIUMBLOB` | `L < 2^24`，值最多 16777215 字节，另加 3 字节长度前缀 | 同上 | 已验证事实。不是业务上限 |
| `LONGBLOB` | `L < 2^32`，值最多 4294967295 字节，另加 4 字节长度前缀 | 同上 | 已验证事实。不是一次可以发送、读回和比较的容量 |
| 行内 65535 字节 | 内部行上限 65535 字节。`BLOB` 只向这个上限贡献约 9 到 12 字节，正文放在行缓冲之外 | 同上，开篇 | 已验证事实。不能用它代替正文上限 |
| 服务器 `max_allowed_packet` 手册默认 | 默认值 `67108864` 字节，也就是 64MB。范围 1024 到 1073741824。它限制一个包、生成的中间字符串，以及 `mysql_stmt_send_long_data()` 送出的参数 | [7.1.8 Server System Variables](https://dev.mysql.com/doc/refman/8.0/en/server-system-variables.html#sysvar_max_allowed_packet) | 已验证事实。只是手册默认，不是开发服务器的值 |
| 协议上限 | 8.0 客户端或服务器能传输的最大包是 1GB。超过 `max_allowed_packet` 时返回 `ER_NET_PACKET_TOO_LARGE` 并关闭连接 | [B.3.2.8 Packet Too Large](https://dev.mysql.com/doc/refman/8.0/en/packet-too-large.html) | 已验证事实 |
| 客户端和服务端各自一份 | 两边都有 `max_allowed_packet`。大包必须两边都提高。服务器不向客户端发送超过当前全局值的字节。客户端库内建默认是 1GB，mysql 客户端程序默认 16MB，mysqldump 默认 24MB | 同上，以及系统变量页对客户端库的说明 | 已验证事实。Connector/J 的值见下一节，不把 mysql 命令行客户端的 16MB 写成 JDBC 的值 |
| 开发环境实际包大小 | 仓库和本轮都没有读到 | 无 | 待环境验证 |

一个通信包可以是发往服务器的一条语句、返回客户端的一行，或复制事件。正文大时，语句和读回的那一行都受包大小限制。类型容量、协议限制和部署参数是三件事。

## 6. JDBC 与内存

根 POM 的 `spring-boot.version` 是 3.5.16，并导入 `spring-boot-dependencies`。该 BOM 的发布文件把 `mysql.version` 写成 9.7.0，`mysql-connector-j` 使用这个属性。`app-worker` 只声明构件，不写版本，也没有覆盖 `mysql.version`。

本轮没有执行 Maven，没有打开本机仓库里的 jar。因此「本地构建已经解析出 9.7.0」标为待解析。下面的驱动行为来自当前在线的 Connector/J 开发指南，URL 没有钉住 9.7.0。没有对照 9.7.0 的发行说明或源码，所以不把这些句子写成已经验证的 9.7.0 行为。

| API | 资料怎么说 | 标记 |
| --- | --- | --- |
| `PreparedStatement.setBytes` | JDBC 把给定的 `byte[]` 设为参数。调用方手里已经有这份数组。指南没有把 `setBytes` 列进「大参数流」那一组 | 待核验到 9.7.0。不能从「有这个方法」推出驱动不再复制缓冲 |
| `ResultSet.getBytes` | 返回 `byte[]`。应用侧因此再得到一份完整数组 | 同上 |
| `setBinaryStream` | 指南把 `setBinaryStream` 算作大参数。客户端预编译和服务端预编译都到 `execute()` 才交换这份数据，之后流按 JDBC 要求关闭 | [6.4 JDBC API Implementation Notes](https://dev.mysql.com/doc/connector-j/en/connector-j-reference-implementation-notes.html) 的 PreparedStatement。版本未钉住，待核验 |
| `getBinaryStream` | 返回流。默认情况下 ResultSet 会整批取回并放进内存。逐行流式要另设只进、只读，且 `setFetchSize(Integer.MIN_VALUE)` | 同上，ResultSet 小节 |
| 流式是否零缓冲 | 不是。默认结果集在内存里。即使改成流式取行，指南也没有承诺 BLOB 字段本身不被驱动缓冲。`emulateLocators=true` 才把 BLOB 数据推迟到显式读取，而且还要求主键和列别名 | 待核验。不能把流式 API 写成端到端零缓冲 |
| 连接属性 `maxAllowedPacket` | 当前指南默认 65535。未设置时，连接后用服务器的 `max_allowed_packet` 初始化，并且不会让驱动值大于服务器值 | [6.3.4 Networking](https://dev.mysql.com/doc/connector-j/en/connector-j-connp-props-networking.html)。这是指南默认，不是已经连上的会话值 |

读回要和调用方持有的输入逐字节比较时：

- 调用方的输入数组一直都在。这是最低内存成本，流式读不掉这份。
- 若再用 `getBytes`，应用侧就是第二份完整数组。
- 若对 `getBinaryStream` 分块比较，应用可以不保留第二份完整数组。驱动仍可能已经把这一行放进内存。要避免这一点，必须同时满足指南里的流式结果集条件，并且确认 9.7.0 对单个 BLOB 也这样做。这两点现在都没有验证。
- Worker 资源里没有堆大小。待环境验证。C1 只保证保存调用串行，不保证进程里没有别的代码留下多份正文。

## 7. 三种上限方案

A 仍不能定成一个数。已测量的美团响应是 6389 字节，京东保存件是 7406 字节，回执里的 9633 没有对应字节。这三数都只是单笔观察，不是观测最大值的充分统计。B 仍未完成。C 仍不由本文件决定。不能用 A 或 B 代替 C，也不能用类型容量代替 C。这两笔的量级远小于 `MEDIUMBLOB`，但样本不够，不能据此把类型上限收成业务上限。

| | 把 C 限制在 `MEDIUMBLOB` 以内 | `LONGBLOB` 再加应用层上限 | 按真实样本分布取更保守的数 |
| --- | --- | --- | --- |
| 标记 | 候选。不是建议把 16777215 当成 C | 候选。不是因为类型更大就选用 | 现在做不到 |
| 类型容量 | 值最多 16777215 字节 | 值最多 4294967295 字节 | 无完整报文 |
| 已有真实样本 | 没有样本，谈不上覆盖 | 同左 | 同左 |
| 扩展余量 | 没有分布，就不能说留了多少 | 列宽不代表给新平台留了已批准余量 | 新样本到达后再算，仍要另批 C |
| 包和内存 | 类型上限小于手册默认的 64MB 服务器包。开发环境的实际包和堆未验证，不能写成已经小于已验证限制 | 类型上限大于手册默认包，也大于协议 1GB 以外的部分不可达。不设应用上限就会先撞上包或堆 | 无 |
| 流式 | 未验证前不要求。是否需要，等 B 完成后再看 C 是否放得进已测的堆 | 更不能靠类型容量推断不需要流式 | 无 |
| 超限 | 写入前按 C 拒绝，不截断 | 列类型宽，不能代替这次拒绝 | 同左 |

现在不能提出一个可信的业务最大长度。原因是没有真实完整报文，技术可支持上限也还没有测完。不把 16MiB 或 `MEDIUMBLOB` 的容量设成 C，也不因为 `LONGBLOB` 更大就选它。
